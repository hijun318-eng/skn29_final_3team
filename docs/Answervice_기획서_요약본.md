## 한눈에 보기

**Answervice는 여러 업무 시스템에 흩어진 데이터를 자연어로 분석하고, 출처가 확인된 결과를 편집 가능한 보고서로 연결하는 기업용 서비스다.**

| 질문 | 짧은 답 |
|---|---|
| 누가 쓰나? | 데이터 분석이 필요한 호텔 운영 관리자와 데이터·시스템 관리자 |
| 무엇을 해결하나? | 여러 시스템을 오가며 데이터를 찾고 수작업으로 보고서를 만드는 문제 |
| 어떻게 해결하나? | 자연어 질문 → 승인된 데이터 조회 → 결과·근거 표시 → 보고서 재사용 |
| 무엇이 다른가? | AI가 만든 SQL을 바로 실행하지 않고 권한·안전·결과를 단계별로 검증 |
| 어떤 데이터인가? | PMS·CRM·POS·시설·연회 시스템을 모사한 합성 데이터 |
| 발표에서 무엇을 보여주나? | 세 데이터 원천을 연결해 객실 매출 감소 원인을 찾고 보고서로 편집하는 흐름 |

## 1. 왜 필요한가

호텔 운영 데이터는 한곳에 있지 않다. 객실과 예약은 PMS, 회원과 채널은 CRM, 식음은 POS, 시설과 연회는 또 다른 시스템에서 관리된다.

이 때문에 간단한 경영 질문도 다음 과정을 거친다.

```text
데이터 위치 문의
→ 담당자별 자료 요청
→ 기준과 기간 맞추기
→ 수작업으로 합치기
→ 보고서에 다시 옮기기
```

이 과정은 시간이 오래 걸리고, 결과를 보고서에 옮기는 순간 질문 조건과 출처가 사라지기 쉽다. Answervice는 이 문제를 다음처럼 바꾼다.

| 기존 방식 | Answervice |
|---|---|
| 담당자에게 데이터 위치를 문의 | DataHub에서 위치·의미·소유자를 확인 |
| 사용자가 직접 SQL과 JOIN을 작성 | 자연어 질문을 승인된 조회로 변환 |
| 결과의 기간·기준을 따로 확인 | 결과 옆에 기간·필터·단위·출처 표시 |
| 보고서를 매번 다시 작성 | 검증된 분석 결과를 보고서 블록으로 재사용 |

## 2. 사용자는 어떻게 쓰나

### 대표 사용자 흐름

1. 사용자가 업무 질문을 입력한다.
2. 시스템이 질문의 기간·지표·대상을 확인한다.
3. DataHub에서 사용할 데이터의 위치와 의미를 찾는다.
4. Trino가 권한 안에서 여러 원천을 읽기 전용으로 조회한다.
5. 화면에 요약, KPI, 표·차트와 데이터 출처가 나타난다.
6. 사용자는 결과를 보고서에 담아 위치·크기·문구를 편집한다.
7. 관리자가 보고서를 검토하고 실행 결과를 확인한다.

### 중간발표 시연 질문

> “7월 마지막 주 객실 매출 감소 구간을 찾고, 예약 채널과 연회 일정 변화를 함께 비교해줘.”

| 원천 | 확인 내용 | 시연 결과 |
|---|---|---|
| PMS | 객실 매출·점유율 | 매출 45.2→40.1백만원, 점유율 76.1%→68.6% |
| CRM | 직접 예약 비중 | 43.5%→38.2% |
| Banquet | 기업 연회 변경과 연계 객실 | 일정 변경 2건, 객실 62박 취소 |

화면은 세 수치가 같은 기간에 함께 변했다는 사실을 보여준다. 원인으로 단정하지 않고 관리자 검토가 필요하다는 한계도 함께 표시한다.

## 3. 서비스는 어떻게 동작하나

```mermaid
flowchart LR
    Q["자연어 질문"] --> C["데이터 위치·의미 확인"]
    C --> S["안전한 조회문 생성·검증"]
    S --> T["Trino 읽기 전용 조회"]
    T --> V["결과·근거 검증"]
    V --> A["분석 결과"]
    A --> R["보고서 블록"]
```

핵심은 AI가 조회문을 만드는 것보다, **AI가 만든 결과를 바로 믿지 않는 구조**다.

| 검증 단계 | 확인하는 내용 | 실패 시 처리 |
|---|---|---|
| G1 질문·데이터 검증 | 기간·지표·권한·데이터 근거가 충분한가 | 필요한 조건을 다시 묻거나 종료 |
| G2 조회 안전 검증 | 읽기 전용인가, 승인된 테이블·JOIN인가 | 한 번만 수정한 뒤 다시 실패하면 종료 |
| G3 결과 검증 | 결과 형식·범위·마스킹·근거가 올바른가 | 설명과 보고서 저장을 막고 추적 ID 제공 |

AI는 질문 정리, 조회문 후보 작성, 검증된 결과 설명을 담당한다. 실행 허용, 권한 판정과 최종 합격 여부는 고정된 검증 단계가 결정한다.

## 4. 어떤 데이터를 연결하나

| 업무 영역 | 주요 데이터 | 저장 엔진 |
|---|---|---|
| PMS | 예약·객실·투숙·요금 | PostgreSQL |
| F&B POS | 주문·매장·상품·결제 | MySQL |
| CRM | 회원·등급 이력·포인트 | SQL Server |
| 시설 운영 | 이용·점검·장애·자원 | ClickHouse |
| 연회 | 행사 예약·상품·매출 | PostgreSQL |

다섯 원천을 하나의 DB로 강제로 합치지 않는다. DataHub는 데이터의 위치와 의미를 관리하고, Trino는 필요한 순간에 승인된 원천만 조회한다. 원천 DB는 수정하지 않는다.

모든 시연 데이터는 합성 데이터다. 실제 고객 이름·연락처·결제정보를 사용하지 않으며 seed와 schema version으로 다시 만들 수 있다.

## 5. 주요 기능

| 기능 | 사용자가 얻는 가치 | 우선순위 |
|---|---|---|
| 자연어 분석 챗 | SQL을 몰라도 여러 원천의 지표를 비교 | P0 |
| 결과·근거 패널 | 수치와 기간·필터·출처를 함께 확인 | P0 |
| 12열 보고서 편집 | 분석 결과를 블록으로 배치·수정·재사용 | P0 |
| 보고서 실행 이력 | 어떤 기준과 데이터로 생성됐는지 확인 | P0 |
| 데이터 카탈로그 | 데이터 위치·상태·담당자·연결 관계 확인 | P1 |
| 운영·감사 | 질문부터 결과·보고서까지 추적 | P0 운영 |

### 현재 제외 범위

MCP Tool 관리, 사내 문서 RAG, ML-as-a-Tool, 고객 360과 외부 보고서 배포는 별도 승인 전까지 구현 범위에 포함하지 않는다. 목업 코드가 남아 있어도 메뉴와 route는 차단한다.

## 6. 안전하고 믿을 수 있는 이유

- 원천 데이터는 조회 전용으로 접근한다.
- 승인되지 않은 테이블·컬럼·JOIN은 실행하지 않는다.
- SQL 수정은 한 번만 허용하고 무한 반복하지 않는다.
- 캐시 결과도 권한과 정책 검사를 다시 거친다.
- 일부 원천이 실패하면 성공과 실패 범위를 분리한다.
- 근거가 부족하면 원인으로 단정하지 않는다.
- 질문, 데이터 근거, 조회, 분석 결과와 보고서를 추적 ID로 연결한다.
- 개인정보·credential·원문 DB 오류와 모델 내부 추론은 화면과 로그에 노출하지 않는다.

## 7. 성공 기준

| 영역 | 합격 기준 |
|---|---|
| 데이터 연결 | 5개 원천의 수집 상태·검색·조회 확인 |
| 안전 | 금지된 DDL·DML·권한 밖 요청의 원본 실행 0건 |
| 대표 질문 | 고정 30건이 올바른 결과 또는 안전한 중단으로 종료 |
| 추적성 | 질문→데이터 근거→조회→분석 결과 재구성률 100% |
| 출처 일치 | 화면·Context·조회 원천 불일치 0건 |
| 개인정보 | 일반 사용자 결과·로그·보고서의 직접식별정보 노출 0건 |
| 보고서 재현 | 같은 조건에서 블록 결과 checksum 일치율 100% |

속도·모델 정확도·GPU·비용은 실제 측정값으로 판단한다. “보고서 작성 시간이 며칠에서 몇 분으로 줄어든다”와 같은 표현은 검증 전 성과가 아니라 목표 가설로만 사용한다.

## 8. 현재 시연에서 보여주는 것

현재 중간발표 목업은 백엔드 연결 없이 고정 합성 데이터로 동작한다. 따라서 네트워크나 DB 상태와 무관하게 하나의 흐름을 안정적으로 보여주는 데 목적이 있다.

```text
질문 입력
→ PMS·CRM·Banquet 분석 결과와 출처 확인
→ 보고서에 담기
→ 블록 이동·크기 조정·문구 수정
→ 보고서 초안 저장
```

시연에서 강조할 메시지는 “AI가 답을 만들어주는 서비스”보다 **“분리된 데이터를 안전하게 연결하고, 근거 있는 분석을 보고서까지 이어주는 서비스”**다.

## 9. 팀 역할과 개발 단계

| 역할 | 책임 |
|---|---|
| R1 | 공통 계약·통합·품질·릴리스 |
| R2 | 데이터 원천·DataHub·Trino·합성 데이터 |
| R3 | AI Node·프롬프트·모델 평가 |
| R4 | FastAPI·Controller·G1/G2/G3·감사 |
| R5 | 프론트엔드·보고서 편집·자동 리포팅 |

개발은 `I0 범위 정렬 → I1 계약 동결 → I2 대표 질문 왕복 → I3 일반 질문 → I4 자동 리포팅 → I5 릴리스` 순서로 진행한다. 상세 일정과 현재 상태는 WBS를 기준으로 한다.
