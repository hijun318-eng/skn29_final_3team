## 1. 목적

이 문서는 현재 구현의 검증·방어 논리를 한 곳에서 확인하고, 운영 승인 전 누락된 Gate를 차단하기 위한 기준이다. 코드에 존재하는 방어만 `구현`으로 기록하며, 테스트 또는 실환경 증거가 부족한 항목은 `부분 구현`이나 `미검증`으로 구분한다.

현재 판정은 다음과 같다.

| 영역 | 판정 | 설명 |
|---|---|---|
| 공통 인증·권한 | 구현 | 서버가 인증한 사용자와 역할만 사용하며 Capability를 중앙 정책으로 판정 |
| 분석·SQL 실행 | 구현 | SQLGlot AST, 승인 자산, 지표·조인·시간 규칙, 파라미터 바인딩을 모두 통과해야 실행 |
| RAG 접근 통제 | 구현 | 명시적 경로, Tool Registry, HMAC, 재전송 차단, 역할·승인·유효기간 검사 적용 |
| RAG 답변 안전 | 부분 구현 | citation 검증과 빈 답변 차단은 구현됐지만 `EvidenceSafetyGate`가 현재 답변기에 연결되지 않음 |
| ML 실행 안전 | 부분 구현 | artifact hash·feature contract·provenance 검증은 구현됐지만 모델이 `CONDITIONAL_PASS`이며 운영 승인 전 상태 |
| MCP 도구 통제 | 부분 구현 | 단일 허용 도구·ACL·입력 검증·감사는 구현됐지만 출력 JSON Schema의 실행 시 strict 검증은 보완 필요 |
| 전체 운영 검증 | 미검증 | 프론트·정적 검증은 통과했지만 전체 백엔드 pytest와 최신 ML·RAG live E2E 증거가 없음 |

따라서 현재 상태를 `운영 완전 검증` 또는 `Production Ready`로 선언하지 않는다.

### 운영 방어 요약

1. **허용·금지 도구**: MCP는 활성화된 read-only `analysis.get_run`만 허용한다. 임의 도구명, 추가 argument, 비활성 Tool, 다른 사용자 결과 조회는 금지한다.
2. **보안 점검**: 인증 주체, Capability, strict 입력, 명시적 route, SQL AST, RAG HMAC·문서 승인, ML artifact·feature contract를 순서대로 확인한다.
3. **필수 추적 항목**: `trace_id`, `latency_ms`, `error_code`를 최소 기준으로 하고 실행 종류별 lineage ID를 추가한다.
4. **구조화 출력**: 응답은 `status`, `error_code`, `data` 경계를 유지하고 Pydantic 또는 JSON Schema 검증 실패 시 성공 응답을 만들지 않는다.
5. **롤백 단위**: feature flag, Tool Registry, model artifact 묶음, 애플리케이션 commit을 서로 독립된 롤백 단위로 사용한다.

## 2. 공통 방어 원칙

1. **서버 소유 정보**: 사용자 ID, 역할, 기준일, 권한 snapshot, release ID는 클라이언트 값으로 확정하지 않는다.
2. **명시적 라우팅**: 일반 질문을 키워드만으로 ML 또는 RAG에 자동 전환하지 않는다.
3. **최소 권한**: Role을 Capability로 변환하고 API·도구·데이터 자산마다 다시 검사한다.
4. **실패 폐쇄**: 계약·권한·Secret·metadata·근거가 불완전하면 실행하지 않고 오류 또는 명확화로 종료한다.
5. **구조화 계약**: Pydantic `ContractModel(extra="forbid")`로 알 수 없는 필드와 잘못된 타입을 거부한다.
6. **근거 우선**: 분석 결과는 SQL·query ID·artifact ID, RAG는 evidence ID·citation, ML은 model hash·Trino query ID를 남긴다.
7. **원문 최소화**: 질문·SQL·도구 입력은 원문 대신 마스킹 값 또는 hash 중심으로 감사한다.
8. **기능별 격리**: ML provenance는 `rag_called=false`를 증명해야 하며, ML과 RAG는 별도 feature flag로 차단한다.

## 3. 신뢰 경계와 실행 순서

```text
브라우저 입력
  → 인증·세션·RequestContext 검증
  → Capability·명시적 route 검증
  ├─ 일반 분석 → 승인 metadata → 모델 출력 검증 → SQL Guard → Trino → 결과·근거 검증
  ├─ RAG       → Tool Registry → HMAC Gateway → 승인 문서 검색 → citation 검증 → 답변 카드
  └─ ML        → Feature Flag → runtime capability → artifact/feature 검증 → Trino history → 예측·감사
```

각 단계가 실패하면 다음 단계로 넘어가지 않는 것이 기본 불변식이다.

## 5. 관측성과 감사 기준

모든 실행은 가능한 범위에서 다음 최소 정보를 연결해야 한다.

| 필드 | 목적 | 현재 구현 |
|---|---|---|
| `request_id` | 단일 HTTP·도구 요청 식별 | 구현 |
| `trace_id` | 프론트→Backend→도구 실행 연결 | 구현 |
| `user_id`·`role` | 실행 주체와 권한 증명 | 구현 |
| `input_hash` | 원문을 저장하지 않고 동일 입력 추적 | RAG·MCP·분석에 구현 |
| `latency_ms` | 지연·timeout 분석 | RAG·MCP·모델 경로에 구현 |
| `error_code` | 실패 유형 집계 | 구현 |
| `query_id`·`artifact_id` | 데이터 결과 lineage | 분석에 구현 |
| `evidence_id`·citation | RAG 답변 근거 | 구현 |
| `model_hash`·`feature_as_of`·`trino_query_id` | ML 재현성과 시점 증명 | 구현 |

LangSmith, MLflow, OpenTelemetry 같은 외부 통합 관측 플랫폼은 현재 코드에서 확인되지 않았다. 운영 요구사항이라면 기존 DB 감사 이벤트를 기준 원장으로 유지하고 외부 trace export는 비차단 비동기 경로로 추가해야 한다. 외부 관측 시스템 장애가 사용자 분석 결과의 성공 여부를 바꾸면 안 된다.

## 6. 표준 실패 처리

1. 인증 실패는 401, 권한 실패는 403으로 구분한다.
2. 입력·계약 오류는 422, stale head·계약 버전 충돌은 409로 처리한다.
3. 비활성 기능·필수 dependency·Secret 누락은 503으로 종료한다.
4. downstream의 잘못된 응답은 502로 변환하고 원문 내부 오류를 사용자에게 노출하지 않는다.
5. timeout은 재시도 가능한 표준 오류로 반환한다.
6. 실패 상태에서 빈 artifact, 빈 근거, 검색 원문을 성공 결과로 꾸미지 않는다.
7. 로그에는 질문·SQL·Secret 원문 대신 redacted 값, hash, 식별 reference를 우선 저장한다.

## 9. 운영 활성화 선택안

### 1안 — 권장

ML·RAG feature flag를 모두 0으로 유지하고 P0 Gate 전체 통과 후 한 기능씩 활성화한다. 가장 안전하며 원인 분리가 쉽다.

### 2안 — 제한된 내부 검증

승인된 관리자 역할과 내부 네트워크에서만 한 기능을 활성화하고, read-only·감사·즉시 rollback 조건을 적용한다. 운영 사용자에게는 공개하지 않는다.

### 3안 — 동시 활성화

ML·RAG를 동시에 활성화한다. 장애 원인과 데이터 경계를 분리하기 어려우므로 현재 상태에서는 권장하지 않는다.

## 10. 롤백 계획

1. ML 문제: `ML_FEATURE_ENABLED=0`으로 즉시 차단한다.
2. RAG 문제: `RAG_FEATURE_ENABLED=0`과 Tool Registry disable을 함께 적용한다.
3. MCP 문제: 해당 Tool Registry 항목을 disable한다.
4. 모델 문제: 승인된 이전 artifact·manifest·approval·feature contract 묶음으로 환경 변수를 원자적으로 되돌린다.
5. 코드 문제: 기준 커밋 이전의 검증된 commit으로 애플리케이션을 롤백한다.
6. DB migration은 코드 롤백과 별도로 downgrade 가능 여부를 확인하며 동일 작업으로 간주하지 않는다.
7. 롤백 후 readiness, 권한 거부, 감사 이벤트 기록을 다시 확인한다.
