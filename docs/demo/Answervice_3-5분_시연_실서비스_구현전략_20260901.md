> 최종 검토일: 2026-09-02  
> 검토 repository: `report-ui-overflow`  
> 최종 배포·브라우저 검증 기준 commit: `60d427b681fe0fda2a36826e02b7b5fdee394d85`
> 문서 성격: 시연 시나리오, 최소 실서비스 구현 계약, 구현 결과와 V-2 검증 기록을 한 문서에 유지한다.
> 데이터 고지: 이 repository의 호텔 데이터는 합성 시연 데이터다. 실제 워커힐 실적이라고 설명하면 안 된다.

## 1. 최종 결론

이번 시연은 새 플랫폼을 만드는 일이 아니다. 현재 구현에 이미 있는 정상 서비스 경로를 연결하고, 화면에서 약하게 드러나는 지점만 보완한다.

핵심 시연 흐름은 다음 다섯 가지다.

1. PostgreSQL·MySQL·ClickHouse 등 이종 DB가 Trino의 승인 통합 View로 연결되어 있음을 짧게 보여준다.
2. 자연어 분석 한 번과 같은 결과의 빠른 그래프 전환을 보여준다. 그래프 전환은 새 분석 쿼리가 없는 typed `PRESENTATION` 경로다.
3. 한 문장에서 Analysis·RAG·ML을 함께 요청하고, 서버가 저장한 `SupervisorCompositionReceipt.v1`을 근거로 멀티 Agent 완료 트리를 보여준다.
4. 시연 전에 실제 서비스로 준비한 8월 보고서용 Artifact 4개와 시연 중 복합 Analysis가 생성한 Artifact 1개, 총 5개를 월간보고서에 모두 사용한다.
5. Report Assistant가 다섯 Artifact만으로 차트 유형·표 밀도·블록 순서를 제안하고, 사용자가 미리보기를 승인해 새 Revision을 만든다.

권장 Artifact 수는 **총 5개**다. 현재 Report Assistant 계약이 대표 1개와 추가 4개까지 허용하기 때문이다. 6개는 프론트·백엔드 계약과 모델 입력 예산 검증을 함께 바꿔야 하므로 이번 최소 구현 범위에서 제외한다.

권장 핵심 시연 시간은 **3분 45초**, 실제 응답 지연 buffer를 포함하면 **4분 05초**다. 감사 로그는 핵심 시연을 끝낸 뒤 10~15초가 실제로 남을 때만 기존 화면을 보여준다.

### 1.1 하드코딩 여부

이 전략은 **시연 cue는 고정하지만 서비스 결과는 고정하지 않는다.** 고정된 질문을 준비하는 것과 질문별 정답을 production 코드에 심는 것은 전혀 다른 일이다.

| 구분 | 허용 여부 | 설명 |
|---|---|---|
| 발표자가 말할 A 질문 고정 | 허용 | 촬영 cue다. 일반 자연어 resolver를 그대로 통과한다. |
| B·C·D·E를 촬영 전에 실제 Analysis로 생성 | 허용 | 정상 서비스가 만든 Artifact를 보관하는 운영 준비다. |
| `막대그래프로 보기` typed 퀵액션 | 허용 | 호환되는 모든 분석 결과에 적용되는 범용 제품 기능이며 서버가 재검증한다. |
| exact 질문을 eval fixture에 추가 | 허용 | 회귀 검증용 입력이지 runtime 응답 코드가 아니다. |
| 질문 문자열별 production `if/else` | 금지 | 시연 문장에만 맞는 분기다. |
| A~E Artifact ID를 상수로 저장 | 금지 | 촬영 계정의 특정 데이터에 결합된다. |
| 고정 수치·표·차트 JSON 반환 | 금지 | 실제 Trino 결과가 아니다. |
| Agent 목록·citation·ML 예측을 미리 작성 | 금지 | 실제 Supervisor·RAG·ML receipt가 아니다. |
| Assistant의 6개 patch를 서버에서 강제 반환 | 금지 | 모델과 typed validator를 우회한다. |

퀵액션의 `PRESENTATION + BAR`처럼 UI가 사용자의 명시적 동작을 typed command로 보내는 것은 하드코딩이 아니다. BI 제품의 “막대그래프로 보기” 버튼과 같은 일반 기능이다. 서버는 source Artifact·query·지원 가능한 ViewSpec을 확인하고, 조건이 맞지 않으면 실패로 닫아야 한다.

촬영 전에 생성한 B·C·D·E도 fixture나 DB insert가 아니다. 실제 사용자와 같은 Analysis UI/API를 거쳐 생성한 결과이며, 촬영에서는 새로 만드는 시간을 줄이기 위해 보관해 두는 것이다. 촬영 계정에 특정 Artifact ID를 코드로 연결하지 않고, 서버가 반환한 최근 승인 Artifact를 사용자가 화면에서 선택한다.

## 2. 냉정한 검토 결과

기존 전략은 구현 가능한 아이디어를 많이 담고 있었지만, 시연 성공에 필요하지 않은 새 계약과 범용 기능이 P0에 섞여 있었다. 아래처럼 정리한다.

| 항목 | 최종 결정 | 이유 |
|---|---|---|
| 자연어 Analysis | 멀티 Agent 장면에 통합 | 별도 단일 분석 장면 없이 복합 요청의 primary Analysis로 실제 Trino 분석을 보여준다. |
| 빠른 그래프 전환 | 유지·보완 | 기존 typed `PRESENTATION` fast path를 퀵액션에 연결하면 된다. |
| 멀티 Agent | 축소 | 새 실시간 상태 시스템 대신 기존 terminal composition receipt를 화면에 연결한다. |
| 실시간 Agent별 RUNNING 상태 | 후속 | 현재 progress registry는 Analysis 전용이고 복합 RAG·ML은 그 전에 순차 실행된다. |
| Trino 이종 DB 강점 | 유지하되 표현 수정 | 연결 상태와 승인 통합 View는 보여주되, 결과별 재귀 lineage가 이미 있다고 말하지 않는다. |
| 결과별 `upstream_catalogs` 계약 | 삭제 | capability 봉인·compiler·Evidence·UI까지 새 경로가 필요하다. 최소 구현이 아니다. |
| 7월 대비 8월 × 호텔 비교 차트 | 삭제 | 현재 `period + hotel_code` 차트는 닫혀 있어 series/pivot 제품 개발이 필요하다. |
| 첫 질문 | 8월 호텔별 분석+RAG+ML 복합 질문으로 통합 | 한 번의 live 질문으로 데이터 사일로와 멀티 Agent를 함께 보여준다. |
| 예약 취소율 Artifact | 삭제 | 현재 semantic catalog에 사용할 수 있는 metric이 없다. |
| 월간보고서 Artifact | 5개로 확정 | Assistant의 현재 최대 결속 수와 정확히 맞는다. |
| Artifact 검색·자동 선택·자동 cleanup | 삭제 | 촬영 계정에는 보고서에 쓸 5개만 남긴다. |
| 저장 제목 입력 기능 | 삭제 | 현재 질문 문장을 저장 제목으로 쓰는 경로로 충분하다. 새 modal은 핵심이 아니다. |
| Report Assistant | 유지 | 기존 `existing_artifact` typed patch와 승인·Revision 경로가 있다. |
| Assistant에서 block 삭제 | 핵심 동선에서 제외 | 자동 compact를 끈 상태에서 삭제·재삽입하면 빈 공간이 생길 수 있다. |
| `compactDraftLayout()` 자동 호출 제거 | 명시 요구로 유지 | load·save와 명시적 전체 재배치가 아닌 편집은 사용자의 빈 공간·좌표를 보존한다. `레이아웃 정돈`, 방향 변경의 semantic reflow, 손상 legacy 복구만 예외다. |
| Recharts·dnd-kit 교체 | 삭제 | 필요한 bar·horizontal-bar·line과 drag 기능은 이미 지원한다. |
| 보고서 감사 event 신설 | 삭제 | 핵심 시연과 무관하고 event·transaction·dedupe 범위가 커진다. |
| 기존 감사 로그 화면 | 완전 선택 | 이미 준비된 Analysis 로그가 있고 시간이 남을 때만 보여준다. |

이 축소는 데모용 정적 응답을 만들기 위한 것이 아니다. 질문은 정상 resolver와 semantic contract를 통과하고, Analysis는 Trino를 실제 호출하며, RAG·ML·Report Assistant도 각각 현재 서비스 경로를 사용해야 한다.

### 3.2 최초 검토에서 확인한 부족한 부분과 처리 결과

1. `composition` 보존과 Supervisor tree는 persisted receipt를 source of truth로 연결했다.
2. typed `PRESENTATION` 퀵액션과 `기존 분석 재사용 · 새 분석 쿼리 없음` 상태를 연결했다.
3. 같은 분석 형상과 표현 변경 문장을 재분석으로 오인하던 resolver를 수정했다.
4. 가로 막대 의도를 `ViewSpec.chart_type=horizontal-bar`까지 보존하고 실제 renderer 선택 상태를 검증했다.
5. 보고서 기본 폭, provenance badge, Artifact preview, 편집 진입, 열람 화면을 정리했다.
6. `compactDraftLayout()`의 암묵 호출을 제거하고 명시적 정돈·방향 변경·손상 복구만 reflow 예외로 남겼다.
7. 다섯 Artifact Assistant 적용과 저장·재열람을 최종 배포본의 실제 브라우저에서 검증했다.

### 3.3 정적 코드만으로 확인할 수 없는 것

다음은 문서나 단위 테스트만으로 성공을 선언하면 안 된다.

- 촬영 환경의 Trino catalog와 `hotel_operations_daily` View가 실제로 준비됐는지
- 다섯 질문이 촬영 시점의 Node 1·Node 2 모델에서 정확히 해석되는지
- RAG corpus가 복합 질문에 실제 인용을 반환하는지
- ML capability의 `as_of`, property, 최대 예측 기간이 9월 1일~7일과 맞는지
- Report Assistant가 exact 5-Artifact payload로 원하는 typed patch를 안정적으로 제안하는지
- 화면·HTML·PDF renderer에서 최종 보고서가 깨지지 않는지

따라서 live preflight는 기능 개발과 별개의 필수 촬영 gate다.

### 3.4 현재 로컬 실행 상태 확인

2026-09-02 현재 비밀값을 출력하지 않고 실제 실행 환경을 읽기 전용으로 확인했다.

| 항목 | 확인 결과 | 개발 판단 |
|---|---|---|
| RAG | `RAG_FEATURE_ENABLED=1`, `answervice-rag-api` healthy, `RagRuntimeReceipt.v1` 유효, active corpus 41문서 | 새 RAG 구현·설치 없음 |
| ML | `ML_FEATURE_ENABLED=1`, `answervice-ml-runtime` healthy, `MLRuntimeCapability.v2` 유효 | 새 ML runtime 구현·설치 없음 |
| Supervisor | `SUPERVISOR_FEATURE_ENABLED=1`, backend 내부 planner 구성 성공, model dependency ready | 새 Supervisor 서비스·상태 플랫폼 없음 |
| 통합 readiness | backend `/readiness`에서 `trino`, `model`, `rag_runtime`, `ml_runtime` 포함 전체 dependency `ready` | 촬영 직전 동일 probe만 재실행 |

현재 ML은 `room-demand-timeseries-hgbr-v2.2.0`, `CONDITIONAL_PASS`, `VALIDATED_SYNTHETIC`, `synthetic_training_data=true`다. 현재 촬영 환경은 `ML_ALLOW_CONDITIONAL=true`이며, GRAND `as_of=2026-08-31`, horizon 7의 실제 runtime 검증에서 2026-09-01~09-07 예측 7건과 Trino provenance가 확인됐다. 따라서 A의 예측 기간은 현재 로컬 capability 안에 있다.

이 확인은 기능이 **있고 현재 켜져 있다**는 증거다. exact A 문장을 Supervisor가 세 작업으로 안정적으로 분해하는지는 외부 모델 호출을 동반하므로 V-2 rehearsal에서 확인한다. `.env.example`의 기본값 `0`을 현재 실행 상태로 오해하지 않으며, 반대로 오늘의 healthy 상태를 촬영일까지 보장한다고 가정하지도 않는다.

## 4. 데이터 사일로 강점을 정직하게 보여주는 방식

### 4.1 실제 구조

```text
PMS / PostgreSQL ───── 객실 운영 ───┐
POS / MySQL ───────── 식음 운영 ───┤
Banquet / PostgreSQL ─ 연회 운영 ───┼─> Trino 승인 serving View
Facility / ClickHouse ─ 시설 운영 ──┘      hotel_operations_daily
                                              │
                                              └─> Analysis Agent ─> 검증 Artifact

내부 운영 문서 ─> RAG Agent ───────┐
객실 수요 모델 ─> ML Agent ────────┼─> Supervisor composition receipt
Analysis Artifact ─────────────────┘

Artifact A~E ─> Report Assistant typed patch ─> 사용자 승인 ─> Revision +1
```

### 4.2 시연에서 말해도 되는 문장

> “운영 데이터는 PostgreSQL, MySQL, ClickHouse처럼 서로 다른 시스템에 있지만, Trino에서 승인된 운영 View로 연결되어 있습니다. 지금 질문은 그 통합 View를 정상 서비스 경로로 한 번 조회합니다.”

> “앱이 질문마다 원본 DB를 임의로 조인하는 방식은 아닙니다. 도메인별 선집계 데이터를 승인 View가 결합하고, Analysis Agent는 그 단일 asset을 조회합니다.”

### 4.3 말하면 안 되는 문장

- “이번 결과 화면이 원본 DB까지 재귀 lineage를 실시간으로 증명합니다.”
- “질문할 때마다 PostgreSQL·MySQL·ClickHouse를 즉석에서 직접 조인합니다.”
- “실제 워커힐 실적입니다.”
- “모든 Agent가 동시에 병렬 실행됩니다.”

현재 복합 실행은 순차 실행이다. 시연에서는 “역할을 나눠 처리했다”라고 말하고 “동시에 처리했다”라고 말하지 않는다.

Admin 연결 페이지를 열면 catalog readiness probe용 Trino query가 별도로 실행될 수 있다. 따라서 영상 전체의 전역 Trino query가 1회라고 말하지 않는다. `이번 Analysis 쿼리 1회`, `이번 표현 전환의 새 분석 쿼리 0회`처럼 범위를 한정한다.

## 5. 8월 월간보고서용 Artifact 정책

### 5.1 총 5개를 선택하는 이유

| 수량 | 판단 |
|---|---|
| 4개 | 가능하지만 월간보고서의 KPI·매출·인력·추이를 모두 보여주기엔 약하다. |
| **5개** | 현재 Assistant 최대치와 같고, 한 세션에서 모두 검증·편집할 수 있다. 이번 기준안이다. |

6개가 꼭 필요해지는 시점에는 별도 기능으로 상한·prompt budget·repository·UI·E2E를 함께 변경한다. demo constant 하나만 5에서 6으로 바꾸지 않는다.

### 5.2 권장 Artifact 5개

모든 기간은 같은 보고 연도 `REPORT_YEAR`의 `[08-01, 09-01)`로 고정한다. 현재 후보는 2026년이지만, 실제 촬영 환경의 ML `as_of`를 확인한 뒤 cue sheet에서 한 번만 확정한다.

| ID | 생성 시점 | 자연어 질문 | 결과 역할 | 보고서에서 사용할 view |
|---|---|---|---|---|
| A | 시연 중 복합 Turn | “2026년 8월 월간보고서를 준비하려고 해. 먼저 호텔별 총 운영 매출을 표로 비교해줘. 내부 운영 보고서에서 같이 봐야 할 내용도 찾아주고, GRAND의 9월 1일 기준 향후 7일 객실 수요도 예측해줘.” | 호텔별 전체 매출 + RAG + ML | Analysis sub-result의 chart와 table |
| B | 촬영 전 실제 서비스로 생성 | “2026년 8월 전체 객실 점유율을 알려줘.” | 월간 객실 KPI | KPI |
| C | 촬영 전 실제 서비스로 생성 | “2026년 8월 GRAND 객실 매출 흐름을 날짜별로 보여줘.” | GRAND 객실 매출 추이 | line chart |
| D | 촬영 전 실제 서비스로 생성 | “2026년 8월 호텔별 초과근로시간을 표로 정리해줘.” | 인력 운영 | compact table |
| E | 촬영 전 실제 서비스로 생성 | “2026년 8월 식음 매출 흐름을 날짜별로 보여줘.” | 식음 매출 추이 | line chart |

`REPORT_YEAR`가 2026이 아니면 A~E와 ML 예측 기간을 모두 같은 연도로 바꾼다. 일부 질문만 연도를 바꾸면 월간보고서 근거가 섞이므로 촬영을 중단한다.

B·C·D·E exact 문구는 현재 모든 조합이 live gold로 입증된 상태가 아니다. B의 `kpi`, C·E의 `chart`, D의 `table`을 실제 Artifact의 `available_views`로 확인한 뒤에만 확정한다. 식음 일별 chart가 안정적이지 않으면 촬영 전에 다른 승인 sum metric의 일별 trend를 선택하고 이 문서와 cue를 함께 갱신한다. 촬영 중 자동 fallback은 두지 않는다.

### 5.3 Artifact 준비 규칙

1. B·C·D·E는 DB seed나 fixture 삽입이 아니라 정상 Analysis UI/API로 한 번 생성한다.
2. 각 run은 같은 사용자 소유이며 `SUCCEEDED` 또는 제품 계약이 허용하는 `PARTIAL` 상태여야 한다. 연결 Artifact는 별도로 `APPROVED`, active, archive되지 않은 상태여야 한다.
3. 각 Artifact에 `artifact_id`, `trino_query_id`, 64자 checksum이 있어야 한다.
4. 가능하면 다섯 개 모두 같은 product·semantic release에서 생성한다.
5. B는 `available_views`에 `kpi`, C·E는 `chart`, D는 `table`이 실제로 있어야 한다.
6. A에서 보고서에 쓰는 것은 복합 Turn의 Analysis sub-result다. RAG 답변과 ML 예측 자체는 현재 Report Artifact가 아니다.
7. A만 촬영 중 실제로 생성한다. 따라서 촬영 계정은 시작 시 B·C·D·E 네 개만 남긴다.
8. A rehearsal은 별도 계정이나 별도 환경에서 한다. 같은 계정을 썼다면 촬영 전에 rehearsal run을 수동 archive한다.
9. 촬영 중 A가 생긴 뒤 활성 Artifact 목록은 정확히 A~E 다섯 개여야 한다.
10. 현재 ad-hoc Analysis 시작 경로가 임시 definition과 `analysis_run_links`를 만들므로 B~E를 별도로 `분석 저장`할 필요는 없다. 대신 Report library의 `approvedOnly` 목록에서 촬영 전 B~E 정확히 4개, A 생성 후 A~E 정확히 5개가 보이는지 확인한다.
11. 자동 cleanup·제목 검색·질문별 자동 선택 로직은 만들지 않는다.

저장 definition 제목이 기존 run picker 제목에 다시 연결된다고 가정하지 않는다. 현재 저장은 새 definition을 만들지만 기존 run을 그 definition으로 back-link하지 않는다. 다섯 개뿐이므로 제목·기간·생성 시각을 사람이 확인해 선택한다. 정확한 제목을 만들기 위해 replay하고 duplicate Artifact를 만드는 방법은 사용하지 않는다.

### 6.2 장면 0 — 데이터 사일로 연결

준비 화면은 기존 Admin 데이터 연결 페이지다. 새 lineage 화면을 만들지 않는다.

화면에서 보여줄 것:

- PMS · PostgreSQL · 준비됨
- POS · MySQL · 준비됨
- Banquet · PostgreSQL · 준비됨
- Facility · ClickHouse · 준비됨

CRM 카드가 함께 보이더라도 총 운영 매출의 근거라고 설명하지 않는다.

발표자 대사:

> “호텔 운영 데이터는 시스템과 DB가 제각각입니다. Answervice는 이 연결을 Trino의 승인 View로 묶어, 사용자가 원본 위치를 외우지 않아도 한 질문으로 분석할 수 있게 합니다.”

이 화면은 connection readiness 증거다. 개별 결과의 재귀 source lineage 증거가 아니다.

### 6.3 장면 1 — 한 번의 자연어 요청으로 Artifact A와 멀티 Agent 증명

사용자 질문:

> “2026년 8월 월간보고서를 준비하려고 해. 먼저 호텔별 총 운영 매출을 표로 비교해줘. 내부 운영 보고서에서 같이 봐야 할 내용도 찾아주고, GRAND의 9월 1일 기준 향후 7일 객실 수요도 예측해줘.”

보고서를 준비하는 실무자가 한 번에 할 법한 요청으로 구성한다. `인식 객실 매출`, `체크아웃 기준`, DB column명 같은 내부 semantic 용어는 cue에 넣지 않는다.

Supervisor가 나눌 역할은 다음 세 가지다.

- Analysis Agent: 2026년 8월 호텔별 총 운영 매출
- RAG Agent: 승인 내부 운영 보고서 검색·인용
- ML Agent: GRAND의 9월 1일~7일 객실 수요 예측

기대 서버 해석:

- composite response type: `COMPOSITE`
- primary route: `ANALYSIS`
- metric: `total_operating_revenue_krw`
- period: `[2026-08-01, 2026-09-01)`
- dimension: `hotel_code`
- presentation: `TABLE`
- direct asset: `serving.analytics_v4_3.hotel_operations_daily`
- 이 Analysis plan의 app-level dynamic join edge: 0
- 새 Analysis Trino query: 1
- terminal receipt: `SupervisorCompositionReceipt.v1`
- 실제 실행: 현재 구현 순서에 따른 RAG·ML·primary Analysis

서버 receipt와 UI 표시명은 다음 mapper를 거친다. 서버 enum을 UI가 임의로 줄여 해석하지 않는다.

| 서버 receipt enum | 프론트 표시 ID | 사용자 표시명 |
|---|---|---|
| `ANALYSIS_WORKFLOW` | `ANALYSIS` | Analysis Agent |
| `INTERNAL_GUIDELINE` | `RAG` | RAG Agent |
| `ML_PREDICTION` | `ML` | ML Agent |

세 값 이외의 enum, 중복, schema 불일치가 있으면 성공 트리를 표시하지 않고 일반 복합 결과로 fail-close한다. 진행 중에는 실제 Agent별 상태 계약이 없으므로 기존 일반 로딩만 사용하며, 가짜 timer·duration·`RUNNING`을 만들지 않는다.

완료 뒤 결과 상단에 다음 구조를 10~15초 보여준다.

```text
Supervisor · 3개 작업 완료
├─ Analysis Agent · 완료
├─ RAG Agent      · 완료
└─ ML Agent       · 완료
```

이 트리는 결과 카드 유무가 아니라 저장된 receipt의 Agent 목록으로 만든다. receipt에 없는 세부 objective나 처리 시간은 꾸며내지 않는다.

화면에서 보여줄 것:

- 위 Supervisor 완료 트리
- GRAND·VISTA·DOUGLAS 등 호텔별 행
- 단위가 적용된 총 운영 매출 값
- Evidence drawer의 direct asset, Artifact ID, query ID
- RAG가 반환한 실제 문서 제목과 citation
- ML이 반환한 날짜별 예측과 model/as-of 정보

발표자 대사:

> “한 문장을 Supervisor가 세 역할로 나눴습니다. 운영 데이터는 Analysis Agent, 내부 문서는 RAG Agent, 미래 수요는 ML Agent가 맡았습니다. 객실·식음·연회·시설 매출은 이종 DB에서 승인 통합 View로 모이며, 지금 보이는 표는 그 View를 실제로 조회한 결과입니다.”

> “완료 트리는 화면이 추측한 것이 아니라 서버에 저장된 실행 receipt를 표시한 것입니다. 현재 실행은 순차 구성이라 병렬 처리라고 설명하지 않습니다. 데이터는 실제 호텔 실적이 아닌 합성 운영 데이터입니다.”

현재 bundled conditional ML 후보를 쓰는 경우 한 문장만 덧붙인다.

> “수요 예측도 합성 데이터로 검증한 시연 후보 모델의 결과입니다.”

실패 조건:

- metric clarification이 뜬다.
- 다른 기간이나 다른 metric으로 해석된다.
- 표가 아니라 scalar만 나온다.
- 세 서버 Agent enum이 모두 receipt에 없다.
- RAG citation 또는 ML 실행 정보가 없다.
- Analysis source·Artifact·query 연결 정보가 없다.

### 6.4 장면 2 — 저장과 typed Trino 0-query 멀티턴

먼저 A의 `분석 저장`을 누른다. 저장 목록에 현재 질문 기반 제목이 나타나는 것만 확인한다. 새 제목 입력 modal은 만들지 않는다.

이어서 A 결과 카드의 `막대그래프로 보기` 퀵액션을 누른다. 버튼은 대화에 다음 자연스러운 후속 문장을 남긴다.

> “호텔별 차이가 잘 보이게 막대그래프로 바꿔줘.”

서버에는 다음 typed action을 함께 보낸다.

```json
{
  "requested_route": "PRESENTATION",
  "presentation_type": "BAR",
  "inherit_previous_context": true
}
```

`sourceTurn`은 바로 앞 A turn으로 명시한다. 이 두 번째 turn이 멀티턴 맥락 재사용 장면이다. 서버는 typed 신호와 source Artifact를 재검증하며, 프론트가 결과를 직접 바꾸거나 ViewSpec을 만들지 않는다.

기대 결과:

- route: `PRESENTATION`
- artifact_id: A와 동일
- query_id: A와 동일
- 새 view_spec_id: 생성
- DataHub·metric selection fast path
- 새 Analysis Trino query: 0

화면에서 보여줄 것:

- 표가 호텔별 막대그래프로 전환된다.
- 작은 배지: `기존 분석 재사용 · 새 분석 쿼리 없음`
- 기술 상세에서는 같은 Artifact ID·query ID를 확인할 수 있다.

배지는 `cached`나 응답 속도로 추정하지 않는다. `PRESENTATION` route와 동일 Artifact·query 식별자 검증이 모두 성공했을 때만 표시한다.

발표자 대사:

> “앞선 분석 맥락은 그대로 두고 표현만 바꿨습니다. 기존 Artifact를 다시 그렸기 때문에 이번 turn에는 새 분석 쿼리가 없습니다.”

### 6.5 장면 3 — 8월 월간보고서 생성

A 결과의 `보고서에 담기`를 누르고 제목을 입력한 뒤 modal의 `초안 만들기`를 누른다.

> `2026년 8월 호텔 운영 월간보고서`

보고서가 열리면 분석 원본 보관함에는 정확히 다섯 개만 보여야 한다.

1. A · 호텔별 총 운영 매출
2. B · 전체 객실 점유율
3. C · GRAND 일별 객실 매출
4. D · 호텔별 초과근로시간
5. E · 일별 식음 매출

보고서 최초 A block 배치는 다음이 권장값이다.

- summary 6/12 + KPI 6/12
- chart 12/12
- table 12/12

초안이 여러 페이지가 되는 것은 허용한다. 이번 목표는 억지로 한 페이지에 압축하는 것이 아니라 읽기 쉬운 월간보고서를 만드는 것이다.

### 6.6 장면 4 — 다섯 Artifact를 Report Assistant로 편집

Assistant의 `근거 변경`에서 A를 대표 근거로 유지하고 B·C·D·E를 모두 선택한다. picker footer의 `5 / 5개 선택`과 닫힌 버튼의 `근거 변경 · 5`가 보여야 한다.

권장 요청:

> “이 다섯 개 근거로 2026년 8월 월간보고서를 정리해줘. 기존 호텔별 총 운영 매출 차트는 가로 막대로 바꾸고 표는 간결하게 유지해줘. 그 아래에는 전체 객실 점유율 KPI, GRAND 일별 객실 매출 선그래프, 전체 일별 식음 매출 선그래프, 호텔별 초과근로시간 표를 이 순서로 가로 폭 전체로 추가해줘.”

권장 typed patch 의미:

1. A chart: `update_chart_settings(chart_type="horizontal-bar")`
2. A table가 compact가 아니면 `update_table_settings(density="compact")`; 이미 compact면 no-op
3. B: `add_artifact_view(view="kpi", placement.width="full")`
4. C: `add_artifact_view(view="chart", chart_type="line", placement.width="full")`
5. E: `add_artifact_view(view="chart", chart_type="line", placement.width="full")`
6. D: `add_artifact_view(view="table", density="compact", placement.width="full")`

모두 기존 Artifact 편집이며 삭제 operation이 없다. 이 선택은 자동 compact를 끈 상태에서도 제거된 block 자리를 만들지 않고, 위험한 변경 체크박스를 추가로 다루지 않아도 된다.

화면에서 보여줄 것:

- route: `기존 분석 결과 편집`
- 새 데이터 analysis plan 없음
- 현재 block 상태에 따라 5~6개 변경 미리보기
- 각 변경의 대상 view와 영향
- 사용자 승인 전에는 Revision이 바뀌지 않음
- 승인 후 Revision `1 → 2`
- 최종 blocks가 A·B·C·D·E를 각각 한 번 이상 참조
- `새 데이터 분석 없음` 또는 같은 의미의 기존 route 표시

Assistant가 다섯 Artifact를 선택만 하고 일부를 보고서에 쓰지 않은 경우는 실패다. 최종 block의 `artifact_id` 집합이 A~E를 모두 포함해야 한다.

Assistant가 exact payload에서 필수 5개 의미 변경(A 차트 변경과 B~E 추가)을 만들지 못하면 촬영 중 임의 문구를 바꾸지 않는다. A 표가 이미 compact라면 별도 table operation이 없는 5개 proposal이 정상이다. 촬영 전에 동일 요청을 두 turn으로 나눌지 결정하고 cue sheet를 다시 고정한다.

- Turn 1: B KPI, C·E line chart, D table을 순서대로 추가
- Turn 2: A chart를 가로 막대로, A table을 compact로 변경

두 turn 모두 `existing_artifact`이며 새 Analysis query는 0이다. 단일 turn과 2-turn 중 하나만 사전 rehearsal로 선택하고 촬영 중 자동 fallback을 두지 않는다.

### 6.7 장면 5 — 결과 확인과 선택 감사 로그

승인 후 보고서에서 다음만 짧게 확인한다.

- Revision `1 → 2`
- A~E가 각각 적어도 한 block의 `artifact_id`로 남음
- Report Assistant session의 `analysis_plan`이 없음
- Presentation과 보고서 편집 동안 새 Analysis query가 없음

발표자 대사:

> “미리 만든 정적 보고서를 연 것이 아닙니다. 시연 전에 실제 서비스로 만든 네 개의 8월 Artifact와 방금 생성한 Artifact를 한 보고서에 결속했고, Assistant의 변경안은 검토 후 새 Revision으로 승인했습니다.”

핵심 동선이 4분 이내에 끝났고 기존 Analysis 감사 로그가 미리 준비된 경우에만 10~15초 보여준다.

새 보고서 감사 event, 새 권한, 새 transaction 정책은 만들지 않는다. 로그가 준비되지 않았거나 계정 전환이 필요하면 이 장면은 생략한다.

## 7. 시연 중 새 Analysis query 예산

| 동작 | 새 Analysis query | 판정 근거 |
|---|---:|---|
| 복합 A의 primary Analysis | 1 | 정상 `ANALYSIS` 실행 |
| 복합 A의 RAG | Analysis query와 별도 | 문서 검색 경로 |
| 복합 A의 ML | Analysis query와 별도 | ML tool의 독립 runtime |
| A 저장 | 0 | definition metadata 저장 |
| A 표→막대그래프 | 0 | typed `PRESENTATION`, 동일 Artifact·query |
| A에서 Report draft 생성 | 0 | 저장된 Artifact snapshot 사용 |
| A~E Assistant 근거 결속 | 0 | App DB의 검증 Artifact 사용 |
| 기존 Artifact patch 제안·승인 | 0 | `existing_artifact`, analysis plan 없음 |
| 보고서 Revision 저장 | 0 | report definition 저장 |

이 표는 Analysis 경로의 query 예산이다. Admin readiness probe나 ML tool 내부 조회까지 포함한 Trino 전역 호출 수를 뜻하지 않는다.

`PRESENTATION`과 Report Assistant의 0-query는 latency로 판단하지 않는다. 단위·통합 테스트에서는 Analysis executor submit 횟수를 검증하고, live 촬영에서는 route·동일 query ID·서버 trace를 함께 확인한다.

## 8. UI/UX 원칙과 BI 벤치마크

- 숨은 자동 compact 제거와 명시적 정돈·방향 변경 reflow 유지
- terminal Supervisor tree
- zero-query 배지

## P0-1. 기존 composition receipt를 Supervisor 완료 트리로 표시

### 목표

### 현재 코드

- composite 응답에는 `composition`, `rag_response`, `ml_prediction`이 있다.
- frontend는 RAG·ML은 붙이지만 composition을 run에 보존하지 않는다.
- 현재 `agentKindsForRun()`은 결과 카드 존재 여부로 Agent 종류를 추정한다.

### 최소 변경

2. `agentResponseMappers.attachAgentResults()`가 composition을 `run.supervisorComposition`으로 보존하게 한다.
3. fresh response는 `data.composition`을 우선하고, 없으면 `serverTurn.resolved_slots.supervisor_composition`을 사용한다.

5. `AgentExecutionBar`는 유효한 receipt가 있을 때 Supervisor parent와 receipt agents child를 그린다.

| `INTERNAL_GUIDELINE` | `RAG` | RAG Agent |
| `ML_PREDICTION` | `ML` | ML Agent |

unknown enum을 `ANALYSIS`로 fallback하지 않는다. schema·enum·중복 검증 중 하나라도 실패하면 Supervisor 성공 트리를 숨기고 기존 일반 결과 표시로 fail-close한다.

## P0-2. typed Presentation 퀵액션과 0-query 표시

같은 결과의 표현 전환을 가장 빠른 기존 경로로 보내고, 새 데이터 분석이 아니라는 강점을 보여준다.

### 최소 변경

1. P0에서는 chart spec이 있는 호환 Analysis 결과에 `막대그래프로 보기` 버튼 하나만 표시한다.

4. source turn을 명시해 오래된 Artifact에 잘못 적용하지 않는다.
5. server response의 route·artifact ID·query ID를 다시 확인한다.
6. 조건이 맞을 때만 `기존 분석 재사용 · 새 분석 쿼리 없음` 배지를 표시한다.

### typed action

| 버튼 | user_message | action |
|---|---|---|
| 막대그래프로 보기 | “호텔별 차이가 잘 보이게 막대그래프로 바꿔줘.” | `PRESENTATION + BAR` |

서버가 지원하지 않는 shape이면 버튼을 숨기거나 서버의 `PRESENTATION_NOT_SUPPORTED`를 그대로 보여준다. 프론트가 임의 데이터를 만들지 않는다.

## V-1. 자연어 질문과 Artifact A~E 실제 서비스 검증

### 목표

시연용 질문을 production에 하드코딩하지 않고 semantic·planner·executor가 실제로 처리하게 한다.

### 작업

1. A의 Analysis sub-request가 `total_operating_revenue_krw + hotel_code + TABLE`로 해석되는 eval case를 추가한다.
2. A가 server enum `ANALYSIS_WORKFLOW`, `INTERNAL_GUIDELINE`, `ML_PREDICTION` 세 개와 primary Analysis를 만드는 integration case를 추가한다.
3. A의 RAG citation과 GRAND 9월 1일~7일 ML capability를 live에서 검증한다.
4. B 질문의 `occupancy_rate` scalar value와 `kpi` available view를 검증한다.
5. C 질문의 `room_revenue + GRAND filter + day bucket + chart`를 검증한다.
6. D 질문의 `overtime_hours + hotel_code + TABLE`을 검증한다.
7. E 질문의 `fnb_revenue + day bucket + chart`를 검증한다.
8. 질문별 runtime branch가 아니라 eval fixture와 contract assertion만 추가한다.

### 안전 규칙

- V-1은 읽기·검증 Gate이므로 exact 질문 실패를 이유로 runtime 코드를 바로 수정하지 않는다. 기존 승인 동의어 안에서 자연스러운 cue를 재선정할 수 있으면 문서와 eval을 함께 갱신한다. 일반 resolver·semantic alias·prompt의 제품 결함 수정이 필요하면 촬영을 중단하고 별도 승인된 제품 작업으로 이관한 뒤 V-1을 처음부터 다시 실행한다.
- 특정 문자열 하나만 통과시키는 `if question == ...` 코드는 금지한다.
- 없는 metric을 새 값으로 꾸미지 않는다.
- RAG citation이 없으면 근거가 있는 다른 승인 문서 질문을 촬영 전에 선택하고 cue를 고정한다.
- ML 기간이 capability 밖이면 날짜만 지원 범위로 고정하고 모든 A~E 연도를 함께 점검한다.

### 완료 조건

- A~E live run이 각각 기대 metric·period·shape·Artifact receipt를 갖는다.
- B·C·D·E는 촬영 계정에 정확히 한 개씩만 남는다.
- A의 RAG는 citation 1개 이상, ML은 capability 범위 내 예측을 반환한다.

## P0-3. 보고서 기본 배치와 `compactDraftLayout()` 자동 압축 제외

### 목표

월간보고서가 처음부터 읽기 쉬운 폭을 사용하고, load·save와 명시적 전체 재배치가 아닌 편집이 사용자의 빈 공간과 유효한 좌표를 임의로 위로 당기지 않게 한다. 이 항목은 시연용 예외가 아니라 report editor의 일반 동작 계약이다.

### 기본 초안의 작은 변경

`app/backend/app/api/report_router_support.py`의 폭 map을 다음처럼 바꾼다.

```text
summary: 6
kpi:     6
chart:  12
table:  12
```

summary와 KPI는 한 행, 차트와 표는 각각 full width가 된다. height 계산과 renderer는 기존 코드를 유지한다.

### `compactDraftLayout()` 범위

함수 자체를 삭제하지 않는다.

유지할 곳:

- 사용자가 직접 누르는 명시적 `레이아웃 정돈`/`compact layout` 명령
- 사용자가 직접 방향을 바꿨을 때의 `setReportOrientation()` semantic reflow
- 좌표 누락·범위 이탈·겹침이 있는 손상된 legacy layout을 복구하는 `restoreDraftLayout` 경로
- 별도로 합의된 repair command

자동 호출을 제거할 정상 제품 경로:

1. 유효한 server block을 editor state로 load할 때
2. dirty signature를 계산할 때
3. 현재 draft를 save payload로 만들 때
4. Artifact content hydration으로 높이를 맞출 때
5. Assistant patch Revision을 reload할 때
6. block을 새로 배치하거나 paste할 때
7. block을 delete할 때
8. drag·resize·chart/table 설정을 적용할 때
9. Document V2의 `insertArtifactBlock()`, `deleteReportBlock()`, `moveReportBlock()`을 실행할 때
10. `serializeReportDocument()`와 `parseReportDocument()`를 실행할 때
11. backend `resize_block` patch를 적용할 때

핵심 규칙:

- 유효한 `(x,y,w,h)`는 그대로 round-trip한다.
- content 높이가 커져 실제 충돌이 생기면 충돌 block만 아래로 민다.
- unrelated block을 위로 당기지 않는다.
- delete 뒤의 빈 공간은 사용자가 명시적으로 정돈하기 전까지 유지한다.
- add·paste는 기존 block 전체를 재정렬하지 않고 요청 위치 또는 다음 충돌 없는 위치에 새 block만 둔다.
- resize가 실제 충돌을 만들 때만 영향받는 block을 아래로 이동한다.
- Assistant의 `compact_report_layout`은 사용자가 명시적으로 요청했을 때만 실행한다.
- 정상 layout에 단순 gap이 있다는 이유만으로 legacy repair를 실행하지 않는다.
- orientation 변경은 page geometry 자체를 바꾸는 명시적 동작이므로 전체 semantic reflow를 허용한다. 촬영 동선에서는 방향을 바꾸지 않는다.

이 요구를 지키기 위해 새 layout engine을 만들지는 않는다. 다만 현재 Draft layout과 Document V2라는 두 좌표 경로에 숨은 재배치가 있으므로 P0-3은 이번 범위에서 가장 큰 독립 editor-contract 작업이다. 각 호출 지점의 무조건적인 `compactDraftLayout()`·`compactReportDocument()`를 제거하고 좌표 보존·collision-only 배치를 공용 helper로 명시한다. 일정이 부족해도 demo 분기로 우회하거나 “작은 수정”이라고 과소평가하지 않는다.

1. 의도적인 세로 gap이 있는 유효 layout을 load→save→reload해 좌표가 동일하다.

- 자동 압축은 사용자 명시 정돈, 명시적 orientation semantic reflow, 손상 legacy repair에서만 발생한다.
- Recharts·dnd-kit dependency를 바꾸지 않는다.

## P0-4. 다섯 Artifact Report Assistant happy path

### 목표

대표 A와 추가 B·C·D·E를 한 세션에 넣고, 새 데이터 분석 없이 실제 report block을 생성한다.

### 현재 계약을 유지할 것

- 대표 Artifact 1개
- `additional_artifact_ids` 최대 4개
- 총 5개 중복 금지
- source alias `source_artifact`~`source_artifact_5`
- patch 최대 12 operations
- 외부 전송 동의가 필요한 경우 기존 동의 흐름 사용
- patch preview와 선택 승인
- 원본 Revision 불변, 승인 후 새 Revision 생성

### 최소 UI 흐름

1. A에서 생성한 report draft를 연다.
2. Assistant 대표 근거가 A인지 확인한다.
3. `근거 변경`에서 B·C·D·E를 체크한다.
4. `5 / 5개 선택`과 `근거 변경 · 5` 표시를 확인한다.
5. exact Assistant 요청을 전송한다.
6. route가 `existing_artifact`인지 확인한다.
7. 6개 patch preview를 확인한다.
8. 모두 승인한다.
9. Revision 2와 최종 block을 확인한다.

### 서버 검증

1. 다섯 Artifact의 owner·approval·status·archive 상태를 다시 확인한다.
2. query ID와 checksum을 확인한다.
3. model에는 내부 alias만 주고 실제 Artifact ID를 임의 생성하게 하지 않는다.
4. 요청된 view가 각 Artifact의 `available_views`에 있는지 확인한다.
5. patch는 allowed operation과 현재 block ID만 사용한다.
6. `analysis_plan`이 없어야 한다.
7. 승인 전에는 definition version이 바뀌지 않아야 한다.
8. 승인 후 version은 정확히 +1이어야 한다.

### 필수 E2E assertion

```text
assistant_session.artifact_ids == (A, B, C, D, E)
proposal.change_kind == "existing_artifact"
proposal.session.analysis_plan is null
patch.operations ⊆ {
  update_chart_settings,
  update_table_settings,
  add_artifact_view
}
final_report.block_artifact_ids ⊇ {A, B, C, D, E}
new_analysis_query_count == 0
definition_version == previous_version + 1
```

### 촬영 경로에서 제외할 operation

- `remove_block`
- `compact_report_layout`
- `resize_block`
- 새 데이터 `analysis_plan`
- 임의 text block에 수치를 생성하는 operation

이 operation들이 제품에서 금지된다는 뜻은 아니다. no-compact와 3~5분 촬영을 안정화하기 위해 exact cue에서 쓰지 않는다는 뜻이다.

### 완료 조건

- 다섯 Artifact가 선택만 된 것이 아니라 최종 report block에 모두 쓰인다.
- 보고서가 화면과 HTML·PDF renderer에서 모두 읽을 수 있다.
- 촬영 중 새로고침 없이 전체 happy path가 끝난다.

Report Assistant session의 Artifact 선택 UI는 reload 후 추가 선택 복원에 간극이 있을 수 있다. 촬영에는 reload를 넣지 않는다. 복원 기능이 필요하면 별도 integration 작업으로 다루며 P0 성공 기준에 포함하지 않는다.

## V-2. Live preflight와 rehearsal

### 목표

정적 테스트가 통과해도 live dependency가 준비되지 않으면 촬영하지 않는다.

### 차단형 preflight

| Gate | 확인할 값 | 실패 시 |
|---|---|---|
| Build | commit, image digest, frontend/backend version | 촬영 중단 |
| App DB | migration head, report/analysis repository read | 촬영 중단 |
| Agent runtime | actual RAG·ML·Supervisor flags, backend `/readiness`, RAG/ML receipts | 촬영 중단 |
| ML approval | `APPROVED` receipt 또는 conditional synthetic 후보의 명시적 촬영 허용·checksum | 촬영 중단 |
| Trino | relevant catalogs ready, integrated View readback | 촬영 중단 |
| Semantic | A~E metric·period·dimension resolution | 촬영 중단 |
| Analysis | A exact composite question, source·Artifact·query receipt | 촬영 중단 |
| Presentation | same A artifact/query, new ViewSpec, submit +0 | 촬영 중단 |
| Supervisor | 3-agent receipt, terminal success | 촬영 중단 |
| RAG | 실제 승인 문서 citation ≥ 1 | 질문을 촬영 전에 재선정 |
| ML | GRAND 지원, as-of, 7일 horizon ≤ max horizon | 날짜를 촬영 전에 재고정 |
| Prepared Artifacts | B·C·D·E exact 4개, expected available views | 다시 정상 서비스로 준비 |
| Library | A 전 active exact 4, A 생성 후 exact 5 | 수동 정리 후 다시 확인 |
| Assistant | 5개 binding, expected patch, input/output budget | 촬영 중단 |
| Renderer | 화면·HTML·PDF block overflow 없음 | layout 수정 후 재검증 |

### rehearsal 횟수

- A exact 질문: fresh conversation에서 3회
- A typed Presentation 퀵액션: 각 A 뒤 3회
- Assistant exact 5-Artifact 요청: 같은 구조의 rehearsal account에서 3회
- 전체 cue: 최소 2회 연속 4분 05초 이내

rehearsal 성공 결과를 production 응답으로 복사하지 않는다. rehearsal은 모델·계약의 안정성을 확인하는 용도다.

### live 증거로 남길 것

- A의 request/trace/artifact/query ID
- composition receipt schema·agent list
- RAG citation ID와 ML execution/model/as-of
- B·C·D·E artifact/query/checksum
- Report Assistant session ID, selected 5 artifact IDs
- patch request ID와 approved operation indexes
- before/after report definition version
- Presentation·Assistant 전후 새 Analysis query가 없다는 trace

credential, token, host password는 캡처하지 않는다. 이를 위해 새 보안 플랫폼을 만들지 않고 기존 UI의 비민감 정보만 사용한다.

## 10. 구현 순서와 중단 기준

### 1단계 — 질문과 데이터부터 검증

1. composition receipt passthrough
2. terminal Supervisor tree

1. 초안 폭 map 6·6·12·12

3. 좌표·gap·collision-only round-trip test
4. 명시적 정돈과 손상 legacy repair 회귀 test

### 4단계 — 5-Artifact Assistant 통합

1. B·C·D·E를 실제 서비스로 준비
2. rehearsal A와 준비 Artifact로 5개 binding 검증
3. exact Assistant 요청 3회
4. 최종 block artifact set A~E 검증
5. renderer 검증

### 5단계 — 최종 촬영 rehearsal

1. 촬영 계정에는 B·C·D·E만 남김
2. 복합 A를 live 생성
3. exact 5개 확인

5. 로그·ID·시간 기록

### 즉시 중단 조건

- 질문별 hardcode가 필요해진다.
- 없는 metric이나 정적 Artifact를 production 코드에 넣어야 한다.
- RAG citation 또는 ML capability가 실제로 없다.
- six-artifact 상한 변경이 core에 끼어든다.
- 새로운 provenance compiler·progress platform·audit subsystem이 필요해진다.
- 자동 compact를 일부 경로에 남긴 채 완료했다고 주장해야 한다.

중단 조건이 발생하면 시나리오를 승인된 기존 기능 안에서 줄인다. production 코드를 demo 질문에 맞춰 속이지 않는다.

AI 개발 Agent는 아래 순서를 그대로 따른다.

1. repository root, branch, HEAD, dirty worktree, repository `AGENTS.md`를 확인한다.

10. 각 제품 P0 사이에 해당 V Gate를 다시 확인한다.
11. 각 단계에서 수정 파일, 실행 테스트, 미실행 테스트, 남은 위험을 기록한다.

| 최종 상태 | `approved` |
| Artifact / block | 5개 / 5개, A~E 모두 포함 |
| 배치 | 전 블록 `x=0`, `w=12`; A 가로 막대, B KPI, C·E 선그래프, D 표 |
| Renderer | `weasyprint-69` |
| HTML | HTTP 200, 17,391자, 다섯 제목 모두 포함 |
| PDF | HTTP 200, 435,494 bytes, `%PDF-` magic |
| PDF checksum | 저장 document receipt와 실제 다운로드 SHA-256 일치 |

저장 document의 `pdf_checksum`과 실제 다운로드 bytes의 SHA-256이 일치했다. document receipt에도 A~E의 Artifact checksum과 Trino query ID가 모두 봉인돼 있다.

### 19.5 감사 로그 실측

관리자 감사 화면을 실제 브라우저에서 열어 `ANALYSIS_SUCCEEDED`, `ANALYSIS_ARTIFACT_ARCHIVED`, `REPORT_ARCHIVED` event가 검색 가능한 작업 이력에 표시되는 것을 확인했다. 최종 A의 Analysis event에는 Artifact와 query ID, 그리고 `ROUTER → MODEL → CONTEXT → G1 → G2 → QUERY → G3 → ARTIFACT` trace가 남아 있다.

새로운 강한 감사 체계는 만들지 않았다. 시간이 남으면 기존 화면에서 Analysis 성공과 Artifact·Report 보관 이력만 10~15초 보여준다.

### 19.6 최종 배포본 브라우저 E2E 결과

Report Assistant의 실제 모델 경로는 `https://api.openai.com`의 `gpt-5.4-mini`, Supervisor는 같은 origin의 `gpt-5.6-terra`다. V-2에서 전송된 범위는 사용자 지시, 보고서 metadata·layout·block content, 선택한 다섯 Artifact의 metadata·narrative·metrics·chart spec·table snapshot이다. 인증 토큰·비밀번호·DB/SQL 자격 증명과 선택 Artifact 밖의 원본 DB 행은 제외됐다.

최종 배포본에서 한 번의 처음부터 끝까지 브라우저 E2E로 다음을 확인했다.

1. 최종 A cue가 Analysis·RAG·ML을 모두 실행하고 Supervisor가 3개 완료 receipt를 표시했다.
2. “호텔별 차이가 잘 보이게 가로 막대그래프로 바꿔줘.”가 실제 가로 막대로 바뀌었다.
3. DB receipt 기준 Analysis request와 query execution은 전환 전후 각각 1건으로 유지되어 Trino 0-query를 확인했다.
4. 다섯 Artifact Assistant 요청은 `existing_artifact`로 5개 의미 변경을 제안했다. A 표는 이미 compact라 별도 no-op을 만들지 않았다.
5. 적용 후 revision은 v1→v2, block은 4→8, 3페이지가 되었고 A 가로 막대·B KPI·C/E 선그래프·D 표 순서를 확인했다.
6. 저장 후 목록으로 나갔다가 `열람`으로 다시 들어와도 8개 block이 모두 보였고 빈 화면·Artifact load error가 없었다.
7. 관리자 감사 로그를 실제 브라우저에서 열어 최근 Analysis·Artifact·Report lifecycle 이력을 확인했다.
8. 리허설 보고서는 휴지통으로 이동했고, 시연 시작 상태는 active 보고서 0개와 B~E active Artifact 4개다.

이 절은 기능 경로의 브라우저 통과 기록이다. 촬영 당일의 네트워크·외부 모델 지연을 보장하지 않으므로, 촬영 직전 readiness와 exact cue 1회 smoke test는 계속 수행한다.

### 19.7 최종 source gate

최종 문서·테스트 보정 tree에서 다음 gate를 모두 통과했다. dependency가 다른 suite는 CI 계약과 같은 격리 환경으로 나눴으며 skip은 통과 수에 더하지 않았다.

| Gate | 결과 |
|---|---|
| OpenAPI export/check | `OPENAPI_CONTRACT_VERIFIED` |
| code documentation | 579 source files, 81 executable configs 통과 |
| architecture invariant | 495 source files 통과 |
| repository integrity | 1,333 files 통과 |
| Python core | 1,896 passed, 75 skipped, 500 subtests passed |
| RAG | 229 passed, 37 subtests passed |
| Node2 | 29 passed, 11 subtests passed |
| ML runtime | Python 3.12·scikit-learn 1.9 격리 환경에서 83 passed |
| Frontend | 47 passed, production build 통과 |
| Compose | `dev`, `full`, `split-host` config 통과 |
| Python compileall / diff | compileall 통과, `git diff --check` 통과 |

전체 단일 Python 프로세스의 첫 실행은 잘못된 basetemp 부모 경로 때문에 실패했고 PASS로 세지 않았다. 두 번째 단일 프로세스에서 드러난 dependency lane 차이는 CI와 같은 환경으로 분리했으며, migration head·fail-close HTTP 기대값·Node2 source receipt의 실제 drift를 보정한 뒤 모든 대상 test file을 해당 lane에서 통과시켰다.
