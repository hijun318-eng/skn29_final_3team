ANSWERVICE P0 사용자 기능 요구사항 및 구현·검증 계획
=====================================================

문서 ID: ANS-P0-UX-001
기준일: 2026-08-13
상위 기준: 01_MVP_PRD.md, 02_Golden_Path_유저플로우.md, 03_E2E_아키텍처_및_계약.md
목적: 사용자 기능 요구를 구현 가능한 작업과 실제 검증 기준으로 변환한다.


0. 적용 결정
-----------

1) 기능 수를 병렬로 늘리지 않고 한 번에 하나의 Vertical Slice만 완료한다.
2) 현재 dirty worktree에서 이미 진행 중인 자연어 질문·기간·지표 명확화 Slice를 먼저 끝낸다.
3) 이후 로그인/세션, 실행 상태/오류, 결과/Evidence, 저장/이력, Report 순서로 확장한다.
4) P0 완료는 코드나 문서 작성이 아니라 실제 Docker·HTTP·브라우저 재현으로 판정한다.
5) fake, fixture, 이전 성공 결과와 하드코딩 KPI는 제품 성공 근거로 사용하지 않는다.
6) 인증, 권한, G1·G2·G3, Trino read-only, 오류 처리와 trace는 어떤 Slice에서도 생략하지 않는다.
7) RAG, ML-as-a-Tool, 새 Source, 새 Agent framework, 모델 재학습, 외부 배포는 이 문서의 P0 범위가 아니다.

제품 사용자와 최종 메시지:

- 1차 제품 사용자는 호텔 C-level 또는 사업책임자다.
- 현재 runtime의 hotel_analyst는 이 사용자 흐름을 검증하는 MVP 역할이다.
- 핵심 가치는 Text-to-SQL이 아니라 승인된 업무 정의·권한·검증·추적·Report 재사용이다.
- 최종 발표 메시지는 다음으로 고정한다.

  "권한이 제한된 사업책임자가 여러 업무 시스템을 연결한 KPI 질문을 하면,
   Answervice가 승인된 Metadata와 업무 정의를 사용해 안전하게 조회하고,
   실패를 통제하며, 근거 있는 결과를 반복 가능한 Report로 제공한다."

상태 값:

- NOT_VERIFIED: 구현 또는 검증 여부를 확인하지 않음
- IN_PROGRESS: 코드 변경 중이며 제품 Exit Gate 미통과
- PASS: 지정한 자동 검증과 실제 제품 경로를 모두 통과
- FAIL: 검증 실행 결과가 기대와 다름
- BLOCKED: 외부 환경 또는 권한이 없어 검증 불가

완료 증거의 최소 단위:

- 변경 파일과 계약 Version
- 실행한 자동 테스트와 결과
- 실제 HTTP 요청·응답
- 브라우저 화면에서 사용자가 수행한 절차
- request_id, trace_id, query_id, artifact_id
- 필요한 경우 DB/Trino 상태와 재시작 전후 영속성
- 실행하지 못한 검증과 이유


0.1 중간발표 평가 피드백 반영

공통 평가 결론:

- 설계 범위를 더 넓히는 것보다 하나의 실제 End-to-End 흐름을 증명한다.
- 단일 Source 조회가 아니라 객실·멤버십·F&B를 연결한 C-level KPI를 시연한다.

0.2 역할과 정보 전달 경계
------------------------

Planner:
- 현재 구성: Controller + Router + Node 1
- 입력: 자연어 질문, request context, 승인 business term 목록
- 출력: 구조화 질문, 확인 필요 상태, 고정 실행 경로
- 금지: 권한·SQL 실행·최종 합격을 자유 판단

Metadata:
- 현재 구성: DataHub + Asset Binding + Business Rule + Context Builder + G1
- 입력: 구조화 질문, role/permission, Metadata, Rule/Binding Version
- 출력: Approved Context Package와 G1 상태
- 금지: 권한 밖 Asset 포함, 임의 Metric·JOIN 생성

Query:
- 현재 구성: Node 2 + Node 2 Repair + Trino adapter
- 입력: Approved Context와 정형 G2 오류
- 출력: SQL 초안, 최대 1회 수정 SQL, Trino Query ID/Result
- 금지: 직접 실행 승인, 쓰기 SQL, 무한 Repair

Validation:
- 현재 구성: G1 + G2 + G3 + SQLGlot + Trino policy
- 입력: Context, SQL AST, Raw Result
- 출력: PASS/BLOCKED/FAILED, Safe Result와 오류 코드
- 금지: LLM 자체 합격 판정, G3 전 Raw Result 외부 전달

Report:
- 현재 구성: Node 3 + Artifact + Analysis/Report domain
- 입력: Safe Result, Evidence, Analysis Artifact
- 출력: 근거 기반 설명, 저장 Run, Report Block/Run
- 금지: 결과 재계산, 근거 없는 인과 생성, 과거 결과 덮어쓰기


0.3 P0/P1/P2 범위
-----------------

P0 — 최종평가 전에 실제 구현·검증:

- 이 문서의 P0 요구와 E2E-P0-01~30
- 대표 1 Source, 2 Source, PMS·CRM·POS 3 Source 분석
- 권한 허용·거부·마스킹
- G2 1회 Repair와 최종 차단
- 오류·부분 실패·저장·재실행·Report 수동 실행
- 정량 평가와 재현 가능한 Docker Demo

P1 — P0 완료 후 조건부 확장 또는 기존 구현 회귀만 유지:

- Report Schedule
- Report Assistant
- read-only MCP
- 편집 편의 기능 중 P0가 아닌 UX 권장 항목

P2 — 최종평가 구현 완료로 표현하지 않음:

- RAG와 비정형 문서 결합
- ML-as-a-Tool, Customer 360
- 자유형 고급 KPI 추천
- 외부 Report 배포와 복잡한 승인 Workflow
- HTML/PDF 고도화 Export
- 새 Agent framework와 Kubernetes/Production 확장
- 모델 재학습과 복수 SQL 후보 실험

이미 구현된 P1 기능은 삭제하지 않되 P0 Slice 변경 시 회귀만 확인한다. P1 기능 확장은 P0 완료를 방해하지 않는다.


0.4 통합 작업 제안 정합성 판정 (2026-08-13)
-------------------------------------------

검토 대상: `통합_작업_제안_20260813.md`. 이 문서를 대체하지 않는 보강 제안으로만 취급한다.

채택:

- S9에서 실제 Connection Registry·DataHub·Trino를 교차해 현재 구성되고 권한·Rule·Binding으로
  승인된 capability inventory를 만든다. schema·table·column·metric·join metadata drift는
  fail-closed로 차단하고 Connection별 오류를 구분한다.
- S10에서 현재 구성된 모든 Backend Connection과 모든 승인 Asset이 최소 1회 실제 read-only
  query를 통과하도록 동적 검증 대상을 만든다. 조합 폭발은 pairwise와 경계값으로 제한하되
  Connection·승인 Asset coverage는 생략하지 않는다.
- 검증 결과에는 Connection ID, Source URN/FQN, schema version, 질문·plan, G1·G2·G3,
  Trino query ID, Result checksum, Artifact ID와 필요한 Report Run ID를 기록한다.
- 기존 SQLGlot AST, typed parameter, 실제 Result schema, Artifact 기반 Report, Source별 실패 분리,
  readiness 계약은 유지하고 S9·S10에서 전체 회귀한다.

조건부 채택:

- 새 Connection은 credential·adapter·DataHub metadata·권한·Metric·JOIN Rule·Asset Binding이
  명시적으로 승인된 뒤 inventory에 포함한다. 단순 등록만으로 자동 실행 범위를 넓히지 않는다.
- 자유 질문 지원은 Approved Context가 표현할 수 있는 범위에 한정한다. 지원 불가·모호성·권한 부족은
  구체적 이유와 함께 차단하며 임의 Asset·Column·JOIN 탐색으로 우회하지 않는다.

거부 또는 P0 제외:

- 제안서 목표 E2E의 `Node 2 → G1` 순서는 보안 경계와 충돌하므로 채택하지 않는다.
  Node 2는 반드시 Metadata와 G1이 만든 Approved Context 뒤에 실행한다.
- 모든 schema·table·column을 곧바로 질의 가능하게 하거나 새 연결을 무승인 자동 포함하는 범위는
  P0가 아니며 최소 권한·승인 JOIN 원칙에 어긋난다.
- P0에서 임의 Source/Metric 조합을 전부 지원하거나 전 조합 Cartesian E2E를 요구하지 않는다.
  S10은 현재 승인 capability의 bounded coverage를 증명한다.

2. 기능 요구사항
----------------

2.1 로그인과 권한

P0 필수:

- AUTH-P0-01 아이디·비밀번호로 로그인한다.
- AUTH-P0-02 잘못된 아이디와 비밀번호를 구분하지 않는 안전한 오류를 표시한다.
- AUTH-P0-03 로그인 처리 중 버튼을 비활성화해 중복 제출을 막는다.
- AUTH-P0-04 세션 만료 시 로그인 화면으로 보내기 전에 재로그인이 필요함을 명확히 알린다.
- AUTH-P0-05 세션 만료 전 작성 중이던 질문과 Report 초안 변경을 보존한다.
- AUTH-P0-06 로그아웃할 수 있고, 로그아웃 즉시 보호 API와 화면 접근이 차단된다.
- AUTH-P0-07 현재 계정 역할을 Header 또는 계정 영역에 표시한다.
- AUTH-P0-08 역할별로 허용된 메뉴만 표시한다.
- AUTH-P0-09 분석 사용자와 Report 관리자의 실행·승인 권한을 분리한다.
- AUTH-P0-10 권한 없는 URL 직접 접근을 Frontend route와 Backend API 양쪽에서 차단한다.
- AUTH-P0-11 인증 오류(401/403)와 서버·네트워크 장애(5xx/network)를 다른 문구와 행동으로 안내한다.
- AUTH-P0-12 세션 토큰은 브라우저 영구 저장소에 보관하지 않는다.

사용성 권장:

- AUTH-UX-01 비밀번호 표시/숨김을 제공한다.
- AUTH-UX-02 Caps Lock 활성 상태를 안내한다.
- AUTH-UX-03 개발환경에서만 로그인 계정 예시를 표시한다.
- AUTH-UX-04 마지막 로그인 역할 이름만 기억할 수 있다. 토큰·비밀번호는 저장하지 않는다.

구현 결정:

- 미전송 질문 draft는 sessionStorage를 사용할 수 있으나 토큰·분석 결과의 단일 원본으로 사용하지 않는다.
- Report의 서버 저장 draft가 단일 원본이다. 저장 전 로컬 변경이 있다면 sessionStorage에는 비민감 layout diff만 임시 보존하고 로그인 성공 후 사용자가 복원 여부를 선택한다.
- 명시적 로그아웃 시 세션 토큰과 임시 draft를 정리한다. 세션 만료에 의한 재로그인에서는 draft를 유지한다.


2.2 분석 질문 입력

P0 필수:

- QUESTION-P0-01 시작일·종료일 입력 없이 자연어 질문만 제출한다.
- QUESTION-P0-02 질문에서 Metric, 기간, 집계 단위, Filter를 구조화한다.
- QUESTION-P0-03 실제 승인 Context로 실행 가능한 예시 질문을 제공한다.
- QUESTION-P0-04 공백만 있는 질문은 Frontend와 Backend 양쪽에서 차단한다.
- QUESTION-P0-05 동일 질문의 빠른 중복 제출을 막는다.
- QUESTION-P0-06 처리 중 전송 버튼을 비활성화한다.
- QUESTION-P0-07 제출한 질문과 실패 후 수정 중인 질문을 유지한다.
- QUESTION-P0-08 이전 질문을 수정해 새 request_id로 다시 분석할 수 있다.
- QUESTION-P0-09 최대 1,000자를 적용하고 초과 전에 남은 길이 또는 초과 안내를 표시한다.

승인 예시:

- 2026년 6월 GOLD 고객의 인식 객실 매출을 월별로 보여줘.
- 2026년 5월과 6월 GOLD 고객의 객실·식음 통합 매출을 비교해 줘.
- 이번 달 식음 순매출을 일별로 분석해 줘.

3. Slice 1 상세 구현 계약
------------------------

목표:

사용자가 날짜 Field 없이 자연어 질문만 제출하고, Backend가 승인된 Metric과 정확히 하나의 기간을 확정하거나 구체적인 선택·수정 안내를 반환한다.

입력 예:

A. 2026년 6월 GOLD 고객의 인식 객실 매출을 월별로 보여줘.
B. 2026년 5월과 6월 GOLD 고객의 객실·식음 통합 매출을 비교해 줘.
C. 2026년 6월 객실 매출을 분석해 줘.
D. 객실 매출을 분석해 줘.

기대 결과:

- A: 2026-06-01 이상 2026-07-01 미만, 단일 승인 Metric으로 실행
- B: 2026-05-01 이상 2026-07-01 미만, PMS·CRM·POS 승인 Context로 실행
- C: CONTEXT_INCOMPLETE와 인식 객실 매출/숙박일 배분 객실 매출 선택지
- D: CONTEXT_INCOMPLETE와 기간 포함 예시, Node 2·Trino 호출 0회

Backend 계약:

- AnalysisRequest.question: 1~1,000자
- AnalysisRequest.parameters: 신규 질문에서는 빈 Object 허용
- Node 1: metric_candidates, selected_metric_id, period_candidates 반환
- Context Builder: period_candidates가 정확히 1개일 때만 기간 봉인
- ErrorBody: code, message, retryable, suggestions
- 외부 오류 code: CONTEXT_INCOMPLETE
- 내부 원인: PERIOD_REQUIRED 또는 INVALID_METRIC
- suggestions: 현재 권한에 포함된 승인 한글 업무명만 반환
- 차단 뒤 Node 2·G2·QUERY·G3·ARTIFACT 성공 event 금지

Frontend 계약:

- 날짜 Input 제거
- 빈 질문과 처리 중 중복 제출 차단
- 원래 질문 유지
- 승인 Metric Button 선택 시 원래 질문을 보완해 새 request로 제출
- 성공 응답의 Evidence 기간만 저장 분석 Parameter로 사용
- 실패·확인 요청에서 이전 성공 Result를 표시하지 않음

- Frontend 질문-only 요청과 제안 선택 contract PASS
- 기존 1 Source와 3 Source 회귀 PASS
- 공식 Docker HTTP 정상/선택/차단 3건 PASS
- 실제 Browser에서 지표 선택 후 성공 PASS
- 성공 Evidence 기간과 저장 Definition Parameter 일치
- query_id/artifact_id/request_id/trace_id 확인

4.1 정량 평가 계약
-----------------

측정 원칙:

- 같은 data snapshot, Context/Rule/Binding/Policy Version과 실행 환경을 사용한다.
- 표본 수, 성공 정의, timeout, retry 수와 warm/cold 조건을 결과표에 함께 기록한다.
- 측정하지 않은 값을 PASS 또는 100%로 표현하지 않는다.
- SQL 문자열 일치보다 실제 Result와 Gold Result의 일치를 우선한다.
- 순서가 무의미한 Row는 정렬하고 Decimal·Null·Tolerance 규칙을 고정한다.

필수 지표:

- METRIC-EVAL-01 질문 완료 성공률
  정의: 사용자 확인을 포함해 최종 SUCCEEDED/PARTIAL의 허용 기준에 도달한 Case / 전체 Positive Case

- METRIC-EVAL-02 Interpreter Contract Parse Success
  정의: Node 1 출력이 strict Schema를 만족한 Case / Node 1 호출 Case

- METRIC-EVAL-03 Context Grounding Success
  정의: Gold Metric·Asset·JOIN·기간·권한을 모두 선택한 Case / Context 대상 Case

- METRIC-EVAL-04 SQL Parse Success
  정의: Trino dialect AST parsing 성공 Case / Node 2 출력 Case

- METRIC-EVAL-05 G2 정상 SQL Acceptance
  정의: 정상 Gold SQL을 과대 차단하지 않은 Case / 정상 Gold SQL Case

- METRIC-EVAL-06 G2 Security Corpus Block Rate
  정의: 정의한 위험 Corpus를 차단한 Case / 해당 Corpus 전체
  P0 안전 기준: 준비한 Critical Corpus에서 미차단 0건

- METRIC-EVAL-07 Query Success
  정의: G2 통과 뒤 Trino 실행 성공 Case / Trino 실행 Case

- METRIC-EVAL-08 Result Accuracy
  정의: 정규화한 Result가 Gold Result와 일치한 Case / 실행 가능한 Positive Case
  P0 Golden 기준: 대표 1·2·3 Source 시나리오 불일치 0건

- METRIC-EVAL-09 Context Violation
  정의: Approved Context 밖 Asset·Column·JOIN을 사용한 Case 수
  P0 안전 기준: 0건

- METRIC-EVAL-10 민감정보 노출
  정의: Safe Result·UI·Node 3·Report에 권한 없는 민감정보가 노출된 Case 수
  P0 안전 기준: 0건

- METRIC-EVAL-11 Source DB Write
  정의: 폐기 가능한 합성 Test 환경의 write probe 성공 건수
  P0 안전 기준: 0건, 전후 Row count/checksum 불변

- METRIC-EVAL-12 End-to-End Latency
  기록: cold/warm p50, average, p95, maximum, timeout 수
  판정: 실행 환경과 표본 수를 먼저 고정하고 실측값을 보고한다. 측정 전 목표값을 만들지 않는다.

- METRIC-EVAL-13 단계별 Latency
  기록: 질문 해석, Context, model, G2/Repair, Query, G3, Narrator, Persist 단계

4.2 최종평가 시연 순서
---------------------

정상 시연:

1) C-level/사업책임자 Persona로 로그인하고 현재 runtime role을 확인한다.
2) "2026년 5월과 6월 GOLD 고객의 객실·식음 통합 매출을 비교하고 변화와 근거를 보여줘"를 입력한다.
3) 시스템이 기간, GOLD, 객실·식음 통합 매출의 승인 정의를 표시한다.
4) DataHub Asset, Metric, Time Rule, Identity/JOIN Rule과 Permission으로 만든 Context 근거를 펼친다.
5) G1·G2 통과 SQL만 Trino에서 read-only로 실행됐음을 확인한다.
6) 객실·F&B·통합 매출의 월별 값과 증감을 표·차트로 확인한다.
7) 원인을 표현할 때 조회된 객실/F&B 구성 변화만 설명하고 데이터에 없는 인과를 생성하지 않는다.
8) Artifact를 저장하고 같은 Analysis를 다른 기간으로 재실행한다.
9) Report 초안을 생성·저장하고 approved version을 수동 실행한다.
10) request_id에서 Report Run까지 Trace와 Version을 확인한다.

실패 시연:

1) 모호한 "2026년 6월 객실 매출"을 입력해 승인 Metric 선택지를 확인한다.
2) 기간 없는 질문을 입력해 Node 2·Trino 미호출과 구체적 수정 안내를 확인한다.
3) 권한 없는 민감 Field 요청의 Context 제외 또는 실행 차단을 확인한다.
4) 별도 G2 실패 Case에서 오류 코드와 Repair 1회를 확인한다.
5) 두 번째 G2 실패가 다음 단계로 진행하지 않고 명시적으로 종료되는지 확인한다.
6) 일부 Source 실패 Report가 전체 성공이 아닌 PARTIAL_SUCCESS로 표시되는지 확인한다.
7) 실패 Block이 과거 성공 결과를 이번 실행 결과처럼 표시하지 않는지 확인한다.


5. P0 완료 판정
----------------

P0 완료는 다음을 모두 만족할 때만 선언한다.

1) 이 문서의 P0 ID가 코드·자동 테스트·브라우저 시나리오 중 하나 이상과 연결돼 있다.
2) S1~S10이 각 Exit Gate를 통과했다.
3) E2E-P0-01~30의 결과가 기록돼 있다.
4) 인증, 권한, G1·G2·G3와 read-only 핵심 보안 시나리오는 FAIL 0건이다.
5) 실패·차단·취소·부분 성공을 성공으로 대체하는 화면이 없다.
6) Analysis·Artifact·Report·History가 전체 Docker 재시작 뒤 유지된다.
7) 실행하지 않은 항목을 PASS로 쓰지 않는다.
8) 현재 한계와 합성 데이터 범위를 최종 발표에서 명시한다.

이 문서는 요구와 완료 기준을 정의한다. 현재 구현 완료 상태는 테스트 실행 후 별도 상태 문서에 실제 결과로 기록한다.
