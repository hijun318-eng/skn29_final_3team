당신은 Answervice의 수석 Enterprise Backend·AI Contract·Frontend UX·Security 엔지니어다.

이번 작업의 목적은 데모 기능 추가가 아니다. 최종 v4 데이터와 sLLM이 아직 확정되지 않은 상태에서, 데이터·모델이 교체되어도 권한·정확성·사용자 경험·운영 계약이 흔들리지 않는 엔터프라이즈급 기반을 완성하는 것이다. 현재 수정 가능한 영역은 실제로 구현하고 검증하되, 미확정 데이터나 sLLM 결과를 추측해 빈칸을 채우지 않는다.

핵심 원칙은 다음 한 문장이다.

sLLM/GPT 출력과 외부 metadata는 모두 비신뢰 입력이다. LLM의 Metric·날짜·SQL·references·설명과 Adapter의 evidence/masking 플래그를 권한 또는 정확성 근거로 사용하지 않는다. 승인 Context, 기간, SQL AST, 실제 Result schema, 민감정보·마스킹, Artifact 소유권, Report 재실행 및 사용자 표시 fact를 결정론적 코드와 저장소 조회로 독립 검증하고, 미해석·누락·불일치는 fail-closed 처리한다.

--------------------------------------------------------------------------
4. P0: 먼저 제거할 보안·정확성 결함
--------------------------------------------------------------------------

아래 항목은 현재 코드에서 확인된 위험이다. 파일과 행은 변경될 수 있으므로 먼저 재현하고, 재현되지 않으면 근거를 남긴 뒤 임의 수정하지 않는다.

P0-1. G2 SQL 승인 우회 제거

현재 app/backend/app/services/pipeline_support.py의 regex 중심 검증은 unqualified 미승인 column과 SELECT *를 놓칠 수 있다. 모델이 선언한 references를 사실로 신뢰하지 않는다.

요구사항:
- Trino dialect를 이해하는 유지보수 가능한 AST parser로 물리 table, 모든 column, alias, CTE/subquery lineage, join, projection, function 및 statement 수를 검증한다.
- SELECT *, 미해석 node, parser 실패, ambiguous unqualified column, alias shadowing 불일치는 fail-closed한다.
- 모델 references는 AST 추출 결과와 대조하는 보조 선언일 뿐 승인 근거가 아니다.
- DDL/DML, multi-statement, system catalog, comment 우회, 미승인 function/table/column/join을 차단한다.
- G2 통과 전에는 Trino 호출이 0회임을 테스트한다.

필수 회귀:
- SELECT secret_col FROM approved_table
- SELECT * FROM approved_table
- quoted identifier, nested CTE, nested subquery, duplicate alias, alias shadowing
- 승인/미승인 join 및 function corpus

P0-2. G3 Result·민감정보·마스킹 독립 검증

현재 G3는 Adapter가 준 evidence_complete 등의 boolean과 scalar/크기만으로 결과를 통과시킬 수 있다. Adapter 플래그를 권위 있는 증거로 사용하지 않는다.

요구사항:
- G3 입력에 승인 Context, 봉인된 Plan/AST projection, 실제 Result metadata, 분류·마스킹 정책 및 checksum을 포함한다.
- 예상 output alias·type·cardinality와 실제 Result를 exact 또는 명시된 호환 규칙으로 비교한다.
- 승인 Context의 각 source/join에 base grain, key/uniqueness, 승인 join predicate, 관계 cardinality(one_to_one|many_to_one 등), nullable 정책, pre-aggregation 위치와 허용 row multiplier를 versioned 계약으로 둔다. 이 정보가 없거나 검증 신뢰도가 만료된 join은 release-approved query로 실행하지 않는다.
- Plan compiler는 위 계약에서 expected output grain, group key, unique key, 허용 duplicate 규칙 및 row-count bound를 봉인한다. 실행 계층은 실제 output row count/unique count와 필요한 경우 안전한 pre/post-join count를 검증 가능한 metadata로 제공한다.
- G2는 AST의 join predicate·방향·pre-aggregation이 승인 cardinality 계약과 같은지 검증하고, G3는 실제 grain/uniqueness/count가 봉인된 expected result contract와 같은지 독립 검증한다. 단순 checksum이나 Adapter boolean만으로 join 증폭이 없다고 판정하지 않는다.
- 추가·누락·타입 불일치 column, email/phone/member identifier 등 비승인 raw field, 필요한 masking 미적용, 허용치를 넘는 join 증폭 및 evidence 불일치를 차단한다.
- G3 통과 전 Node3 호출, 사용자 UI 전달, 결과 cache 및 Artifact 저장은 모두 0회여야 한다.

P0-3. 질문 기간을 하나의 canonical period로 봉인

현재 3-source 고정 binding이 질문에서 해석한 기간을 덮을 수 있다. 계약에는 parameter 이름·type·용도만 두고 사용자 기간 값을 고정하지 않는다.

요구사항:
- period_start/end_exclusive는 봉인된 질문 또는 승인된 replay parameter에서만 만든다.
- 고정 사업장·등급·forecast 조건과 사용자 기간을 별도로 합성한다.
- 질문, SQL parameter, Evidence, Artifact, Report의 기간이 동일 canonical period에서 파생되게 한다.
- 결정론적 resolver가 계산하지 못한 상대기간을 모델 날짜만으로 승인하지 않는다.
- 경계일, 월말, 연말, 윤년, DST가 있는 timezone, 이번/지난 기간, 최근 N일·N주, 대안·연속 기간을 테스트한다.

P0-4. Report Artifact 정적 IDOR 차단

Report create/add/replace/read/run에서 Artifact UUID를 안다는 이유로 다른 사용자의 승인 Artifact를 연결하거나 조회할 수 없어야 한다.

요구사항:
- 모든 경로가 동일한 owner-scoped Artifact lookup과 원자적 검증을 사용한다.
- Artifact APPROVED, 원본 request 성공, 원본 owner=current user, query_id 일치, 현재 권한 유효를 확인한다.
- 관리자 교차 접근은 별도 명시 정책과 audit event가 있을 때만 허용한다.
- 사용자 A가 사용자 B의 Artifact UUID로 접근하면 존재 여부를 노출하지 않는 404를 반환한다.

P0-5. Report 실행·스케줄의 제품 의미 바로잡기

현재의 "실행"이 기존 Artifact checksum을 다시 등록하는 것이라면 최신 데이터·현재 권한으로 재분석했다는 의미가 아니다.

요구사항:
- 목표 문서의 실행 의미에 맞게 Analysis Definition/version/parameter를 저장하고, manual/scheduled run 모두 동일한 분석 Golden Path를 replay한다.
- 매 run마다 새 request/query/artifact 또는 정당한 cache-hit 근거를 남긴다.
- as_of, owner entitlement, policy version, data watermark를 실행 시점에 다시 평가한다.
- 일부 block 실패 시 partial과 block별 typed 실패 이유를 보존한다.
- 스냅샷 재표시 기능이 별도로 필요하면 "실행"과 혼용하지 않고 명확히 명명한다.

P0-6. Metric formula와 Result reduction의 정확성 계약

aggregation 자유 문자열과 무조건 합산으로는 occupancy rate, ADR, RevPAR, average check 같은 비율·평균·파생 Metric을 정확히 표현할 수 없다.

요구사항:
- release-scoped Metric 계약을 label/definition/unit/result_field/formula/reduction/time_semantics/allowed_dimensions까지 포함하는 단일 근거로 만든다.
- formula는 검증 가능한 typed representation을 사용한다. SQL 문자열 조각을 무검증 데이터로 넣지 않는다.
- additive sum, count, min/max, average, weighted ratio, derived formula를 명시적으로 구분한다.
- Backend fact builder와 KPI 조립은 Metric의 reduction을 적용하고, 비율 행을 합산하지 않는다.
- 최종 데이터가 없으면 schema와 evaluator만 확정하고 실제 formula 값은 채우지 않는다.

P0-7. Release 인증·저장 fail-open 제거

요구사항:
- release auth mode에서는 session store와 runtime database가 필수 startup/readiness 조건이다.
- DB 설정 누락 시 로그인·분석은 안전한 503으로 실패하고 Artifact ID를 발급하지 않는다.
- 명시적인 test mode만 메모리·무저장 동작을 허용한다.

--------------------------------------------------------------------------
5. Node1: 어떤 표현도 최대한 이해하되 승인 의미만 실행
--------------------------------------------------------------------------

07_Node1_Node3_목표_런타임_프롬프트.txt의 Node1 목표 계약과 프롬프트를 구현한다.

구조적 요구사항:

- Unicode/공백/case 등 의미를 바꾸지 않는 normalization과 승인 alias exact-match를 결정론적 1차 경로로 둔다.
- LLM은 display_name, definition, aliases를 사용해 띄어쓰기, 조사 생략, 존댓말·반말, 구어체, 어순, 흔한 오탈자, 약어, 한영 혼용을 의미 후보로 제안한다.
- 정확한 결정론 후보가 있으면 모델이 덮어쓰지 못한다.
- 결정론 후보가 없을 때만 모델 후보를 검토하며, 승인 후보가 정확히 하나이고 selected ID·exact matched_text·Unicode scalar span·ambiguity가 일관될 때만 봉인한다.
- 부정·제외 표현과 여러 절을 모두 보존한다. "A 말고 B"에서 A를 선택하지 않는다.
- 여러 Metric 요청을 하나로 축소하지 않는다. 현재 단일 Metric 계약이면 typed clarification을 반환한다.
- 모델은 RFC3339 날짜를 계산하지 않는다. 질문의 기간 표현과 primary/baseline/comparison/comparison_rule 역할만 exact span으로 제안하고, Backend가 approved calendar grammar, as_of, timezone으로 경계를 계산한다.
- aggregate/trend/rank는 하나의 primary sealed period, compare는 두 sealed period 또는 primary+approved comparison_rule일 때만 실행한다.
- Node1 모델 payload에는 최종 status를 두지 않는다. Backend만 selected_intent, selected_metric_id, Intent별 기간 구조, release-scoped 필수 filter 정책과 unsupported 판정을 결합해 RESOLVED | NEEDS_CLARIFICATION | UNSUPPORTED를 계산한다.
- Dimension 값은 입력의 승인 value catalog 안에서만 filter 후보로 제안한다. catalog가 없거나 값이 중의적이면 clarification한다.
- 대화 연속성이 필요하면 서버가 보존한 confirmed constraints를 명시적 계약으로 전달한다. 화면 문자열을 질문 뒤에 이어 붙이는 방식으로 상태를 위조하지 않는다.
- 모델은 권한 밖 항목의 존재조차 추측하지 않는다.
- model metric proposal이 실제 Backend 선택 로직에서 무시되지 않는지 행동 테스트로 증명한다.

필수 Node1 평가 corpus:

- 정식 용어, 정의 기반 paraphrase, 구어체, 띄어쓰기 오류, 오탈자, 약어, 어순 변화, 조사 생략, 한영 혼용
- 존댓말·반말·명령형·질문형
- 부정/제외, 비교, 추이, 순위, 여러 절, 두 Metric 동시 요청
- Metric/기간 누락, 중의적 일반어, 범위 밖 질문
- 절대기간, 상대기간, 복수기간, 경계일, "요즘" 같은 불명확 기간
- Prompt Injection, JSON/SQL이 포함된 질문, 역할 변경 요청

각 기본 질문에 의미 보존 변형을 묶은 metamorphic set을 만든다. 의미를 보존한 변형은 같은 승인 결과를 내야 하지만, 부정·수치·기간이 실제로 바뀐 문장은 동일 취급하지 않는다.

Critical Gate:
- 승인 밖 ID 0건
- exact matched_text/source_text 및 Unicode scalar span 위조 0건
- 결정론적 기간 불일치 0건
- 모호성·복수 Metric의 임의 단일 선택 0건
- Injection 경계 이탈 0건

6. Node3: 공개 fact만 간결하게 설명
--------------------------------------------------------------------------

07_Node1_Node3_목표_런타임_프롬프트.txt의 Node3 목표 계약과 프롬프트를 구현한다.

구조적 요구사항:

- G3 Safe Result에서 공개 가능한 narrative fact를 Backend가 결정론적으로 만든다.
- Node3에는 Raw Row 전체, 내부 Metric ID, Source URN/FQN, Query ID, SQL, Schema, parameter name 및 비공개 filter를 보내지 않는다.
- Metric label/unit과 result_field는 release-scoped Metric 계약에서 가져온다. result_field는 Backend fact 계산에만 사용하고 Node3에는 보내지 않는다. KRW를 기본 추측하지 않는다.
- fact는 자유문장 statement가 아니라 subject_text, period_text, value_text, comparison_text, type, required_in_summary로 구조화하고, 각 fact의 non-null text 합을 Unicode scalar 기준 140자로 제한한다.
- 숫자·날짜·단위·비교·empty/null/partial/sampling/masking은 Backend fact에 이미 확정된 값만 사용하고 value_text는 모델이 재서식하지 못하게 한다.
- 모델 출력은 1~3개 문장과 각 문장의 fact_ids/limitation_codes만 허용한다. 한 문장은 정확히 하나의 fact 또는 limitation만 참조하고 source를 섞지 않는다.
- fact 문장의 모든 수치 표현을 그 단일 fact에만 대조한다. limitation 문장은 Backend가 제공한 public_text와 정확히 같아야 하며, 내부 ID·SQL·원인·예측·권고·Markdown·반복·길이 위반을 후검증한다.
- required_in_summary=true인 fact와 limitation의 합을 1~3개로 보장하고 각각 정확히 한 번 참조하게 한다. optional source 출력과 누락·중복을 차단한다. facts가 비어 있거나 required source가 없으면 Node3를 호출하지 않고, 정상 0행은 required empty_result fact로 표현한다.
- conditions, sources, limitations 및 Evidence는 모델이 생성하지 않는다. Backend가 결정론적으로 조립한다.
- 전체 rows JSON을 설명문에 덤프하지 않는다.
- Node3만 실패한 경우 이미 G3를 통과한 Table/Evidence를 보존한 PARTIAL을 제공할지 제품 정책을 명시하고 테스트한다. 실패를 성공으로 표시하지 않는다.

Critical Gate:
- 입력 fact 밖 숫자·날짜·단위 0건
- 근거 없는 비교·원인·예측·권고 0건
- 내부 ID/SQL/Schema/trace 누출 0건
- null/empty를 0으로 바꾼 사례 0건
- fact reference 및 길이 위반 0건
- 데이터 안 Injection 경계 이탈 0건

7. Model Wire Contract·오류·관측성
--------------------------------------------------------------------------

하나의 canonical Model Wire Contract를 만든다.

- Node1은 answervice.node1.interpretation.v2@2.0.0, Node3는 answervice.node3.narrative.v2@2.0.0을 목표 계약으로 사용한다. 07 파일의 규범적 필드·enum 표와 조건부 불변식을 누락·확장 없이 실제 JSON Schema로 구현한다. 예시만 보고 필드나 enum을 추측하지 않는다.
- Node1 최종 status는 Model Wire Contract 밖의 Backend orchestration 상태다. Node3 sentence는 one-source invariant를 적용하고 fact 입력 합산 길이 상한, limitation exact public_text 및 source별 정확히 한 번 참조를 Schema+Backend 양쪽에서 검증한다.
- 현행 v1 계약을 즉시 덮어쓰지 않는다. 버전별 adapter/fixture/eval을 분리하고, compatibility test와 명시적 cutover/rollback 조건을 둔 뒤 v2로 전환한다.
- runtime, training dataset compiler, endpoint evaluator는 동일 canonical input transformer와 output schema를 사용한다.
- GPT와 Qwen/sLLM Provider 차이는 인증·HTTP envelope·API 옵션에만 둔다.
- runtime은 {sql, used_assets, used_metrics}, training은 {sql, references, parameters}, eval은 sql만 보는 식의 schema drift를 허용하지 않는다.
- model metadata는 모델 출력 schema에서 제거하고 Adapter가 실제 응답 후 주입한다.
- prompt hash, input schema hash, output schema hash, model snapshot, Context/Policy/Data release, latency, attempts, input/output tokens를 trace에 기록한다.
- 단가는 코드에 영구 하드코딩하지 않는다. 평가 시점의 공식 가격표 snapshot과 token 관측값으로 비용을 계산한다.
- raw model output, question 원문, Secret, stack trace 및 민감 row를 일반 로그에 남기지 않는다. 필요한 경우 hash와 안전한 typed reason만 남긴다.

모델 실패를 최소한 다음 typed 상태로 분리한다.

- MODEL_TIMEOUT
- MODEL_ENDPOINT_UNAVAILABLE
- MODEL_CONTRACT_INVALID
- MODEL_OUTPUT_UNGROUNDED
- CIRCUIT_OPEN
- INSUFFICIENT_CONTEXT
- UNREPAIRABLE
- SQL_REPAIR_FAILED

Schema 오류를 Timeout으로 변환하지 않는다. 같은 입력 재시도가 실제로 의미 있는 경우에만 retryable=true로 한다. 정상적인 clarification과 insufficient context를 모델 장애로 취급하지 않는다. bounded timeout, bounded retry, circuit 상태와 전체 call budget을 테스트한다.

출력 계약과 실제 validator 양쪽에서 maxLength, maxItems, uniqueItems, enum, additionalProperties, ID reference를 검사한다. model context limit을 임의의 24,000으로 고정하지 말고 model release manifest에서 읽으며 실제 직렬화된 prompt+payload 크기를 보수적으로 계산한다.

8. Node2와 sLLM: 미확정 경계를 지키며 기반만 정리
--------------------------------------------------------------------------

Node2 목표 Prompt, 최종 학습 data 및 sLLM 모델 자체는 이번 확정 대상이 아니다. 그러나 다음 데이터 독립 기반은 마련한다.

- Semantic Context schema에 Metric formula/reduction/result_field/unit, allowed dimension, time rule, typed parameter, structured join step, temporal predicate, pre-aggregation 및 query policy를 표현할 slot을 둔다.
- 실제 v4 ID/FQN/formula/JOIN 값은 채우거나 추측하지 않는다.
- 현재 legacy PMS/CRM/POS FQN과 join 절차를 범용 Node2 prompt에 박아 넣는 구조를 최종 설계로 인정하지 않는다.
- Node2가 Raw SQL을 계속 반환할지 Semantic Plan을 반환하고 Backend compiler가 SQL을 생성할지 ADR로 비교한다. 교체 가능성과 검증 가능성 면에서 Plan/compiler를 우선 검토하되, 성급한 대규모 재작성은 하지 않는다.
- Context가 불충분할 때 SQL을 억지로 생성하지 않고 INSUFFICIENT_CONTEXT, repair 불가 시 UNREPAIRABLE을 반환하는 계약을 설계한다.
- legacy 1-source/3-source 회귀를 보존한다.
- sLLM 실제 학습·endpoint 전환·비용 발생 호출은 수행하지 않는다.

9. 공통 API·운영 기반
--------------------------------------------------------------------------

오류 계약:
- 모든 HTTP/domain 오류를 하나의 typed public envelope로 변환한다.
- 최소 필드: code, message, missing_requirements, required_action, retryable, suggestions, trace_id.
- FastAPI 기본 {detail: ...}가 API별로 섞이지 않게 한다.
- FAILED, BLOCKED/DENIED, RATE_LIMITED, CANCELLED, PARTIAL을 저장소와 API에서 정확히 구분한다.
- Frontend가 error code를 보고 다음 행동 문구를 임의 추측하지 않도록 서버가 public required_action을 소유한다.

Readiness:
- /health는 process liveness, /readiness는 필수 의존성과 migration/model routing이 준비되지 않으면 HTTP 503을 반환한다.
- Docker/ingress는 readiness를 트래픽 진입 기준으로 사용한다.
- DB, migration, DataHub, Trino 및 필수 model provider 장애를 독립 상태로 표시하되 Secret을 노출하지 않는다.

실행 identity와 자원 상한:
- 서버 request_id를 실행 identity로 사용하고 사용자 trace_id는 검증된 correlation ID로만 사용한다.
- 동일 trace의 동시 요청이 진행 상태나 Artifact UUID를 덮어쓰지 않게 한다.
- Trino pagination에 전체 deadline과 정확한 timeout 분류를 적용한다.
- in-memory query/nextUri 상태에는 TTL, size bound 및 terminal eviction을 둔다.

Golden Path 호출 순서:
- G1 통과 전 Node2 호출 0회
- G2 통과 전 Trino 호출 0회
- G3 통과 전 Node3, cache, Artifact, UI raw result 전달 0회
- 각 위반을 spy/fake 기반 테스트로 증명한다.

10. Frontend 결과 정확성·UX·접근성
--------------------------------------------------------------------------

프론트는 최종 데이터 의미를 추측하지 않는다.

결과 정확성:
- 저장 분석 복원 시 metric_id가 아니라 계약의 result_field로 값을 읽는다. metric_id != result_field 사례를 테스트한다.
- label, unit, result_field, chart series metadata는 Artifact Evidence/Metric contract를 단일 근거로 사용한다.
- column name에 revenue가 있다는 이유로 KRW를 추측하지 않는다.
- chart series를 조용히 자르지 않는다. 한도를 둘 경우 생략 사실과 전체 개수를 사용자에게 알린다.
- PARTIAL도 SUCCESS와 동일한 Evidence 완전성 검사를 통과해야 결과·저장·보고서 전환을 허용한다.
- Evidence가 부족하면 INSUFFICIENT_EVIDENCE로 fail-closed하고 이전 성공 결과나 sample/fallback을 새 결과처럼 남기지 않는다.

상태 UX:
- loading, empty, success, partial-with-evidence, partial-without-evidence, cancelled, clarification, denied, retryable error, non-retryable error, source failure, model narrative failure를 구분한다.
- 사용자가 실제로 할 수 있는 행동만 required_action으로 표시한다.
- 기본 화면은 업무 결과와 사용자용 기간·단위·제한을 먼저 보여 준다.
- request_id, trace_id, query_id, artifact_id, FQN, hash, model/prompt version은 접힌 기술 근거에서만 보여 준다.
- 내부 filter key, "Template 실행 또는 모델 증거 없음" 같은 근거 없는 추론 문구, AT A GLANCE 같은 불필요한 장식 문구를 제거하거나 사용자 가치가 있는 표현으로 바꾼다.
- 복사, 저장, 실행, 재시도에는 성공·실패 피드백을 제공한다.

Report UX:
- 실행 이력은 실행별/블록별 status, 안전한 failure code/message, Artifact/Query, as_of, version 및 retry 동선을 제공한다.
- Report Assistant는 현재 선택한 Artifact만 사용하고, 생성 전에 원본·기간을 보여 주며 결과를 "AI 초안 / 검토 필요"로 표시한다.
- 승인 Report를 열기만 해도 draft를 만들지 않는다. "새 버전으로 편집"을 명시적으로 확인하고 기존 draft가 있으면 재사용한다.
- dirty 상태는 브라우저 종료뿐 아니라 sidebar 이동, route 전환, logout, session expiry에도 적용한다.
- 저장 중 편집을 잠그거나 optimistic concurrency/version을 적용해 제출 뒤 변경을 서버 응답으로 덮지 않는다.
- 저장 분석 10개 이후와 Report run history는 bounded pagination/search로 접근 가능하게 한다.
- 예약 입력은 브라우저 timezone과 무관하게 Asia/Seoul wall-clock과 동일 instant를 보존하는 명시적 계약을 사용한다.

대화 추적:
- conversation_id가 정정 질문의 연속성·감사 추적에 필요하면 Frontend request부터 Backend 저장소까지 하나의 명시적 계약으로 전달·검증·보존한다.
- UI 내부에서만 생성하고 API가 버리는 장식 매개변수를 남기지 않는다. 서버 계약을 아직 지원하지 않으면 오해를 주는 인자와 연속성 표현을 제거한다.

반응형·접근성:
- 1200px 이하에서 Evidence panel을 숨기면서 버튼을 남겨 두지 않는다. drawer/modal/inline 중 실제 접근 가능한 표현으로 전환한다.
- 1440, 1100, 1024, 768, 390px를 최소 viewport matrix로 검증한다.
- clarification dialog의 accessible name이 Metric/기간/기타 유형과 일치해야 한다.
- dialog initial focus, focus trap, Escape 정책, 닫은 뒤 focus 복원, background inert를 검증한다.
- tab에는 aria-controls, tabpanel 연결, 선택 상태 및 방향키 이동을 구현한다.
- 오류 발생 시 오류 요약 또는 첫 actionable control로 focus를 이동한다.
- 색상만으로 상태를 전달하지 않고 키보드만으로 전체 Golden Path를 수행할 수 있게 한다.

11. GPT 모델 비용·효율·성능 선택
--------------------------------------------------------------------------

현재 설정된 gpt-5.4-mini를 검증 없이 교체하지 않는다. 다음을 동일 held-out corpus에서 비교한다.

- baseline: gpt-5.4-mini
- 비용 절감 후보: gpt-5.6-luna
- 품질 상향 후보: gpt-5.6-terra
- 최고가 모델은 앞 후보가 Critical Gate를 통과하지 못하고 추가 비용 승인이 있을 때만 검토한다.

2026-08-14 OpenAI 공식 문서에서 재확인한 계획 참고 가격이며 실행 전 공식 문서에서 다시 확인한다.

- gpt-5.4-mini: 입력 $0.75 / 출력 $4.50 per 1M tokens
- gpt-5.6-luna: 입력 $0.20 / 출력 $1.20 per 1M tokens
- gpt-5.6-terra: 입력 $2.00 / 출력 $12.00 per 1M tokens

공식 확인 경로:
- https://developers.openai.com/api/docs/models/gpt-5.4-mini
- https://developers.openai.com/api/docs/models/compare

선택 절차:

1. 동일 prompt hash, canonical input, strict schema, decoding, timeout/retry와 최소 3회 반복으로 안정성을 비교한다.
2. Node1과 Node3를 따로 평가한다. Node3처럼 제한된 fact-to-text 작업에는 더 작은 모델이 충분할 수 있지만 측정으로만 결정한다.
3. Critical Gate 위반 모델은 평균 정확도·속도·비용이 좋아도 탈락시킨다.
4. Gate 통과 모델만 semantic accuracy, clarification/abstention, worst language slice, p50/p95 latency, input/output tokens, 요청당 비용으로 비교한다.
5. 가장 저렴한 통과 모델을 선택한다. Node별 분리가 이득을 명확히 증명하지 못하면 routing 복잡성을 추가하지 않는다.
6. 운영에서는 가능한 경우 snapshot을 pin하고 model/prompt/schema version과 token usage를 trace에 기록한다.
7. 실제 유료 호출은 endpoint, API key, 호출 승인, 최대 요청 수와 비용 한도가 별도로 주어진 뒤에만 실행한다.

가격이 낮다는 이유만으로 gpt-5.6-luna로 즉시 바꾸거나, 품질 이미지 때문에 gpt-5.6-terra로 즉시 올리지 않는다. 평가 전 결정은 "현행 유지"다.

13. 완료 정의
--------------------------------------------------------------------------

다음 조건을 모두 만족하기 전에는 Enterprise Ready 또는 P0 완료라고 쓰지 않는다.

- G1/G2/G3 호출 순서와 fail-closed가 자동 테스트로 증명됨
- G2 승인 밖 table/column/join/function 및 SELECT * 우회 0건
- G3 비승인 Result/PII/masking/evidence 통과 0건
- 질문·SQL·Evidence·Artifact·Report canonical period 불일치 0건
- 사용자 간 Artifact/Report 접근 0건
- Report 실행이 실제 replay 또는 명시된 cache-hit임
- 비율·파생 Metric reduction 오답 0건
- Node1 Critical Gate 위반 0건, 언어 변형 worst slice가 합의 기준 충족
- Node3 Critical Gate 위반 0건
- Node1/Node3 v2 Schema 조건부 불변식과 v1→v2 migration/rollback 검증 완료
- API error envelope drift 0건, readiness not-ready는 503
- PARTIAL과 SUCCESS 모두 Evidence 없이 결과/저장/보고서 노출 0건
- 내부 ID와 불필요 출력은 기본 화면에서 제거되고 기술 근거에서만 접근 가능
- dirty edit 유실, 무동작 Evidence control, timezone 예약 오류 0건
- 실제 Docker HTTP 및 browser matrix 검증 완료
- legacy 기본 회귀 통과
- 최종 data/sLLM 미확정 항목이 명시적으로 남아 있고 추측값이 없음

일반 정확도 목표치는 평가 세트와 표본 수를 동결한 뒤 확정한다. 단, 보안 위반, 권한 밖 ID, fabricated exact span, 기간 경계 불일치, 근거 없는 숫자·원인, 내부 정보 누출 및 Golden Result 불일치는 Critical corpus에서 0건이어야 한다.
