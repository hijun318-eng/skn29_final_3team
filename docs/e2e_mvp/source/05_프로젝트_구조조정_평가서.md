# Answervice 프로젝트 구조조정 평가서

> **HISTORICAL / 실행 기준 아님** — 아래 내용은 2026-08-11 저장소를 평가한 원문 기록이다. 현재 인증·데이터 플랫폼·보고서 구현의 기준은 루트 `AGENTS.md`와 `docs/product/` 문서이며, 아래에 기록된 과거 환경 변수나 demo 경로를 복원하지 않는다.

- 평가 기준일: 2026-08-11
- 평가 관점: 기존 프로젝트 참여자가 아닌 외부 평가자
- 평가 근거: 현재 저장소의 실행 코드, 구성 파일, 테스트, 런타임 연결 상태
- 평가 제외: 기존 메모리, WBS, 역할별 보고서, 진행률 주장, 문서에 기록된 완료 선언

---

## 1. 최종 평가

현재 저장소는 **구현 코드가 없는 문서 프로젝트는 아니다.** FastAPI 백엔드, React 프런트엔드, PostgreSQL 저장소, Trino/DataHub 어댑터, Report 도메인 및 AI 관련 코드가 실제로 존재한다.

그러나 현재 상태를 **사용 가능한 E2E 서비스**라고 평가할 수는 없다. 각 구성요소가 개별적으로 존재하고 계약 테스트도 많지만, 기본 실행 설정에서 다음 흐름이 끝까지 연결되지 않는다.

```text
사용자 질문
→ 실제 인증
→ 분석 API
→ 실제 데이터 조회
→ 실제 모델 또는 승인된 분석 실행
→ 근거가 포함된 응답
→ 실행 이력 저장
→ 실제 응답 기반 Report 초안 생성
→ Report 실행 및 결과 확인
```

현재 프로젝트의 정확한 단계는 다음과 같다.

> **구성요소별 구현은 상당히 진행됐지만 제품 흐름은 끊겨 있는 통합 전 프로토타입**

앞으로의 최우선 과제는 기능 추가, 문서 보강, 테스트 확대가 아니다. **기존 구현을 줄이고 하나의 실제 사용자 흐름을 끝까지 연결하는 것**이다.

## 2. 현재 상태에서 확인된 핵심 문제

### 2.1 역할 분업 구조가 통합을 방해한다

현재 CI와 저장소 운영 방식은 업무를 사용자 가치가 아니라 역할과 기술 영역별로 분리한다. 그 결과 각 영역은 자신의 계약과 테스트를 통과시킬 수 있지만, 전체 사용자 흐름의 완성 책임자는 없다.

확인된 구조적 문제는 다음과 같다.

- 역할별 branch에 따라 서로 다른 테스트만 실행한다.
- 역할별 허용 경로와 handoff 절차가 변경 비용을 높인다.
- 최종 제품 승인과 예외 판단이 특정 인원에 집중되어 있다.
- 연결 문제를 발견한 담당자가 직접 수정하기보다 다른 영역으로 반환하게 된다.
- 기능 완료보다 계약 문서, 상태 기록, 검증 증거 생성이 독립적인 업무가 됐다.

따라서 과거 역할별 분업 명칭만 제거해서는 부족하다. 역할별 Gate, branch별 테스트 분리, handoff 중심 운영까지 함께 폐기하거나 재작성해야 한다.

### 2.2 기본 실행 구성이 실제로 연결되지 않는다

저장소 기준 기본 구성에는 다음과 같은 충돌이 있다.

- 프런트엔드는 `Bearer synthetic-local`을 고정 전송한다.
- 백엔드는 기본적으로 `AUTH_MODE=release`이며 별도의 principal 파일을 요구한다.
- 기본 Compose에는 principal 파일을 컨테이너에 제공하는 구성이 없다.
- 백엔드는 `DATA_PLATFORM_MODE=real`이 기본이다.
- `dev` profile은 프런트엔드, 백엔드, App PostgreSQL만 실행하며 Trino와 DataHub를 포함하지 않는다.
- 모델 기본값은 `template-only`이므로 일반 질문을 실제 모델로 처리하지 않는다.

즉, 코드가 각각 존재하더라도 저장소의 기본 설정만으로는 정상적인 질문 요청이 성공하기 어렵다.

### 2.3 화면에 실제 기능과 데모 기능이 혼재한다

현재 프런트엔드에는 실제 API 호출, fixture, 브라우저 저장소, 하드코딩 데이터가 한 제품 화면 안에 섞여 있다.

- Analysis 화면은 HTTP API를 호출하지만 고정 인증 정보를 사용한다.
- Catalog와 Connections 화면은 실제 서버가 아니라 `catalogFixtures`를 사용한다.
- Report 화면은 실제 Report API와 fixture 화면을 동시에 보유한다.
- Report 편집 데이터 상당 부분이 `localStorage`와 `sessionStorage`에 저장된다.
- 분석 결과를 Report로 넘길 때 일부 KPI와 출처가 실제 응답이 아니라 코드에 고정되어 있다.

이 구조는 시연 화면을 만드는 데는 유리하지만, 무엇이 실제 구현인지 판단하기 어렵게 한다. 제품 경로와 데모 경로를 반드시 분리해야 한다.

### 2.4 Report는 접수까지만 있고 실행자가 없다

Report API는 정의 생성, 승인, 실행 명령 접수와 저장 구조를 갖고 있다. 그러나 수동 실행 명령을 처리하는 worker가 없다.

현재 상태는 다음과 같다.

```text
Report 실행 요청 → queued 저장 → 종료
```

`queued` 이후 실제 분석 실행, 블록 생성, 상태 갱신, 결과 저장을 수행하는 경로가 없으므로 Report 실행 기능은 완성되지 않았다.

### 2.5 실제 AI 제품 경로가 준비되지 않았다

AI 관련 코드, prompt registry, fake model, serving client, 학습 및 평가 도구는 존재한다. 그러나 제품 기본값은 `template-only`이고 model release candidate도 `DRAFT / NOT_READY` 상태다.

따라서 현재 제품을 “AI 분석 서비스”라고 표현하려면 다음 중 하나를 명확히 선택해야 한다.

1. 첫 출시 범위를 승인 SQL Template 기반 분석 서비스로 제한한다.
2. 실제 모델 endpoint를 연결하고 일반 질문 경로를 제품 범위에 포함한다.

두 방식을 동시에 완료한 것처럼 운영해서는 안 된다.

### 2.6 테스트가 제품 완성을 대신하고 있다

테스트 자체가 많은 것은 문제가 아니다. 문제는 테스트가 검증하는 대상과 사용자가 사용하는 경로가 다르다는 것이다.

현재 CI는 주로 다음을 검증한다.

- Python 단위·계약 테스트
- 프런트엔드 계약 테스트와 build
- Compose 문법과 구성 생성
- 역할 범위 및 문서 규칙

하지만 실제 컨테이너를 실행하여 한 건의 질문을 처리하고 Report까지 연결하는 검증은 없다. 따라서 CI가 모두 통과해도 제품이 동작한다고 결론 내릴 수 없다.

## 3. 구조조정 원칙

모든 파일과 기능은 다음 질문을 통과해야 한다.

1. 첫 번째 Golden Path 실행에 직접 필요한가?
2. 런타임에서 실제로 참조되는가?
3. 실제 사용자 결과를 만들거나 보호하는가?
4. 동일 목적의 다른 구현과 중복되지 않는가?
5. fixture나 완료 주장 없이 동작을 증명할 수 있는가?

판단 결과는 다음 네 가지로 구분한다.

| 구분 | 의미 |
|---|---|
| 유지 | Golden Path에 직접 필요하며 현재 구조를 활용할 가치가 있음 |
| 수정 후 유지 | 기반은 유효하지만 현재 상태로는 제품 경로에서 사용할 수 없음 |
| 격리 | 향후 가치가 있을 수 있으나 현재 제품 범위에서 제외해야 함 |
| 삭제 후보 | 중복·역할 운영·증거 보관 목적이며 런타임 가치가 낮음 |

## 4. 유지할 자산

### 4.1 백엔드 핵심 골격

다음 구현은 제품 기반으로 유지한다.

- `app/backend/app/main.py`
- `app/backend/app/api/router.py`
- `app/backend/app/controllers/analysis_controller.py`
- `app/backend/app/services/analysis_service.py`
- `app/backend/app/services/state_machine.py`
- `app/backend/app/services/execution_control.py`
- `app/backend/app/services/context_builder.py`
- `app/backend/app/services/pipeline_support.py`
- `app/backend/app/contracts.py`
- `app/backend/app/analysis_contracts.py`

유지 이유:

- 분석 요청의 기본 흐름과 상태 전이가 구현되어 있다.
- G1·G2·G3 검증 구조는 제품의 차별 요소가 될 수 있다.
- API 응답, evidence, artifact, trace 구조를 다시 만드는 비용이 크다.

단, 역할명과 Wave/Gate 흔적이 코드 주석이나 오류 메시지에 남아 있다면 제품 용어로 정리해야 한다.

### 4.2 실제 데이터 접근 계층

다음 구현은 유지한다.

- `app/backend/app/adapters/i2_data_platform.py`
- `src/data/i2_adapters.py`
- `infrastructure/database/trino/`
- Golden Path에 필요한 DDL, seed, query 파일

유지 이유:

- Trino 실행과 DataHub metadata 확인 로직이 실제로 구현되어 있다.
- 파라미터 바인딩, read-only 검증, query status 처리 기반을 재사용할 수 있다.

단, 첫 Slice에 사용하지 않는 source와 engine은 실행 profile에서 제외한다.

### 4.3 애플리케이션 PostgreSQL과 영속화

다음 구현은 유지한다.

- `app/backend/migrations/`
- `app/backend/app/adapters/analysis_repository.py`
- `app/backend/app/adapters/context_registry_repository.py`
- `app/backend/app/adapters/report_repository.py`

유지 이유:

- 분석 실행 이력과 Report 정의를 서버에서 관리하기 위한 필수 기반이다.
- 브라우저 저장소 의존을 제거하려면 이 계층이 필요하다.

단, migration의 단일 head와 실제 스키마 적용 여부를 제품 E2E에서 검증해야 한다.

### 4.4 Report 도메인

다음 구현은 유지한다.

- `src/report/domain.py`
- `src/report/router.py`
- `src/report/repository.py`
- `app/backend/app/api/report_router.py`
- `app/backend/app/report_contracts.py`

유지 이유:

- Report 정의, 버전, 승인, 실행 상태의 도메인 구조가 존재한다.
- 완전히 새로 설계할 필요는 없다.

단, worker가 구현되지 않으면 사용자에게 Report 실행 기능을 노출하지 않는다.

### 4.5 프런트엔드 기본 구조

다음 구현은 유지한다.

- 공통 layout과 routing
- Analysis 입력 및 상태 표시 UI
- Analysis/Report contract 정규화 코드
- 오류·빈 상태·로딩 상태 UI

유지 이유:

- 실제 API 응답을 표시할 수 있는 구조가 이미 있다.
- 전체 화면을 다시 만드는 것보다 fixture 의존을 제거하는 편이 효율적이다.

## 6. 제품 경로에서 즉시 격리할 자산

다음 항목은 삭제보다 먼저 제품 실행 경로에서 격리한다.

### 6.1 fake·mock·fixture 런타임

- `app/backend/app/adapters/fake_data_platform.py`
- `app/backend/app/adapters/fake_model.py`
- `src/ai/fake_model.py`
- `app/enterprise-react/src/data/analysisFixtures.ts`
- `app/enterprise-react/src/data/catalogFixtures.ts`
- 프런트엔드의 mock/fixture client

조치:

- 테스트 전용 경로 또는 `demo/` 영역으로 이동한다.
- 제품 Compose에서 선택 가능한 runtime mode로 두지 않는다.
- fixture를 사용한 실행은 제품 E2E 성공으로 인정하지 않는다.

### 6.2 하드코딩된 Report 결과

다음 데이터는 제품 코드에서 제거한다.

- 고정 KPI 값
- 고정 Report 요약
- 고정 source 목록
- 고정 chart 값
- 고정 기간과 seed 표시

모든 Report block은 Analysis API가 반환한 artifact와 evidence만으로 생성해야 한다.

### 6.3 학습·LoRA·ModelOps 실험 영역

다음 영역은 당장 삭제하지 않되 제품 범위에서 제외한다.

- `src/ai/training/`
- `evals/`
- `src/modelops/`
- `notebooks/`

격리 이유:

- 실제 모델 endpoint와 release 결정이 완료되지 않았다.
- Golden Path 완성 전에 학습·평가 체계를 확대하면 다시 테스트와 증거 생산으로 작업이 이동한다.

복귀 조건:

- 실제 모델 endpoint가 제품 구성에 연결됨
- 일반 질문 경로가 제품 범위로 승인됨
- 동일 Golden Path에서 모델 호출 결과를 재현할 수 있음

### 6.4 첫 Slice에 포함되지 않는 데이터 source

첫 Golden Path에 직접 사용하지 않는 source DB와 DataHub ingestion은 기본 실행 대상에서 제외한다.

권고 첫 범위:

```text
PMS 또는 이미 승인된 serving analytics view
→ Trino
→ 객실 운영/매출 Template 1개
```

CRM, POS, Facility, Banquet는 첫 Slice 성공 후 한 source씩 추가한다. “5개 source가 정의돼 있다”는 사실은 “5개 source가 제품에서 사용 가능하다”는 증거가 아니다.

## 7. 삭제 후보

다음 항목은 Golden Path가 새 구조에서 동작한 후 참조 여부를 확인하여 삭제한다.

### 7.1 역할별 운영 산출물

- `handoffs/` 아래 역할별 JSON
- 역할별 실행 카드와 상태 ledger
- 역할별 전용 branch scope 규칙
- 역할별 허용 경로 검사
- 역할별 승인·반환 절차

삭제 이유:

- 런타임에서 사용되지 않는다.
- 통합 비용과 의사결정 지연을 만든다.
- 역할 체계 폐기 후에는 유지 목적이 없다.

보존이 필요하면 Git history로 충분하다. 저장소의 현재 제품 구조에 계속 둘 이유는 없다.

### 7.2 중복 SQL 및 migration proposal

- `src/report/migration_proposal.sql`
- `src/report/migration_proposal_v1_1.sql`
- 이미 Alembic에 반영된 별도 배포 SQL 사본
- release 폴더 안의 동일 DDL 중복본

삭제 조건:

- Alembic migration이 canonical schema임을 확인
- CI에서 migration 적용과 rollback 또는 재생성을 검증
- 런타임 코드가 proposal 파일을 읽지 않음을 확인

### 7.3 상태 증거용 manifest

JSON manifest는 다음 기준으로 정리한다.

- 런타임에서 직접 읽는 파일: 유지
- 테스트 입력으로 사용하는 파일: `tests/fixtures/`로 이동
- 과거 PASS, handoff, release 주장만 기록한 파일: 삭제 또는 저장소 외부 보관

manifest가 많다는 사실은 기능이 많다는 뜻이 아니다. 런타임 참조가 없는 manifest는 유지 비용만 증가시킨다.

### 7.4 역할 중심 문서와 중복 설명서

프로젝트 운영에 필요한 문서는 최종적으로 다음 정도만 남긴다.

1. 실행 방법
2. 시스템 구조
3. API와 데이터 계약
4. 배포·복구 방법
5. 현재 미완성 항목

역할별 매뉴얼, 과거 Wave 기록, 반복된 진행 보고서는 현재 제품 저장소에서 제거한다. 필요한 이력은 Git에서 확인한다.

## 8. 새 Golden Path

첫 번째 공식 제품 범위는 다음 한 가지로 제한한다.

### 사용자 시나리오

> 호텔 분석 담당자가 기간을 지정하여 객실 운영 또는 객실 매출을 질문하고, 실제 데이터 기반 결과와 근거를 확인한 뒤 그 결과를 Report 초안으로 저장한다.

### 필수 흐름

```text
1. 사용자가 인증한다.
2. 프런트엔드에서 질문과 기간을 입력한다.
3. FastAPI가 실제 인증 주체와 권한을 확인한다.
4. 승인된 Template을 선택한다.
5. Trino에서 실제 또는 공식 synthetic DB를 조회한다.
6. G1·G2·G3 검증을 통과한다.
7. 결과, 기간, source, query_id, artifact_id를 반환한다.
8. 분석 실행 이력을 PostgreSQL에 저장한다.
9. 프런트엔드는 API 응답만으로 결과를 표시한다.
10. 사용자가 Report 초안을 생성한다.
11. Report block이 서버에 저장된다.
12. 새로고침 후에도 동일 Report를 다시 조회할 수 있다.
```

### 완료 조건

다음 조건을 모두 만족해야 완료다.

- fixture adapter를 사용하지 않는다.
- 브라우저 저장소를 결과의 단일 원본으로 사용하지 않는다.
- KPI와 source가 프런트 코드에 하드코딩되어 있지 않다.
- 한 명의 실제 인증 주체로 동작한다.
- 새 환경에서 한 명령으로 실행할 수 있다.
- E2E 테스트가 실제 컨테이너에 HTTP 요청을 보낸다.
- 실패 시 어느 단계에서 실패했는지 확인할 수 있다.
- 시연자가 코드나 DB를 수동 수정하지 않아도 재현된다.

## 9. 새 진행 방식

### 9.1 역할 대신 Slice 공동 소유

개별 역할의 고정 소유권을 폐기한다. 모든 작업자는 같은 Golden Path의 완성을 공동으로 책임진다.

예시:

- 인증 연결
- 실제 query 실행
- 분석 결과 저장
- 프런트 표시
- Report 초안 저장
- E2E 자동화

각 항목은 프런트·백엔드·데이터 경계를 넘을 수 있다. 경로 소유권보다 기능 완료가 우선이다.

### 9.2 작업 완료 기준

다음은 완료로 인정하지 않는다.

- 문서만 작성됨
- interface만 정의됨
- fixture로만 동작함
- mock test만 통과함
- API만 있고 화면에서 사용할 수 없음
- 화면만 있고 서버에 저장되지 않음
- 명령이 queued가 됐지만 처리되지 않음
- Compose config가 생성되지만 서비스가 실행되지 않음

완료는 실제 화면 또는 실제 HTTP 요청으로 사용자 결과를 재현할 때만 인정한다.

### 9.3 작업량 통제

- 동시에 진행하는 Vertical Slice: 1개
- 신규 주요 기능: Golden Path 완료 전 금지
- 신규 문서: 실행·배포·계약 변경에 필요한 경우만 허용
- 신규 단위 테스트: 실제 결함 또는 Golden Path 보호 목적만 허용
- 일일 통합: 최소 1회
- docs-only 커밋: 별도 사유가 없으면 금지

### 9.4 CI 재구성

CI 순서는 다음과 같이 단순화한다.

```text
1. 정적 검사와 build
2. 단위·계약 테스트
3. migration 적용
4. 핵심 컨테이너 실행
5. Golden Path E2E 1건
6. 실패·권한 E2E 1건
```

역할별 테스트 선택과 최종 분리 Gate는 제거한다. 변경된 영역에 따라 테스트를 최적화할 수는 있지만, `dev` 통합 시에는 항상 전체 Golden Path를 검증한다.

## 10. 실행 순서

### 단계 1. 제품 경로 고정

- 첫 Golden Path 질문과 Template 1개를 결정한다.
- 공식 실행 profile 하나를 결정한다.
- 첫 Slice에 필요하지 않은 메뉴와 서비스를 숨긴다.
- 제품 모드와 demo 모드를 분리한다.

### 단계 2. E2E 차단 요소 제거

- 인증 토큰과 principal 구성을 통일한다.
- backend의 data mode와 Compose 서비스를 일치시킨다.
- 실제 query가 성공하도록 source와 Trino를 연결한다.
- Analysis 실행 결과가 PostgreSQL에 저장되는지 확인한다.

### 단계 3. 프런트엔드 실제화

- 고정 사용자, 역할, 날짜를 제거한다.
- Catalog/Connections fixture 메뉴를 숨기거나 demo로 이동한다.
- Report의 하드코딩 KPI와 source를 제거한다.
- Report draft를 서버에 저장하고 다시 조회한다.

### 단계 4. Report 범위 결정

다음 중 하나를 선택한다.

- worker를 구현하여 queued 이후 실제 실행까지 완성한다.
- worker 구현을 미루고 수동 실행 UI와 Run History를 제품 범위에서 제거한다.

중간 상태를 완성된 기능처럼 유지하지 않는다.

### 단계 5. 정리

- 새 Golden Path가 통과한 후 역할별 handoff와 Gate를 제거한다.
- 사용되지 않는 fixture, proposal, manifest를 삭제한다.
- 중복 문서를 정리한다.
- 최종 실행 방법과 미완성 범위만 문서화한다.

## 11. 중단해야 할 작업

Golden Path가 완성될 때까지 다음 작업은 중단한다.

- 추가 역할별 문서 작성
- 새로운 handoff 카드 발행
- 추가 source 확대
- 새로운 Report 화면 추가
- LoRA 학습 및 평가 확대
- 새로운 상태 manifest 생성
- 테스트 케이스 수를 늘리는 목적의 테스트 작성
- 실제로 연결되지 않은 API contract 추가
- UI 시연을 위한 하드코딩 데이터 추가

## 13. 평가자의 최종 권고

이 프로젝트는 전면 재작성할 필요가 없다. 사용할 수 있는 기반 코드는 충분하다. 그러나 현재 구조를 그대로 유지하면서 기능을 추가하면 문서, 계약, fixture, 테스트가 다시 늘어나고 E2E Gray 영역도 확대될 가능성이 높다.

가장 위험한 선택은 다음이다.

> 기존 구조를 보존한 채 명칭만 바꾸고, 여러 기능을 병렬로 계속 개발하는 것

가장 합리적인 선택은 다음이다.

> 현재 구현을 `core`, `demo`, `archive`로 분리하고, 하나의 Golden Path만 실제 환경에서 끝까지 완성한 뒤 나머지 기능의 생존 여부를 다시 판단하는 것

프로젝트의 다음 성과 기준은 작성한 문서 수, 테스트 수, contract 수가 아니다.

> **새 환경에서 서비스를 실행하고, 실제 인증된 사용자가 질문 한 건을 제출하여 실제 데이터 결과와 Report 초안을 끝까지 확인할 수 있는가**

이 조건을 만족하기 전까지 프로젝트 상태는 “통합 완료” 또는 “서비스 구현 완료”가 아니라 **통합 진행 중**으로 관리하는 것이 타당하다.
