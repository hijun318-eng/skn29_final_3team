## 1️⃣ 목적과 범위

**Answervice:**  자연어로 호텔 운영 데이터를 분석하고, 검증된 결과를 재현 가능한 보고서로 제공하는 서비스

**핵심 구성:**  DataHub(메타데이터) | Trino(읽기 전용 조회) | FastAPI(G1·G2·G3 통제)

### 1.1 우선순위

| 구분 | 범위 | 완료 판단 |
|---|---|---|
| P0 | 합성 데이터, 인증·권한, Context, Guarded Text-to-SQL, 결과·근거·Artifact, 보고서 정의·수동 실행·이력·감사 | I1~I4 계약과 통합 Gate에서 소비 가능한 산출물 및 검증 증거 확보 |
| P1 | 5개 논리 소스 ingestion·카탈로그·연결 상태, Context 승인·버전, 스케줄 활성화 | P0 수동 경로 안정화 후 승인된 계약과 권한 안에서 검증 |
| P2 | MCP, 문서 RAG, ML-as-a-Tool, 외부 Report 배포 | R1의 별도 편입 결정 전 구현 범위 제외 |
| 선택 | 고객 360 | identity mapping·masking·전용 권한·일정 영향 승인 전 구현 범위 제외 |

### 1.2 사용자 역할

| 역할 | 주요 권한 |
|---|---|
| 일반 사용자 | 승인 범위의 질문·결과·근거 확인, Artifact 생성, 보고서 열람 |
| 관리자 | 보고서 정의 편집·승인, 수동 실행, Gate 통과 후 스케줄 관리 |
| 데이터·시스템 관리자 | 자산·Context·연결·권한·서비스 상태와 감사 추적 관리 |
| 감사자 | 권한·정책·실행 증적의 읽기 전용 검색·내보내기 |
| 선택 범위 사용자 | 고객 360 편입 승인 후 마스킹된 고객 단위 내부 분석 |

## 3️⃣ 핵심 수용 시나리오

8가지 대표 사용 사례의 수용 기준을 정의합니다. **각 시나리오는 P0 구현의 최소 기준**입니다.

| # | 시나리오 | 관련 요구사항 | 수용 기준 |
|---|---|---|---|
| 1 | **대표 분석 질문** | REQ-F-003~010, REQ-AI-001~009 | 인증된 사용자의 질문이 Context → G1 → SQL → G2 → Trino → G3까지 **하나의 trace**로 재구성 |
| 2 | **모호한 질문** | REQ-F-004, REQ-AI-003 | 필수 조건 부족 시 SQL 미실행, **수정 가능한 확인 질문** 반환 |
| 3 | **금지된 SQL** | REQ-D-003, REQ-AI-005~006 | DDL·DML·미승인 JOIN은 차단, **1회 수정 후 종료** |
| 4 | **교차 소스 분석** | REQ-D-002, REQ-D-007~009 | I2부터 PMS+CRM 2-source, 이후 **승인된 JOIN만** 검증 |
| 5 | **Chat → Report** | REQ-F-009, REQ-RPT-001~006 | 성공 Artifact를 **미리보기·승인 후** block으로 삽입 |
| 6 | **보고서 부분 실패** | REQ-RPT-006~010, REQ-O-003 | Block별 상태 표시, **이전 증거 보존** 후 제한 재실행 |
| 7 | **감사 추적** | REQ-UI-006, REQ-S-003, REQ-O-002 | user/role → context/policy/model → query/Gate → artifact/report **전체 검색** |
| 8 | **재현 시연** | REQ-D-001~004, REQ-O-004~005, REQ-NFR-002 | 고정 seed·schema·manifest로 재구축, **checksum 비교** |
