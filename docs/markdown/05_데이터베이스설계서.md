## 3. 설계 원칙

1. DataHub Core는 메타데이터 기준 시스템이며 원천 데이터를 저장하지 않는다.
2. 실제 조회는 Trino가 5개 source catalog를 읽는 방식으로 수행한다.
3. Application PostgreSQL은 Context 승인본, 분석 실행, Artifact, Report, Audit을 저장한다.
4. source DB에는 원자 운영값만 저장한다.
5. OCC·ADR·RevPAR·TRevPAR·RevPOR·RevPASH·HPOR·CPOR는 View에서 계산한다.
6. source 내부 관계만 물리 FK로 구현한다.
7. source 간 고객 관계는 `crm_customer_map`과 승인 `JOIN_POLICY`만 사용한다.
8. 회원 등급 조건은 `crm_member_grade_history`의 event-time 유효기간으로 판정한다.
9. `crm_members.membership_grade`는 현재 표시용 snapshot이며 과거 거래 등급 판정에 사용하지 않는다.
10. 2026년 7~12월은 `FORECAST_SCENARIO`이며 실제 실적이 아니다.
11. 실제 이름·전화·이메일·주소·카드·계정·credential을 저장하지 않는다.
12. DDL 생성과 5개년 합성 데이터 생성은 별도 SQL 작업으로 분리한다.

### 4.1 병렬구현 Source binding 계약

| source_id | Engine | ingestion role | query role | DataHub platform instance | Trino catalog |
|---|---|---|---|---|---|
| `pms` | PostgreSQL | `pms_ingest` | `pms_query` | `hotel_pms` | `pms` |
| `pos` | MySQL | `pos_ingest` | `pos_query` | `hotel_pos` | `pos` |
| `crm` | SQL Server | `crm_ingest` | `crm_query` | `hotel_crm` | `crm` |
| `facility` | ClickHouse | `facility_ingest` | `facility_query` | `hotel_facility` | `facility` |
| `banquet` | PostgreSQL | `banquet_ingest` | `banquet_query` | `hotel_banquet` | `banquet` |

- 5개 source는 DB·credential·recipe·platform instance·catalog를 공유하지 않는다.
- DDL은 비밀번호 없는 역할과 grant 경계만 정의한다. 실제 login·secret 연결은 R5가 담당한다.
- ingestion role은 적재에 필요한 최소 DML, query role은 승인 schema/view의 `SELECT`만 허용한다.
- 각 source의 DataHub URN과 Trino FQN은 R3의 `asset_binding` 한 레코드에서 함께 versioning한다.
- `connection.data_sources`에는 논리 `source_id`에 해당하는 `source_code`, `platform_instance`, `trino_catalog`, versioned recipe 참조를 저장한다.

### 4.2 R2 adapter·health handoff

- DataHub adapter는 search/get asset/schema/relationship/ingestion status를 typed object로 반환한다.
- Trino adapter는 execute/status/cancel/pagination/source watermark를 제공하고 query ID·stats·warning·source별 typed error를 정규화한다.
- adapter는 권한이나 G2를 대신 판정하지 않으며 R3의 검증 증표 형식만 확인한다.
- Source health는 liveness, read-only query, watermark, 최근 성공 시각을 반환한다.
- 공통 source health enum은 `HEALTHY`, `DEGRADED`, `DOWN`, `UNKNOWN`이다. DataHub ingestion health와 Trino catalog health는 별도 field로 유지한다.
- credential·원문 query parameter·DB 원문 오류는 adapter 응답에 포함하지 않는다.

### 6.1 R2 논리 entity와 물리 테이블 mapping

새 병렬구현 매뉴얼의 entity 이름은 논리 이름이다. 다음 mapping을 사용하며 같은 의미의 중복 물리 테이블을 추가하지 않는다.

| Source | R2 논리 entity | v4.6 물리 구현 |
|---|---|---|
| PMS | `guest`, `reservation`, `stay` | `pms_guests`, `pms_reservations`, `pms_stays` |
| PMS | `room` | `pms_room_inventory_daily`의 `room_type_code`·공급 grain; 객실 unit은 `pms_stays.room_unit_code` |
| PMS | `room_revenue` 또는 revenue fact | `pms_stays.room_revenue`; Trino View에서 숙박일별 배부 |
| POS | `store`, `order`, `order_line` | `pos_stores`, `pos_orders`, `pos_order_items` |
| POS | `item` | `pos_order_items.item_code`·`item_category`; 별도 master가 필요한 변경은 R2 proposal 후 신규 version |
| POS | `payment` | `pos_orders.payment_status`·`payment_amount`; 다중 결제수단 요구 전에는 별도 fact를 만들지 않음 |
| CRM | `member`, `point_transaction` | `crm_members`, `crm_point_transactions` |
| CRM | `member_grade_history` | `crm_member_grade_history` |

### 7.2 합성 데이터 재현성 계약

```text
seed             = 20260728
schema_version   = schema-v4.6-websql
scenario_version = scenario-v4.6
property_id      = SYNTHETIC_HOTEL_001
synthetic        = true

```

- SQL 생성 시 live web 검색값으로 고정 기준값을 교체하지 않는다.
- 실행 결과는 source별 table row count, `max(source_updated_at)`, 핵심 결과 checksum을 출력한다.
- checksum은 PK 안정 정렬 후 핵심 컬럼을 정규화해 계산한다.
- 재실행 전후 row count·watermark·checksum이 모두 같아야 멱등성 PASS다.
- SQL 파일 생성만 한 경우 `DB_EXECUTION_NOT_RUN`으로 기록한다.
- 실제 실행 증거는 Application `governance.audit_events.details_json_redacted`에 seed·버전·결과를 기록한다.
- source별 manifest에는 `source_id`, engine, schema version, scenario version, seed, generated_at, row count, watermark, checksum을 기록한다.
- manifest와 정답 fixture는 실제 SQL 실행 전에는 `DB_EXECUTION_NOT_RUN`이며 예상값을 실측값처럼 기록하지 않는다.

### 7.3 평가 fixture 계약

- 필수 수용 30건은 단일 source 10건, 교차 source 10건, 모호·근거 부족 5건, 권한·금지 5건으로 구성한다.
- Gold 120건은 `paraphrase_group` 전체를 같은 split에 배치하고, train·prompt 조정용 세트와 최종 test gold를 분리한다.
- 각 case는 `case_id`, question, user role, `as_of`, timezone, expected intent/metric/dimension/time range, reference URN, 허용 SQL/plan, expected result hash, allow/block, error type, 업무·데이터 검토자를 가진다.
- expected result hash는 고정 seed DB에서 정렬·타입 정규화 후 생성한다.
- 이 fixture는 대화형 분석 평가용이다. 객실수요예측 ML의 시계열 train/validation/test label과 혼합하지 않는다.

### 10.1 핵심 KPI 공식

```text
OCC = rooms_sold / available_room_nights
```

분모가 0이면 결과는 0이 아니라 `NULL`이며 reason code를 함께 제공한다.

### 10.2 공통 View 계약

- 모든 View는 `property_id`, `data_period_status`, `is_forecast`를 출력한다.
- 실제 실적 기본 경로는 `is_forecast=false`만 사용한다.
- 서로 다른 fact는 먼저 View grain으로 사전 집계한 뒤 JOIN한다.
- 원시 fact끼리 월·일자만으로 직접 JOIN해 행을 증폭시키지 않는다.
- 금액은 원화 `decimal(18,2)`, 비율은 `decimal(18,6)`으로 반환한다.
- 분모 0은 `NULL`과 `reason_code='ZERO_DENOMINATOR'`로 표현한다.
- `source_updated_at <= :as_of_utc` 조건을 적용하고 source별 `max(source_updated_at)`을 watermark로 제공한다.
- `business_unit_code`는 승인 파생 dimension이며 `ROOMS`, `FNB`, `FACILITY`, `BANQUET`만 허용한다.
- PMS 객실 매출의 `business_unit_code`는 `ROOMS`다. Facility `department`를 객실 매출 사업부로 대체하지 않는다.

| View | Grain | 필수 계산 규칙 |
|---|---|---|
| `analytics.hotel_daily_metrics` | property_id+business_date+room_type_code+period status | 완료 stay를 숙박일별로 펼치고 `room_revenue/occupied_room_nights`를 일별 배부, 공급과 판매를 각각 사전 집계 후 JOIN |

### 10.3 대표 질문 실행 계약

대표 질문:

```text
이번 달 골드 회원의 객실 매출을 사업부별로 보여줘.
```

고정 해석:

1. `as_of=2026-07-28T00:00:00+09:00`, timezone은 `Asia/Seoul`이다.
2. 기간은 `2026-07-01T00:00:00+09:00` 이상, `as_of` 미만이다.
3. 객실 매출은 완료된 `pms_stays.room_revenue`만 사용한다.
4. PMS guest는 stay event time이 `crm_customer_map.[valid_from, valid_to)`에 포함될 때만 member와 연결한다.
5. GOLD는 같은 event time이 `crm_member_grade_history.[valid_from, valid_to)`에 포함되고 `grade_code='GOLD'`인 경우다.
6. `valid_to`와 event time이 같으면 해당 이력은 유효하지 않다.
7. `business_unit_code='ROOMS'`로 집계한다.
8. `source_updated_at <= as_of`인 point-in-time 행만 사용한다.
9. 현재 snapshot인 `crm_members.membership_grade`로 과거 거래 등급을 판정하지 않는다.

## 12. 보안·권한

- DDL은 관리자 계정으로만 실행한다.
- 애플리케이션 runtime 계정은 필요한 Application schema만 읽기·쓰기한다.
- Trino 일반 사용자 경로와 source DB 계정은 read-only다.
- 기본 제품 role은 `hotel_analyst`, `report_admin`, `data_admin`이며 실제 권한은 versioned `access-policy.yaml`에서 결정한다.
- 정책에는 schema version, content hash, approver, activated_at, previous version을 기록하고 Application role seed와 Trino access control 결과의 hash·diff를 검증한다.
- DDL/DML/procedure/passthrough/system catalog 요청은 분석 실행 경로에서 차단한다.
- `connection_ref`, `endpoint_ref`, `artifact_ref`에는 secret 원문을 저장하지 않는다.
- `data_snapshot_json`, RAG 본문, 오류 메시지는 최소 저장·마스킹한다.
- 일반 role의 query result, model input/output, API, log, trace, artifact, report snapshot, export에서 직접식별 원문 노출은 0건이어야 한다.
- P2 Tool/RAG/ML은 P0/P1 통과 전 기능 flag를 비활성화한다.

초기 보존 기준은 Result Cache 24시간, 일반 Artifact·실행 결과 30일, 승인 Report snapshot 90일, audit·policy·Gate·trace metadata 180일이다. Report definition과 Context release는 프로젝트 존속 기간과 종료 후 90일까지 보존한다. 실제 데이터 적용 전 재승인하며 초기 복구 목표는 `RPO 24시간`, `RTO 4시간`이다.
