## 0. 역할 한 문장

박준희는 기획서의 공통 계약을 고정하고, 다섯 서비스의 Docker Compose·환경변수·CI·통합 테스트·병합 Gate·릴리스 증거를 단일 관리하는 기술 PM이다.

R1은 개별 기능을 대신 구현하지 않는다. 각 담당자가 만든 서비스를 하나의 재현 가능한 시스템으로 조립하고, 기획서 수용 기준을 충족했는지 검증한다.

## 1. 최종 책임과 제외 범위

### 1.1 R1 최종 책임

- P0·P1·I5 이후 후속 범위와 변경 결정 관리
- 요구사항·metric·time·상태·오류·권한·평가 계약 관리
- 역할·개인 브랜치·파일 소유권·작업 카드 관리
- 루트 Docker Compose와 통합 실행 profile 관리
- 루트 `.env.example`, 공통 포트, 서비스 이름, health/readiness 계약 관리
- CI, 통합·보안·장애·복구·재현성·릴리스 테스트 관리
- 개인 브랜치의 순차 병합 조정과 Gate 판정
- 필수 30건·gold 120건의 검수 절차와 최종 수용 판정
- Release SHA·data/model/prompt/policy version·runbook 동결

### 1.2 R1이 직접 구현하지 않는 영역

- 원천 DB DDL·seed·DataHub·Trino 내부 설정: R2 정승
- LLM Node·prompt·학습·model serving 내부 구현: R3 윤대성
- FastAPI·Controller·Gate·Cache·Artifact·Worker 내부 구현: R4 김재홍
- React·Chat·Report domain/UI 내부 구현: R5 송민지

통합 실패 시 R1은 담당 파일을 직접 고치지 않고 재현 절차, 오류 증거, 기대 계약을 포함한 수정 요청을 소유자에게 전달한다.

## 2. 단일 작성자와 충돌 방지 계약

| 대상 | 단일 작성자 | 다른 역할의 전달물 |
|---|---|---|
| 루트 Compose·통합 profile | R1 박준희 | 서비스 fragment, port, dependency, health 요구 |
| 루트 `.env.example`·공통 secret 이름 | R1 박준희 | 필요한 변수명·필수 여부·예시 설명 |
| CI·통합/E2E/release harness | R1 박준희 | 역할별 test command·fixture·필요 서비스 |
| metric·time·상태·오류·수용 원장 | R1 박준희 | 계약 변경 요청과 영향 분석 |
| DB·seed·DataHub·Trino·adapter | R2 정승 | R1은 실행 요구만 전달 |
| AI·prompt·model server | R3 윤대성 | R1은 endpoint·health·resource 요구만 통합 |
| 공통 backend·OpenAPI·migration chain·worker | R4 김재홍 | R1은 router/service 등록 요청만 전달 |
| frontend·Report module·화면 | R5 송민지 | R1은 UI 수용 기준만 전달 |

서비스별 Dockerfile은 해당 서비스 소유자가 작성한다.

- R2: 데이터 서비스 설정과 기동 요구
- R3: model server Dockerfile 또는 실행 manifest
- R4: backend·worker Dockerfile과 실행 명령
- R5: frontend Dockerfile과 production build 명령
- R1: 위 전달물을 루트 Compose와 CI에서 조립

## 5. 카드별 핵심 절차

### R1-00~03 — 계약과 충돌을 먼저 제거

1. 프로젝트 표기, backend 구조, P0/P1/P2, 대표 질문을 확정한다.
2. 담당자를 `R1 박준희/junhee`, `R2 정승/seung`, `R3 윤대성/daesung`, `R4 김재홍/jaehong`, `R5 송민지/minji`로 고정한다.
3. 요구사항→데이터→API→화면→테스트→발표 증거 연결 규칙을 만든다.
4. `as_of`, `Asia/Seoul`, `[start, end)`, event-time 등급, 승인 JOIN을 공통 계약에 넣는다.
5. 분석 상태, 화면 상태, Report block 상태, 공통 오류 코드를 versioned contract로 고정한다.
6. FastAPI와 기존 임시 구조가 충돌하면 I0 결정 기록 없이 구현을 진행하지 않는다.

완료 기준:

- 다른 역할이 임의 API·schema·상태값을 만들 필요가 없다.
- 미확정 사항은 `가정` 또는 `추가 결정`으로 분리된다.
- P2 MCP·문서 RAG·ML Tool과 고객 360이 현재 P0/P1·I5 카드에 섞이지 않고, I5 이후 후속 단계로 남아 있다.

### R1-04~06 — 통합 플랫폼 기반

1. R2~R5에게 서비스 이름, image/build, port, volume, env, health, dependency, resource 요구를 받는다.
2. `dev`는 fixture·최소 source, `full`은 5개 source·DataHub·Trino, `split-host`는 model endpoint 분리로 정의한다.
3. Compose는 기동 순서가 아니라 health/readiness를 기준으로 연결한다.
4. backend·worker·frontend·model server·DataHub·Trino·source 장애를 구분한다.
5. CI를 문서·schema·unit·contract·integration·security 순으로 구성한다.
6. 외부 GPU와 실제 credential이 필요한 job은 승인된 수동 job으로 분리한다.

**R1-06 fail policy — 차단 대상과 경고 대상.** "역할별 실패가 CI를 차단한다"는 **자기 역할의 실패가 자기 branch를 차단한다**는 뜻이며, 무관한 역할의 실패로 다른 역할이 차단되는 것을 뜻하지 않는다. 차단·경고 구분은 다음과 같이 고정한다.

| 구분 | 대상 | 근거 |
|---|---|---|
| **차단** | 허용 경로 침범, handoff 필수 필드 누락·형식 오류, `FAIL`·`BLOCKED`로 기록된 검증, `git diff --check` 실패 | 증거의 무결성 위반 |
| **경고(R1 검토 큐)** | 미실행 검증(`Not Run`), change request, 잔여 위험, 외부 승인 요청 | 불리한 사실의 자발적 보고. 차단하면 기록을 비우는 편이 유리해져 Gate가 수집하려는 증거가 사라짐 |
| **N/A** | 해당 역할에 실행 대상이 아닌 job의 `skipped` | 실행 대상 아님. 단 `if` 조건 오류로 인한 무음 skip을 막기 위해 Summary에 job별 실행 여부를 남긴다 |

**미해결.** 현재 `python-contracts`는 전 branch에서 test 전체를, `document-quality`는 전 branch에서 타 역할 소유 문서를 검사한다. 위 원칙과 "각 역할의 test command가 독립적으로 실행된다"는 완료 기준에 어긋나므로, Wave 2 발행 전에 역할별 test 경로 분기(`tests/{ai,backend,data,frontend}` ↔ branch 매핑)와 전체 회귀의 `dev` 전용 실행으로 교정한다.

완료 기준:

- `.env.example`에는 이름과 설명만 있고 실제 credential이 없다.
- 서비스 하나가 실패해도 원인이 해당 service health로 드러난다.
- 각 역할의 test command가 독립적으로 실행된다.
- 자동 검사 결과와 R1 판정이 Summary·원장에서 분리돼 표시된다.

### R1-07 — 평가 자산 관리

필수 30건:

- 단일 source 10건
- 교차 source 10건
- 모호·근거 부족 5건
- 권한·금지 5건

gold 120건:

- `paraphrase_group` 단위로 train/validation/gold를 분리한다.
- R1은 질문 의도·업무 의미, R2는 SQL·JOIN·결과, R3는 평가 runner를 검수한다.
- 조정에 사용한 데이터가 최종 gold에 누수되지 않게 한다.
- 결과가 없는 경우와 데이터가 누락된 경우를 분리한다.

### R1-08~11 — 단계별 통합

각 Gate에서 다음 순서를 고정한다.

1. 생산자 역할의 계약 test 확인
2. 소비자 역할의 fake adapter test 확인
3. 개인 브랜치를 한 개씩 `dev`에 병합
4. 병합 직후 영향 test 실행
5. R1 Compose 통합 변경 반영
6. 통합 smoke와 대표 trace 실행
7. 실패 role에 결함 반환
8. Gate 증거와 승인자 기록

`fixture 통과`, `dev 병합`, `통합 Gate 통과`는 서로 다른 상태다.

I3에서는 DataHub Analytics Agent를 설치했다는 사실만 비교하지 않는다. 동일 질문·데이터·권한 조건에서 제공 기능, 실행 경계, 결과 정확도, trace, 안전 통제를 비교한다. 실행하지 못한 항목은 문서 비교와 실제 비교를 구분하고 `Not Run`으로 남긴다.

### R1-12~13 — 릴리스

반드시 검증할 항목:

- 원천 DB read-only와 DDL·DML·procedure·passthrough query·`system` catalog 차단
- 역할·row filter·column mask·redaction
- G1/G2/G3 우회와 Cache 권한 오염
- timeout·cancel·retry·idempotency
- source·model·worker·Report block 부분 실패
- 동일 seed·`as_of`·policy·model로 결과 checksum 재현
- 암호화 backup·restore, backup과 분리한 암호화 key 관리, 실제 RPO/RTO 측정
- dependency·image scan
- cold/warm p50/p95와 자원 사용량
- 발표 환경의 빈 상태부터 재기동

미실행 검증은 `Not Run`, 외부 권한 부족은 `Blocked`로 기록한다.

### I5 이후 후속 단계의 소유자

P2와 고객 360은 현재 일정의 완료 조건에서는 제외하지만, I5 이후 반드시 다시 시작할 후속 단계로 관리한다. 아직 시작하지 못했거나 `Not Run`·`Blocked`여도 현재 I5 실패로 처리하지 않는다.

| 후속 범위 | I5 이후 주 소유자 | 필수 협업 |
|---|---|---|
| MCP Tool Registry·호출 통제 | R4 김재홍 | R3 Tool adapter, R5 관리 UI, R1 보안 Gate |
| 사내 운영 문서 RAG | R3 윤대성 | R2 metadata, R4 권한·trace, R5 근거 UI |
| ML-as-a-Tool | R3 윤대성 | R2 feature data, R4 Tool Gate, R5 예측 표시 |
| 고객 360 | R5 송민지 | R2 identity·mask, R4 권한·trace, R1 후속 Gate 승인 |
| 외부 Report 배포·복잡한 cron | R4 김재홍 | R5 UI, R1 운영·보안 승인 |
