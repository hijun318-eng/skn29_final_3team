## 0. 5개 AI 공통 실행 계약

### 0.1 최적화된 역할 경계

| 역할 | 독립 소유 영역 | 다른 역할에 제공하는 계약 |
|---|---|---|
| R1 제품 계약·평가·통합조정 | metric·시간·질문·gold·결정 기록·상태 원장·수용 판정 | 업무 계약, 평가 fixture, 통합 Gate 판정 |
| R2 데이터 플랫폼·메타데이터·연합조회 | 5개 DB, synthetic data, DataHub, Trino, DataHub/Trino adapter | URN/FQN, query adapter, 정답 SQL·결과 |
| R3 대화형 분석 Control Plane·AI | Query API, Controller, Context, G1·G2·G3, LLM Node, Cache, Artifact | OpenAPI, 상태 머신, 분석 artifact |
| R4 사용자 경험·리포팅 Full-stack | frontend 전체, Report domain/API/worker contract, Chat↔Report | UI 상태 요구, report definition/run |
| R5 Platform·ModelOps·보안 QA | 실행환경, CI, vLLM serving, 관측성, 보안·복구·release | 고정 환경, 독립 시험 결과, release evidence |

R1은 기술 구현을 대신하지 않는다. R1의 핵심은 다섯 AI가 서로 다른 가정을 사용하지 않도록 계약과 완료 증거를 통제하는 것이다.

### 0.1A R1 소유 경계와 공유 파일 단일 작성자

R1이 직접 수정하는 영역:

- 업무 metric·time·dimension 계약 문서
- 필수 30건·gold 120건의 평가 schema·fixture·판정 결과
- 작업 카드·계약·결정·상태·증거 원장
- 통합 Gate 판정과 사용자 문구 검수 자료

R1은 제품 source code, DB DDL·seed, OpenAPI 구현, frontend, Compose·CI를 직접 수정하지 않는다. 변경이 필요하면 소유 역할에 계약 변경 요청을 제출한다.

| 공유 대상 | 단일 작성자 | 다른 AI의 전달물 |
|---|---|---|
| 업무·평가 schema와 수용 판정 | R1 | field·정답·test 결과 변경 요청 |
| source DDL·seed·DataHub recipe·Trino catalog/adapter | R2 | schema·runtime 요구 |
| 공통 OpenAPI·Pydantic·FastAPI 등록·Alembic chain | R3 | contract diff·router·migration proposal |
| frontend package·Report domain/API | R4 | UI·Report contract 요구 |
| root dependency·Compose·`.env.example`·CI·배포 | R5 | dependency·service·환경 변경 요청 |

같은 공유 파일을 두 AI가 동시에 수정하는 카드는 만들지 않는다. 단일 작성자는 전달물을 적용한 뒤 원 제안자에게 diff와 검증 결과를 돌려준다.

### 0.2 AI에게 반드시 함께 제공할 입력

```text
ROLE_ID=R1
TASK_CARD_ID=R1-xx
REPOSITORY_ROOT=<절대 경로>
BASE_BRANCH=<통합 기준 branch>
BASE_SHA=<작업 시작 commit SHA>
CONTRACT_VERSION=<현재 승인 contract version>
FIXTURE_VERSION=<현재 승인 fixture version>
ALLOWED_PATHS=<이 카드에서 수정 가능한 경로>
FORBIDDEN_PATHS=<수정 금지 경로>
ACCEPTANCE_CRITERIA=<완료 조건>
EXTERNAL_ACTION_PERMISSION=<비용·배포·데이터 전송 허용 여부>
STOP_CONDITION=<중단·질문 조건>
```

“이 매뉴얼 전체를 구현해줘”라고 지시하지 않는다. 한 번에 하나의 작업 카드만 전달한다.

각 사람은 `docs/markdown/collaboration/README.md`에 정해진 자기 개인 branch(`junhee`, `minji`, `seung`, `daesung`, `jaehong` 중 배정된 branch)와 자기 clone을 사용한다. 다섯 AI가 같은 working directory를 공유하지 않는다. AI는 승인 없이 stage·commit·push·merge하지 않고, 사람이 검증 후 통합한다. 통합 중 공유 파일 변경은 해당 단일 작성자에게 되돌린다.

### 0.2A AI에 전달할 실행 프롬프트

```text
너는 ROLE_ID 담당 AI다. 기준 기획서와 이 역할 매뉴얼을 모두 읽되, 이번에는 TASK_CARD_ID 하나만 수행한다.
먼저 repository root, 적용되는 AGENTS.md, branch, BASE_SHA, dirty worktree, 선행 계약·fixture version을 읽기 전용으로 확인한다.
확인된 사실·가정·blocker와 이 카드의 입력·출력·완료 조건을 짧게 보고한 뒤 작업한다.
ALLOWED_PATHS만 수정하고 FORBIDDEN_PATHS와 다른 역할 소유 파일은 수정하지 않는다.
공유 파일 변경이 필요하면 구현 가능한 독립 module 또는 contract-change-request를 만들고 단일 작성자에게 handoff한다.
기존 변경을 보존하고 승인 없는 설치·비용·배포·데이터 전송·stage·commit·push·merge를 하지 않는다.
완료 조건에 맞는 검증을 실제 실행하고, 미실행 검증은 통과로 쓰지 않는다.
마지막에는 매뉴얼의 handoff 형식으로 변경 파일, 계약 version, 검증, 미검증, 남은 위험을 보고한다.
```

### 0.3 AI 작업 시작 순서

1. repository root의 `AGENTS.md`를 읽는다.
2. 기준 기획서를 읽는다.
3. 이 역할 매뉴얼을 읽는다.
4. `docs/markdown/collaboration/README.md`를 읽는다.
5. 현재 branch와 `git status --short`를 확인한다.
6. 기존 사용자 변경을 보존한다.
7. 현재 작업 카드의 입력·출력·완료 기준만 다시 말한다.
8. 미확정 기술·권한·비용이 있으면 구현 전에 중단 조건으로 보고한다.
9. 허용 경로 안에서 최소 단위로 구현한다.
10. 검증 결과와 다음 역할 인수인계를 남긴다.

### 0.4 AI 공통 금지

- 다른 역할의 소유 파일을 승인 없이 수정
- 기존 변경 삭제·정리
- 선행 contract 없이 임의 API·DB schema 확정
- 외부 비용 발생, dependency 설치, secret 등록
- stage·commit·push·merge
- 실제 고객 데이터 사용
- 실행하지 않은 검증을 `Pass`로 기록
- 한 작업 카드에서 P2 범위까지 확장

### 0.5 통합 Gate

| Gate | 필수 산출물 | 통과 책임 |
|---|---|---|
| I0 기준 정렬 | 주제·backend·기술 우선순위 결정 기록, 역할·branch 배정 | R1, 전원 확인 |
| I1 Contract Freeze | metric/time, OpenAPI example, 공통 오류, fixture, 파일 소유권 | R1 조정, R2·R3·R4·R5 승인 |
| I2 Deterministic Slice | Template 질문의 Context→G1→G2→Trino→G3→Artifact→Report | R3 구현, R1·R2·R4·R5 검증 |
| I3 General LLM | Node 1·2·2′·3, 일반 질문, 역할별 model trace | R3 구현, R1·R2·R5 검증 |
| I4 Reporting | report definition/run, 수동·schedule, partial failure | R4 구현, R1·R3·R5 검증 |
| I5 Release | 필수 30건, full profile, 보안·복구, model 비교 | R5 실행, 전원 판정 |

상위 Gate가 통과하지 않아도 각 역할은 fixture로 다음 작업을 개발할 수 있다. 단, 실제 통합 성공으로 표시해서는 안 된다.

## 1. 이 역할의 최종 책임

R1은 “사용자가 무엇을 물었고, 어떤 데이터와 기준으로 답해야 하며, 결과가 업무적으로 맞는가”와 “다섯 역할이 같은 계약·상태·완료 기준을 사용하는가”를 책임진다.

R1은 다음 사항의 최종 판정자다.

- 질문 의도
- 지표 정의
- 기간과 기준 시각의 의미
- 회원 등급 등 시간에 따라 바뀌는 dimension의 의미
- 합성 데이터에 심을 업무 시나리오
- 정답 질문·SQL plan·결과의 업무적 타당성
- 사용자에게 보여줄 설명과 오류 문구
- Chat에서 Report로 이어지는 사용자 흐름
- 기술 선택의 결정 기록과 미확정 가정
- 역할·branch·작업 카드 배정
- 통합 Gate 상태와 증거 링크
- 공식 산출물별 증거 소유자

R1이 직접 판정하면 안 되는 항목:

- DB schema와 SQL의 기술적 정확성: R2와 공동 판정
- Context·Gate·모델 구현의 기술적 합격: R3와 공동 판정
- 화면 접근성·API 동작: R4와 공동 판정
- 보안·배포·복구 합격: R5가 판정

## 1.1 R1 작업 패키지와 병렬성

| R1-WP3 수용 30건 | 질문·의도·허용/차단 | R2 최소 schema fixture | I1 이후 전 역할과 동시 |
| R1-WP4 gold 120건 | 표현 그룹·정답 공동 검수 | R2 seed와 result fixture | R3 Node 개발과 동시 |

## 2. 다른 역할과 동시에 시작하기 위한 공통 기준

다섯 역할은 다음 대표 질문을 첫 통합 기준으로 사용한다.

```text
이번 달 골드 회원의 객실 매출을 사업부별로 보여줘.
```

초기 공통 조건:

| 항목 | 공통 기준 |
|---|---|
| `as_of` | `2026-07-28T00:00:00+09:00` |
| timezone | `Asia/Seoul` |
| 기간 | 월 시작 이상, `as_of` 미만 |
| 회원 등급 | 매출·투숙 event time에 유효한 등급 |
| source | PMS PostgreSQL + CRM SQL Server |
| metric | `room_revenue` |
| role | `hotel_analyst` |
| 결과 | 표, 차트, 설명, 출처, 필터, 기간, 기준 시각 |

R1은 이 기준의 업무 의미를 확정해 R2·R3·R4·R5에 동일한 문장으로 전달한다.

## 3. 착수 전에 받아야 할 입력

| 입력 | 제공자 | 없을 때 처리 |
|---|---|---|
| 전체 기획서 | 팀 리드 | 해당 문서를 먼저 읽고 P0/P1 범위를 표시 |
| 현재 화면 fixture | R4 | 화면 없이 사용자 흐름 문서부터 작성 |
| 5개 source 후보 schema | R2 | entity·field 요구 목록을 먼저 전달 |
| API·공통 객체 초안 | R3 | 필요한 업무 field 목록을 먼저 전달 |
| 보안 role 초안 | R5 | 최소 `hotel_analyst`, `report_admin`, `data_admin`을 가정으로 표시 |

입력이 없다는 이유로 작업을 기다리지 않는다. 확인되지 않은 항목은 `가정`으로 구분해 작성하고, 확정 담당자와 확인 조건을 함께 기록한다.

## 4. 단계별 상세 작업

### 단계 R1-00 — Repository 기준 정렬

목적: 기획서·`AGENTS.md`·`README.md`·기존 화면·활성 산출물이 서로 다른 전제를 가질 때 다섯 AI가 임의로 선택하지 않게 한다.

수행:

1. `AGENTS.md`, `README.md`, 기준 기획서, 문서 관리 규칙, 활성 번호 산출물, 현재 code·test를 목록화한다.
2. `확정`, `현재 구현`, `잠정`, `참고`, `충돌`로 상태를 구분한다.
3. 호텔 VOC·운영 지원 주제와 이번 DataHub 기반 대화형 분석·Report 범위의 포함 관계를 한 문장으로 확정한다.
4. 기획서의 FastAPI 단일 계약과 README의 잠정 Django 인증·job/FastAPI 분석 분리안 중 이번 구현 기준을 결정한다.
5. 기존 frontend fixture에서 재사용할 화면과 폐기할 가정을 구분한다.
6. 기술 version과 서비스 구성은 spike 전 `미확정`으로 남긴다.
7. 결정마다 승인자·근거·영향 역할·rollback을 기록한다.
8. I0 확인 전에는 공통 directory·API·DB migration을 만들지 않는다.

출력:

| 항목 | 현재 근거 | 상태 | 이번 결정 | 영향 역할 | 재검토 조건 |
|---|---|---|---|---|---|

완료 기준:

- 다섯 역할이 같은 backend 경계, 문서 우선순위, P0 범위와 파일 소유권을 확인한다.
- 충돌 항목이 `가정`인 채로 구현 계약에 섞이지 않는다.

### 단계 R1-01 — P0/P1 범위 표시

목적: 팀이 P2 기능을 섞어 구현하지 않도록 업무 범위를 고정한다.

수행:

1. 기획서에서 P0·P1·P2·선택 범위를 각각 목록화한다.
2. P0에서 반드시 시연할 사용자 행동을 추출한다.
3. P1 중 P0의 기술 선행 조건을 표시한다.
4. P2와 고객 360을 별도 제외 목록으로 만든다.
5. 팀원에게 “이번 구현에서 하지 않는 것”을 전달한다.

P0 사용자 행동:

- 자연어 질문
- 결과 표·차트·설명 확인
- 데이터 출처·필터·기간·기준 시각 확인
- 모호한 질문의 재질문
- 정책 차단·부분 실패 확인
- 결과를 보고서에 담기
- 보고서 수동 실행
- 기본 주기 schedule
- 실행 이력과 trace 확인

완료 증거:

- P0/P1/P2 분류표
- 제외 범위 목록
- 다섯 역할의 확인 기록

### 단계 R1-02 — 사용자와 업무 과업 정의

목적: 화면과 API가 누구의 어떤 문제를 해결하는지 고정한다.

수행:

1. 사용자를 `현업 실무자`, `보고서 관리자`, `데이터·시스템 관리자`로 구분한다.
2. 사용자별 시작 조건과 원하는 결과를 작성한다.
3. 사용자가 직접 수행하는 행동과 시스템 자동 행동을 구분한다.
4. 사용자에게 보이면 안 되는 내부 정보를 표시한다.
5. 성공·빈 결과·권한 거부·부분 실패 과업을 작성한다.

작성 형식:

| 사용자 | 시작 상황 | 입력 | 기대 결과 | 허용 행동 | 금지 노출 |
|---|---|---|---|---|---|
| 현업 실무자 | 지표 변화 확인 필요 | 자연어 질문 | 표·차트·근거 | 질문, 후속 질문, 보고서 담기 | DB 원문 오류, 내부 정책 상세 |

완료 기준:

- 각 사용자마다 최소 1개 정상 과업과 1개 실패 과업이 있다.
- 화면 이름이 아니라 사용 목적과 완료 상태로 작성되어 있다.

### 단계 R1-03 — 업무 용어 사전 작성

목적: 사용자 표현과 DataHub·DB field의 의미를 연결한다.

수행:

1. 대표 질문에서 명사와 조건을 분리한다.
2. 사용자 용어, 표준 용어, metric, dimension, 동의어를 정리한다.
3. source별로 이름이 다른 같은 개념을 표시한다.
4. 동음이의어와 모호어를 표시한다.
5. 자동 해석 가능한 용어와 재질문이 필요한 용어를 구분한다.

예시:

| 사용자 용어 | 표준 용어 | 유형 | 해석 | 모호성 처리 |
|---|---|---|---|---|
| 객실 매출 | `room_revenue` | metric | 투숙 기준 객실 매출 합계 | 취소·세금 포함 여부가 없으면 기본 정책 적용 |
| 골드 회원 | `membership_grade=GOLD` | dimension | event time 유효 등급 | 현재 등급을 묻는 경우 별도 의도 |
| 이번 달 | month-to-date | time | 월 시작 이상 `as_of` 미만 | timezone 누락 시 서비스 기본값 |

R2 전달:

- 용어가 연결될 entity·column 후보
- source별 식별자 차이

R3 전달:

- Node 1이 출력해야 하는 표준 field
- 재질문 조건

### 단계 R1-04 — Metric 정의

목적: SQL이 실행돼도 업무 의미가 틀리는 문제를 방지한다.

각 metric에 다음을 작성한다.

| 필드 | 내용 |
|---|---|
| metric ID | 변경되지 않는 식별자 |
| 이름 | 사용자 표시 이름 |
| 설명 | 업무 의미 |
| source | 기준 source |
| field | 기준 field |
| aggregation | `sum`, `count`, `avg`, ratio 등 |
| time field | 기간 필터 기준 |
| 포함 조건 | 완료·정상 거래 등 |
| 제외 조건 | 취소·테스트 데이터 등 |
| 단위 | 원, 건, 명, % |
| owner | 승인 담당 |
| 검증 질문 | metric을 검증할 질문 |

검토 순서:

1. R1이 의미와 포함·제외 조건을 작성한다.
2. R2가 실제 schema와 계산 가능한지 확인한다.
3. R2가 정답 SQL과 결과를 만든다.
4. R1이 결과를 업무 기준으로 승인한다.
5. R3가 Context Registry 형식으로 등록한다.

완료 기준:

- 모든 P0 질문이 승인 metric을 참조한다.
- 같은 이름의 metric에 계산식이 두 개 존재하지 않는다.

### 단계 R1-05 — 시간 정책 정의

목적: 같은 질문이 실행 시점마다 다르게 해석되는 문제를 방지한다.

수행:

1. 서비스 timezone을 정한다.
2. `as_of` 생성 시점을 정한다.
3. 일·주·월 경계를 정한다.
4. 기간의 시작 포함·종료 제외 규칙을 정한다.
5. `current_date`, `now()`처럼 실행 시각에 의존하는 표현을 금지한다.
6. 보고서 실행 시 모든 block이 같은 `as_of`를 사용하는지 명시한다.
7. 현재 등급과 event-time 등급 질문을 구분한다.

필수 반례:

- 월 첫날 실행
- 자정 경계
- `valid_to`와 event time이 같은 경우
- 현재 GOLD지만 거래 당시 SILVER인 회원
- 거래 당시 GOLD지만 현재 SILVER인 회원

완료 증거:

- time policy 표
- 경계값 질문과 기대 결과
- R2의 SQL 검증

### 단계 R1-06 — 합성 데이터 시나리오 설계

목적: 시연 질문에 답할 수 있으면서도 결론을 과도하게 강제하지 않는 데이터를 만든다.

수행:

1. 필요한 entity와 관계를 R2에 전달한다.
2. 정상 패턴과 반례 패턴을 함께 설계한다.
3. 취소·누락·중복·빈 결과를 포함한다.
4. source별 로컬 ID가 우연히 같은 문자열로 연결되지 않게 한다.
5. 실제 고객과 혼동될 개인정보 형식을 사용하지 않는다.
6. 동일 seed에서 같은 결과가 나오도록 요구한다.
7. 의도한 업무 패턴과 expected result를 연결한다.

시나리오 카드:

```text
시나리오 ID:
목적:
관련 질문:
사용 source:
필요 entity:
생성 규칙:
반례:
기대 결과:
검증 담당:
```

완료 기준:

- 모든 대표 질문에 연결된 시나리오가 있다.
- 원인을 확인할 근거가 없는 질문도 포함한다.
- 합성 데이터임을 명시한다.

### 단계 R1-07 — 필수 수용 세트 30건 작성

구성:

| 분류 | 건수 | 목적 |
|---|---:|---|
| 단일 source | 10 | metric·filter·기간 검증 |
| 교차 source | 10 | identity·JOIN·event time 검증 |
| 모호·근거 부족 | 5 | 올바른 재질문·중단 검증 |
| 권한·금지 | 5 | G1·G2 차단 검증 |

각 케이스 필드:

```text
case_id
question

user_role
as_of
timezone
expected_intent
expected_metric
expected_dimension
expected_time_range
reference_urns
expected_sql_or_plan
expected_result_hash
allow_or_block
expected_error_type
business_reviewer
data_reviewer
reviewed_at
```

작성 순서:

1. R1이 질문·의도·기간·예상 행동을 작성한다.
2. R2가 URN·SQL·결과를 작성한다.
3. R1과 R2가 함께 실행 결과를 확인한다.
4. R3가 자동 평가 가능한 형식으로 변환한다.
5. R5가 release test에서 독립 실행한다.

완료 기준:

- 모든 케이스가 성공 또는 중단 중 하나로 명확하다.
- 정답이 없는 항목을 임의 SQL 성공으로 처리하지 않는다.

### 단계 R1-08 — Gold 120건 확장

목적: prompt와 모델 비교에서 우연한 성공을 배제한다.

수행:

1. 30건을 기반으로 metric·source·난이도별 질문을 확장한다.
2. 같은 의미의 표현 변형을 `paraphrase_group`으로 묶는다.
3. 표현 그룹 전체가 하나의 split에만 속하도록 한다.
4. 경계값·빈 결과·중복 JOIN을 포함한다.
5. SQL 문자열이 달라도 결과와 의미가 같으면 정답으로 인정할 기준을 작성한다.
6. 모델 학습 또는 prompt 조정에 사용한 세트와 최종 gold를 분리한다.

금지:

- LLM이 만든 SQL을 사람이 검수하지 않고 gold로 채택
- 결과가 우연히 같은 작은 fixture만 사용
- 같은 표현 그룹을 train과 gold에 나눠 넣기

### 단계 R1-14 — 최종 수용 판정

수행:

1. 필수 30건의 실제 결과를 확인한다.

### 단계 R1-15 — Analytics Agent 기준선·제품 채택 판정

목적: DataHub Analytics Agent와 기능이 겹치는 부분을 숨기지 않고, 본 프로젝트의 독립 기여와 도입 결정을 증거로 남긴다.

동일 조건:

- 같은 synthetic source와 seed
- 같은 대표 질문·필수 수용 질문
- 같은 role·권한 범위
- 같은 `as_of`·timezone
- 가능한 한 같은 metric 정의와 결과 정규화

비교 항목:

| 항목 | 판정 질문 |
|---|---|
| 자연어→SQL→실행→차트 | 같은 질문을 완료하는가 |
| DataHub context | 어떤 metadata와 관계를 근거로 쓰는가 |
| 연합 조회 | 2~3 source와 Trino 경로를 지원하는가 |
| 안전 | G1·G2·G3와 read-only·mask 증거가 남는가 |
| 재현 | Context·policy·model·prompt·`as_of`가 versioned 되는가 |
| Report | artifact를 definition·run snapshot으로 재사용하는가 |
| 운영 | 장애·trace·비용·자원·복구를 설명할 수 있는가 |

수행:

1. R3·R5의 baseline 실행 결과와 지원하지 않는 항목을 받는다.
2. 지원하지 않는 기능을 임의로 실패 처리하지 않고 `NOT_APPLICABLE`로 분리한다.
3. 본 프로젝트의 추가 책임이 Context Package·Guarded 실행·Trino 연합·Report artifact에 실제로 남는지 확인한다.
4. 기능 중복, 독립 기여, 운영 비용, 도입 위험을 각각 판정한다.
5. `그대로 채택`, `일부 참조`, `기준선만 사용`, `사용하지 않음` 중 하나를 결정하고 근거를 기록한다.
6. Analytics Agent 사용 여부와 본 프로젝트 완료 여부를 같은 판정으로 섞지 않는다.

### 단계 R1-16 — 계약·상태·결정·증거 원장 운영

R1은 다음 네 원장을 유지한다.

| 원장 | 필수 field | 갱신 시점 |
|---|---|---|
| 계약 원장 | contract ID·version·owner·consumer·breaking 여부·fixture | I0/I1와 변경 승인 시 |
| 작업 상태 원장 | 카드 ID·담당 역할·branch·base SHA·상태·blocker | 카드 시작·handoff 시 |
| 결정 원장 | 결정·대안·근거·승인자·rollback·재검토 조건 | 기술·범위 선택 시 |
| 증거 원장 | Gate·요구사항·test·artifact/report/trace ID·판정 | I2~I5 검증 시 |

수행:

1. 각 AI에 카드 ID와 허용·금지 경로를 배정한다.
2. 카드 시작 시 base SHA와 contract version을 고정한다.
3. 변경 요청이 breaking인지 판정하고 영향을 받는 consumer를 표시한다.
4. 완료 보고의 검증 결과를 증거 링크와 연결한다.
5. 충돌은 코드 작성자가 아니라 단일 작성자에게 반환한다.
6. 한 Gate의 필수 증거가 없으면 다음 Gate의 실제 통합 성공으로 표시하지 않는다.
7. fixture 통과와 실제 component 통과를 별도 상태로 둔다.
8. 결함 수정 후 영향받는 Gate와 수용 case만 우선 회귀하고 전체 회귀 시점을 기록한다.

## 8. 병합 운영 매뉴얼과 권장 병합 체크포인트

병합 절차의 단일 기준은 `docs/markdown/collaboration/README.md`다. 아래 내용은 그 정책을 이 프로젝트의 5개 역할과 통합 Gate에 적용한 것이다. 날짜가 아니라 완료된 계약·기능 단위로 병합한다.

### 8.1 병합 기본 원칙

1. 팀원은 배정된 개인 branch에서만 작업한다.
2. `main`·`dev`에서는 기능 작업을 하지 않는다.
3. 새 카드 시작 전 working tree가 깨끗할 때 최신 `dev`를 개인 branch에 반영한다.
4. 한 commit은 한 의도, 한 병합 요청은 서로 강하게 연결된 1~3개 카드로 제한한다.
5. fixture 구현은 병합할 수 있지만 실제 통합 성공과 구분해 표시한다.
6. 공유 파일은 단일 작성자의 개인 branch에서만 최종 반영한다.
7. 관리자만 검증된 개인 branch를 `dev`에 순차 병합한다.
8. I5 완료 전에는 `dev`를 `main`에 병합하지 않는다.

### 8.2 개인 branch 병합 준비

다음 조건을 모두 만족해야 관리자에게 병합을 요청한다.

- [ ] 작업 카드와 허용 경로가 명확하다.
- [ ] 최신 승인 contract·fixture version을 사용했다.
- [ ] 관련 단위·contract·build 검증이 실제 통과했다.
- [ ] 미실행 검증과 fixture 제한을 handoff에 적었다.
- [ ] 다른 역할 소유 파일을 직접 수정하지 않았다.
- [ ] secret·실제 데이터·생성된 `data/raw`·`data/processed`·대용량 결과물을 포함하지 않았다.
- [ ] `git status`, staged diff, commit 내용을 사람이 확인했다.
- [ ] 개인 branch가 원격 개인 branch와 일치하고 push가 끝났다.
- [ ] 변경 파일·검증·contract version·남은 위험을 관리자에게 전달했다.

AI에게 실제 병합을 요청하는 경우 repository의 `merge-branch-to-dev` Skill 절차를 사용한다. 병합 요청이 없으면 AI가 임의로 stage·commit·push·merge하지 않는다.

### 8.3 관리자 `dev` 병합 순서

각 개인 branch를 한 번에 하나씩 처리한다.

1. `dev` working tree가 깨끗한지 확인한다.
2. 원격을 fetch하고 `dev`를 fast-forward로 최신화한다.
3. local `dev`와 `origin/dev` SHA가 같은지 확인하고 `base SHA`를 기록한다.
4. 대상 원격 개인 branch를 병합한다.
5. 충돌이 나면 내용을 추측해 수정하지 않고 병합을 중단해 소유자에게 돌려보낸다.
6. 대상 카드 검증과 해당 Gate 회귀를 실행한다.
7. 병합 직후 `head SHA`, source branch, 검증 결과로 팀 보고를 통합한다.
8. 검증이 모두 통과한 뒤에만 `dev`를 push한다.
9. 다음 개인 branch 담당자는 이 최신 `dev`를 자기 branch에 반영한 뒤 후속 카드를 진행한다.

### 8.4 권장 병합 체크포인트

| 체크포인트 | 여기까지 완료하고 병합 | 권장 `dev` 반영 순서 | 병합 후 최소 회귀 |
|---|---|---|---|
| M0 / I0 기준 정렬 | R1-00·01, backend 경계, P0, 역할↔개인 branch, 파일 소유권, 계약 ID 체계 | R1 | 문서 링크·결정 원장·5명 확인 |
| M1 / I1 Contract Freeze | metric/time, 최소 schema·URN/FQN fixture, adapter interface, 공통 API·오류, Report schema, version·health·access 계약 | R1 → R5 → R2 → R3 → R4 | schema/contract consumer-provider test |
| M2 / I2 Deterministic Slice | 최소 2-source seed·ingestion·Trino, Template→Context→G1/G2→query→G3→Artifact, 최소 Chat→Report fixture | R2 → R3 → R4 → R5 | 대표 질문 결과 hash·trace·read-only·smoke |
| M3 / I3 General LLM | gold subset, model serving profile, Node 1·2·2′·3, 일반 질문 UI 상태 | R1·R2 fixture → R5 serving → R3 → R4 → R5 검증 | Node 평가·repair 상한·Gate 우회·모델 trace |
| M4 / I4 Reporting | Report domain/API·migration proposal, 공통 등록, worker, 수동/schedule, run history·부분 실패 | R4 module → R3 등록 → R5 worker → R4 실제 API 연결 → R5 검증 | Report contract·migration·중복 job·snapshot·restore |
| M5 / I5 Release | 5 source, 필수 30건, 모델 비교, 보안·retention·backup·scan, runbook | 결함 소유 역할의 작은 수정 → R5 전체 검증 → R1 판정 | full regression·수용 trace·미해결 위험 |
| M6 / `main` | I5 Pass, 승인된 baseline, release evidence와 rollback | 관리자 `dev` → `main` | 배포 전 smoke와 release tag/SHA 확인 |

M4는 R4가 두 번 병합될 수 있다. 첫 병합은 Report 독립 module·proposal, 두 번째 병합은 R3·R5 변경을 받은 실제 API 연결이다. 두 병합 사이에 R4는 최신 `dev`를 반영해야 한다.

### 8.5 병합을 미루거나 중단해야 하는 경우

- contract version 없이 consumer와 provider를 동시에 변경함
- 공통 OpenAPI·FastAPI entrypoint·Alembic chain을 R3 이외 branch가 직접 수정함
- root dependency·Compose·CI를 R5 이외 branch가 직접 수정함
- migration head가 둘 이상 생기거나 동일 endpoint가 중복 등록됨
- fixture test만 통과했는데 실제 통합 Pass로 보고함
- 필수 negative test, build, migration, secret 검사를 실행하지 못함
- 개인 branch에 최신 `dev` 반영 중 충돌이 발생함
- 실제 데이터·secret·외부 비용·배포가 승인되지 않음
