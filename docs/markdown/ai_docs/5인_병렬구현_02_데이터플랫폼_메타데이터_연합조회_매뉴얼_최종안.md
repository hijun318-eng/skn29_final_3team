## 0. 역할 한 문장

정승은 5개 합성 데이터 원천을 재현 가능하게 만들고, DataHub 자산 식별자와 Trino 실행 경로를 연결해 백엔드가 안전하게 조회할 데이터 계약과 adapter를 제공한다.

## 1. 최종 책임과 경계

### 1.1 R2 최종 책임

- PMS·POS·CRM·시설·연회 5개 논리 source와 4종 엔진
- 논리·물리 schema, DDL, deterministic synthetic seed
- schema/seed/scenario version, row count, checksum
- CRM `customer_identity_map`과 `member_grade_history`
- 데이터 품질·참조 무결성·전처리 규칙과 rejected fixture
- source별 ingestion account와 application read-only account 요구
- DataHub recipe·platform instance·URN·metadata·lineage
- Trino catalog·connector·type mapping·FQN
- metric 계산 가능성, 승인 JOIN Registry, cardinality·event-time 검증
- source watermark, 정답 SQL·result hash
- DataHub Search/Graph·Trino query/status/cancel·source health adapter
- 다섯 번째 source 온보딩 재현

### 1.2 직접 수정하지 않는 영역

- 루트 Compose·`.env.example`·CI·통합 harness: R1 박준희
- LLM·prompt·model serving: R3 윤대성
- FastAPI·Context·Gate·Artifact·worker: R4 김재홍
- frontend·Report·Catalog 화면: R5 송민지

R2는 각 데이터 서비스의 설정·기동 요구를 만들고 R1에 service fragment로 전달한다. 루트 Compose는 수정하지 않는다.

## 2. 파일·계약 소유권

| R2 단일 소유 | 다른 역할에 제공 |
|---|---|
| source DDL·seed·quality fixture | schema/seed version, row count, checksum |
| DataHub recipe·metadata 설정 | URN, domain, owner, tag, quality status |
| Trino catalog·connector 설정 | FQN, type mapping, read-only 결과 |
| JOIN·identity·watermark fixture | 승인 JOIN, event-time 조건, cache invalidation 입력 |
| DataHub·Trino·source adapter | typed interface, fake와 실제 구현 |
| 정답 SQL·result fixture | 필수 30건과 gold 평가 근거 |

공통 API schema나 Context 객체 변경이 필요하면 R4에게 contract change request를 전달한다. UI 표시 field는 R5에게 fixture로 제공한다.

## 5. 단계별 필수 상세

### 5.1 Schema와 synthetic data

각 source registry 필수 필드:

```text
source_id, source_name, domain, engine, database_name, schema_name,
data_owner, technical_owner, synthetic_flag, schema_version, seed_version,
timezone, query_account, ingestion_account, datahub_platform_instance,
trino_catalog, watermark_rule, active_status
```

각 table·column에 최소한 다음을 기록한다.

- table grain, PK·FK·업무키, retention, synthetic 여부
- 물리·논리 이름, source type, Trino type, nullable 이유
- 금액의 단위·세금·취소 포함 여부
- timestamp timezone과 event-time 의미
- ID가 source-local인지 통합 ID인지
- sensitivity, masking, quality, preprocessing 규칙

seed 규칙:

1. 실제 사람·연락처·예약번호 형태를 모사하지 않는다.
2. 고정 seed와 scenario version을 사용한다.
3. 정상·취소·빈 결과·null·중복·orphan·경계 시각을 포함한다.
4. 동일 로컬 ID 문자열만으로 source를 자동 연결하지 않는다.
5. 파일 용량이 큰 생성 결과는 저장소 정책에 따라 commit하지 않고 생성 script와 checksum을 관리한다.

### 5.2 Identity·시간·JOIN

- 교차 고객 연결은 CRM bridge를 유일한 기준으로 한다.
- 한 로컬 ID의 복수 활성 회원 매핑을 차단한다.
- 등급은 현재값이 아니라 거래 event time의 유효 이력을 기본으로 한다.
- 상대 기간은 R1 time policy가 만든 절대 parameter만 사용한다.
- SQL의 `now()`·`current_date` 직접 사용을 금지한다.
- JOIN Registry에는 좌·우 URN/field, cardinality, temporal condition, null policy, duplication risk, 승인 사용처, version을 넣는다.
- JOIN 전후 row count와 metric 증폭 여부를 검사한다.

### 5.3 DataHub

1. source별 platform instance와 recipe를 분리한다.
2. schema·description·owner·domain·tag·sensitivity·synthetic·quality를 수집한다.
3. ingestion 실행 ID, 시작·종료, 상태, asset 수를 기록한다.
4. 검색 결과의 URN을 Context 후보와 결과 출처에 사용한다.
5. DataHub 설명은 탐색용이며 metric·JOIN·권한의 최종 승인은 R1/R4 계약을 따른다.
6. 색인 지연·pagination·asset 없음·접근 거부를 서로 다른 오류로 반환한다.

### 5.4 Trino와 Adapter

1. catalog별 read-only account와 source 격리를 확인한다.
2. source와 Trino의 타입·null·timezone 변환을 비교한다.
3. 단독 조회 후 승인된 2-source, 3-source 순으로 확장한다.
4. query ID, state, page/next URI, stats, warnings를 정규화한다.
5. timeout 뒤 실제 query 상태와 cancel 결과를 확인한다.
6. adapter는 G1/G2/G3를 판정하지 않는다.
7. R4에는 fake와 실제 adapter가 같은 interface를 제공한다.
