## 0. 역할 한 문장

송민지는 사용자가 질문·상태·근거·표·차트를 이해하고 검증된 Artifact를 편집·승인·반복 실행 가능한 보고서로 만드는 frontend와 Report domain을 담당한다.

## 1. 최종 책임과 경계

### 1.1 R5 최종 책임

- G1 재질문, G2 차단, G3 증적 실패, timeout, 빈 결과, 부분 실패 UI
- Chat Artifact를 Report block으로 삽입하는 흐름
- Report Definition·Version·Run·Block domain
- Report router/API 독립 module과 migration proposal
- 12-column 기반 보고서 편집기와 승인 전 변경

### 1.2 R5가 구현하지 않는 것

- 루트 Compose·CI·통합 릴리스: R1 박준희

- LLM·prompt·model serving: R3 윤대성
- 공통 FastAPI·Controller·Gate·worker·migration chain: R4 김재홍

### 1.3 I5 이후 후속 범위

다음은 I5 이후 별도 단계에서 구현한다. 현재 P0/P1·I5가 끝나지 않았다는 이유가 되지 않으며, R1이 후속 실행 묶음을 승인하기 전에는 route와 메뉴를 비활성화한다.

- MCP Tool 관리
- 사내 운영 문서 RAG
- ML-as-a-Tool
- 고객 360 전용 기능
- 외부 보고서 배포
- 복잡한 자유 cron

기존 UI에 해당 화면용 고정 테스트 데이터(fixture)가 있어도 P0/P1보다 우선하지 않는다.

### 3.3 공통 수행 순서

1. 기획서 사용자 시나리오와 R1 화면 수용 기준을 읽는다.
2. 현재 `app/react`와 `app/enterprise-react` 중 활성 기준을 확인하고 I0 결정 전 병합하지 않는다.
3. R4 OpenAPI example로 frontend type과 mock을 먼저 만든다.
4. success만 만들지 않고 empty·blocked·partial·failed fixture를 함께 만든다.
5. mock UI를 독립적으로 검증한다.
6. Report module은 공통 backend와 분리해 작성한다.
7. router·migration 등록 요청을 R4에 넘긴다.
8. 실제 API 연결 후 mock과 response drift를 검사한다.
9. frontend Dockerfile과 build/health 요구를 R1에 전달한다.

### 3.4 push하면 자동으로 도는 검사 (GitHub Actions)

개인 브랜치 `minji`에 push하면 GitHub Actions가 자동으로 실행된다. **자동 검사 통과는 기계 검증이 끝났다는 뜻일 뿐, R1의 제품 수용·계약 Freeze·Gate 승인을 대체하지 않는다.** 판정 기준의 단일 출처는 `docs/markdown/collaboration/Gate_실행_카드_원장.md`다.

| Job | 무엇을 보는가 | R5에서 |
|---|---|---|
| `role-scope` | `origin/dev` 대비 변경한 파일이 이번 실행 묶음의 `ALLOWED_PATHS` 안인지, 공백·충돌 표시가 없는지, handoff manifest가 정합한지 | **실행** |
| `python-contracts` | Python compile 검사와 `tests` 전체 실행 | **실행** |
| `document-quality` | 문서 정책, WBS 형식, 일일보고 형식 검증 | **실행** |
| `frontend-contracts` | `npm ci` 재현 설치, production build, 화면 계약 test | **실행** |
| `compose-config` | DataHub service fragment와 `dev`·`full`·`split-host` profile 설정 검증 | 건너뜀 |
| `quality-gate` | 위 결과 집계와 최종 통과 판정, R1 대시보드 출력 | **실행** |

> 현재 CI 실행 범위와 실패 판정은 `docs/markdown/collaboration/README.md`를 단일 기준으로 확인한다. 이 매뉴얼에는 R5 소유권과 카드별 추가 검증만 유지하고 시점별 공통 CI 동작은 복제하지 않는다.

**가장 흔한 실패 원인은 허용 경로 침범이다.** `ALLOWED_PATHS` 밖 파일을 하나라도 수정하면 `role-scope`가 FAIL하고 Summary에 침범한 경로가 그대로 출력된다. 다른 역할 파일이 필요하면 직접 고치지 말고 change request로 넘긴다.

#### handoff manifest

통합 판정(`REVIEW`)을 요청하기 전 `handoffs/<EXECUTION_BUNDLE_ID>.json`을 제출한다. 초안은 아래 명령으로 만든다. 이미 제출된 manifest는 덮어쓰지 않는다.

```text
python .github/scripts/gate_scope.py --branch minji --base origin/dev --head HEAD --mode merge-base --write-handoff
```

필수 항목은 13개다. `EXECUTION_BUNDLE_ID`, `ROLE`, `BRANCH`, `BASE_SHA`, `RESULT_SHA`, `COMPLETED_CARDS`, `CHANGED_FILES`, `CONTRACT_VERSIONS`, `TEST_RESULTS`, `NOT_RUN`, `CHANGE_REQUESTS`, `RESIDUAL_RISKS`, `EXTERNAL_APPROVAL_REQUIRED`. 초안은 `COMPLETED_CARDS`가 비어 있고 `TEST_RESULTS`에 안내 문구가 들어 있으므로 반드시 실제 값으로 채운다.

#### 잔여 위험을 적으면 어떻게 되는가

**차단되지 않는다. 적어야 한다.**

| 판정 | 언제 | CI 차단 |
|---|---|:---:|
| `PASS` | 경로·필수 필드·검증이 모두 정상 | — |
| `FAIL` | 허용 경로 침범, 필수 필드 누락·형식 오류, `FAIL`·`BLOCKED` 검증 결과 | **차단** |
| `REVIEW_REQUIRED` | `NOT_RUN`·`CHANGE_REQUESTS`·`RESIDUAL_RISKS`·`EXTERNAL_APPROVAL_REQUIRED`에 값이 있음 | 차단하지 않음 |
| `NOT_RUN` | 아직 manifest를 내지 않음 | 차단하지 않음 |
| `N/A` | `MERGED_DEV`·`VERIFIED_GATE`라 새 handoff가 필요 없음 | — |

미실행 검증·잔여 위험·외부 승인 요청은 R1 검토 큐에 올라갈 뿐 CI를 실패시키지 않는다. 반대로 **실행하지 않은 검증을 `PASS`로 적는 것은 증거 위조로 취급**하며, 발견 시 실행 묶음이 원 소유 역할로 반환된다. 모르면 비워 두지 말고 `Not Run`과 사유를 적는다.

## 5. 사용자 경험 상세

### 5.1 Chat

필수 영역:

- 질문 입력·후속 질문
- 처리 상태와 취소·재시도
- 설명·표·차트
- metric·단위·기간·`as_of`·filter
- DataHub 자산·source·근거
- Artifact·trace 연결
- Report에 담기

사용자에게 노출하지 않는 것:

- DB 원문 오류와 stack trace
- credential·민감 parameter
- 내부 allowlist·정책 상세
- 숨겨진 prompt와 모델 사고 과정

### 5.2 상태·오류

API 실행 상태:

```text
idle
queued
running
success
blocked
partial
failed
cancelled
```

사용자 화면 상태:

```text
LOADING
EMPTY
READY
DELAYED
PARTIAL
ERROR
FORBIDDEN
INSUFFICIENT_EVIDENCE
CANCELLED
```

API 실행 상태는 실제 처리 진행을 뜻하고, 사용자 화면 상태는 무엇을 보여줄지를 뜻한다. 예를 들어 실행 `success` 결과가 0건이면 화면은 `EMPTY`, 일부 source만 성공하면 실행과 화면 모두 `PARTIAL`로 표시한다. 이 매핑은 I1 UI 계약에서 고정한다.

구분해야 할 사례:

- G1 문맥 부족: 필요한 조건만 재질문
- 권한 거부: 내부 정책 없이 안전한 안내
- G2 차단: 실행되지 않았음을 명시
- Trino/source 실패: 재시도 가능 여부와 실패 source
- G3 실패: 결과를 정상 표·차트로 표시하지 않음
- 정상 0건: 실패가 아니라 조건과 빈 결과를 표시
- 부분 실패: 성공·실패 source/block을 분리
- stale/cached: 기준 시각과 watermark 표시
- cancelled: 취소 시각·범위와 새 실행 방법 표시

색상, 아이콘, 문구를 함께 사용하고 스크린리더가 상태 변화를 인식하게 한다.

### 5.3 Evidence·표·차트

- API가 반환한 shaped result만 렌더링한다.
- frontend 계산으로 공식 metric을 만들지 않는다.
- 표 헤더·단위·정렬·null·빈 값을 명시한다.
- 차트 축·단위·범례·sampling 여부를 표시한다.
- source URN은 사용자 친화 이름과 함께 상세에서 확인 가능하게 한다.
- 민감 SQL·parameter는 role과 API redaction 결과를 따른다.
- 모든 업무 결과 가까이에 `synthetic`, seed, schema version, `as_of`, timezone을 표시한다.

## 6. Report 상세

### 6.1 Domain 원칙

- Report Definition과 Run을 분리한다.
- 승인된 Definition Version은 immutable이다.
- 편집은 draft version에서 수행한다.
- Run은 실행 당시 definition version·`as_of`·policy·Context·watermark를 저장한다.
- Block Run은 query/artifact ID, snapshot/checksum, 상태를 가진다.
- 과거 Run을 최신 Definition으로 다시 해석하지 않는다.

### 6.2 Chat↔Report

1. Chat 성공 Artifact에서 `보고서에 담기`를 선택한다.
2. Artifact ID와 질문·조건·기간·출처·chart spec을 Report block에 연결한다.
3. 사용자는 block 제목·크기·위치를 draft에서 편집한다.
4. 승인 동작으로 새 immutable version을 만든다.
5. 수동 또는 schedule Run이 같은 R4 worker 경로를 호출한다.
6. Run History에서 block별 성공·실패·partial·기준 시각을 확인한다.

기존 block은 AI가 자동 덮어쓰지 않는다. 변경 전·후 요약과 사용자 승인을 거친다.

### 6.3 Report API·Migration 경계

R5가 제공:

- Report domain/repository/router 독립 module
- request/response example
- ReportJobPayload와 event contract
- migration proposal
- contract/unit test

R4가 수행:

- 공통 FastAPI router 등록
- 인증·권한 middleware 연결
- migration head 조정
- 영속 job store·worker·schedule 실행; 외부 queue는 필요가 확인될 때만 분리

### 6.4 Schedule

MVP 주기:

- daily
- weekly
- monthly

요구:

- timezone과 다음 실행 시각 표시
- 활성·비활성·소유자 표시
- manual/schedule 동일 실행 경로
- 수동 실행 재현성·idempotency·부분 실패·취소가 통과하기 전 schedule 활성화 금지
- 실행 시작 시 하나의 `as_of`
- 중복 클릭·재전달 idempotency
- block timeout·cancel·partial 상태

자유 cron과 외부 배포는 P2로 미룬다.

## 7. Catalog·Audit·접근성

Catalog:

- 5개 logical source와 engine
- 활성 상태·최근 ingestion·담당 조직
- asset·column·description·quality
- DataHub URN과 Trino FQN
- API 검색을 사용했다는 trace

Audit:

- `request_id`, 사용자, 기간, 상태 검색
- `conversation_id`, `route_type`, `as_of`, `time_policy_version`, `entitlement_hash`
- `context_release`, template/SQL plan cache, model/prompt/SQL policy와 G1·G2·G3 결과
- query ID 또는 result cache key, artifact, report definition/plan/run 연결
- redaction된 오류와 source/block 상태

접근성:

- keyboard로 질문·표·editor·modal 조작
- focus 순서와 visible focus
- label·heading·table semantics
- 상태 변화 live region
- 색상 외 텍스트·아이콘
- mobile/desktop 핵심 동선

UI role 숨김은 보안 통제가 아니며 API 권한 결과를 따른다.

## 10. 최종 체크리스트

- [ ] 활성 frontend 하나가 결정되고 이중 구현이 없다.
- [ ] API 실행 상태와 `LOADING·EMPTY·READY·DELAYED·PARTIAL·ERROR·FORBIDDEN·INSUFFICIENT_EVIDENCE·CANCELLED` 화면 상태가 구분된다.
- [ ] 표·차트·설명이 같은 shaped result를 사용한다.
- [ ] metric·filter·기간·`as_of`·source·근거가 결과 가까이에 표시된다.
- [ ] 모든 업무 결과에 `synthetic`, seed, schema version, timezone이 표시된다.
- [ ] G3 실패 결과가 정상 표·차트로 보이지 않는다.
- [ ] Chat Artifact ID가 Report block과 Run까지 유지된다.
- [ ] Report Definition Version과 Run이 분리되고 승인본이 immutable이다.
- [ ] manual·schedule이 같은 worker contract를 사용한다.
- [ ] block 부분 실패를 전체 성공으로 표시하지 않는다.
- [ ] Catalog 상태가 R2 fixture와 일치한다.
- [ ] Audit에서 request→context→query→artifact→report를 찾을 수 있다.
- [ ] production build·E2E·keyboard·focus·상태 접근성을 검증했다.
- [ ] P2와 고객 360은 I5 이후 후속 단계로 남아 있고, 현재 route·메뉴·완료율에서 비활성이다.
