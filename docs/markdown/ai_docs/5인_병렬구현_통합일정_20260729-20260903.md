## 2. 일정 운영 원칙

1. 기획서와 각 역할 매뉴얼을 함께 AI에 제공한다.
2. 한 AI에는 한 번에 현재 통합 Wave의 역할별 실행 묶음 하나를 준다. 묶음의 `TASK_CARD_RANGE` 안에서는 카드 번호 순서대로 재승인 없이 진행한다.
3. 실행 묶음 번호·범위·상태·발행 값은 `docs/markdown/collaboration/Gate_실행_카드_원장.md`에서 확인한다.
4. 각 사람은 자기 개인 브랜치와 별도 working directory를 사용한다.
5. 실행 묶음에는 `EXECUTION_BUNDLE_ID`, `TARGET_INTEGRATION_GATE`, `CHECKPOINT_GATES`, `TASK_CARD_RANGE`, `BASE_SHA`, `ALLOWED_PATHS`, 완료·검증·중단 조건을 기록한다.
6. 역할 소유 파일 밖 변경은 직접 수정하지 않고 change request로 넘긴다.
7. API·DB·model 연결 전에는 versioned fixture와 fake adapter로 병렬 개발한다.
8. `CHECKPOINT_GATES`에서는 계약·증거를 확인한 뒤 역할 branch에서 계속 진행한다. 현재 일정에서는 I0만 단독 checkpoint로 사용하며, 목표 통합 Gate에 도달하면 변경·검증·handoff를 제출하고 R1이 소비 가능한 완료분만 `dev`에 병합한다.
9. R1은 루트 Compose·env·CI를 마지막에 통합하지만 개별 서비스 내부를 대신 수정하지 않는다.
10. `fixture 통과`, `dev 병합`, `통합 Gate 통과`를 별도 상태로 관리한다.
11. P2 MCP·문서 RAG·ML Tool·외부 Report 배포와 선택 고객 360은 별도 승인 전까지 제외한다.
12. 8월 28일 기능 동결, 9월 2일 코드·data·model·prompt·policy 동결, 9월 3일 발표를 기준으로 한다.
13. 기획서의 개발 계획은 10주 참조안이지만 본 일정은 7월 29일~9월 3일로 압축한다. 따라서 대표 2-source deterministic slice를 먼저 완성하고 5 source는 catalog 단독·승인된 2~3-source JOIN으로 검증한다.

## 3. Gate와 병합 원칙

| Gate | 목표 | 통과 증거 | 최종 판정 |
|---|---|---|---|
| I0 기준 정렬 | 역할·범위·backend·파일 소유권 확정 | 결정 원장, branch mapping | R1, 전원 확인 |
| I1 Contract Freeze | metric/time/schema/API/model/Report/health 계약 | versioned contract·fixture | R1 |
| I2 Deterministic Slice | 대표 질문을 LLM 생성 없이 전체 왕복 | result hash·trace·화면 | R1 |
| I3 General LLM | 일반 질문과 Node 1·2·2′·3 통합 | 필수 30건 subset·trace | R1 |
| I4 Reporting | Chat→Artifact→Report→Run History | 수동·예약·partial trace | R1 |
| I5 Release | 보안·장애·복구·재현성·발표 환경 | release manifest·runbook | R1, 전원 확인 |

Gate는 계약·증거 checkpoint와 실제 통합 Gate를 구분한다. I0에서는 역할 구현을 자동 병합하지 않고, Wave 1의 I1·Wave 2의 I2·Wave 3의 I3·Wave 4의 I4~I5에서 소비 가능한 완료분을 통합한다.

달력상 checkpoint 도달이나 부분 구현만으로 병합하지 않는다. 각 역할은 승인된 Wave 범위에서 fake/fixture로 최대한 독립 진행하고, 목표 통합 Gate 도달·범위 완료·역할 밖 변경 필요·계약 충돌·필수 검증 실패 시 멈춘다.

발표 당일에는 승인된 `main` SHA와 고정 version만 사용한다. 실제 경로 실패 시 사전 검증한 fixture·capture를 사용하되 실시간 성공으로 표현하지 않는다.

## 6. 매일 운영

### 오전 공유

```text
담당자/branch:
현재 작업 카드:
사용 contract/fixture version:
어제 완료 증거:
오늘 완료 목표:
blocker:
다른 역할 변경 요청:
```

### 오후 통합 확인

1. 계약·fixture version 변화 확인
2. 다른 역할 파일을 직접 수정한 변경이 없는지 확인
3. 다음 병합 branch 한 개 선택
4. 병합 직후 영향 test 실행
5. 실패를 소유 역할에 반환
6. Gate 직전에는 신규 카드보다 회귀·handoff 우선

카드 상태:

```text
READY
IN_PROGRESS
REVIEW
BLOCKED
MERGED_DEV
VERIFIED_GATE
```
