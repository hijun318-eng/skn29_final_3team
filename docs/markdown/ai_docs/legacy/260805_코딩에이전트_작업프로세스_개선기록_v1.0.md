이 문서는 코딩 에이전트 협업 과정에서 확인한 비효율, 적용한 개선, 검증 결과를 한 번에 확인하기 위한 과거 기록이다. 현재 규칙이나 실행 상태를 판단할 때는 위의 현재 운영 기준을 다시 확인한다.

## 1. 개선 배경

역할별 파일 소유권과 승인 Gate는 안전성을 높였지만 실제 작업에서는 다음 문제가 반복됐다.

1. `BASE_SHA`가 최신 `dev`와 다르다는 이유만으로 변경 충돌 여부와 관계없이 새 실행 token을 기다렸다.
2. `BLOCKED` 상태의 다음 조치가 명확하지 않아 작업자가 기존 카드 재개 가능 여부를 다시 확인해야 했다.
3. R1·R2·R3·R4가 종료 상태이고 R5만 차단됐을 때 전체 진행이 한 역할에 직렬로 묶였다.
4. CI dashboard가 현재 Wave와 무관하게 다음 Gate를 `I2`로 고정 표시했다.
5. 모든 개인 branch에서 전체 Python test를 반복해 역할 변경과 무관한 검증 비용이 발생했다.
6. 문서 규칙은 `BLOCKED` 카드의 제품 코드 변경을 금지했지만 기존 자동 검사는 원래 `ALLOWED_PATHS`를 계속 허용했다.

## 2. 개선 원칙

개선은 승인·보안 경계를 줄이지 않고 불필요한 대기와 중복 실행만 제거하는 방향으로 정했다.

- 기준 SHA가 오래됐다는 사실과 실제 파일 충돌을 분리한다.
- 파일 소유권은 유지하고 의존성이 없는 역할은 병렬로 검증한다.
- 차단된 작업은 새 owner-scoped `REWORK` 카드로만 재개한다.
- 개인 branch는 역할 대상 검증에 집중하고 통합 branch에서 전체 회귀를 수행한다.
- 외부 비용, secret, 제품 Gate와 최종 수용 결정은 기존 승인 경계를 유지한다.

## 3. 적용 과정

### 3.1 현재 상태와 병목 확인

공식 WBS와 활성 Gate 원장을 대조했을 때 실행 WBS는 99개 중 완료 61개, 진행 18개, 대기 19개, 차단 1개였다. 활성 역할 상태는 R1 `VERIFIED_GATE`, R2~R4 `MERGED_DEV`, R5 `BLOCKED`였다.

R5의 차단 원인은 실제 Report API 브라우저 검증과 UI 요청 경쟁 상태였다. R5 카드의 허용 경로에는 backend·migration·worker가 포함되지 않아 다른 역할 변경이 필요할 경우 기존 카드만으로 해결할 수 없었다.

### 3.2 기준 SHA 충돌 판정 추가

`.github/scripts/gate_scope.py`에 다음 판정을 추가했다.

| 판정 | 의미 | 처리 |
|---|---|---|
| `SYNCED` | 현재 기준 branch가 작업 HEAD에 포함됨 | 계속 진행 |
| `SAFE_STALE` | `dev`가 앞서지만 역할 변경 파일과 겹치지 않음 | 기존 token으로 계속 진행 |
| `REFRESH_REQUIRED` | 기준 이후 `dev`와 역할 작업이 같은 파일을 변경함 | 최신 SHA로 카드 재발행 |
| `DIVERGED` | 발행 기준과 현재 기준의 Git 이력이 갈라짐 | 카드 재발행 및 충돌 검토 |
| `N/A` | 차단·종료 상태로 구현 대상이 아님 | 신규 구현 금지 |

이 판정으로 단순 SHA 불일치는 경고 근거가 되고, 실제 같은 파일 충돌만 재승인 조건이 됐다.

### 3.3 차단 상태의 실행 경계 일치

`BLOCKED` 카드에서는 개인 일일보고와 공용 보고 경로만 허용하도록 자동 검사를 변경했다. 제품 코드를 다시 수정하려면 R1이 owner-scoped `REWORK` 묶음을 발행해야 한다.

둘 이상의 역할이 필요한 경우 한 카드에 파일 소유권을 섞지 않고, 같은 checkpoint를 공유하는 역할별 카드를 병렬 발행한 뒤 생산자 contract를 소비자보다 먼저 통합하도록 `AGENTS.md`에 기록했다.

### 3.4 현재 Gate 자동 선택

CI dashboard의 고정 `--next-gate I2`를 `--next-gate auto`로 교체했다. 자동화는 활성 묶음의 목표 Gate를 먼저 사용하고, 활성 묶음이 없으면 마지막 `VERIFIED_GATE` 다음 단계를 선택한다.

2026-08-05 검증에서는 R5 차단 상태와 `I5` 발행 준비를 표시하고 다음 조치로 `Issue owner-scoped REWORK bundle`을 출력했다.

### 3.5 CI 검증 범위 분리

개인 branch와 통합 branch의 Python 검증을 다음처럼 나눴다.

| Branch | 기본 Python 검증 |
|---|---|
| `junhee` | `tests/integration` |
| `seung` | `tests/data` |
| `daesung` | `tests/ai` |
| `jaehong` | `tests/backend` |
| `minji` | Report OpenAPI·등록 contract test |
| `dev` | 전체 `tests` |

역할 카드의 `TEST_COMMANDS`가 기본 CI보다 넓으면 선언된 생산자·소비자 검증을 추가 실행한다. 개인 branch 통과를 전체 저장소 통과로 표현하지 않는다.

### 3.6 변경 범위 기반 CI·병합 검증

2026-08-06에는 역할별 test 분리 이후에도 남은 반복 검사를 줄이고 실패한 source의 통합을 차단했다.

1. workflow 변경은 전체 job, 일반 변경은 Python·문서·frontend·Compose 중 영향받은 job만 실행한다.
2. 문서 검사는 고정 목록 대신 실제 변경된 Markdown만 검사한다.
3. 같은 branch에 새 push가 들어오면 이전 CI를 자동 취소한다.
4. 구현 전에 `--check-planned-path`로 예상 변경 경로가 현재 카드의 `ALLOWED_PATHS` 안인지 확인한다.
5. 개인 branch를 `dev`에 병합하기 전에 push된 source SHA의 CI가 `completed/success`인지 확인한다.
6. 여러 branch를 한 번에 통합할 때 날짜별 팀 요약과 주간보고는 마지막 source 뒤 한 번만 commit한다.

### 3.7 역할 작업 bootstrap

작업 위치와 실행 권한을 여러 문서에서 수동으로 조합하던 절차를 다음 명령 하나로 묶었다.

```powershell
python .github/scripts/gate_scope.py --branch <본인 branch> --bootstrap
```

bootstrap은 현재 worktree root, 실제 branch, dirty 상태, 마지막 non-`PLANNED` 카드와 상태를 확인한다. 카드가 `READY`·`IN_PROGRESS`가 아니거나 실제 branch가 `PERSONAL_BRANCH`와 다르거나 기존 변경이 있으면 구현을 차단한다.

문서 읽기도 다음처럼 구분했다.

| 읽기 범위 | 문서 |
|---|---|
| 전체 읽기 | `AGENTS.md`, Gate 실행 카드 원장, 해당 역할 매뉴얼 |
| 현재 카드 관련 절 읽기 | 기획서, WBS, 협업 규칙, AI 개발 환경, 통합 일정 |

이 구분으로 긴 기획서·WBS를 매 작업마다 전부 읽는 비용을 줄이면서 역할·Gate·소유권 경계는 전체 확인한다.

### 3.8 다중 branch 사전점검과 카드 종료

R1이 여러 개인 branch를 통합할 때 branch마다 반복하던 worktree·SHA·CI 확인을 한 번에 실행할 수 있게 했다.

```powershell
python .agents/skills/merge-branch-to-dev/scripts/check_merge_preflight.py --phase batch --sources junhee seung daesung jaehong minji
```

이 명령은 `dev`와 `origin/dev` 일치, 각 개인 branch worktree 위치, dirty 상태, local·remote SHA 일치와 source CI 성공을 읽기 전용으로 검사한다. 실제 merge·push는 계속 명시적 사용자 승인과 기존 순서에 따라 수행한다.

병합 뒤 실행 카드가 `IN_PROGRESS`로 남아 같은 작업을 재개하는 문제도 막았다. 통합 기록 commit에서 source 카드를 `MERGED_DEV`로 변경하고 `RESULT_SHA`·`RESULT_CI`를 기록하며, final 사전검사는 카드가 `MERGED_DEV`·`VERIFIED_GATE`가 아니면 실패한다.

### 3.9 공통 지침 단일화

역할 매뉴얼 5개에 복제돼 있던 과거 CI 설명을 제거했다. 현재 CI 실행 범위와 실패 판정은 `docs/markdown/collaboration/README.md`만 기준으로 확인하고, 역할 매뉴얼에는 소유권·카드별 추가 검증만 유지한다. 이로써 CI가 바뀔 때 다섯 매뉴얼을 각각 갱신하지 않아 생기던 내용 불일치를 줄였다.

## 7. 남은 항목

1. R5 실제 Report API 작업은 기존 `BLOCKED` 카드를 재개하지 않고 새 owner-scoped `REWORK` 카드 발행이 필요하다.
2. 브라우저 fixture/API 흐름 자동화는 기존 dependency가 없어 이번 개선에서 추가하지 않았다. 반복 수동 검증 시간이 다시 병목이 될 때 승인된 browser test 도구로 편입한다.
3. batch 사전점검은 읽기 전용이다. 자동 merge·push는 권한과 충돌 해결 범위를 넓히므로 도입하지 않았다.
4. bootstrap의 clean 성공 확인과 `dev` 전체 test는 이번 변경을 commit·push한 뒤 개인 branch·`dev` CI에서 최종 확인한다.

## 8. 재사용 점검표

- [ ] 작업 시작 전 `--bootstrap`이 branch·dirty 상태·현재 카드를 통과했는지 확인한다.
- [ ] bootstrap의 전체 읽기 문서는 EOF까지, 관련 읽기 문서는 현재 카드 관련 절을 확인한다.
- [ ] 기준 SHA가 다르면 같은 파일 변경 여부부터 확인한다.
- [ ] `SAFE_STALE`이면 기존 token으로 진행하고 `REFRESH_REQUIRED`·`DIVERGED`이면 R1에게 반환한다.
- [ ] `BLOCKED` 카드에서 제품 코드를 수정하지 않는다.
- [ ] 개인 branch에서 역할 test와 카드의 추가 contract test를 실행한다.
- [ ] 여러 branch 통합 전 `--phase batch --sources ...`로 모든 worktree·SHA·CI를 확인한다.
- [ ] 통합 기록 commit에서 source 카드를 `MERGED_DEV`로 종료하고 결과 SHA·CI를 기록한다.
- [ ] `dev` 통합 후 전체 test와 보고 통합을 확인한다.
- [ ] 실행하지 못한 검증은 `Not Run` 또는 `Blocked`와 사유로 기록한다.
