> 문서 상태: 팀 검토용 초안  
> 작성 기준일: 2026-07-28  
> 대상 역할: R2 데이터 플랫폼·메타데이터·연합조회 담당

## 0. 5개 AI 공통 실행·충돌 방지 계약

### 0.1 R2 독립 소유 영역

R2 AI가 직접 수정할 기본 영역:

```text
data/**
source별 schema·seed 영역
DataHub recipe·metadata 설정 영역
Trino catalog·connector 설정 영역
DataHub·Trino integration adapter 영역
데이터 무결성·query adapter 단위 test 영역
```

R2 AI가 직접 수정하지 않는 영역:

```text
공통 OpenAPI·Pydantic contract
Controller·G1·G2·G3
LLM prompt·model adapter
Report domain·frontend
전체 Compose·CI·secret 정책
Alembic 공통 migration chain
root dependency 파일
```

실제 경로는 I0에서 확정한다. 경로가 확정되기 전에 새로운 디렉터리 구조를 임의 생성하지 않는다.

### 0.2 공유 파일 단일 편집자

| 공유 영역 | 단일 편집자 | R2 변경 방법 |
|---|---|---|
| 공통 API·schema | R3 | URN/FQN·query adapter 요구사항 전달 |
| FastAPI app 등록 | R3 | adapter factory interface 전달 |
| root dependency | R5 | driver·library 이름, 버전 근거 전달 |
| Docker Compose | R5 | DB·DataHub·Trino service fragment 전달 |
| `.env.example` | R5 | 필요한 변수 이름·설명 전달 |
| 평가 schema | R1 | 데이터 field·정답 항목 변경 요청 |

### 0.3 AI 작업 입력

```text
ROLE_ID=R2
TASK_CARD_ID=R2-xx
REPOSITORY_ROOT=<절대 경로>
BASE_BRANCH=<통합 기준 branch>
BASE_SHA=<작업 시작 commit SHA>
CONTRACT_VERSION=<현재 승인 metric/time contract version>
FIXTURE_VERSION=<현재 source/schema version>
ALLOWED_PATHS=<이 카드에서 수정 가능한 경로>
FORBIDDEN_PATHS=<수정 금지 경로>
ACCEPTANCE_CRITERIA=<완료 조건>
EXTERNAL_ACTION_PERMISSION=<외부 실행·설치·데이터 전송 허용 여부>
STOP_CONDITION=<중단·질문 조건>
```

각 사람은 `docs/markdown/collaboration/README.md`에 정해진 자기 개인 branch(`junhee`, `minji`, `seung`, `daesung`, `jaehong` 중 배정된 branch)와 자기 clone을 사용한다. 다섯 AI가 같은 working directory를 공유하지 않는다. AI는 승인 없이 stage·commit·push·merge하지 않고, 사람이 검증 후 통합한다. 통합 중 공유 파일 변경은 해당 단일 작성자에게 되돌린다.

### 0.3A AI에 전달할 실행 프롬프트

```text
너는 ROLE_ID 담당 AI다. 기준 기획서와 이 역할 매뉴얼을 모두 읽되, 이번에는 TASK_CARD_ID 하나만 수행한다.
먼저 repository root, 적용되는 AGENTS.md, branch, BASE_SHA, dirty worktree, 선행 계약·fixture version을 읽기 전용으로 확인한다.
확인된 사실·가정·blocker와 이 카드의 입력·출력·완료 조건을 짧게 보고한 뒤 작업한다.
ALLOWED_PATHS만 수정하고 FORBIDDEN_PATHS와 다른 역할 소유 파일은 수정하지 않는다.
공유 파일 변경이 필요하면 독립 module·service fragment·contract-change-request를 단일 작성자에게 handoff한다.
기존 변경을 보존하고 승인 없는 설치·비용·배포·데이터 전송·stage·commit·push·merge를 하지 않는다.
완료 조건에 맞는 검증을 실제 실행하고, 미실행 검증은 통과로 쓰지 않는다.
마지막에는 매뉴얼의 handoff 형식으로 변경 파일, contract·schema version, 검증, 미검증, 남은 위험을 보고한다.
```

### 0.4 AI 작업 순서

1. `AGENTS.md`, 기준 기획서, 이 매뉴얼, 협업 README를 읽는다.
2. branch·`git status --short`를 확인하고 기존 변경을 보존한다.
3. 한 작업 카드만 수행한다.
4. 선행 contract가 없으면 versioned fixture를 생산하고 실제 계약으로 확정하지 않는다.
5. 공유 파일 변경이 필요하면 직접 수정하지 않고 변경 요청을 남긴다.
6. 검증과 인수인계 후 작업을 종료한다.

## 1. 이 역할의 최종 책임

R2는 5개 논리 source의 합성 데이터를 재현 가능하게 만들고, DataHub 자산과 Trino 실행 source를 연결하며, R3가 안정적으로 호출할 DataHub·Trino adapter까지 책임진다.

최종 책임:

- 5개 source schema
- synthetic seed와 schema version
- source 내부 참조 무결성
- 교차 source identity bridge
- 회원 등급 event-time 이력
- DataHub ingestion recipe와 자산 URN
- Trino catalog와 타입 mapping
- 승인 JOIN과 cardinality
- 대표 질문의 정답 SQL·결과 hash
- source watermark
- DataHub Search·Graph adapter
- Trino query·cancel·status adapter
- source health adapter

R2가 단독 결정하지 않는 항목:

- metric의 업무 의미: R1과 공동 승인
- Context Package와 Gate 정책: R3와 공동 승인
- 인프라 배포·보안 최종 합격: R5가 독립 검증

## 1.1 R2 작업 패키지와 병렬성

## 4. 단계별 상세 작업

### 단계 R2-01 — 엔진·source 구성표 작성

목적: 5개 논리 source와 4종 엔진을 혼동하지 않게 한다.

수행:

1. source 이름, engine, DB 이름, schema, account 역할을 정리한다.
2. PMS와 연회 PostgreSQL을 별도 DB·계정·catalog로 분리한다.
3. ingestion account와 query account를 구분한다.
4. 각 engine의 후보 image·version·driver를 작성한다.
5. R5와 함께 실제 기동 가능한 조합을 검증한다.
6. 최종 버전과 실패한 후보를 결정 기록에 남긴다.

출력:

| source ID | engine | DB/schema | ingestion account | query account | DataHub instance | Trino catalog |
|---|---|---|---|---|---|---|

완료 기준:

- 5 source·5 credentials·5 recipe·5 catalog가 구분된다.

### 단계 R2-02 — 논리 데이터 모델 작성

PMS:

- guest
- reservation
- stay
- room
- room_revenue 또는 revenue fact

F&B POS:

- store
- item
- order
- order_line
- payment

CRM:

- member
- member_grade_history
- customer_identity_map
- point_transaction

시설:

- facility
- usage
- inspection
- incident

연회·매출:

- banquet_booking
- banquet_product
- banquet_revenue

수행:

1. entity별 PK를 정한다.
2. source 내부 FK를 정한다.
3. 상태값과 허용 전이를 정한다.
4. 금액·시간·ID 타입을 정한다.
5. nullable column과 의도한 orphan을 구분한다.
6. R1의 metric·scenario와 연결한다.

완료 증거:

- source별 entity·column·PK·FK 표
- 질문→entity mapping

### 단계 R2-03 — 물리 schema와 DDL 작성

수행:

1. 논리 모델을 engine별 DDL로 작성한다.
2. 각 engine의 identifier·timestamp·decimal 차이를 반영한다.
3. 금액 field는 부동소수 대신 명확한 정밀도 타입을 사용한다.
4. timezone 저장 규칙을 통일한다.
5. PK·unique·check·FK 제약을 가능한 DB 경계에서 적용한다.
6. DDL과 seed 실행을 분리한다.
7. schema version을 기록한다.
8. 재실행·rollback 방법을 작성한다.

검증:

- 빈 DB에서 DDL 실행
- DDL 재실행 시 의도한 처리
- 제약 위반 fixture 차단
- DB별 schema introspection

### 단계 R2-04 — Synthetic seed 설계

수행:

1. seed 번호를 고정한다.
2. 데이터 규모를 source별로 정의한다.
3. 실제 고객과 혼동될 이름·전화번호·이메일을 피한다.
4. source별 로컬 ID 형식을 다르게 만든다.
5. 정상·취소·누락·빈 결과를 포함한다.
6. R1의 시나리오 카드와 expected result를 연결한다.
7. 생성 순서를 FK 의존성에 맞춘다.
8. seed 실행 후 row count와 hash를 기록한다.

필수 metadata:

```text
synthetic=true
seed=<고정값>
schema_version=<버전>
generated_at=<시각>
scenario_version=<버전>
```

완료 기준:

- 같은 seed에서 같은 핵심 결과 hash가 나온다.
- seed 변경 시 version이 바뀐다.

### 단계 R2-05 — CRM Identity Bridge 구현

`customer_identity_map` 필수 field 후보:

```text
member_no
pms_guest_id
pos_customer_ref
facility_user_ref
banquet_customer_id
active_from
active_to
```

수행:

1. CRM SQL Server에 물리 table로 만든다.
2. source별 local ID와 `member_no`를 연결한다.
3. 한 local ID가 여러 활성 회원에 매핑되지 않게 한다.
4. 회원별 source ID 중복을 검사한다.
5. 의도한 미매핑 fixture를 별도 표시한다.
6. DataHub ingestion 대상에 포함한다.
7. Trino `crm` catalog에서 조회한다.
8. 별도 DataHub URN을 확보한다.

negative fixture:

- 중복 local ID
- 한 local ID의 활성 기간 중첩
- 존재하지 않는 member
- 필수 source ID 누락

### 단계 R2-06 — 회원 등급 이력 구현

`member_grade_history`:

```text
member_no
grade_code
valid_from
valid_to
```

규칙:

- 유효기간은 `[valid_from, valid_to)`
- `valid_from < valid_to`
- `valid_to`가 null이면 현재까지 유효
- 같은 회원의 기간 중첩 금지

검증 질문:

1. 거래 당시 GOLD, 현재 SILVER
2. 거래 당시 SILVER, 현재 GOLD
3. `valid_to`와 거래 시각이 같은 경계
4. 이력 공백 기간
5. 중첩 이력

완료 기준:

- event-time JOIN 결과가 R1 기대와 일치한다.

### 단계 R2-07 — Source 내부 참조 무결성 검사

검사:

- PK 중복
- FK orphan
- 상태 전이
- 예약·투숙·매출 시간 순서
- 취소 거래의 집계 제외
- 금액 음수·비정상 범위
- identity mapping cardinality
- 등급 기간 중첩
- timezone·기간 경계

각 검사는 실패 fixture를 한 개 이상 포함한다.

### 단계 R2-08 — 읽기 전용 계정 구성

수행:

1. source별 query account를 생성한다.
2. SELECT에 필요한 최소 권한만 부여한다.
3. ingestion account 권한을 별도로 둔다.
4. INSERT·UPDATE·DELETE·DDL을 실행해 차단을 확인한다.
5. 민감 column은 승인 view 또는 mask 정책과 연결한다.
6. R5가 독립 계정으로 동일 negative test를 실행하게 한다.

완료 기준:

- 애플리케이션 실수와 SQL 검증 실패가 있어도 원본 계정이 마지막 차단선으로 작동한다.

### 단계 R2-09 — DataHub recipe 작성

source별 수행:

1. connection과 platform instance를 정의한다.
2. schema/table include·exclude를 정의한다.
3. credential은 환경 변수로 분리한다.
4. owner·domain·tag·description 입력 방법을 정한다.
5. ingestion을 실행한다.
6. 실행 ID, 상태, 시작·종료 시각을 기록한다.
7. 기대 table·column 수와 비교한다.
8. 재실행 시 중복·누락을 검사한다.

5개 recipe 완료 기준:

- source별 자산이 서로 다른 platform instance로 보인다.
- `customer_identity_map`과 `member_grade_history`가 검색된다.

### 단계 R2-10 — DataHub metadata 보강

각 자산에 다음을 제공한다.

- source
- domain
- owner
- tag
- description
- 민감도
- 기준 시각
- metric 관련성
- 승인 JOIN 후보

주의:

- DataHub description은 탐색 정보다.
- metric·JOIN·권한의 최종 승인본은 Context Registry에 둔다.
- table 이름 번역만 description으로 사용하지 않는다.

### 단계 R2-11 — DataHub Search API 검증

수행:

1. 대표 질문의 핵심 용어로 검색한다.
2. asset URN, schema, column, owner, tag 반환을 확인한다.
3. 무관한 자산이 과도하게 상위에 나오면 description·term을 보강한다.
4. 권한 없는 자산 선필터에 필요한 domain·tag를 제공한다.
5. API 결과 fixture를 R3·R4에 전달한다.

완료 증거:

- 질문별 검색 결과 JSON
- 기대 URN 일치표

### 단계 R2-12 — Trino catalog 5개 구성

source별:

1. connector 설정을 작성한다.
2. query account를 연결한다.
3. catalog에서 schema·table을 조회한다.
4. 단일 source count와 기본 집계를 검증한다.
5. timestamp·decimal·boolean·string 타입을 확인한다.
6. predicate·aggregation pushdown을 확인한다.
7. query ID와 source query를 추적한다.

완료 기준:

- 5개 catalog가 각각 단독 조회된다.
- source 하나의 장애가 다른 catalog 권한을 우회하지 않는다.

### 단계 R2-13 — 타입 Mapping 검증

engine별 확인:

- timestamp와 timezone
- date
- decimal precision
- unsigned 또는 범위 차이
- boolean
- UUID·문자 ID
- nullable
- ClickHouse array·special type 사용 여부

수행:

1. 대표 타입 table을 만든다.
2. Trino 조회 결과와 원본 결과를 비교한다.
3. 문제 타입은 명시적 CAST 또는 schema 변경을 결정한다.
4. 원본·Trino·Context의 타입 표현을 연결한다.

### 단계 R2-14 — 승인 JOIN Registry 작성

각 JOIN:

| 항목 | 내용 |
|---|---|
| left URN/field | 좌측 자산·key |
| right URN/field | 우측 자산·key |
| cardinality | one-to-one, many-to-one 등 |
| null 처리 | 제외·유지 |
| temporal 조건 | event-time validity |
| 승인 상태 | active/inactive |
| owner | 승인자 |
| version | 정책 버전 |

검증:

- 정상 JOIN row count
- 중복 증폭
- null key
- 잘못된 key
- 비승인 JOIN
- temporal boundary

### 단계 R2-18A — DataHub·Trino·Source Health Adapter 구현

R3가 내부 client 구현을 중복하지 않도록 R2가 connector 차이를 숨기는 adapter를 제공한다.

#### DataHub adapter

```text
search_assets(query, platform_instance, domain, tag)
get_asset(urn)
get_schema(urn)
get_relationships(urn, max_hops)
get_ingestion_status(source_id)
```

수행:

1. DataHub Search·Graph API의 실제 응답을 내부 typed object로 변환한다.
2. URN, platform instance, FQN, schema, glossary, owner, domain, tag, relationship를 정규화한다.
3. pagination·timeout·indexing delay·asset 없음·권한 거부를 서로 다른 안전 오류로 반환한다.
4. 테스트에서 고정 fixture와 실제 API 응답의 contract를 비교한다.
5. R3 Context Builder에는 승인 전 후보 metadata만 반환하고 권한·Gate를 판정하지 않는다.

#### Trino adapter

```text
execute(sql, parameters, execution_policy)
get_status(query_id)
cancel(query_id)
get_result(query_id, page_token)
get_source_watermarks(query_id)
```

수행:

1. query account와 session property를 고정한다.
2. `execution_policy`의 timeout·row limit·resource group을 실제 요청에 적용한다.
3. Trino query ID, state, next URI/page, stats, warnings를 정규화한다.
4. cancel 후 terminal state를 확인한다.
5. connector별 오류를 source ID와 함께 typed error로 변환하되 credential·원문 query parameter를 노출하지 않는다.
6. adapter 자체는 G2를 판정하지 않고 R3가 전달한 검증 증표의 형식만 확인한다.
7. read-only·timeout·부분 source 실패·pagination·cancel contract test를 작성한다.

#### Source health adapter

1. source별 liveness, read-only query, watermark, 최근 성공 시각을 반환한다.
2. DataHub ingestion health와 Trino catalog health를 구분한다.
3. R4 Catalog fixture와 R5 readiness test에 같은 상태 enum을 제공한다.

완료 조건:

- R3 fake adapter와 실제 adapter가 같은 interface를 사용한다.
- R3가 DataHub·Trino vendor client를 직접 import하지 않아도 된다.
- R5가 adapter entrypoint로 장애·보안 negative test를 실행할 수 있다.

### 단계 R2-19 — 다섯 번째 Source 온보딩 재현

수행:

1. 기존 4개 source 상태에서 시작한다.
2. 다섯 번째 schema와 seed를 실행한다.
3. DataHub recipe를 추가한다.
4. 새 platform instance 자산을 확인한다.
5. Search API에서 URN을 조회한다.
6. Trino catalog를 추가한다.
7. binding·metric·JOIN proposal을 R3에 전달하고 R1 승인 version이 Context Registry에 등록됐는지 확인한다.
8. 동일 질문을 다시 실행한다.
9. Context 후보와 SQL plan 반영을 확인한다.

완료 기준:

- “DataHub 화면에 보임”뿐 아니라 URN→Context→SQL source→결과 출처가 연결된다.

## 8. R2 병합 절차와 권장 병합 시점

병합의 단일 기준은 `docs/markdown/collaboration/README.md`이며, 전체 체크포인트는 R1 매뉴얼의 M0~M6을 따른다.

### 공통 절차

1. 배정된 개인 branch의 working tree가 깨끗할 때 최신 `dev`를 반영한다.
2. 한 병합 요청은 아래 패키지 하나와 그에 필요한 1~3개 카드만 포함한다.
3. schema·seed·recipe·catalog·adapter version과 검증 결과를 handoff에 적는다.
4. 사람이 staged diff를 확인한 뒤 개인 branch에 commit·push한다.
5. 관리자가 개인 branch 하나씩 `dev`에 병합하고 해당 R2 회귀를 실행한다.
6. 충돌 시 관리자가 임의 수정하지 않고 R2가 최신 `dev`를 반영해 자기 branch에서 해결한다.

### 권장 R2 병합 패키지

| 병합 | 여기까지 완료 | 선행 | 병합 직후 소비자 | 필수 검증 |
|---|---|---|---|---|
| R2-M1 / I1 | source 경계, 최소 PMS·CRM schema/seed, URN/FQN fixture, adapter interface | R1 metric/time 초안 | R3 Context·R5 profile | DDL·seed 재실행, 정답 row count, contract test |
| R2-M2 / I2 | PMS·CRM ingestion, 2 catalog, 대표 2-source JOIN, DataHub·Trino adapter 최소 구현 | R5 source runtime | R3 deterministic slice | Search URN, read-only, result hash, execute/status/cancel |
| R2-M3 / I3 | 5 source schema·recipe·catalog, type mapping, 승인 JOIN·cardinality | R2-M2 | R3 일반 질문·R4 Catalog | 5 catalog 단독 조회, 2~3-source JOIN, health 상태 |
| R2-M4 / I4 | watermark, 정답 SQL·result fixture, 재적재·부분 source 실패 계약 | R3 artifact contract | R4 Report·R5 worker/장애 test | watermark 변화, partial failure, fixture version |
| R2-M5 / I5 | 다섯 번째 source 온보딩 재현, 최종 gold hash·성능 증거 | full profile | R1·R5 수용 | 빈 환경 재생성, 필수 30건 관련 hash, connector 회귀 |

R2-M1은 5개 source 전체를 기다리지 않고 먼저 병합한다. R3가 사용할 interface와 대표 2-source fixture를 일찍 고정하는 것이 재작업을 줄인다.

병합하지 않는 상태:

- seed가 매번 다른 결과를 만듦
- schema version과 migration·재생성 방법이 없음
- DataHub URN과 Trino FQN이 연결되지 않음
- R2 branch가 공통 OpenAPI·Compose·root dependency를 직접 수정함
- write 차단·credential redaction 검증이 실패함
