## 1. 일정 운영 원칙

1. 10주 참조안은 사용하지 않고 9월 3일 최종발표일에 맞춘다.
2. 주말은 필수 작업일로 계산하지 않고 지연 복구·자율 검증 buffer로만 사용한다.
3. 작업 완료는 날짜가 아니라 Gate 종료 조건과 검증 증거로 판정한다.
4. 각 사람은 자기 개인 branch와 자기 AI를 사용하고 한 번에 작업 카드 하나만 처리한다.
5. 기능을 크게 만든 뒤 한 번에 병합하지 않고 M0~M6 체크포인트마다 작은 단위로 `dev`에 병합한다.
6. 8월 28일 이후에는 P0 신규 기능을 추가하지 않고 결함·발표·재현성만 다룬다.
7. P2 MCP·문서 RAG·ML Tool·복잡한 cron·외부 Report 배포는 최종발표 이후로 미룬다.
8. 실제 고객 데이터는 사용하지 않고 R1 시나리오와 R2 synthetic seed만 사용한다.

## 5. 단계별 상세 일정

### 5.1 7월 29일~31일 — M0 기준 정렬

목표: 다섯 AI가 서로 다른 구조를 만들기 전에 공통 기준을 고정한다.

| 역할 | 작업 카드 | 결과물 |
|---|---|---|
| R1 | R1-00·01·02·16 | backend 결정, P0/P1, 사용자 과업, 역할·계약·상태 원장 |
| R2 | R2-01·02 | 5 source·4 engine 구성표, 논리 데이터 모델 |
| R3 | R3-01·02·03 | module 경계, 공통 객체, 오류 계약 초안 |
| R4 | R4-01·02·05 | 기존 frontend 조사, IA, 상태별 mock 목록 |
| R5 | R5-01·02·03 | 자원표, dev/full/split 후보, version matrix |

7월 31일 종료 조건:

- FastAPI 단일 구조와 Django+FastAPI 분리안 중 하나가 결정됐다.
- R1~R5와 개인 branch가 연결됐다.
- 공통 파일 단일 작성자가 확정됐다.
- 각 역할의 첫 작업 카드에 `BASE_SHA`, `ALLOWED_PATHS`, `CONTRACT_VERSION`이 입력됐다.
- 결정되지 않은 항목은 구현 사실이 아니라 `가정`으로 기록됐다.

### 5.2 8월 3일~7일 — M1 Contract Freeze

목표: 실제 구현을 연결할 최소 계약과 synthetic data 기반을 고정한다.

| 역할 | 작업 카드 | 결과물 |
|---|---|---|
| R1 | R1-03~07 | 용어·metric·time·합성 시나리오·필수 30건 초안 |
| R2 | R2-03~08·18A interface | PMS·CRM DDL, synthetic seed, identity bridge, 등급 이력, read-only |
| R3 | R3-02~08 | OpenAPI·오류·DB 모델·요청 context·Router·Controller |
| R4 | R4-03~05·R4-RPT-01 | frontend type·client·mock, Report domain contract |
| R5 | R5-04~06·17 | service skeleton, `.env.example`, health, CI |

데이터 생성 범위:

- R1이 합성 업무 시나리오와 반례를 정의한다.
- R2가 실제 DDL·synthetic seed·고객 identity·회원 등급 이력을 생성한다.
- seed 값, schema version, row count, expected result를 고정한다.
- 실제 고객·워커힐 운영 데이터는 사용하지 않는다.

8월 7일 종료 조건:

- PMS·CRM을 빈 환경에서 DDL+seed로 재생성할 수 있다.
- 업무 계약과 API·Report·health 계약 version이 고정됐다.
- R3·R4·R5가 같은 fixture version을 사용한다.
- M1 병합 후 모든 개인 branch가 최신 `dev`를 반영했다.

### 5.6 8월 31일~9월 2일 — Release·발표 준비

#### 9월 1일 화요일 — 1차 전체 리허설

1. 빈 환경 또는 발표 환경을 runbook으로 기동한다.

#### 9월 2일 수요일 — RC2·최종 동결

## 7. 매일 운영 방법

### 오전 15분

각 역할이 다음만 공유한다.

```text
현재 카드:
어제 완료 증거:
오늘 완료 목표:
필요한 contract/fixture:
blocker:
다른 역할 파일 변경 요청:
```

### 오후 통합 확인

- contract version이 바뀌었는지 확인한다.
- 공유 파일 변경 요청을 단일 작성자에게 전달한다.
- 같은 날 병합할 branch를 한 개씩 순서대로 정한다.
- Gate 직전에는 새 카드보다 회귀·handoff를 우선한다.

### 카드 상태

```text
READY
IN_PROGRESS
REVIEW
BLOCKED
MERGED_DEV
VERIFIED_GATE
```

`fixture 통과`, `dev 병합`, `Gate 검증`은 서로 다른 상태로 관리한다.

## 8. 지연 발생 시 우선순위
