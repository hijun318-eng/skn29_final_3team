## 범위와 책임

- 이 문서는 평가 case의 구조와 승인 상태만 관리한다. 질문·정답 SQL·결과 hash는 R2 fixture, model 실행 결과는 R3 runner가 도착한 뒤 등록한다.
- R1은 업무 질문·중단 조건·최종 판정, R2는 SQL·JOIN·결과 정답, R3는 model 실행·평가 지표를 검토한다.
- 실제 고객 데이터는 금지하며 모든 case에 `synthetic`, schema·seed·scenario version을 기록한다.

## I2 수용 subset

실제 질문·SQL·결과 hash·runner 출력은 역할별 handoff가 도착한 뒤 채운다. 아래 네 슬롯은 I2 판정에서 빠지면 안 되는 결과 유형과 trace 증거만 고정한다.

| 슬롯 | 기대 결과 | 필수 생산자 근거 | R1 판정 기준 | 상태 |
|---|---|---|---|---|
| `I2-SUCCESS-01` | 성공 | R2 정답 hash, R3 runner, R4 request→artifact trace, R5 화면 증거 | `request_id`·`trace_id`·`artifact_id`가 이어지고 승인 metric·기간·source·hash가 화면까지 보존됨 | `INTEGRATED_PASS` |
| `I2-CLARIFY-01` | 재질문 | R3 모호성 결과, R4 상태 trace, R5 재질문 화면 | query·Artifact를 만들지 않고 같은 `request_id`·`trace_id`에서 필요한 추가 조건을 요청함 | `INTEGRATED_PASS` |
| `I2-BLOCKED-01` | 차단 | R4 G1/G2 차단 trace, R5 차단 화면 | 차단 이후 Trino 실행·G3·Artifact가 없고 승인 error contract가 화면까지 보존됨 | `INTEGRATED_PASS` |
| `I2-SOURCE-FAIL-01` | source 실패 | R2 source 식별자, R4 query/source 실패 trace, R5 실패 화면 | 실패 source가 식별되고 성공 Artifact를 만들지 않으며 재시도 가능 여부가 API 결과대로 표시됨 | `INTEGRATED_PASS` |

## Gold 120건 관리 규칙

1. `paraphrase_group`은 서로 다른 split에 나누지 않는다.
2. tuning에 사용한 case는 최종 gold 판정에 재사용하지 않는다.
3. `train`, `validation`, `gold`의 수량은 R2 fixture와 R3 runner handoff 후 확정한다.
4. 질문·정답·근거 중 하나라도 reviewer 승인이 없으면 `APPROVED`로 바꾸지 않는다.
5. 동일 입력의 재실행은 schema·seed·scenario·model·prompt·policy version과 결과 hash가 같아야 한다.

## Case schema

| 필드 | 필수 | 값·용도 |
|---|---|---|
| `case_id` | 예 | 고유 ID |
| `set` | 예 | `required30` 또는 `gold120` |
| `category` | 예 | 단일 source, cross-source, 모호성·근거 부족, 권한·금지 요청 |
| `paraphrase_group` | 예 | 유사 질문 누수 방지 그룹 |
| `split` | 예 | `train`, `validation`, `gold` |
| `question` | 예 | 합성 데이터 기준 자연어 질문 |
| `role_policy` | 예 | 요청 role과 적용 policy version |
| `time_context` | 예 | `as_of`, timezone, 기간 경계 |
| `expected_outcome` | 예 | 성공, 재질문, 차단, partial, 실패 |
| `expected_state_error` | 예 | 기대 상태와 error code |
| `expected_query_result` | 조건부 | 승인 SQL/JOIN과 결과 hash |
| `sources` | 조건부 | DataHub URN과 Trino FQN |
| `versions` | 예 | contract·schema·seed·scenario·model·prompt version |
| `reviewers` | 예 | R1·R2·R3 검토 상태 |
| `evidence` | 예 | fixture, trace, 실행 로그 경로 |
| `status` | 예 | `DRAFT`, `REVIEW`, `APPROVED`, `BLOCKED` |

## 승인 조건

- 필수 30건은 위 할당을 충족하고 성공·재질문·차단·source 실패를 포함한다.
- Gold 120건은 중복·split 누수 없이 R1·R2·R3 reviewer 승인을 모두 받는다.
- `APPROVED` case는 질문·정답·version·근거를 덮어쓰지 않고 새 version으로 교체한다.
- 기존 I2 성공·재질문·차단·source 실패의 component·fixture·mock browser 증거는 회귀 근거로 유지한다.
- 통합 승인은 실제 DB Template→R2 Trino→R4 API→R5 production 화면의 동일 trace가 확인될 때까지 부여하지 않는다.
- 필수 30건·Gold 120건 case manifest는 아직 없으므로 전체 평가 세트는 0/30·0/120을 유지하며 I2 subset 승인과 혼동하지 않는다.
