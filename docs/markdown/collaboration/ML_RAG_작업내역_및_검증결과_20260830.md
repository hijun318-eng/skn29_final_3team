ML과 RAG는 서로 다른 기능이다. ML은 객실 수요 숫자를 예측하고, RAG는 승인된 내부 문서에서 업무 근거를 검색한다. 두 기능은 별도 라우팅·기능 플래그·감사 경계를 사용한다.

## 2. 지금까지 수행한 작업

### 2.1 ML 객실 수요예측

1. 미래 정답 누수를 막기 위해 과거 데이터만 사용하는 44개 Feature 계약을 구성했다.
2. 객실 판매 수를 물리 객실 수로 나눈 점유율을 Target으로 사용했다.
3. Seasonal baseline과 XGBoost, LightGBM, HGBR 후보를 동일 평가 구간에서 비교했다.
4. WAPE 단독 순위가 아니라 비열등성, RMSE, R2, Bias, 재학습 시간을 함께 평가했다.
5. HGBR를 종합 운영 후보로 선정하고 `joblib` 모델과 manifest·checksum을 패키징했다.
6. ML 요청과 RAG 호출을 분리하고 ML provenance에서 `rag_called=false`를 확인하는 구조를 정의했다.

### 2.2 RAG 내부 업무지침 검색

1. PostgreSQL·pgvector 기반 Dense 검색과 BM25를 결합한 Hybrid 검색을 구현했다.
2. 검색된 근거 안에서만 답변하고 문서명·citation·evidence ID를 반환하도록 구성했다.
3. 재전송, 만료 서명, 알 수 없는 역할을 거부하는 보안 경로를 검증했다.
4. Dense-only, BM25-only, Hybrid, Hybrid+BGE reranker 후보를 정량 비교했다.
5. BGE reranker는 성능 후보로만 유지하고 기본 운영 경로에는 활성화하지 않았다.
6. 업무 담당자 승인 전에는 RAG Tool이 활성화되지 않도록 계약을 정합화했다.

### 2.3 채팅·서비스 통합 경계

```text
사용자 질문
  -> 인증·세션·권한 확인
  -> 서버 라우팅
  |- 일반 분석 -> SQL Guard -> Trino -> 분석 결과
  |- ML 예측   -> Feature 검증 -> HGBR -> 예측 결과
  `- 내부 지침 -> RAG Gateway -> Hybrid 검색 -> 근거 답변
```

- ML 예측은 RAG 검색 결과에 의존하지 않는다.
- RAG 답변은 ML 예측 모델을 호출하지 않는다.
- 장애가 발생해도 다른 기능으로 질문을 임의 전환하지 않는다.
- 기능별 provenance와 오류 상태를 별도로 기록한다.

## 3. ML 최종 결과

### 3.1 모델 정보

| 항목 | 값 |
|---|---|
| 모델 버전 | `room-demand-hgbr-occupancy-v3.3.0` |
| 알고리즘 | `HistGradientBoostingRegressor` |
| Target | `target_rooms_sold / physical_rooms` |
| Feature 수 | 44개 |
| 예측 범위 | 기준일 이후 최대 10일 |
| 모델 파일 크기 | 931,014 bytes |
| SHA-256 | `96b8527372c47341f1432b3b8288b770fabd90ae5bf0a55649bcd7eab2ba3f8c` |
| 운영 승인 | `false` |

### 3.2 HGBR 설정

```text
loss=squared_error
max_iter=240
learning_rate=0.06
max_leaf_nodes=31
min_samples_leaf=40
l2_regularization=0.2
```

### 3.3 모델 비교

| 모델 | F/G 통합 WAPE | 최종 학습 시간 |
|---|---:|---:|
| XGBoost | 16.9031% | 85.87초 |
| LightGBM | 16.9104% | 10.81초 |
| HGBR | 16.9253% | 7.42초 |

- HGBR는 F/G 4개 구간 중 2개 구간에서 WAPE 1위였다.
- HGBR는 F/G 4개 구간 모두 RMSE와 R2가 1위였다.
- HGBR-XGBoost WAPE 차이의 95% 신뢰구간 상한은 `0.0790%p`였다.
- HGBR-LightGBM WAPE 차이의 95% 신뢰구간 상한은 `0.0765%p`였다.
- 두 결과 모두 사전 비열등성 기준 `0.20%p` 이내였다.
- 통합 WAPE 단독 1위는 XGBoost다. HGBR는 정확도 비열등성과 운영 효율을 함께 고려해 선정했다.

### 4.3 검색 품질

| 시스템 | Recall@5 | nDCG@5 | MRR@10 |
|---|---:|---:|---:|
| Dense-only | 0.9323 | 0.8445 | 0.8345 |
| BM25-only | 0.8958 | 0.7236 | 0.6925 |
| Hybrid | 0.9531 | 0.8521 | 0.8378 |
| Hybrid + BGE reranker | 0.9844 | 0.9204 | 0.9118 |

- Hybrid는 Dense-only보다 고난도·교차 도메인 Recall@5를 개선했다.
- BGE reranker는 nDCG@5를 `+0.0683` 개선했다.
- BGE 개선 95% 신뢰구간은 `+0.0201 ~ +0.1178`이었다.
- BGE GPU P95는 154.69ms, 오류는 0건이었다.
- 96개 평가 질문은 개발자 평가셋이며 업무 담당자 승인 Gold는 아니다.

### 5.3 검증 중 해결한 문제

| 문제 | 원인 | 해결 |
|---|---|---|
| RAG Docker 상태 테스트 불일치 | 테스트가 과거 `CODE_INTEGRATED_E2E_PENDING` 값을 기대 | 최신 `LOCAL_DOCKER_VALIDATED`로 동기화 |
| 승인 대기 중 RAG Tool 활성화 | `enabled=true`와 승인 대기 상태가 충돌 | 승인 전 `enabled=false`로 변경 |
| Health 상태 테스트 불일치 | 구현은 endpoint 제공 상태지만 테스트는 미검증 상태 기대 | `HEALTH_ENDPOINT_AVAILABLE`로 동기화 |

이번 검증은 격리된 Python 3.12 로컬 환경에서 수행했다. 현재 Docker Engine을 사용한 Trino·PostgreSQL·Qwen 동적 E2E는 재실행하지 않았으므로, 2026-08-29 dated E2E 근거와 구분한다.

## 7. 발표 가능한 표현

- HGBR를 WAPE 비열등성, RMSE, R2, Bias, 학습 효율을 고려한 종합 운영 후보로 선정했다.
- RAG 검색·답변·인용 17건을 2026-08-29 로컬 Docker 환경에서 검증했다.
- ML·RAG 관련 로컬 자동 테스트 85건을 2026-08-30 모두 통과했다.
- ML과 RAG는 별도 라우팅·기능 플래그·감사 경계를 사용한다.

다음 표현은 사용하면 안 된다.

- HGBR가 F/G 통합 WAPE 단독 1위다.
- ML이 실제 Walkerhill PMS 데이터에서 같은 성능으로 검증됐다.
- BGE reranker가 운영 기본 경로에 활성화됐다.
- RAG 평가 질문이 업무 담당자 승인 Gold다.
- ML·RAG가 최종 운영 승인 또는 Production Ready 상태다.

## 8. 남은 작업 우선순위

1. HGBR v3.3을 서비스 Runtime Artifact 계약으로 변환한다.
2. 실제 Trino -> HGBR -> PostgreSQL provenance ML E2E를 수행한다.
3. RAG 업무 담당자 Gold 질문·정답을 승인받아 재평가한다.
4. BGE feature flag와 Hybrid fallback을 통합 검증한다.
5. 동일 release SHA에서 Backend·Frontend·ML·RAG 동적 E2E를 수행한다.
6. Secret·HTTPS·역할별 권한·부하·장애·롤백 Gate를 통과한다.
7. 사람 승인 기록 후에만 운영 feature flag와 `production_approved`를 변경한다.
