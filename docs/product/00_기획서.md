## 2. 현재 결론

### 결정

1. 특정 dataset release나 질문별 seed를 애플리케이션 기본값으로 고정하지 않는다. 배포 대상 release는 DataHub native governance·semantic metadata와 Trino schema의 전체 read-back이 일치할 때만 활성화한다.
2. P0를 같은 릴리스 후보에서 모두 검증하기 전에는 P1·P2 기능을 확장하지 않는다.
3. P0는 DataHub가 승인한 Metric·Dimension·Join·Time·권한 계약 범위의 자연어 질문을 처리한다. 특정 예시 문장 목록으로 지원 범위를 결정하지 않는다.
4. DataHub Business Glossary를 업무 용어의 런타임 기준으로 사용한다. 실행 가능한 Metric 계산식·JOIN·시간·권한 정책은 별도 버전 계약으로 유지하되 Glossary Term과 연결한다.
5. 로컬 JSON은 공개 schema·version manifest·설정·명시적 test fixture로만 사용한다. 요청별 Context·Metric·정답 SQL이나 운영 metadata cache로 사용하지 않는다.
6. 현재 Docker Compose 기반 모듈러 모놀리스를 P0 동안 유지한다. 마이크로서비스·새 Agent framework·Kubernetes는 도입하지 않는다.
7. P0 사용자 경험은 한 질문에 모든 결과를 펼치는 화면이 아니라, 같은 대화에서 승인된 분석 조건과 결과를 이어 쓰는 **제한된 멀티턴**이다. 지원 후속 동작은 기간·승인 필터·차원 변경, 고정 비교, 표·차트 전환, 호환되는 차트 표현 변경, 선택 결과의 Report 초안 추가로 한정한다.
8. Analysis Run은 계속 원자적이다. Metric·기간·필터·차원·grain·비교 범위처럼 데이터 의미가 바뀌면 현재 권한과 의미 계약으로 새 Run을 만들고 APP-G1~G3와 Trino 경로를 다시 통과한다. 표·차트 전환처럼 데이터가 바뀌지 않으면 기존 Artifact를 다시 조회하지 않고 View만 바꾼다.
9. 대화 전체 원문을 모델의 장기 기억으로 사용하지 않는다. 서버가 검증한 직전 분석 명세, 현재 초점 Artifact, View와 Report Draft 참조만 구조화해 이어가며, 상속한 조건과 이번 Turn에서 바뀐 조건을 사용자에게 표시한다.

### 확인된 사실

- 애플리케이션은 DataHub GraphQL의 전체 release snapshot·semantic search·native governance를 읽고 Trino `information_schema`의 실제 table/column fingerprint와 교차 검증한다. snapshot이 불완전하거나 서로 다르면 stale/local fallback 없이 차단한다.
- SQL 생성·binding·Gate 검사는 동일 SQLGlot AST 결과를 공유하며, 질문 문자열·정규식·고정 CTE로 특정 답을 재생성하는 경로는 제거됐다.
- 기본 CI의 model/data test double은 contract/unit 회귀 증거일 뿐 live 검증으로 부르지 않는다. 실제 DataHub·Trino·model·App DB와 같은 release로 연결되지 않은 통과 수는 제품 완료 증거가 아니다.
- 2026-08-17 metadata-only live gate에서 release scope 51 datasets/578 columns, 7개 runtime metric Glossary Term, 8개 governance entity와 458 aspects를 DataHub Rest.li·GraphQL 및 Trino로 독립 재조회했다. catalog hash `d8efc5cb11f543a93ce8d3b584899a90f9548d9f9deb6b897e737a629a720ce8`이 일치해 catalog/Glossary gate는 `READY`다.
- semantic search·embedding·vector index는 이번 metadata-only 발행 범위가 아니며 positive 검증도 하지 않았다. Frontend→FastAPI→model→실제 query·artifact까지의 production E2E Release Gate는 별도이며 아직 `NOT_READY`다.
- 현재 `AgentPage`는 화면에서 현재 질문과 `run` 하나만 유지하며 새 질문이 이전 결과를 대화 Turn으로 누적하지 않는다. Frontend의 `POST /analysis` body는 `question`과 `parameters`만 보내고 Backend도 `RequestContext.conversation_id`를 실제 요청에서 채우지 않으므로 현재 동작은 single-turn이다.
- App DB에는 `chat.conversations`와 `chat.analysis_requests.conversation_id` 골격이 있지만 현재 분석 저장 경로는 conversation을 생성·검증·연결하지 않는다. 골격 존재를 멀티턴 구현 완료로 보지 않는다.
- 현재 Artifact는 표와 차트 payload를 함께 가질 수 있고 Frontend에는 제한된 차트 표시 전환, Report에는 Artifact·표·차트 block과 `visibleViews` 기반이 있다. 그러나 자연어 표현 Turn, 현재 초점 View 보존, 여러 Turn의 선택 결과를 같은 Report Draft에 누적하는 대화 연결은 구현되지 않았다.

## 3. 한 줄 정의

Answervice는 사용자가 업무 언어로 기업 데이터를 질문하면, 승인된 용어·자산·권한·계산 규칙 안에서 여러 원천을 읽기 전용으로 분석하고 결과와 근거를 반복 가능한 분석·보고서 자산으로 만드는 서비스다.

## 4. 해결하려는 문제

### 업무 문제

- 객실, 식음, 회원, 시설과 연회 데이터가 서로 다른 시스템에 있어 새 질문마다 수작업 추출과 조정이 필요하다.
- 같은 “매출”도 인식 시점, 환불, 세금·봉사료, 집계 grain에 따라 값이 달라질 수 있다.
- 데이터 위치와 연결 키를 아는 사람에게 분석 요청이 집중된다.
- 일회성 채팅 답변은 다음 보고에서 같은 기준으로 재실행하기 어렵다.

### 신뢰 문제

- AI가 어떤 지표·데이터·JOIN을 선택했는지 보이지 않으면 결과를 승인하기 어렵다.
- 화면 메뉴만 숨겨서는 권한을 보장할 수 없다.
- SQL이 read-only여도 잘못된 JOIN, 기간 또는 지표 정의로 틀린 결과가 나올 수 있다.
- 과거 결과나 fixture가 현재 실패를 덮으면 서비스처럼 보이지만 실제로는 동작하지 않는다.

### 기존 BI와의 경계

정해진 KPI를 같은 형태로 반복 조회하거나 실시간 모니터링하는 일은 기존 BI가 더 적합하다. Answervice는 승인된 범위 안에서 기존 화면에 없는 교차 질문을 처리하고, 그 분석을 저장·재실행·보고서에 재사용해야 하는 상황에 집중한다.

## 5. 사용자와 가치

| 사용자 | 실제 목적 | P0에서 제공할 가치 | P0에서 제공하지 않는 것 |
|---|---|---|---|
| 현업 분석 담당자 (`analyst`) | 업무 질문을 분석하고 반복 실행한다. | 자연어 질문, 확인 요청, 결과·근거, 저장·재실행, 보고서 초안 | 모든 자연어 질문과 임의 SQL |
| 관리자 (`admin`) | 분석·보고서·데이터 연결·계정을 통합 관리한다. | `analyst` 기능 전체, 보고서 관리, 연결 상태, 계정·감사 관리 | DataHub publish·Trino setup·Source DB service identity의 직접 상속 |
| 사업책임자·의사결정자 | 여러 업무 영역의 변화와 근거를 본다. | 검증된 분석·보고서 결과 소비 | 별도 C-level 전용 권한·화면 전체 |

승인 범위의 데이터 분석 Agent를 사용하며, 서버 Capability가 관리 기능을 구분한다.

## 6. 제품 가설과 차별점

### 제품 가설

사용자가 원시 테이블·컬럼을 몰라도 승인된 업무 용어와 runtime catalog 범위에서 교차 분석을 시작하고, 결과와 근거를 저장·재실행·보고서에서 이어서 사용할 수 있다면 반복 분석 업무의 재작업과 검증 부담을 줄일 수 있다.

### 차별점

| 차별점 | 의미 |
|---|---|
| Text-to-SQL보다 의미 계약 | Metric 정의·단위·기간·JOIN을 승인 계약으로 제한한다. |
| DataHub 중심 용어·자산 근거 | 공식 용어, Domain·Owner·승인 상태와 관련 자산을 런타임 Context에 연결한다. |
| AI와 통제 책임 분리 | AI는 해석·SQL 후보·설명을 돕지만 권한·실행·공개 합격을 결정하지 않는다. |
| 세 단계 검증 | APP-G1은 Context, APP-G2는 SQL, APP-G3는 결과 공개 위험을 각각 검사한다. |
| 재사용 가능한 실행 이력 | 정의·실행·결과·보고서 버전을 분리하고 과거 결과를 덮어쓰지 않는다. |
| 실패의 정직한 표시 | 실패·빈 결과·일부 성공을 fixture나 과거 성공으로 대체하지 않는다. |

## 7. P0 제품 범위

P0는 다음 한 흐름을 끝까지 연결하는 데 필요한 것만 포함한다.

P0 인수 환경은 단일 호스트·통제된 네트워크의 release candidate다. 외부 고객 운영, 기업 IAM/SSO와 고가용성은 제외하지만 브라우저 로그인, 서버 권한, App→Trino service identity와 Source DB read-only 최소 권한은 실제 경로로 검증한다. 개발·운영 경로 모두 Trino HTTPS, password 인증, CA 검증과 service principal을 필수로 하며, 무인증 transport는 제공하지 않는다. 네트워크 I/O를 대체하는 `MockTransport`는 외부 연결을 하지 않는 단위 테스트에서만 명시적으로 주입한다.

제한된 멀티턴은 별도 자율 Agent 기능이 아니라 P0 Vertical Slice의 사용자 계약이다. 다만 실제 V4.1 데이터, 권한, 의미 계약과 APP-G1~G3보다 먼저 성공했다고 선언할 수 없다. 일정이 부족하면 지원 Chart 종류와 후속 동작 수를 줄이고 승인 질문군을 더 좁힌다. 데이터·보안·실패 Gate를 빼거나 raw transcript 기억으로 빠르게 대체하지 않는다.

```text
로그인·역할 확인
→ Conversation 생성 또는 같은 로그인 세션의 활성 Conversation 복원
→ 첫 업무 질문 제출 또는 모호성 확인
→ DataHub Glossary·관련 자산·권한으로 최소 Context 구성
→ APP-G1
→ 승인 Context 안의 SQL 후보 생성
→ APP-G2와 최대 1회 제한 수정
→ Trino read-only 조회
→ APP-G3·Safe Result
→ 새 Analysis Run과 Artifact 저장
→ 핵심값·해석을 간단히 표시하고 조건·근거는 필요할 때 펼침
→ 후속 Turn 분류
   ├─ 데이터 의미 변경 → 검증된 직전 분석 명세에 patch → 새 Analysis Run
   ├─ 표현 변경 → 기존 Artifact의 허용 View 생성, Trino 재조회 없음
   ├─ Report 추가 → Artifact + View 설정을 현재 Draft block으로 추가
   └─ 참조가 모호함 → 대상·기간·표현을 확인하고 실행 보류
→ Analysis 저장·새 Run 재실행·과거 이력 보존
→ Report 초안·편집·관리자 승인·수동 실행·부분 실패
```

### P0 제한 멀티턴 계약

- 로그인 세션과 Conversation을 구분한다. 한 로그인 세션에서 여러 Conversation을 만들 수 있고, 각 Turn은 `conversation_id`, 순서, 응답 대상 Turn, 동작 유형과 현재 초점 Artifact를 가진다.
- 권위 있는 대화 상태는 원문 transcript가 아니라 서버가 검증한 `metric_ids`, 절대 기간, dimension, filters, grain, comparison rule, `as_of`, release/version과 Artifact 참조다.
- `그 전 달은?`은 직전 성공 분석의 Metric·사용자 필터·차원을 유지하고 source 기간만 바꾼 새 Run이다. `지난/저번 달`은 wall clock 기준 별칭이므로 source-period 표현처럼 재해석하지 않는다. `두 달 비교해줘`는 승인된 비교 계약으로 새 Run과 비교 Artifact를 만든다.
- `그래프로 보여줘`, `다른 그래프로`, `표로도 보여줘`는 현재 초점 Artifact의 행·열과 허용 Chart가 호환되면 Presentation Turn이다. Artifact에 필요한 grain이나 field가 없으면 숫자를 임의 분해하지 않고 필요한 차원을 확인한 뒤 새 Analysis Run을 만든다.
- `다른 그래프`는 임의 생성이 아니라 데이터 형태별 allowlist에서 현재 View와 다른 다음 호환 표현을 선택하고 바뀐 Chart 종류를 밝힌다. 후보가 둘 이상이고 선택이 결과 해석을 바꾸면 사용자에게 선택지를 제시한다.
- `표로`는 현재 View를 대체하고 `표로도`는 기존 View를 유지한 채 표 View를 추가한다. 이처럼 한국어의 변경·추가 의미를 Turn 계약에서 구분한다.
- Report에는 대화 문장이나 화면 캡처가 아니라 검증된 `artifact_id`와 View 설정을 block으로 담는다. 같은 Artifact의 Chart와 Table을 각각 담을 수 있고 중복 재시도는 같은 idempotency key로 중복 block을 만들지 않는다.
- 각 새 Analysis Run은 현재 사용자 권한을 다시 확인한다. 과거 Run의 permission snapshot, cache, 성공 상태를 새 Run의 권한이나 결과로 승계하지 않는다.
- 상대 기간은 서버 소유 기준시점과 시간대를 기준으로 절대 기간으로 확정해 매 Turn에 표시한다. 달력 기간이 데이터 범위 밖이면 `OUT_OF_DATA_RANGE`와 가용 월을 보여 주며, 사용자가 선택한 월은 제3의 상대 기준이 아니라 명시적 `ABSOLUTE [start,end)` 새 Turn으로 저장한다.
- 한 Conversation 안에서도 서로 다른 `product_release_id`, Metric 정의·단위·grain의 결과를 조용히 비교하거나 한 Report block 의미로 합치지 않는다. 호환되지 않으면 새 버전 재실행 또는 새 Conversation을 안내한다.

### 사용자가 다르게 말해도 이해하는 범위

“어떻게 말하든 이해”를 무제한 자유질문 성공으로 약속하지 않는다. P0는 **지원 의도가 같다면 표현이 달라도 같은 typed request로 수렴**하게 만든다.

- 존댓말·반말, 조사 생략, 띄어쓰기, 어순, 흔한 한 글자 오탈자, 승인된 한국어/영어 Metric 별칭, `지난달/저번달/전월`, `띄워줘/보여줘/바꿔줘` 같은 표현 차이를 후보 정규화한다. 월 별칭은 모두 `WALL_CLOCK`이며 source Turn 기준은 `그 전 달`처럼 구분한다.
- 정규화·model 결과는 후보일 뿐이다. DataHub의 승인 Term·alias, 현재 Conversation의 typed slot, Artifact schema와 Rule Layer를 통과해 하나의 Metric·기간·filter·동작으로 확정될 때만 실행한다.
- 띄어쓰기·존댓말처럼 의미가 보존되는 차이는 조용히 정규화할 수 있지만 Metric·기간·대상·집계 grain을 바꿀 수 있는 교정은 해석 chip을 보여 주고 모호하면 짧게 확인한다.
- 숫자·날짜·단위, 부정(`말고/제외`), 비교 방향, `이상/초과`, 호텔·등급, 대체/추가를 가르는 `로/로도`는 critical token이다. 정규화 과정에서 삭제·교체하지 않고 달라지면 다른 intent 또는 명확화로 처리한다.
- 이해한 Metric·절대 기간·filter·dimension·grain·표현 종류를 응답마다 사람이 읽는 chip으로 보여 주고 사용자가 수정할 수 있게 한다. 잘못 이해한 채 실행하는 것보다 한 번 정확히 되묻는 것을 성공으로 본다.
- P0 지원 범위 밖 의도는 가장 가까운 지원 질문을 꾸며 내지 않고 `UNSUPPORTED_INTENT` 또는 후보 확인으로 끝낸다. 권한 밖 요청과 prompt injection은 발화 유사성과 무관하게 차단한다.
- Golden utterance마다 존댓말/반말·띄어쓰기/조사·어순·오탈자·Glossary 별칭·후속 지시어 변형을 사전 봉인한 equivalence set과 의미가 달라지는 contrast set을 만든다. 같은 의미는 같은 resolved request hash로, 다른 의미는 다른 hash 또는 명확화로 판정해야 한다.

| 층 | 담당 | 맡기지 않는 것 |
|---|---|---|
| 결정론적 정규화 | Unicode, 공백, 명확한 날짜 형식, 승인된 exact alias 같은 의미 보존 변환 | 자유 문장 전체 이해, 임의 오탈자 보정 |
| GPT/Node 1 후보 해석 | 반말·존댓말·어순·축약·경미 오탈자·지시어를 typed candidate로 변환 | 공식 Metric·권한·최종 실행 결정 |
| 서버 resolver | DataHub Term·Rule·source Turn·Artifact schema·권한으로 unique-resolution, 아니면 명확화 | 모델의 높은 확신만으로 추측 실행 |

즉, 정규식만으로 이해하거나 GPT 프롬프트만 믿는 구조가 아니다. **GPT가 폭넓게 후보를 만들고, 결정론적 계약이 최종 승인한다.**

## 9. Runtime catalog release 전환 원칙

### 전환 목표

전환 대상은 사용자가 읽기 전용 check에서 확인한 release scope다. 애플리케이션은 namespace나 테이블 수를 코드에 고정하지 않고, 확인된 authoring policy의 target·predecessor checksum과 물리 identity를 DataHub와 Trino 양쪽에서 다시 검증한다. 이전 release는 rollback rehearsal과 안정화 관찰이 끝날 때까지 물리적으로 보존하되 활성 검색·선택에는 동시에 섞지 않는다.

### 전환 완료로 보지 않는 상태

- ZIP을 저장소에 복사한 상태
- SQL 파일의 정적 검사만 통과한 상태
- 각 DB에 일부 테이블만 생성된 상태
- Trino 뷰만 보이는 상태
- DataHub에 Dataset만 수집되고 Glossary·관계·권한이 연결되지 않은 상태
- 앱이 구 계약으로 성공한 상태

### 전환 완료 상태

1. 알려진 SQL 결함을 수정하고 독립 정적 검토를 통과한다.
2. 격리 namespace에서 DATA-G0~G7, replay hash와 제품 Gold와 분리된 Serving 정합성 oracle을 통과한다.
3. DataHub 후보가 실제 URN·스키마·Domain·Owner·Lifecycle·Glossary·관련 자산 관계를 반환하고 Rule·Binding·policy까지 전체 read-back된다.
4. 위 후보가 확정된 뒤 held-out 검증을 봉인하고 앱의 semantic/metric/join/context 계약과 prompt를 같은 `product_release_id`로 연결한다. 애플리케이션 내부의 별도 source registry 파일은 만들지 않는다.
5. P0 정상·거부·실패 흐름이 명시적 candidate ID의 실제 Trino query ID와 artifact로 통과한다.
6. 사전 고정한 RTO/RPO·rollback trigger로 복구 훈련을 통과하고 pre-cutover 승인을 받은 뒤 같은 `product_release_id`로 기본 경로를 전환한다.
7. 전환 후 readiness·Golden smoke를 통과해야 P0 전환 완료로 판정한다. 실패하면 이전 승인 릴리스로 복구한다. 이후 안정화 관찰 기간은 이전 승인 릴리스 폐기 조건이며 P0 완료 조건과 분리한다.

## 10. 의미 거버넌스 원칙

### 권위 분리

| 정보 | 권위 원본 | 비고 |
|---|---|---|
| 용어명·별칭·설명·단위·Domain·Owner·승인 상태 | DataHub Business Glossary | 런타임 조회 대상 |
| Term과 Dataset/Column 관계 | DataHub | 후보 발견과 근거 |
| 계산식·필수 필터·JOIN·시간·Identity·권한 정책 | 버전된 실행 계약 | Glossary Term URN·Version과 연결 |
| 물리 존재·삭제 상태·스키마 | DataHub + 실제 Trino preflight | 둘이 다르면 차단 |
| 로컬 JSON | 공개 schema·version manifest·설정·test fixture | 요청별 Context·Metric·정답·운영 cache로 사용 금지 |

DataHub 장애 시 오래된 JSON이나 마지막 성공 결과로 조용히 성공하지 않는다. process-local bounded TTL snapshot도 만료 후 refresh에 실패하면 stale 값을 반환하지 않고 `METADATA_UNAVAILABLE`로 fail-closed한다.

## 11. P0 동작 archetype

P0 검증은 특정 자연어 문장·지표 ID·table FQN·정답 SQL을 제품 코드나 운영 manifest에 고정하지 않는다. test lane은 서로 이름이 다른 동형 schema와 programmatic request를 사용하고, live lane은 그 시점의 승인 catalog에서 발견된 자산으로만 실행한다.

- 단일 Metric 집계: 승인 Term과 연결된 물리 column·aggregation·time field를 사용하고 AST evidence가 일치하는지 확인한다.
- 모호성 확인: 여러 Metric·기간·차원이 동률이면 후보의 승인된 label·definition만 제시하고 선택 전에는 SQL을 실행하지 않는다.
- 기간·비교: server clock과 runtime data range로 절대 구간을 확정하며 범위 밖 요청을 과거 데이터로 자동 보정하지 않는다.
- 다중 자산: DataHub가 제공한 structured join edge·cardinality·preaggregation grain을 사용하고 누락된 predicate나 fan-out 위험을 차단한다.
- 표현 전환과 Report: 데이터 의미가 같으면 기존 Artifact를 재사용하고, 의미가 바뀌면 새 Run·Gate·query·artifact를 만든다.
- 권한·민감정보: entitlement와 column policy 밖의 요청은 Context 또는 결과 공개 경계에서 차단하며 허용 범위를 임의 확대하지 않는다.

각 archetype은 해석한 typed request, Context hash, AST 검증 결과, Run/Artifact/View/Report block ID와 실제 query 발생 여부를 evidence로 남긴다. fixture 기반 검증은 contract/unit으로만 명명하고 live E2E 증거로 승격하지 않는다.

## 12. 성공 기준

### 기능 성공

- 승인 catalog에서 선택된 요청이 실제 원천과 Trino를 조회하고 독립 검증한 결과·lineage와 일치한다.
- 모호한 질문은 사용자 확인 전 Node 2·Trino를 호출하지 않는다.
- 권한 밖·쓰기·미승인 Metric/Asset/JOIN 요청은 fail-closed한다.
- 결과가 표·차트·설명뿐 아니라 Glossary Term, Dataset URN/FQN, 기간, 버전, Gate, query/trace/artifact와 연결된다.
- 같은 Conversation에서 승인된 조건 상속과 변경이 정확하고, 모호한 대상은 확인 전 실행하지 않는다.
- 데이터 의미가 바뀐 Turn은 새 Run·query·artifact를 만들고, 호환되는 표현 전환은 동일 Artifact를 재사용하며 새 Trino query를 만들지 않는다.
- 선택한 Chart·Table View가 Report block으로 추가되어도 원 Artifact·query·release 근거가 유지된다.
- 저장 분석의 새 Run과 보고서 실행이 과거 결과를 덮어쓰지 않는다.
- 실패·빈 결과·일부 성공이 서로 구분된다.

### 정량 성공

다음 항목을 고정 평가 계약에서 측정한다. sealed calibration set으로 기준선을 얻은 뒤 held-out 결과를 보기 전에 표본 manifest·metric·threshold·허용 오차·반복 횟수·승인자를 봉인한다. held-out 결과를 본 뒤 목표를 낮추거나 같은 Gold를 prompt 선택·학습에 재사용하지 않는다.

- 질문 해석·명확화 정확도
- 후속 Turn의 대상 참조·조건 상속·조건 변경 정확도와 잘못된 상속률
- Presentation Turn의 불필요한 모델·Trino 재호출률과 Artifact/View 일치율
- Golden Dialogue 완주율, Report block 중복 방지율과 provenance 연결률
- Context/Glossary/Asset 선택 정확도
- SQL 정책 통과·차단 정확도
- 실행 결과 정확도
- 정상 요청 성공률과 단계별 latency
- 저장 분석·보고서 재실행 일치율
- 역할별 허용·거부·마스킹 결과

### 증거 성공

한 번의 릴리스 검증 묶음에 commit SHA, V4.1 release/checksum, DataHub Glossary version, context/policy/model/prompt version, Docker image, HTTP request/response, Trino query ID, DB request/trace/artifact, 브라우저 네트워크와 화면을 함께 남긴다.

| 잘못된 대화 조건 상속 | 매우 높음 | 원문 기억 대신 검증된 명세 patch, 상속·변경 diff 표시, 모호하면 실행 보류 |
| 표현 변경을 데이터 재분석으로 오인 | 높음 | Run 생성 결정표, 동일 Artifact·query 검증, 불필요한 Trino 재호출률 측정 |
| 멀티턴 추가로 P0가 다시 범용 Agent화 | 매우 높음 | Golden Dialogue와 allowlist 밖 동작은 P1 이후로 차단하고 안전 Gate 범위를 줄이지 않음 |
| Report에서 View와 원 Artifact 근거 분리 | 높음 | Report block에 immutable Artifact·View·release 참조를 함께 저장하고 중복·권한 검증 |

## 14. 용어

| 용어 | 의미 |
|---|---|
| Glossary Term | 승인된 업무 용어·별칭·정의·단위와 소유 정보를 가진 DataHub 항목 |
| Metric 실행 계약 | Term에 연결된 계산식·필터·시간·허용 grain의 버전 계약 |
| Asset Binding | DataHub Dataset URN과 Trino FQN의 검증된 연결 |
| Approved Context | 현재 질문·역할에 허용된 Term·Asset·Rule·기간의 최소 묶음 |
| DATA-G0~G7 | 데이터 release의 사전점검·DDL·seed·무결성·분포·replay·Trino·보안 경계 |
| APP-G1/G2/G3 | Context 완전성, SQL 안전성, 결과 공개 가능성을 각각 판단하는 앱 경계 |
| Conversation | 같은 분석 목적 안에서 Turn의 순서와 현재 초점 Artifact·Report Draft를 묶는 서버 객체. 로그인 세션이나 장기 사용자 기억이 아님 |
| Turn | 사용자 입력과 서버가 판정한 `ANALYSIS`, `PRESENTATION`, `REPORT_ACTION` 중 한 동작. 조건이 모호하면 원 동작의 결과를 `BLOCKED + NEEDS_CLARIFICATION`으로 남김 |
| Analysis Definition | 재실행 가능한 분석 의미와 parameter schema |
| Analysis Run | 특정 사용자·시점·버전·조건의 한 번의 실행 |
| Artifact | Safe Result, 표·차트·설명과 근거를 묶은 저장 자산 |
| View | Artifact의 검증된 행·열을 표 또는 허용 Chart로 표현하는 설정. 데이터 결과 자체가 아님 |
| Report Version/Run | 편집·승인되는 보고서 기준본과 그 기준본의 한 번의 실행 |
| Release candidate | 코드·데이터·메타데이터·정책·모델 버전이 고정된 검증 단위 |
