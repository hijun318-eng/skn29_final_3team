# Answervice P0 사용자 흐름

## 1. 목적과 공통 전제

이 문서는 P0에서 반드시 연결할 정상·확인·거부·실패·저장·보고서 흐름을 정의한다. 화면 목록이 아니라 사용자 행동과 서버 상태, 외부 의존성, 종료 조건, 증거를 함께 고정한다.

모든 흐름의 공통 전제는 다음과 같다.

- V4.1 SQL의 알려진 결함이 수정되고 실제 DB·Trino validator가 통과했다.
- 애플리케이션 기본 계약이 V4.1을 참조한다.
- DataHub Business Glossary와 Term-Asset 관계가 runtime authority다.
- 사용자는 server-side 권한을 가진다.
- fake model/data adapter, fixture 결과, 하드코딩 KPI를 제품 흐름에 사용하지 않는다.
- 모든 Analysis Run은 `request_id`, `analysis_run_id`, release/version/checksum, terminal `run_status`와 별도 `reason_code`를 가진다. Report Run은 `report_run_id`를 공통 식별자로 쓰고 block마다 연결된 `analysis_run_id`를 가진다.
- 인증을 유지하는 기술 `session`과 분석 문맥을 유지하는 `conversation`은 다른 객체다. 한 session에서 여러 conversation을 만들 수 있고, session 재인증이 conversation의 소유권·release·Turn 이력을 바꾸지 않는다.
- P0 conversation은 장기 기억이 아니라 같은 업무 질문 안의 제한된 후속 요청만 지원한다. 서버가 확정한 Metric·절대 기간·dimension·filter·grain과 Artifact/View 참조만 상속하며 전체 대화 원문을 권한 또는 실행 Context로 신뢰하지 않는다.

위 전제가 충족되지 않은 현재 상태에서는 아래 흐름이 목표 계약이지 검증된 현재 동작이 아니다.

## 2. 공통 상태 모델

```text
turn_command / analysis_request (실행 중 재연결 대상)
PENDING → RUNNING → TERMINAL_COMMIT

turn_status (모든 저장 Turn)
SUCCEEDED | BLOCKED | PARTIAL | FAILED | CANCELLED

run_status
RECEIVED → ROUTED → SUCCEEDED
                  → BLOCKED
                  → PARTIAL
                  → FAILED
                  → CANCELLED

progress_stage (run_status와 별도)
ROUTER → CONTROLLER → CONTEXT → APP-G1 → MODEL/APP-G2
       → QUERY → APP-G3 → ARTIFACT
```

실행 중 재연결·복구 상태는 idempotent command/request와 active lease에 두고, preflight에서 완전하게 resolved된 `ANALYSIS`는 별도 Run 생성·상태, attempt·heartbeat·외부 query 제출 증거를 상태 전이하며 저장한다. immutable Turn, Conversation head, focus·ViewSpec·Draft 같은 사용자 가시 domain mutation은 terminal commit 때만 생기거나 바뀐다. `turn_status/turn_reason_code`와 Analysis `run_status/reason_code`는 별도다. Run이 없는 표현·보고서·명확화 결과도 Turn에는 terminal 결과가 있다. `AUTHORIZED`, `UNDERSTANDING`, `RUNNING` 같은 진행 단계와 `NEEDS_CLARIFICATION`, `EMPTY_RESULT`, `QUERY_TIMEOUT` 같은 원인을 status로 만들지 않으며 terminal Turn/Run을 덮어쓰지 않는다.

Conversation의 모든 Turn이 Analysis Run인 것은 아니다. `ANALYSIS` Turn은 데이터 의미·범위가 바뀌어 새 Analysis Run을 만들고, `PRESENTATION` Turn은 승인 Artifact의 같은 행을 다른 View로 표현하며, `REPORT_ACTION` Turn은 Artifact/View 참조를 보고서 바구니나 초안에 추가한다. 명확화는 네 번째 종류가 아니라 원 종류의 Turn이 `BLOCKED + NEEDS_CLARIFICATION`으로 끝나는 결과다. 나머지 Turn을 Analysis 성공으로 가장하거나 가짜 `query_id`를 만들지 않는다.

## 3. UF-01 로그인과 권한 복원

**Actor:** `analyst`, `report_admin`, 통제된 인수환경의 `platform_admin`

1. 사용자가 로그인 정보를 제출한다.
2. Backend가 principal과 password hash를 확인하고 만료 가능한 session을 만든다.
3. Frontend가 인증 session 응답의 서버 소유 Role·Capability로 권한 기반 메뉴를 그린다.
4. 새로고침 후에도 유효 session이면 복원하고, 만료·변조 session이면 로그인으로 돌린다.
5. 로그아웃 시 server-side session을 무효화한다.

**거부 흐름:** 반복 실패, 잘못된 비밀번호, 비활성 principal, 권한 없는 API 직접 호출.

**완료 증거:** cookie 속성, session DB 기록, 허용·거부 HTTP, 객체 권한 test, 브라우저 network. 메뉴 숨김만으로 권한 완료를 판정하지 않는다.

## 4. UF-02 P0 Golden Path 분석

**Actor:** `analyst`

**고정 후보 질문**

> 2025년 6월과 7월의 호텔별 객실·식음·연회·유료시설 매출 및 총 운영매출을 비교하고, 변화가 큰 영역과 사용한 지표·데이터 근거를 보여줘.

정확한 Metric ID와 product Gold 값은 DATA-001~004와 GOV-001~008 candidate readiness가 통과하고 DataHub Term·Asset 관계와 Rule·Binding·policy를 모두 read-back한 뒤, GOV-009 activation 전에 Gold manifest로 고정한다.

1. 사용자가 질문을 제출한다.
2. Backend는 idempotency record를 먼저 조회하고 새 요청이면 session·role·`expected_head_turn_id`를 검사해 command와 Conversation active lease를 예약한다. 이 시점에는 Turn·Analysis Run이 없다.
3. Turn-level understanding preflight는 현재 principal의 coarse/object/metadata visibility로 먼저 후보를 제한한 뒤 원문·승인 alias·source Turn에서 의도·기간·dimension·Metric을 DataHub 승인 Term으로 unique-resolution한다. 권한 없는 Term·Asset 이름·정의는 후보에도 노출하지 않는다. 모호하거나 범위 밖이면 terminal `BLOCKED` Turn만 commit하고 Run은 0건이다.
4. 완전한 typed request가 하나로 확정되면 새 Analysis Run을 만들고 현재 entitlement에서 permission snapshot과 `POLICY_REQUIRED_FILTER`를 생성한다. 사용자 slot patch는 `INHERIT/SET/REMOVE`를 구분하되 정책 필터는 상속·삭제하지 않는다.
5. DataHub에서 관련 Dataset·Column을 찾고 schema·삭제 상태를 확인한다.
6. Rule Layer가 Term URN에 연결된 계산·filter·join·time·identity 계약을 더해 Approved Context를 만든다.
7. APP-G1이 버전·관계·권한·기간·schema를 검사한다.
8. Node 2가 Approved Context 범위 안에서 parameterized read-only SQL을 만든다.
9. APP-G2가 AST, allowlist, limit, scan/timeout 예산을 검사한다. 제한 수정은 최대 한 번이다.
10. Trino가 승인 Serving view를 조회하고 `query_id`와 통계를 반환한다.
11. APP-G3가 schema·행수·노출·근거 완전성을 검사한다.
12. Backend가 Safe Result, 표·차트 payload, 설명, Context·query·Gate trace를 한 artifact로 저장한다.
13. Backend는 결과 domain mutation, command terminal화, terminal Turn, 새 head와 lease 해제를 한 transaction으로 commit한다. Frontend는 서버 artifact만 렌더링한다.

**완료 조건:** 승인 Gold Result와 일치하고 브라우저 request부터 DB artifact까지 ID가 연결된다. “원인”이라고 단정하지 않고 관측된 변화와 구성 영역별 기여로 설명한다.

## 4.1 UF-02A 같은 대화의 P0 bounded multi-turn

**Actor:** `analyst`

**범위:** 기간 변경, 이전 결과 비교, 승인된 filter·dimension·grain 변경, 같은 Artifact의 그래프·표 표현 변경, 분석 근거 열람, 보고서 바구니 누적만 P0에서 지원한다. 여러 conversation을 넘는 장기 기억, 사용자의 성향 추론, 승인 Context 밖의 자유형 작업 계획은 P1 이후 별도 계약이다.

각 conversation은 소유자, `conversation_id`, 고정된 `product_release_id`·`semantic_release_id`, 생성 시각, 현재 head Turn을 가진다. 각 Turn은 `turn_id`, 선형 부모 `reply_to_turn_id`, 비교·조합 의미 입력의 ordered `source_turn_ids`(P0 최대 2), 선택적 `clarifies_turn_id`, `client_turn_id`, 종류, redacted utterance, 서버가 확정한 Context snapshot과 Run/Artifact/View 결과를 저장한다. owner에게 대화를 복원할 원문이 필요하면 별도 암호화 message store·보관기간·삭제 정책으로 제한하고 generic log·evidence에는 복사하지 않는다.

Focus 전이는 고정한다.

| terminal Turn | data focus | View focus |
|---|---|---|
| `SUCCEEDED ANALYSIS` + APP-G3 Safe Artifact | 새 Analysis/Artifact로 갱신 | 승인 기본 View로 갱신 |
| `SUCCEEDED PRESENTATION` | 유지 | 새 View와 ordered visible views로 갱신 |
| `SUCCEEDED REPORT_ACTION` | 유지 | 유지 |
| `PARTIAL/BLOCKED/FAILED/CANCELLED` | 유지 | 유지 |

P0에서 `PARTIAL`은 implicit source/focus가 아니다. `source_turn_ids`는 같은 owner·Conversation·release의 선행 `SUCCEEDED ANALYSIS`와 Safe Artifact만 가리킨다. 사용자 입력 patch는 `USER_REQUESTED_FILTER`의 `INHERIT/SET/REMOVE`만 허용하고 현재 `POLICY_REQUIRED_FILTER`는 매 Analysis Run 새 권한 snapshot에서 다시 만든다.

### 발화 정규화와 해석 확인

1. Frontend는 사용자 원문을 고치지 않고 전달한다. 서버는 Unicode·공백·조사·존댓말·흔한 오탈자 후보, DataHub 승인 alias, 현재 Turn의 명시 참조를 사용해 typed 후보를 만든다.
2. model은 표현을 이해하는 후보 생성에 쓸 수 있지만 공식 Metric·기간·권한·Artifact를 확정하지 않는다. 결정론적 resolver가 승인 Term, Rule, Conversation slot, source Turn과 Artifact schema로 후보를 검증한다.
3. 유일한 해석이면 원문과 함께 `이해한 조건` chip에 Metric·절대 기간·filter·dimension·grain·동작을 표시한다. 사용자는 다음 Turn에서 chip을 수정할 수 있고 수정은 기존 Turn을 덮어쓰지 않는다.
4. Metric·기간·filter·grain 중 하나라도 두 후보 이상이면 상위 후보를 임의 실행하지 않고 가장 작은 질문 하나로 확인한다. 단순 띄어쓰기·존댓말 차이는 확인 없이 같은 resolved request hash로 정규화할 수 있다.
5. 지원 범위 밖 질문, 권한 우회 문구, prompt injection은 유사한 허용 질문으로 바꾸지 않는다. `UNSUPPORTED_INTENT`·`ACCESS_DENIED` 또는 안전한 명확화로 끝낸다.

**완료 증거:** 사전 봉인한 equivalence/contrast manifest의 redacted utterance hash, expected route·slot·clarification, 실제 resolved request hash와 잘못된 자동 실행 수를 저장한다. 같은 문장을 prompt/few-shot 선택에 사용한 뒤 held-out으로 재사용하지 않는다.

### 기간 후속 질문과 비교

```text
Turn 1  사용자: 2025년 8월 인식 객실 매출을 보여줘.
        서버: 인식 객실 매출 · 2025-08-01~2025-09-01 미포함 · 전체 호텔

Turn 2  사용자: 그 전 달은?
        서버: 인식 객실 매출 · 2025-07-01~2025-08-01 미포함 · 전체 호텔

Turn 3  사용자: 두 달 비교 분석해줘.
        서버: 인식 객실 매출 · 2025년 7월 대 8월 · 전체 호텔
```

1. Turn 1은 사용자가 지정한 월을 `[start,end)` 절대 기간으로 저장하고 화면에 명시한다.
2. Turn 2는 직전 성공 `ANALYSIS` Turn의 승인 Metric·dimension·filter를 상속하고 기간만 바꾼다. 기간 변경은 새 Analysis Run을 만들고 APP-G1~G3와 Trino를 다시 통과하며 Turn 1을 덮어쓰지 않는다.
3. Turn 3의 비교는 두 기간을 한 승인 Context에서 같은 Metric·filter·grain으로 정렬해야 하므로 새 Analysis Run을 만든다. 서로 다른 release·Metric·단위·grain의 과거 Artifact를 Frontend에서 임의 병합하지 않는다.
4. 각 응답은 상속 조건과 변경 조건을 구분한 Context chip으로 보여 주고, chip에는 절대 기간·Metric·dimension·filter·grain을 사람이 읽을 수 있는 이름으로 표시한다.
5. 기본 답변은 핵심 수치·한 문장 요약과 현재 요청에 필요한 View만 간결하게 보여 준다. 전체 표·모든 차트·기술 근거는 `상세 보기`, `다른 표현`, `분석 근거`에서 점진적으로 연다.

실제 current clock에서 `이번 달`이 승인 데이터 범위 밖이면 `ANALYSIS` Turn을 `BLOCKED + OUT_OF_DATA_RANGE`로 terminal commit하되 `analysis_run_id`·query·Artifact는 모두 0건이다. 서버는 가용 절대 기간을 표시하고, 사용자가 `2025년 8월로 볼게`처럼 명시한 새 Turn부터 Run을 만든다. 테스트 clock은 production API header가 아니라 격리 profile에서만 고정하며 이를 current-clock E2E로 가장하지 않는다.

### 같은 Artifact의 그래프 → 다른 그래프 → 표

```text
Turn 1  사용자: 2025년 7월 인식 객실 매출을 보여줘. → 새 Analysis Run, Artifact A
Turn 2  사용자: 그래프로 띄워줘.              → Artifact A의 line View
Turn 3  사용자: 다른 그래프로 띄워줘.         → Artifact A의 bar(세로 막대) View
Turn 4  사용자: 표로도 띄워줘.                → Artifact A의 table View
Turn 5  사용자: 현재 그래프와 표를 보고서에 담아줘. → 두 Report block
```

1. GD-02 Gold manifest는 Artifact A의 승인 day grain·value role과 표현 순서 `line → bar(세로) → table`을 봉인한다. APP-G3 evidence가 완전하면 Turn 2~4는 `PRESENTATION` Turn으로 저장하고 같은 Artifact·query를 참조한다. 봉인 schema가 실제로 없으면 Gate를 실패시킨다.
2. `다른 그래프`는 데이터 역할에 맞는 allowlist 안에서만 전환한다. 시간축은 선·영역·막대, 범주 비교는 세로·가로 막대처럼 호환 가능한 표현만 제시하고 어떤 표현으로 바뀌었는지 응답에 명시한다. 값·축·series를 모델이 임의 생성하지 않는다.
3. 현재 Artifact가 월 합계 한 값만 가지고 있어 의미 있는 그래프의 x축이 없으면 “일별·호텔별·객실 유형별 중 어떤 기준인가”를 확인한다. 선택 전에는 query를 만들지 않고, 선택 후에는 grain이 바뀌므로 새 `ANALYSIS` Turn과 Analysis Run을 만든다.
4. `표로도`가 현재 그래프와 같은 행을 뜻하면 같은 Artifact의 table View를 재사용한다. 더 상세한 행이나 새 column을 요구하면 의미 범위 변경으로 처리해 새 Run을 만든다.
5. Turn 5는 현재 `bar` View와 table View를 사용자가 지정한 순서대로 서로 다른 Report block에 연결하는 `REPORT_ACTION`이다. 새 Analysis Run·query는 없고 중복 요청은 같은 두 block을 다시 만들지 않는다.
6. 이전 Turn과 View는 불변 이력으로 남기고 새 표현이 과거 응답을 덮어쓰지 않는다. 새로고침 뒤에도 같은 Artifact/View 참조로 복원한다.

| 후속 요청 | Turn 종류 | 새 Analysis Run·Trino query |
|---|---|---|
| `그 전 달은?`, `호텔별로`, `일별로`, 새 filter·Metric | `ANALYSIS` | 필요 |
| `두 달 비교 분석해줘` | `ANALYSIS` | 필요 |
| 같은 행을 `그래프로`, `다른 그래프로`, `표로` | `PRESENTATION` | 금지 |
| Artifact에 없는 grain·column으로 그래프·표 요청 | 확인 후 `ANALYSIS` | 필요 |
| `분석 근거 보여줘`, 보고서 바구니 추가 | `PRESENTATION` 또는 `REPORT_ACTION` | 금지 |

**완료 증거:** 다섯 Turn의 `reply_to_turn_id`와 의미 참조, Turn 1의 `analysis_run_id`·`query_id`·Artifact A, Turn 2~4의 동일 Artifact checksum과 서로 다른 View, Turn 5의 순서가 고정된 두 Report block, Turn 2~5 동안 Trino 미호출이 브라우저 network·backend trace·App DB에서 함께 확인된다.

## 5. UF-03 모호한 질문 확인

**질문 예:** `2025년 7월 매출을 보여줘.`

1. Node 1이 여러 승인 Metric·범위 또는 `그거`, `다른 그래프`, `표로`가 가리킬 수 있는 Artifact/View가 여러 개인 상태를 감지한다.
2. DataHub의 승인된 후보명·정의·단위만 사용자에게 보여 준다.
3. 원 `ANALYSIS` Turn은 `BLOCKED + NEEDS_CLARIFICATION`으로 끝나며 Analysis Run과 query는 만들지 않는다.
4. 사용자 선택 전에는 Node 2와 Trino를 호출하지 않는다.
5. 사용자가 선택하면 `clarifies_turn_id`로 원 요청을 가리키는 새 `ANALYSIS` Turn과 Analysis Run을 만든다.
6. 새 Run은 UF-02의 APP-G1부터 진행한다.

`PRESENTATION` 또는 `REPORT_ACTION`의 지시 대상만 모호한 경우에는 Analysis Run을 만들지 않고 원 종류의 Turn을 immutable `BLOCKED + NEEDS_CLARIFICATION`으로 끝낸다. 사용자의 Artifact/View 선택은 `clarifies_turn_id`로 원 Turn을 가리키는 새 child Turn이며, 확인된 표현 변경 또는 보고서 추가만 수행한다. 원 Turn을 수정하거나 성공으로 바꾸지 않는다.

**취소·무응답:** 상태를 유지하되 자동 성공·자동 후보 선택을 하지 않는다.

**완료 증거:** 첫 Turn에는 `analysis_run_id`·query ID가 없고, 두 번째 Turn의 선택·Context·새 Run·query ID가 `clarifies_turn_id`로 연결된다.

## 6. UF-04 거부와 안전 차단

### 권한 밖 요청

**질문 예:** `2025년 7월 PREMIER 회원별 생년월일과 VOC 원문을 모두 보여줘.`

- 권한 필터 또는 APP-G1에서 금지 field·row·원문을 제거하거나 전체 요청을 거부한다.
- Node 2와 Trino에 금지 field가 전달되지 않는다.
- 응답은 허용 가능한 집계 범위와 거부 이유를 구분한다.
- 후속 Turn마다 현재 session, conversation 소유권, 참조 Artifact의 객체 권한과 field·row 권한을 다시 검사한다. 앞 Turn에서 허용됐다는 이유로 철회된 권한이나 다른 사용자의 Artifact를 상속하지 않는다.
- 권한이 없으면 브라우저에 남은 과거 응답·View·보고서 바구니 복사본으로 대체하지 않고, 해당 Turn을 차단하며 query를 만들지 않는다.

### Conversation release 변경

- conversation 생성 시 `product_release_id`와 `semantic_release_id`를 고정하고 각 Turn·Artifact에 기록한다.
- active release가 바뀌어도 기존 conversation의 과거 Turn을 새 release로 조용히 재해석하지 않는다. 고정 release가 계속 실행 가능하면 그 release로 후속 Turn을 실행한다.
- 고정 release를 더 이상 실행할 수 없으면 Node 2·Trino 전에 차단하고 “기존 대화 열람” 또는 “최신 release로 새 대화 시작”을 명시적으로 선택하게 한다. 최신 release로 전환한 Turn을 같은 comparison에 섞지 않는다.
- 서로 다른 release의 Artifact를 비교하거나 한 보고서 바구니에서 같은 기준인 것처럼 합치지 않는다. 새 release로 필요한 항목을 재실행한 뒤 새 Artifact로 교체한다.

### Metadata·Glossary 문제

- DataHub 장애, stale cache, 삭제된 Term, 끊어진 관계, schema drift는 `METADATA_UNAVAILABLE` 또는 `SCHEMA_DRIFT`로 끝낸다.
- 오래된 로컬 JSON으로 조용히 성공하지 않는다.

### SQL 문제

- write, DDL, 다중 statement, Context 밖 column, 비허용 join은 `BLOCKED + SQL_POLICY_BLOCKED`다.
- 수정 가능한 컴파일 오류만 한 번 제한 수정하고, 재실패 시 종료한다.

### Prompt injection

- 사용자 질문뿐 아니라 DataHub alias·설명, schema 설명, source/result 문자열도 비신뢰 데이터다.
- 이 문자열의 지시문은 system 정책·승인 Context·tool allowlist를 바꾸지 못하며, 비승인 field·tool·secret 접근 시도를 차단한다.

**완료 증거:** 실제 dependency와 차단 단계, Trino 미호출 또는 cancelled query, 오류 코드, audit decision을 같은 trace에서 확인한다.

## 7. UF-05 취소·빈 결과·장애·부분 성공

| 경우 | 사용자 결과 | 서버 계약 |
|---|---|---|
| 실행 중 취소 | 취소됨, 결과 없음 | Trino query cancel 전파, `CANCELLED + REQUEST_CANCELLED` |
| 유효하지만 0행 | 조건·기간·출처와 빈 결과 안내 | `BLOCKED + EMPTY_RESULT`, 성공 차트 없음 |
| Source timeout | 재시도 가능 여부와 실패 source | bounded retry 후 `FAILED + QUERY_TIMEOUT` |
| 필수 source/block 실패 | 결과 사용 불가 | `FAILED + reason_code`, 지난 결과 대체 금지 |
| 선택 block 실패 | 핵심 결과와 누락 범위 | 의미가 유지될 때만 `PARTIAL + PARTIAL_FAILURE` |
| 모델 장애 | 실행 전/후 단계와 재시도 안내 | `FAILED + MODEL_TIMEOUT/DEPENDENCY_UNAVAILABLE`, SQL·결과 조작 금지 |
| 같은 conversation 동시 제출 | 입력 보존, 현재 Turn 완료 후 재시도 안내 | `409 CONVERSATION_BUSY`, 두 번째 Run·query 미생성 |
| 다른 탭의 stale head 제출 | 최신 Turn을 다시 불러오고 재확인 안내 | `409 CONVERSATION_CONFLICT`, `expected_head_turn_id` 불일치 |
| 새로고침 중 실행 | 기존 진행 상태에 재연결 | 같은 `client_turn_id`·request/run 복원, 중복 POST·query 금지 |

마지막 성공 결과를 보여 줄 수는 있지만 반드시 오래된 결과와 당시 data/glossary version을 표시하고 이번 Run의 결과로 저장하지 않는다.

### 새로고침·재인증·동시 제출

1. Conversation, Turn, 확정 Context snapshot, Artifact/View 참조와 보고서 바구니는 서버에 저장한다. URL 또는 서버가 반환한 `conversation_id`로 새로고침 후 복원하며 browser storage를 실행 원본으로 삼지 않는다.
2. 입력 중이지만 제출하지 않은 문구만 conversation별 임시 draft로 둘 수 있다. 재인증 뒤에도 서버 이력을 다시 읽고, 임시 draft가 서버 head Turn을 바꾸지 않는다.
3. 실행 중 새로고침하면 `client_turn_id`로 기존 command/request와 선택적 Analysis Run에 재연결한다. terminal commit 전에는 `turn_id`가 없으며 응답을 잃었다는 이유로 같은 질문을 자동 재제출하지 않는다.
4. P0에서는 conversation마다 active command lease 하나로 모든 head-changing mutation을 직렬화한다. Backend는 idempotency record를 head CAS보다 먼저 조회하므로 완료 응답 재전송은 head가 전진한 뒤에도 기존 Turn을 반환한다.
5. `CONVERSATION_BUSY` 또는 `CONVERSATION_CONFLICT`가 발생하면 두 번째 입력을 지우지 않고 최신 Turn을 복원한 뒤 사용자가 다시 제출하게 한다. 실패한 동시 제출을 성공 이력이나 Analysis Run으로 저장하지 않는다.
6. Backend 재시작 시 만료 lease의 비terminal Analysis Run을 reconcile한다. 실행 중 Trino query는 취소하고 결과 commit 여부가 불명확하면 `FAILED + ORPHANED_EXECUTION/RESULT_COMMIT_UNKNOWN`으로 닫는다. 자동 재조회하지 않으며 사용자가 명시적으로 새 Turn을 제출해야 한다.

## 8. UF-06 저장 분석과 Report 실행

### 분석 저장·재실행

1. analyst가 성공한 분석의 Definition과 parameter schema를 저장한다.
2. 저장 항목은 과거 Result가 아니라 재실행 가능한 Definition을 가리킨다.
3. 재실행 시 새 Run을 만들고 현재 권한·Glossary·Rule·Binding을 다시 검증한다.
4. 새 query ID와 artifact를 저장하고 과거 Run을 덮어쓰지 않는다.

### Report 초안·승인

1. analyst는 각 성공 Turn에서 현재 표시한 View의 `보고서에 담기` 또는 Artifact 전체의 `전체 분석 담기`를 선택한다. Conversation의 보고서 바구니는 값이나 화면 캡처가 아니라 `artifact_id`·version/checksum·`analysis_run_id`·`view_id/view_spec`·표시 제목을 서버에 저장한다.
2. 같은 Artifact의 그래프와 표는 서로 다른 바구니 항목으로 담을 수 있다. 완전히 같은 Artifact/View를 다시 담을 때는 중복을 알리고 사용자가 명시적으로 허용하지 않으면 하나만 유지한다.
3. 사용자는 여러 Turn의 항목 순서를 확인한 뒤 새 Report 초안을 만들거나 자신이 편집 가능한 기존 초안에 누적한다. Backend는 소유권·현재 권한·evidence·release를 검사하고 `expected_draft_revision` CAS와 append idempotency hash로 block 추가·순서·revision 증가를 한 transaction으로 commit한다. stale 편집은 `409 REPORT_DRAFT_CONFLICT`이며 기존 block을 덮지 않는다.
4. 각 data block은 현재 초안 미리보기용 `source_artifact_id`·View와 향후 Report Run용 소유 Analysis Definition의 ID·version·parameter schema·`period_mode`를 함께 참조한다. 재실행 가능한 Definition이 없는 Artifact는 승인된 source Run에서 Definition을 저장한 뒤에만 실행 가능한 data block으로 추가한다.
5. 그래프 유형·표 밀도·표시 View 같은 presentation 설정은 저장하되 Artifact 원본 값·근거를 복사하거나 변조하지 않는다. 이 단계에서 새 Analysis Run·Trino query를 만들지 않는다.
6. 바구니와 아직 확정하지 않은 초안은 새로고침 후 복원한다. 일부 항목의 권한·Artifact·checksum 검증이 실패하면 정상 항목까지 숨기지 않되, 실패 항목을 지난 성공 결과로 대체하거나 조용히 제외하지 않고 초안 반영을 중단해 사용자 선택을 받는다.
7. 승인 요청 시 stable block ID·order·`is_required`·criticality policy, Definition·parameter·period mode·ViewSpec, product/semantic release를 checksum으로 고정한 immutable Report Version을 만들고 승인 큐에 전달한다.
8. report_admin이 할당·소유권을 확인하고 승인 또는 반려한다.
9. 승인은 위 snapshot과 layout·static text를 고정할 뿐 미래 데이터 값이나 미래 schema 호환을 승인하는 것이 아니다.
10. 수정은 새 Version을 만들며 승인된 snapshot을 바꾸지 않는다.

**바구니·초안 완료 증거:** 사용자가 두 개 이상의 Turn에서 그래프와 표를 담고 새로고침한 뒤 같은 순서·Artifact checksum·View 설정으로 바구니를 복원한다. 이어서 새 초안 또는 기존 초안에 한 번 반영했을 때 block 수·순서·Definition/Artifact/View 참조가 App DB와 브라우저에서 일치하고, 이 과정의 Trino 호출은 0건이어야 한다.

### 수동 실행

1. 실행 actor인 `report_admin`이 승인된 Version을 실행한다.
2. Backend는 승인 Version의 product/semantic release와 하나의 `report_as_of`를 사용하고, canonical idempotency hash에 version·release·`report_as_of`를 포함한다. active pointer를 다시 읽지 않으며 고정 release가 실행 불가하면 Report Run과 Turn 생성 전 `409 RESOURCE_CONFLICT`다.
3. Report Run 시작 시 Definition 원 소유자를 effective subject로 고정하고 subject별 현재 권한·활성 상태를 하나의 `report_permission_snapshot_id`로 만든다. 모든 child Analysis Run이 같은 snapshot을 참조하며 관리자 권한으로 확대하지 않는다. 이는 독립 사용자 Analysis Run마다 새 snapshot을 만드는 규칙의 Report 일관성 예외다.
4. App은 인증된 query service identity로 Trino에 접속하고 actor·effective subject·service identity·policy version을 함께 기록한다.
5. `ABSOLUTE` 기간 block은 원 절대 기간을 유지하고, 승인된 `RELATIVE` template block만 `report_as_of`를 기준으로 새 절대 기간을 계산해 화면·DB에 남긴다. Conversation의 과거 anchor를 Report Run에 재사용하지 않는다.
6. 각 data block은 고정된 `semantic_release_id`의 Glossary·Rule·Binding으로 새 Analysis Run과 `result_artifact_id`를 실제 생성한다.
7. 저장 ViewSpec은 새 Artifact의 field role·grain·type과 다시 호환 검증한다. 호환되지 않으면 `VIEW_SCHEMA_INCOMPATIBLE`로 block을 실패시키며 초안의 source Artifact 값·screenshot·과거 query로 대체하지 않는다.
8. block별 status·reason·checksum·Term/Asset/query 근거를 Report Run에 연결하고 APP-G3를 다시 통과한다.
9. 필수 block 실패 시 Report Run을 `FAILED`; 핵심 의미가 유지되는 선택 block 실패만 `PARTIAL`로 둔다.
10. 재시작 후 App DB에서 Version·Run·Block Run·artifact를 복원한다.

P0에서 저장 Report Run과 Artifact는 소유 `analyst`와 권한 있는 `report_admin`만 제품 안에서 열람한다. 사업책임자는 별도 로그인 역할이 아니며 승인된 결과의 조직 내 수동 전달은 제품 밖 절차다. export 전달·열람 UI와 직접 열람 역할은 P1 이후 별도 계약으로 둔다.

**완료 증거:** 실행 이력 행만 생기는 것으로는 부족하다. 각 data block의 새 `analysis_run_id`와 Trino `query_id`가 있어야 한다.

**현재 간극:** 현재 report execution은 claim의 `owner_id`를 replay owner로 전달한다. 이것이 항상 각 Analysis Definition 원 소유자와 같은지, 세 신원이 분리 감사되는지, 비활성 owner를 차단하는지는 검증되지 않았다.

## 9. P1 이후 흐름

예약 실행, 자유형 작성 지원, conversation을 넘는 장기 기억·사용자 성향 기억, MCP 조회는 P1이다. P0 Report 수동 실행과 bounded multi-turn이 L3로 검증되고 idempotency·권한·실패 의미가 고정되기 전에는 장기 memory, 예약 UI나 worker를 확장하지 않는다.

## 10. 화면 증거의 사용 원칙

- screenshot은 화면 상태를 보여 주는 보조 증거다.
- 실제 서비스 증거는 브라우저 network, HTTP, backend trace, DataHub/Trino 호출, App DB artifact가 같은 ID로 연결된 묶음이다.
- 합성·재구성·디자인 시안 이미지는 반드시 `mockup`으로 표기하고 실행 증거 폴더에 두지 않는다.
- 실제 screenshot에는 commit·release·run ID를 함께 기록하되 secret이나 민감 결과를 넣지 않는다.
