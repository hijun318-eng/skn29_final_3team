# Answervice 아키텍처와 전환 계약

## 1. 결론

v3.4에서도 P0는 React·FastAPI·PostgreSQL·DataHub·Trino 기반 modular monolith와 결정론적 Analysis Core를 유지한다. 승인 데이터 전환, Semantic Contract, G1/G2/G3, 실제 E2E 증거가 먼저다. P1은 이 Core를 `analysis.run`으로 감싼 뒤 Analysis·RAG·ML Agent와 안전한 MCP Tool을 연결한다. Neo4j는 DataHub·Semantic Registry의 승인 관계를 읽기 전용으로 투영한 선택형 보강 계층이며 Core의 필수 의존성이 아니다.

문서 기준은 **Answervice v3.4 / Walkerhill V4.3 / 2026-08-19**다. 목표 구조와 실제 구현 완료 상태는 구분하며, V4.3 실제 적재·조회 성공은 실행 evidence가 있을 때만 완료로 판정한다.

이 문서는 세 상태를 섞지 않는다.

- **현재 구현 확인:** repository에서 읽은 코드·설정
- **P0 목표:** 이번 Vertical Slice의 필수 구조
- **P1/P2 후보:** P0 이후 실측에 따라 채택할 수 있는 구조

## 2. 현재 구현 확인

```text
Browser
  → Nginx + React/Vite
  → FastAPI modular monolith
      → external OpenAI-compatible model
      → DataHub GraphQL
      → Trino
          → PMS / POS / CRM / Banquet / Facility Source DB
      → App PostgreSQL
```

확인된 한계는 다음과 같다.

- production adapter는 DataHub의 전체 release snapshot·semantic search·native governance를 읽고 Trino schema와 교차 검증하며, 요청별 static Context JSON·고정 source registry·키워드 ranking을 사용하지 않는다.
- DataHub catalog snapshot은 bounded TTL single-flight로 갱신되지만 refresh 실패 때 stale 값을 반환하지 않는다. 이 때문에 catalog completeness가 확보되지 않은 환경은 의도적으로 `NOT_READY`다.
- SQL 생성·검증·binding은 Schema Context와 하나의 SQLGlot AST 결과를 공유한다. 단일 승인 `VIEW_REUSE` 공통 연산은 typed plan에서 결정론적으로 생성하고, 다중 asset 후보만 제한된 Node 2를 거친다. prompt와 repair가 특정 FQN·CTE 답안을 보유하지 않는다.
- CI의 model/data test double은 contract lane으로만 명명한다. live Trino·DataHub·model·App DB 검증은 환경변수와 실제 release가 없으면 skip하며 제품 E2E로 간주하지 않는다.
- 실제 Frontend HTTP client, FastAPI orchestration, external model adapter, DataHub/Trino adapter, App DB persistence 코드는 존재한다. 그러나 2026-08-16 live DataHub에는 기대 scope 일부와 Dataset semanticContent가 없어 positive E2E receipt를 만들 수 없었다.
- semantic-search Compose DAG와 generic producer는 소스에 반영됐지만 현재 실행 중 stack은 이전 OpenSearch 구성이다. 구조 검증 통과와 live rollout 완료를 구분한다.
- 현재 Agent 화면은 질문 하나와 Run 하나만 렌더링하고 `POST /analysis`도 `question`, `parameters`만 받는다. clarification은 이전 요청을 resume하지 않고 문자열을 붙인 새 요청이며 현재 제품 동작은 **single-turn**이다.
- App DB의 `chat.conversations`, request의 nullable `conversation_id`, Backend `RequestContext.conversation_id`는 골격으로 존재하지만 runtime 생성·조회·소유권·Turn 이력·head 동시성에 연결되지 않았다.
- Report는 여러 block과 Artifact 기반 문서를 만들 수 있지만 대화에서 선택한 여러 Artifact·View를 같은 초안에 누적하는 orchestration은 없다. 따라서 현재 구조를 multi-turn 또는 대화 기반 보고서 조합 완료라고 설명할 수 없다.

따라서 현재 구조는 동적 거버넌스 구현과 fail-closed negative 검증을 통과했지만, 완전한 catalog publish·semantic indexing·positive live query가 없는 상태에서 “실제 서비스 완료”라고 설명할 수 없다.

## 3. P0 목표 구조

### 요청 경로

```text
User
  → React/Nginx
  → FastAPI API + application services
      ├─ Auth/RBAC + object policy
      ├─ Conversation Orchestrator
      │   ├─ owner·head·product_release_id·wall_clock_anchor
      │   ├─ command/idempotency lookup → expected-head CAS + active lease
      │   ├─ Understanding preflight: 원문 → 표현 정규화·승인 alias 후보·typed candidate
      │   ├─ 직전 승인 명세 + 현재 Turn → inherited/changed fields
      │   ├─ unique-resolution validator → 확정 또는 최소 명확화
      │   └─ ANALYSIS / PRESENTATION / REPORT_ACTION routing
      ├─ Conversation·Turn·Run·Artifact·View·Report state ─→ App PostgreSQL
      ├─ resolved ANALYSIS → 새 원자적 Analysis Run
      │   ├─ Glossary/asset discovery ───────────────────→ DataHub
      │   ├─ Rule registry + APP-G1
      │   ├─ Node 2 SQL compile ─────────────────────────→ Model adapter
      │   ├─ APP-G2 + query budget
      │   ├─ read-only execute ──────────────────────────→ Trino → 5개 논리 Source / 4종 DBMS
      │   └─ APP-G3 + immutable Artifact ────────────────→ App PostgreSQL
      ├─ PRESENTATION → 호환 시 같은 Artifact + 새 ViewSpec, query 없음
      └─ REPORT_ACTION → 선택 Artifact + ViewSpec을 Draft block에 연결

Report admin
  → React/Nginx
  → Report workflow
      ├─ draft → immutable approval version
      ├─ approve/reject with object policy
      └─ manual run → block마다 새 Analysis Run → 위 APP-G1/APP-G2/Trino/APP-G3 경로
                                               └→ App PostgreSQL
```

네 개의 Archify 시각화는 위 읽기 순서와 [`../architecture/README.md`](../architecture/README.md)에 둔다. 논리 컴포넌트에는 특정 data release 이름 대신 `승인 데이터`, `승인 Serving`, `호텔 운영 Source`를 사용한다. 실제 버전명·namespace·checksum은 정적 감사와 evidence에만 기록한다. HTML은 설명용이며 구현 완료 증거는 아니다. HTML receipt의 source evidence `verified`는 pinned commit에 source path가 존재한다는 뜻일 뿐 제품 기능 검증이 아니다.

### v3.4 P1 확장 경로

```text
General Orchestrator
  ├─ Analysis Agent → analysis.run → 결정론적 Analysis Core
  ├─ RAG Agent      → rag.search   → 문서 Evidence
  └─ ML Agent       → ml.predict   → 승인된 Forecast Task

복잡한 Cross-domain 질문 또는 관계·경로 재계획만:
semantic.resolve → graph.resolve → 후보 Context
→ Semantic Contract 재검증 → G1/G2/Trino/G3
```

MCP Tool 7개는 `analysis.run`(수치 분석), `artifact.get`(검증 결과 조회), `semantic.resolve`(의미 규칙 확인), `graph.resolve`(관계 후보 탐색), `rag.search`(문서 근거 검색), `ml.predict`(승인 예측), `report.add_block`(보고서 블록 추가)다. 모두 읽기 전용 또는 승인된 고수준 동작만 제공한다. `execute_raw_sql`, 자유 Cypher, 임의 Table 조회, Policy 우회 Tool은 제공하지 않는다. Report는 Agent가 아니라 Artifact와 승인 Workflow를 다루는 Service다.

| 논리 용어 | 뜻 |
|---|---|
| 승인 데이터 | 모든 Gate를 통과해 현재 사용자 기본 경로가 조회하는 데이터 |
| 후보 데이터 릴리스 | 검증 중이며 아직 사용자 기본 경로가 아닌 데이터 |
| 이전 승인 릴리스 | 장애 때 복구할 수 있도록 보존한 직전 기본 데이터 |
| 승인 Serving | 앱이 직접 조회하는, 검증된 통합 view 계약 |

### single-turn 실행과 bounded multi-turn 조율

`single-turn`과 `multi-turn`은 서로 대체하는 선택지가 아니다. P0는 두 층을 겹쳐 쓴다.

| 층 | 불변 원칙 | 이유 |
|---|---|---|
| Conversation·Turn 조율 | 같은 업무 대화의 승인된 조건, 변경분, 현재 초점 Artifact·View·Draft를 구조화해 연결 | `그 전 달은?`, `다른 그래프로`, `표로도`, `보고서에 담기`를 안전하게 해석하기 위해 |
| Atomic Analysis Run | preflight에서 완전하게 resolved된 Analysis Turn만 새 Run을 만들고 현재 권한·APP-G1/G2/G3·Trino를 통과 | 모호/범위 밖 Turn에는 Run을 만들지 않고 과거 권한·SQL·결과도 재사용하지 않기 위해 |
| Presentation View | source Artifact에 필요한 grain·column이 있으면 새 query 없이 결정론적 ViewSpec만 저장 | 같은 값을 다시 조회하는 비용과 서로 다른 query처럼 보이는 거짓 lineage를 막기 위해 |
| Report block | 사용자가 선택한 `artifact_id + view_spec_id + analysis_definition_id`를 연결 | 채팅 문장·화면 캡처를 데이터 근거로 복사하지 않기 위해 |

권위 있는 대화 상태는 raw transcript나 모델 memory가 아니다. 서버가 검증한 `metric_ids`, 절대 기간, dimension, filters, grain, 비교 규칙, `wall_clock_anchor`, data watermark, `product_release_id`, source Turn·Artifact·View 참조다.

| 이해 계층 | 역할 | 안전 경계 |
|---|---|---|
| Deterministic normalizer | Unicode·공백·날짜 형식·승인 exact alias의 의미 보존 정리 | 자유 의미를 정규식으로 추측하지 않음 |
| GPT/Node 1 candidate parser | 반말·존댓말·어순·축약·경미 오탈자·지시어를 typed candidate로 생성 | 공식 Metric·권한·실행을 결정하지 않음 |
| Deterministic resolver | metadata visibility를 적용한 DataHub Term, Rule, source Turn, Artifact schema로 하나만 확정 | 복수 후보·critical token 변화는 명확화 |

상대기간은 `WALL_CLOCK`과 `SOURCE_PERIOD`를 구분한다. “이번 달/지난·저번 달”은 Backend-owned `wall_clock_anchor`와 `Asia/Seoul`, “그 전 달/다음 달”은 명시 `source_turn_id`의 절대 기간을 기준으로 한다. production은 client clock override를 신뢰하지 않고 wall clock 기준 변경은 새 Conversation만 허용한다. 이 clock과 release/Asset의 `data_available_from/through` watermark는 별도 필드이며 서로 대신 쓰지 않는다. 달력 기간이 범위 밖이라고 최신 가용 월로 바꾸지 않는다.

실행 중에는 idempotent command/request, Conversation active lease와 resolved Analysis의 Run 상태·attempt·heartbeat·외부 query 제출 증거만 mutable하다. Turn·Conversation head·focus·ViewSpec·Draft block 같은 사용자 가시 domain mutation은 terminal commit 전까지 불변이다. 같은 key/hash 재전송 조회가 head CAS보다 먼저다. preflight가 모호성·범위·지원 intent를 해결하지 못하면 Run 없이 terminal Turn을 commit한다. resolved Analysis만 Run을 만들고, 완료 시 Run terminal 상태·결과 Artifact 또는 ViewSpec/focus·Draft block, command terminal화·immutable Turn·새 head·lease 해제를 한 App DB transaction으로 commit한다.

상속 가능한 사용자 slot은 필드별 `INHERIT/SET/REMOVE`와 `USER_REQUESTED` provenance를 가진다. `POLICY_REQUIRED_FILTER`와 permission constraint는 focus나 과거 Turn에서 상속하지 않고 각 새 Analysis Run의 현재 entitlement로 다시 만든다. data focus는 `SUCCEEDED Analysis + Safe Artifact`만, View focus는 성공 Presentation만 갱신한다. Report Action과 `PARTIAL/BLOCKED/FAILED/CANCELLED` Turn은 기존 focus를 바꾸지 않는다.

P0는 Conversation당 선형 head 하나와 명시 참조 최대 두 Turn만 지원한다. `expected_head_turn_id`와 idempotency key로 이중 클릭·다중 탭의 stale write를 차단한다. branch·merge, Conversation 사이 장기 기억, vector memory, 전체 transcript 재주입, 자율 계획은 P0 범위가 아니다.

Report 수동 실행의 신원은 세 층으로 분리한다.

- **실행자(`actor`)**: 실행 버튼을 누르고 승인 책임을 지는 `report_admin` 또는 같은 `report.manage` Capability가 명시된 통제 환경의 `platform_admin`
- **권한 기준 사용자(`effective_subject`)**: Report block이 참조한 Analysis Definition의 원 소유자. Report Run 시작 시 subject별 **현재 권한**을 한 번 snapshot으로 고정하고, 그 Report Run의 모든 child Analysis Run은 같은 `report_permission_snapshot_id`를 참조한다. 이는 독립 사용자 Analysis Run마다 새 snapshot을 만드는 일반 규칙의 명시적 일관성 예외다.
- **서비스 신원(`service_identity`)**: App이 Trino에 접속할 때 쓰는 인증된 query principal

승인자가 `platform_admin`처럼 더 강한 권한을 가졌더라도 Definition owner보다 넓은 데이터를 조회하지 않는다. 세 신원과 policy version을 같은 audit에 남긴다.

## 4. 의미 체계 권한 모델

DataHub만으로 계산 가능한 서비스가 되는 것은 아니다. 중앙 의미와 실행 규칙을 다음처럼 분리한다.

| 계약 | 원본 | 필수 연결 |
|---|---|---|
| 이름·별칭·정의·단위·Domain·Owner·승인 | DataHub Glossary | immutable Term URN + release/checksum |
| 관련 Dataset·Column·lineage | DataHub relation | 승인 Asset URN |
| 계산식·filter·join·time·identity·permission | versioned Rule Layer | Term URN + rule version |
| 실제 존재·삭제·schema | DataHub + Trino preflight | observed version/time |
| local JSON | bootstrap·test·검증된 cache | source environment/version/checksum/expiry |

Runtime 순서는 다음과 같다.

```text
Node 1 typed intent
  → DataHub 승인 Term 발견
  → Term 관련 승인 Asset 발견
  → 사용자 권한 필터
  → DataHub schema·상태 검증
  → Term에 연결된 Rule 조회
  → Approved Context
  → APP-G1
  → Node 2
```

DataHub 장애에서 cache가 사용되려면 기대 environment·version·checksum이 같고 만료 전이어야 한다. 조건을 만족하지 못하면 `METADATA_UNAVAILABLE`이며 로컬 JSON 독립 판단으로 성공하지 않는다.

Glossary만 따로 활성화하지 않는다. `Glossary Term·관계 + Rule + Binding + policy`를 하나의 `semantic_release_id` manifest로 묶는다. DataHub aspect publish 자체는 원자적이지 않으므로 P0는 staging 또는 release별 shadow/versioned URN 집합으로 후보를 바깥쪽 게시(out-of-place publish)한다. publisher가 후보 Term·관계·Rule·Binding·policy를 전부 다시 읽어 checksum을 확인하기 전에는 runtime에 노출하지 않는다. DataHub 외부 직접 수정은 RBAC로 막고 runtime은 manifest가 허용한 immutable URN만 읽는다. 이 단계가 **candidate readiness**다. candidate canary는 전역 pointer를 바꾸지 않고 명시적 `product_release_id`로 조회한다. **activation**은 pre-cutover Gate 승인 뒤 active pointer와 기본 data/App process를 같은 ID로 전환하는 별도 단계다. policy checksum은 정책 버전이며 사용자별 entitlement는 각 Run의 permission snapshot이다.

### 선택형 Neo4j 의미 Graph

권한 방향은 한쪽이다.

```text
DataHub Local Snapshot + Semantic Registry Release  ← 정본
  → Release 단위 Batch Projection
  → schema·참조·중복·고아 관계·version 검사
  → Neo4j Semantic Graph                            ← 파생·읽기 전용
  → graph.resolve의 고정/파라미터 Traversal
  → Candidate Context
  → Semantic Contract + G1 재검증                   ← 최종 결정
```

Neo4j에는 Metric·BusinessTerm·Dimension·Dataset/View·Column·Grain·TimeRule·Role과 승인 관계만 넣는다. Raw 예약·매출·고객 row, PII 원문, 사용자별 Effective Policy, 검증되지 않은 LLM 관계는 넣지 않는다. Graph 장애나 timeout은 `GRAPH_ENRICHMENT_UNAVAILABLE`로 기록하고 Registry-only 경로로 돌아간다. `ACCESS_DENIED`, PII·쓰기·미승인 Join·데이터 범위 실패는 fallback하지 않고 fail-closed한다.

## 5. 승인 데이터 단계적 전환 순서

제공된 새 SQL로 전환하는 결정은 끝났지만 즉시 기본 경로로 바꾸는 것은 아니다. 논리 아키텍처에서는 특정 버전명을 쓰지 않고 다음 Gate만 고정한다. 정확한 namespace·view·checksum은 정적 감사와 cutover evidence가 담당한다.

현재 data release 선택은 startup 환경변수로 만든 process-local adapter에 결합돼 있고 semantic 선택은 별도 pointer이므로 서로 다른 릴리스가 섞일 수 있다. P0는 code/image·data·semantic·prompt/model/policy·migration·cache namespace를 하나의 `product_release_id`로 고정하고 readiness에서 일치 여부를 검사한다. zero-downtime을 주장하지 않으며 canary/staging에서 process 교체와 rollback을 연습한다. 예상 중단시간·RTO·RPO·측정 시작/종료점·rollback trigger·결정 책임자를 rehearsal 전에 고정한다.

비개발자는 아래 네 묶음으로 읽으면 된다.

| 묶음 | Gate | 답해야 하는 질문 | 실패 시 |
|---|---|---|---|
| 1. 원천 준비 | DATA-G0~G3 | 격리됐고, SQL이 실행되며, 행·키·금액이 계약과 맞는가? | 후보 중단, 현재 승인 데이터 유지 |
| 2. 현실성·재현성 | DATA-G4~G5 | 분포를 사람이 승인했고 같은 seed를 깨끗하게 재생할 수 있는가? | 새 checksum의 후보로 다시 시작 |
| 3. 통합·보안 | DATA-G6~G7 | Serving 값·grain·fan-out이 맞고 인증된 read-only 경계인가? | App 연결·canary 금지 |
| 4. 제품 전환 | semantic read-back → Gold 봉인 → canary → rollback rehearsal(복구 훈련) → cutover | 같은 제품 릴리스가 실제 사용자 경로와 복구 조건을 통과했는가? | 기본 pointer를 바꾸지 않음 |

1. **SQL 정합성:** 원본 archive는 불변 보존하고, 알려진 연회 status history 결함과 validator 모순을 수정한 derived release checksum을 새로 고정한다.
2. **격리 적재:** 새 release namespace에 5개 DB를 적재하고 DBMS별 validator·row count·constraint를 통과한다. 모든 Source에 release 전용 read-only `SELECT` 권한을 명시하고 Trino·DataHub principal에서 visibility를 검증한다.
3. **재현성:** 깨끗한 volume에서 동일 seed를 재적재해 row/hash와 수행 시간을 비교한다.
4. **Serving·검증용 oracle 초안:** release manifest가 선언한 모든 view를 만들고 제품 Gold와 분리된 `serving reconciliation oracle`로 값·grain·fan-out·중복·null·row/hash를 검증한다. 운영매출 Golden Path는 승인된 통합 mart 한 개를 조회하고 lineage로 다중 source 근거를 제시한다. 동적 multi-asset JOIN은 별도 계약 없이는 주장하지 않는다.
5. **복합 의미 후보 게시·역검증:** 후보 Dataset·Column과 Glossary Term·Domain·Owner·승인·관계를 versioned/shadow 영역에 게시한다. Rule·Binding·policy까지 `semantic_release_id`로 묶어 API로 전체 역검증하되 전역 active pointer는 바꾸지 않는다.
6. **최종 제품 Gold 봉인·App 연결:** 후보 의미 계약이 확정된 뒤 product Gold·tolerance·held-out checksum과 Golden Dialogue를 봉인한다. registry, binding, rule, context, prompt, API fixture, Conversation routing·View compatibility 계약을 같은 후보 `product_release_id`로 연결한다. release registry의 전체 asset 수와 요청당 Context 상한은 별도 안전 한도로 유지한다.
7. **Candidate canary:** 현재 승인 경로는 rollback용으로 유지하고 명시적 후보 ID를 실제 E2E·권한·실패·bounded multi-turn·보고서 조합 흐름에서 검증한다. 서로 다른 릴리스의 금액이 같다고 기대하지 않는다.
8. **복구 훈련(rollback rehearsal):** canary/staging의 candidate process를 후보→이전 승인 릴리스→후보 순서로 전환하고, 데이터 손실·cache 오염 없이 복구되는지와 사전 승인한 중단시간·RTO·RPO를 측정한다.
9. **전환 전 승인과 기본값 변경:** 지정 승인자는 candidate DATA-G0~G7, semantic candidate read-back, `P0-GOLD`, `P0-GOLDEN-DIALOGUE`, `P0-E2E-REAL`, `P0-REPORT-RERUN`, `P0-SECURITY`, `P0-FAILURE`, `P0-QUANT`, rollback rehearsal receipt를 모두 승인한다. 그 뒤에만 data·semantic·App process의 기본값을 같은 `product_release_id`로 바꾼다. DATA-006의 activation·readiness·Golden smoke는 전환 후에 닫는다.
10. **전환 후 확인:** 새 process의 readiness·Golden smoke를 확인한다. 실패하면 즉시 연습한 rollback을 실행하며, 성공 receipt까지 있어야 전환 Gate를 `VERIFIED`로 올린다.
11. **구 경로 폐기:** 안정화·관찰 기간과 별도 승인 후 제거한다. 이 작업에서 삭제하지 않는다.

archive 내부 compose는 새 Source SQL을 자동 적재하는 완결된 installer로 간주하지 않는다. 실제 mount·적용 순서와 volume 이름을 cutover runbook에서 명시적으로 검증한다.

## 6. 신뢰·보안 경계

```text
Untrusted: Browser input, raw transcript, model output, claimed Trino username
    ↓ server validation
Trusted by version: session, RBAC policy, DataHub approved term/relation,
                    Rule contract, APP-G1/G2/G3 decision, release manifest
    ↓ read-only credential
Execution: Trino → Source DB
    ↓ safe projection
Persistence: App DB artifact/audit → Frontend
```

- Frontend와 model output은 항상 untrusted다. 사용자 질문뿐 아니라 Glossary alias·설명, schema 설명, source/result 문자열도 prompt injection 가능한 데이터로 취급한다.
- Source DB credential은 read-only 최소 권한이어야 한다.
- Trino는 개발·운영 모두 HTTPS, password 인증, CA 검증과 service identity를 강제한다. 익명 statement와 임의 `X-Trino-User` 주장은 거부하며 무인증 데모 경로를 제공하지 않는다.
- P0 인수 환경은 App이 주장한 `X-Trino-User` 값만으로 신원을 결정하지 않는다. 전용 query service principal, credential 저장·rotation·폐기 절차, 서버 권한 mapping, 다른 principal 사칭 negative test를 security manifest에 고정한다. 외부 연결 없는 `MockTransport`는 단위 테스트의 명시적 의존성 주입으로만 허용한다.
- 외부 모델에는 승인된 최소 context만 전송하고 raw source row·secret·불필요한 PII를 보내지 않는다.
- 과거 대화 원문을 모델 권한이나 실행 Context로 신뢰하지 않는다. 상속 가능한 typed field는 server-side source Turn과 checksum을 가지며 매 Turn 변경 diff를 남긴다.
- cancel은 Trino query까지, timeout은 의존성까지 전파한다.
- result·trace·log에는 permission snapshot과 version을 남기되 secret·민감 원문을 남기지 않는다.

## 7. 배포와 관측

P0 release unit은 하나의 `product_release_id`가 가리키는 다음 묶음이다.

```text
code commit
+ Docker image digests
+ approved data release/checksums
+ composite semantic release ID
  - DataHub Glossary/relation checksum
  - Rule/Binding/policy checksum
+ cache namespace
+ context/policy/prompt/model versions
+ DB migrations
```

`product_release_id`는 검증 시작 전에 봉인하는 immutable candidate manifest ID다. Golden·security·rollback 결과를 이 ID 계산에 다시 넣지 않는다. 실행 뒤 receipt는 candidate ID를 참조하는 append-only `evidence_bundle_id`로 별도 봉인하고, cutover 승인은 `product_release_id + evidence_bundle_id` 쌍을 기록한다. 실패를 고친 후보는 새 product ID와 새 evidence bundle로 처음부터 검증한다.

필수 식별자는 `conversation_id`, `turn_id`, 선형 부모 `reply_to_turn_id`, ordered `source_turn_ids`(P0 최대 2), 선택적 `clarifies_turn_id`, `request_id`, `analysis_definition_id`, `analysis_run_id`, `artifact_id`, `view_spec_id`, `report_version_id`, `report_run_id`, `query_id`다. 한 대화의 각 Turn에서 routing 결정, 상속·변경 field source, Run 또는 View/Report action과 최종 evidence를 연결할 수 있어야 한다. owner UI 원문은 암호화 message store와 보관·삭제 정책으로 격리하고 redacted utterance만 generic audit·trace에 남긴다.

관측 항목은 Turn routing 정확도·확인 요청률·잘못된 상속률, PRESENTATION의 불필요한 model/Trino 호출률, stale head·idempotency 충돌, 단계별 latency, model retry, APP-G1/G2/G3 거부 사유, Trino scanned rows/bytes, result rows, cancellation, source/DataHub readiness, DataHub cache hit·stale·reconciliation과 out-of-band 변경 탐지, report block 상태다. 임의 수치 목표보다 기준선과 표본 수를 먼저 측정한다.

## 8. P1·P2 확장 경계

| 확장 | 도입 조건 | P0 영향 원칙 |
|---|---|---|
| 예약 실행·worker | 동시성·긴 실행·재시도 필요 실측 | 같은 Report/Analysis 계약 재사용 |
| MCP Tool + 3 Agent | `analysis.run`·`semantic.resolve`·`rag.search`·`ml.predict`의 실제 호출과 평가 | G1/G2/G3·RequestContext 우회 금지 |
| Neo4j 의미 Graph | 복잡한 Cross-domain 후보 탐색과 재계획 회복이 OFF 대비 실측 개선 | 정본은 DataHub·Registry, 장애 시 Registry-only |
| RAG·ML Capability | Retrieval Gold Set과 Forecast baseline 대비 가치 검증 | 별도 adapter, 구조화 AgentResult, 부분 실패 표시 |
| IAM/SSO | 실제 조직·고객 요구 | principal mapping을 바꾸되 객체 권한 유지 |
| 다중 인스턴스 | 부하·가용성 기준 초과 | idempotency·distributed state 선행 |
| Microservice 분리 | 독립 배포·소유권·scale 필요가 반복 실측됨 | 경계별 contract/evidence 유지 |
| 장기 대화 기억·branch/merge | bounded multi-turn 정확도와 개인정보·삭제 정책 검증 | P0 typed Turn·lineage를 우회하지 않음 |

지금부터 P1/P2를 그릴 수는 있지만 구현됐다고 표시하지 않는다. P0 modular monolith에서 책임 경계를 코드 모듈과 계약으로 먼저 분리한다.

## 9. Architecture Decision

| 결정 | 이유 | 재검토 Trigger |
|---|---|---|
| P0 modular monolith 유지 | 현재 병목은 서비스 분해가 아니라 data·semantic cutover와 실제 E2E | 팀 소유권·scale·배포 독립성 실측 |
| DataHub Glossary 중앙 의미 기준 | 변경 반영·승인·관계·소유권의 단일 원본 필요 | DataHub 기능·가용성 한계가 측정됨 |
| Rule Layer 별도 유지 | Glossary는 실행 가능한 SQL 정책 전체를 대신하지 않음 | DataHub가 검증 가능한 rule artifact를 공식 지원 |
| local JSON 제한 | bootstrap/test/cache는 유용하지만 독립 원본은 drift 위험 | 항상 online인 metadata architecture 확정 |
| same-release E2E Gate | screenshot·mock·과거 결과의 거짓 완료 차단 | 없음 |
| 원자적 single-turn Run + bounded multi-turn 조율 | 대화 편의성과 실행 재현성·권한 재검증을 동시에 지키기 위해 | Golden Dialogue 실패율·지연·비용이 수용 불가할 때 범위 축소 |
| 표현 변경은 Artifact 재사용 | 같은 값의 불필요한 query와 거짓 lineage 방지 | 요구 View에 필요한 grain이 없어 새 분석이 반복될 때 승인 query 계약 추가 |
| Neo4j는 읽기 전용 Projection | DataHub·Registry와 권한 정본을 중복시키지 않고 관계 탐색만 확장 | OFF/ON Gold Set에서 Recall·회복률·지연 이득이 없으면 기능 OFF |
| Report는 Service 유지 | 승인·부분 실패·Artifact lineage는 자율 Agent보다 결정론적 Workflow가 적합 | 자연어 보고서 조율이 반복 병목으로 측정될 때 상위 Route만 확장 |
