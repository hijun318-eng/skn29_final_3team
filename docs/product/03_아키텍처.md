# Answervice 아키텍처와 전환 계약

## 1. 결론

React·FastAPI·PostgreSQL·DataHub·Trino 기반 modular monolith와 결정론적 Analysis Core는 유지한다. 전환 목표는 **DataHub-first Governed Capability Architecture**다. DataHub는 Glossary, Dataset/schema, Search, lineage, Context Documents, Structured Properties와 capability Gate를 통과한 native semantic authoring의 권위 원본이다. App은 entitlement, release activation/receipt, Conversation, SQL·ML 실행, APP-G1/G2/G3와 Artifact를 소유하며, 별도 semantic authoring 원본을 새로 만들지 않는다.

문서 기준은 **Answervice v3.4 baseline + DataHub-first 전환 계약 / 2026-08-22**다. 목표 구조와 실제 구현 완료 상태는 구분하며, 실제 적재·조회 성공은 같은 product release의 실행 evidence가 있을 때만 완료로 판정한다. `semantic.resolve`는 외부 MCP Tool이 아니라 내부 Context Gateway operation이다. Neo4j와 `graph.resolve`, semantic/hybrid 검색은 정량 Gate를 통과할 때만 도입하는 조건부 경로이며 P0/P1 critical path가 아니다.

이 문서는 세 상태를 섞지 않는다.

- **현재 host:** repository의 dirty source에서 읽은 코드·설정
- **deployed/live:** 실행 image·registry·DB를 read-only로 관측한 상태
- **목표:** DataHub-first 단계별 Gate를 통과한 뒤의 구조

## 2. 현재 구현 확인

```text
Browser
  → Nginx + React/Vite
  → FastAPI modular monolith
      → external OpenAI-compatible model
      → DataHub GraphQL
      → Trino
          → PMS / POS / CRM / Banquet / Facility Source DB
      → App PostgreSQL
```

2026-08-22 Phase 0A 감사에서 상태를 다음처럼 분리했다.

Conversation command 경로는 생겼지만 key와 `expected_head_turn_id`가 선택적이고, 저장 hash
비교보다 replay가 먼저이며, terminal Analysis/Artifact와 Turn/head/lease 전체의 recovery 계약이

설명하지 않는다. 위 표는 2026-08-22 당시 감사 snapshot이며, 삭제된 과거 감사 archive를
현재 증거로 대체하지 않는다. 현재 상태는 코드·설정·마이그레이션·실행 evidence로 다시 판정한다.

## 3. P0 목표 구조

### 요청 경로

```text
User
  → React/Nginx
  → FastAPI API + application services
      ├─ Auth/RBAC + object policy
      ├─ Conversation Orchestrator
      │   ├─ owner·head·product_release_id·wall_clock_anchor
      │   ├─ command/idempotency lookup → expected-head CAS + active lease
      │   ├─ Understanding preflight: 원문 → 표현 정규화·승인 alias 후보·typed candidate
      │   ├─ 직전 승인 명세 + 현재 Turn → inherited/changed fields
      │   ├─ unique-resolution validator → 확정 또는 최소 명확화
      │   └─ ANALYSIS / PRESENTATION / REPORT_ACTION routing
      ├─ Conversation·Turn·Run·Artifact·View·Report state ─→ App PostgreSQL
      ├─ resolved ANALYSIS → 새 원자적 Analysis Run
      │   ├─ bounded lexical Search(URN/type) ────────────→ DataHub
      │   ├─ entitlement + active release membership
      │   ├─ 최소 RuntimeCatalogProjection
      │   ├─ Node1InterpretationContext → Node 1 candidate
      │   ├─ server rebind → RuntimeContextPackage + APP-G1
      │   ├─ Node 2 SQL compile ─────────────────────────→ Model adapter
      │   ├─ APP-G2 + query budget
      │   ├─ read-only execute ──────────────────────────→ Trino → 5개 논리 Source / 4종 DBMS
      │   └─ APP-G3 + immutable Artifact ────────────────→ App PostgreSQL
      ├─ PRESENTATION → 호환 시 같은 Artifact + 새 ViewSpec, query 없음
      └─ REPORT_ACTION → 선택 Artifact + ViewSpec을 Draft block에 연결

Report admin
  → React/Nginx
  → Report workflow
      ├─ draft → immutable approval version
      ├─ approve/reject with object policy
      └─ manual run → block마다 새 Analysis Run → 위 APP-G1/APP-G2/Trino/APP-G3 경로
                                               └→ App PostgreSQL
```

질문 경로와 release compile 경로는 분리한다. 질문마다 전체 catalog를 Scroll하지 않는다.
out-of-band release compiler만 `scrollAcrossEntities`로 전체 멤버십을 열거하고 GraphQL
entity·Rest.li/OpenAPI aspect를 exact read-back한 뒤 Trino schema fingerprint와 대조해 immutable
RuntimeCatalogProjection을 만든다. projection equality, canary, activation receipt와 rollback을
통과한 product release만 위 질문 경로에서 사용할 수 있다.

네 개의 Archify 시각화는 위 읽기 순서와 [`../architecture/README.md`](../architecture/README.md)에 둔다. 논리 컴포넌트에는 특정 data release 이름 대신 `승인 데이터`, `승인 Serving`, `호텔 운영 Source`를 사용한다. 실제 버전명·namespace·checksum은 정적 감사와 evidence에만 기록한다. HTML은 설명용이며 구현 완료 증거는 아니다. HTML receipt의 source evidence `verified`는 pinned commit에 source path가 존재한다는 뜻일 뿐 제품 기능 검증이 아니다.

### 현재/목표 Tool 경계

고정된 “MCP Tool 7개” 목록은 v3.4 delta 기준일 뿐 현재 계약이 아니다.

| Surface | 현재 | 목표 |
|---|---|---|
| HTTP `/analysis`의 `analysis.run` permission | HTTP use-case capability이며 MCP Tool이 아님 | HTTP와 MCP identifier를 계속 분리 |
| `analysis.get_run@1.0.0` | migration·router·live registry에 존재하는 유일한 호환 Tool | 유지. 제거할 때는 versioned deprecation 필요 |
| `analysis.run` MCP | 미구현 | Phase 11에서 결정론적 Analysis Core를 감싸는 고수준 Tool |
| `semantic.resolve` | registry/router에 없음 | 외부 Tool이 아니라 Context Gateway 내부 operation |
| `artifact.get` | 미구현 | `analysis.run` 결과만으로 부족한 경우에만 조건부 |
| `graph.resolve` | 미구현 | Neo4j 정량 Gate를 통과할 때만 조건부 |
| `rag.search` / `rag.answer` | 둘 다 미구현 | `rag.search` 목표는 폐기하고 Phase 12의 citation 포함 `rag.answer` 채택 |
| `ml.predict` | 미구현 | Phase 13의 승인된 ML task만 노출 |
| `report.add_block` | 미구현 | Report Service 위 wrapper가 반복 병목을 줄일 때만 조건부 |

현재 host의 `/mcp`는 protocol `2026-07-28` Stateless Streamable HTTP 경계로
`server/discover`, 요청별 protocol/client capability metadata, `Mcp-Method`·`Mcp-Name`
header 대조, 응답 server identity와 private cache hint를 검증한다. `tools/list`와 `tools/call`은
App 권한뿐 아니라 registry의 ID·이름·semantic version·설명·입출력 schema·transport·timeout·
required role·enabled 상태가 코드 계약과 정확히 같은 `analysis.get_run@1.0.0`만 허용하며, Tool 결과는 공개
`outputSchema`의 다섯 필드로 다시 투영한다. RAG candidate row는 비활성이고 ML·Report MCP Tool은
production registry에 없으므로 어느 것도 discovery에 광고하지 않는다. 활성 Tool의 Analysis run
조회에는 registry와 같은 5초 deadline을 적용하며, timeout도 `tool_runs`에 `FAILED/TOOL_TIMEOUT`으로
기록한 뒤 값 없이 오류로 반환한다.

현재 MCP 전용 분산 rate limit 증거는 없다. 외부 client 또는 향후 변경형 Tool을 공개하기 전에는
인증 주체별 quota를 공유 저장소에서 원자적으로 집계하고, 초과 요청·감사 event·재시도 시간을
동일 release에서 검증해야 한다. 이 경계가 준비되기 전까지 `/mcp`는 내부 read-only Tool 한 개의
제한된 surface로만 운영한다.

Phase 10까지 same-release P0를 봉인한 뒤 Phase 11 `analysis.run`, Phase 12 `rag.answer`,
Phase 13 `ml.predict`, Phase 14 General Orchestrator 순서로 확장한다. 모든 Tool은
RequestContext, entitlement, APP-Gates, trace를 우회할 수 없으며 `execute_raw_sql`, 자유 Cypher,
임의 Table 조회, Policy 우회 Tool은 제공하지 않는다. Report는 계속 Artifact와 승인 Workflow를
다루는 Service다.

| 논리 용어 | 뜻 |
|---|---|
| 승인 데이터 | 모든 Gate를 통과해 현재 사용자 기본 경로가 조회하는 데이터 |
| 후보 데이터 릴리스 | 검증 중이며 아직 사용자 기본 경로가 아닌 데이터 |
| 이전 승인 릴리스 | 장애 때 복구할 수 있도록 보존한 직전 기본 데이터 |
| 승인 Serving | 앱이 직접 조회하는, 검증된 통합 view 계약 |

### single-turn 실행과 bounded multi-turn 조율

`single-turn`과 `multi-turn`은 서로 대체하는 선택지가 아니다. P0는 두 층을 겹쳐 쓴다.

| 층 | 불변 원칙 | 이유 |
|---|---|---|
| Conversation·Turn 조율 | 같은 업무 대화의 승인된 조건, 변경분, 현재 초점 Artifact·View·Draft를 구조화해 연결 | `그 전 달은?`, `다른 그래프로`, `표로도`, `보고서에 담기`를 안전하게 해석하기 위해 |
| Atomic Analysis Run | preflight에서 완전하게 resolved된 Analysis Turn만 새 Run을 만들고 현재 권한·APP-G1/G2/G3·Trino를 통과 | 모호/범위 밖 Turn에는 Run을 만들지 않고 과거 권한·SQL·결과도 재사용하지 않기 위해 |
| Presentation View | source Artifact에 필요한 grain·column이 있으면 새 query 없이 결정론적 ViewSpec만 저장 | 같은 값을 다시 조회하는 비용과 서로 다른 query처럼 보이는 거짓 lineage를 막기 위해 |
| Report block | 사용자가 선택한 `artifact_id + view_spec_id + analysis_definition_id`를 연결 | 채팅 문장·화면 캡처를 데이터 근거로 복사하지 않기 위해 |

권위 있는 대화 상태는 raw transcript나 모델 memory가 아니다. 서버가 검증한 `metric_ids`, 절대 기간, dimension, filters, grain, 비교 규칙, `wall_clock_anchor`, data watermark, `product_release_id`, source Turn·Artifact·View 참조다.

| 이해 계층 | 역할 | 안전 경계 |
|---|---|---|
| Deterministic normalizer | Unicode·공백·날짜 형식·승인 exact alias의 의미 보존 정리 | 자유 의미를 정규식으로 추측하지 않음 |
| GPT/Node 1 candidate parser | 반말·존댓말·어순·축약·경미 오탈자·지시어를 typed candidate로 생성 | 공식 Metric·권한·실행을 결정하지 않음 |
| Deterministic resolver | metadata visibility를 적용한 DataHub Term, Rule, source Turn, Artifact schema로 하나만 확정 | 복수 후보·critical token 변화는 명확화 |

상대기간은 `WALL_CLOCK`과 `SOURCE_PERIOD`를 구분한다. “이번 달/지난·저번 달”은 Backend-owned `wall_clock_anchor`와 `Asia/Seoul`, “그 전 달/다음 달”은 명시 `source_turn_id`의 절대 기간을 기준으로 한다. production은 client clock override를 신뢰하지 않고 wall clock 기준 변경은 새 Conversation만 허용한다. 이 clock과 release/Asset의 `data_available_from/through` watermark는 별도 필드이며 서로 대신 쓰지 않는다. 달력 기간이 범위 밖이라고 최신 가용 월로 바꾸지 않는다.

실행 중에는 idempotent command/request, Conversation active lease와 resolved Analysis의 Run 상태·attempt·heartbeat·외부 query 제출 증거만 mutable하다. Turn·Conversation head·focus·ViewSpec·Draft block 같은 사용자 가시 domain mutation은 terminal commit 전까지 불변이다. 같은 key/hash 재전송 조회가 head CAS보다 먼저다. preflight가 모호성·범위·지원 intent를 해결하지 못하면 Run 없이 terminal Turn을 commit한다. resolved Analysis만 Run을 만들고, 완료 시 Run terminal 상태·결과 Artifact 또는 ViewSpec/focus·Draft block, command terminal화·immutable Turn·새 head·lease 해제를 한 App DB transaction으로 commit한다.

상속 가능한 사용자 slot은 필드별 `INHERIT/SET/REMOVE`와 `USER_REQUESTED` provenance를 가진다. `POLICY_REQUIRED_FILTER`와 permission constraint는 focus나 과거 Turn에서 상속하지 않고 각 새 Analysis Run의 현재 entitlement로 다시 만든다. data focus는 `SUCCEEDED Analysis + Safe Artifact`만, View focus는 성공 Presentation만 갱신한다. Report Action과 `PARTIAL/BLOCKED/FAILED/CANCELLED` Turn은 기존 focus를 바꾸지 않는다.

P0는 Conversation당 선형 head 하나와 명시 참조 최대 두 Turn만 지원한다. `expected_head_turn_id`와 idempotency key로 이중 클릭·다중 탭의 stale write를 차단한다. branch·merge, Conversation 사이 장기 기억, vector memory, 전체 transcript 재주입, 자율 계획은 P0 범위가 아니다.

Report 수동 실행의 신원은 세 층으로 분리한다.

- **실행자(`actor`)**: 실행 버튼을 누르고 승인 책임을 지는 `report_admin` 또는 같은 `report.manage` Capability가 명시된 통제 환경의 `platform_admin`
- **권한 기준 사용자(`effective_subject`)**: Report block이 참조한 Analysis Definition의 원 소유자. Report Run 시작 시 subject별 **현재 권한**을 한 번 snapshot으로 고정하고, 그 Report Run의 모든 child Analysis Run은 같은 `report_permission_snapshot_id`를 참조한다. 이는 독립 사용자 Analysis Run마다 새 snapshot을 만드는 일반 규칙의 명시적 일관성 예외다.
- **서비스 신원(`service_identity`)**: App이 Trino에 접속할 때 쓰는 인증된 query principal

승인자가 `platform_admin`처럼 더 강한 권한을 가졌더라도 Definition owner보다 넓은 데이터를 조회하지 않는다. 세 신원과 policy version을 같은 audit에 남긴다.

현재 General Orchestrator 전환 경계는 한 번의 결정론적 dispatch다. 명시된
`INTERNAL_GUIDELINE`만 RAG Agent port로 보내고, 일반·분석·표현·`REPORT_ACTION`은 기존
Conversation/Analysis workflow port로 보낸다. 승인 capability를 찾지 못한 일반 질문은 별도
범용 GPT로 우회하지 않고 기존 fail-closed 응답으로 종료한다. Report Assistant는 승인된
Artifact·patch·CAS Revision을 소유하는 별도 상태 머신으로 유지하며, ML과 Report Assistant는
실제 adapter 계약이 완성되기 전 General Orchestrator registry에 빈 port로 등록하지 않는다.
현재 두 실행 경로는 FastAPI handler가 아니라 concrete `AgentPort`로 구현된다. 분석 port는
기존 timeout·progress·동시 실행 계약을, RAG port는 승인 snapshot·Gateway use case를 소유하며
HTTP 오류 변환만 router에 남긴다. 일반 대화의 `INTERNAL_GUIDELINE` command는 분석과 같은
`chat.turn_commands` admission·canonical hash·idempotency·CAS·lease를 거쳐 Turn과 terminal
command를 원자적으로 확정한다. 별도 `/rag/query` API는 idempotency key가 없는 기존 명시 API라
legacy `append_rag_turn` 경계를 유지한다. 공개 Conversation command는 `LangGraphAgentRuntime`의
`START → supervisor_route → 선택된 단일 AgentPort → END` 그래프로 실행한다. 이 graph에는 모델
Supervisor, 일반 GPT, fan-out/fan-in을 두지 않으며 서버가 검증한 route만 조건부 edge로 바꾼다.
graph node는 고정 분기문이 아니라 알려진 `AgentKind`에서 생성된다. 교체 ML을 위한
`ML_PREDICTION` 종류·node와 구조화 invocation 전용 `MLPredictionAgentPort`·search-only capability
probe는 구현돼 있다. 다만 production Conversation registry에는 등록하지 않았고 현재 제품 경로는
feature-gated 별도 ML UI와 `/ml/capabilities`·`/analysis/ml` API다. 따라서 public client 자연어가
ML target을 정하거나 Supervisor가 ML을 자동 선택할 수 없다.

Supervisor 내부에는 필수 request fingerprint를 포함하는 `AgentExecutionState.v2`와 순방향 reducer를 두어
`RECEIVED → ROUTED → RUNNING → COMPLETED|FAILED` 상태와 revision을 immutable snapshot으로
만든다. checkpoint identity는 `conversation_id`와 idempotency key를 결속하고, 사용자 대화 원문이나
Agent 결과 payload는 공통 상태에 복제하지 않는다. 대신 admitted identity·release·permission,
canonical command, target Agent와 typed invocation을 포함한 전체 `AgentRequest`의 SHA-256을 상태와
routing outcome에 함께 봉인한다. Supervisor의 `route_with_state`와
`execute_routed_with_state`는 ROUTED checkpoint와 단일 Agent 실행을 분리하므로 향후 LangGraph의
조건부 route node와 Agent node가 같은 reducer 계약을 재사용할 수 있다. 다른 command의 routed
snapshot이나 같은 checkpoint에서 invocation이 바뀐 요청은 fingerprint 검증에서 차단한다. 현재 이 snapshot은 durable checkpointer에
저장하지 않으며 기존 `chat.turn_commands`의 command·CAS·lease 계약이 실행 권위다. 따라서 새
checkpoint 테이블이나 LangGraph 재개 기능을 추가한 상태는 아니다. `turn_commands` terminal
status는 Agent 실행의 durable 수명주기 증거로 사용하지만 reducer revision 전체를 저장한 것으로
간주하지 않는다. LangGraph state의 `AgentRequest`·routing·outcome 객체도 한 command 호출 안에서만
사용하며 Conversation 원문이나 결과 payload를 별도 외부 store로 전송하거나 영속화하지 않는다.

Route 선택은 비동기 `AgentRouteResolver` 경계로 분리한다. 현재 기본 resolver는 위의 명시
`INTERNAL_GUIDELINE`과 governed analysis 기본값만 보존한다. 향후 일반 입력에서 RAG·ML을 자동
선택하려면 교체 Agent가 권한·버전·유효기간을 적용한 search-only capability probe와 재사용 가능한
receipt를 제공해야 한다. `CAPABILITY_EVIDENCE` 결정은 하나 이상의 evidence reference가 없으면
Supervisor 상태에 기록하거나 실행할 수 없다. 분석과 RAG가 동시에 매칭되거나 둘 다 매칭되지 않는
경우의 clarification/out-of-scope 계약이 완성되기 전에는 자동 route를 활성화하지 않는다. 일반 GPT,
키워드 분기, 기존 RAG **답변** 호출을 probe처럼 사용하는 우회는 허용하지 않는다.
`CapabilityEvidenceRouteResolver`는 이 probe fan-in 계약만 구현하며 현재 FastAPI registry에는
연결하지 않는다. 명시 route는 probe를 우회하고, 일반 입력의 0개·복수 매칭과 probe 실패는 각각
typed failure로 끝난다. 독립 probe는 bounded registry 단위로 병렬 실행하되 결과 판정과 evidence
순서는 registry 순서로 고정하며, 하나의 장애나 교차 probe receipt 중복도 전체 판정을 실패시킨다.
0개·복수 매칭처럼 Agent 선택 전 끝난 실패는 가짜 decision을 만들지 않고 해당 receipt를 별도
`terminal_evidence_refs`에 보존한다.
일반 입력은 `command_id`와 permission/product/semantic receipt가 모두 결속된 admission context가
아니면 resolver가 어떤 probe도 호출하기 전에 `AGENT_CAPABILITY_CONTEXT_INCOMPLETE`로 종료한다.
RAG에는 `InternalGuidelineCapabilityProbe`와 `InternalManualAgent.search_capability`를 추가했다.
이 경로는 답변 endpoint를 호출하지 않고 승인된 내부 검색 endpoint의 technical release,
embedding revision, 승인 document/evidence 식별자만 검증한 뒤 원문 없는 checksum receipt를
반환한다. App Tool Registry가 비활성·미승인이면 검색 전에 차단된다. ML도 구조화 invocation을
runtime capability와 비교하는 search-only probe와 실행 `AgentPort`를 제공하지만, production
Conversation registry와 자동 capability resolver에는 연결하지 않는다.
분석 경로에는 `GovernedAnalysisCapabilityProbe`가 추가되어, 공통 command admission이 고정한
permission snapshot·product/semantic release와 동일한 Runtime Catalog의 bounded BUSINESS Metric
후보만 checksum reference로 봉인한다. admission 전 요청, release drift, 불완전 projection은 match가
아니라 probe 실패로 닫는다. 이 probe는 아직 registry에 연결하지 않는다. Supervisor가 admission보다
먼저 자동 route를 실행하면 같은 idempotency key의 replay가 새 검색 결과에 따라 다른 Agent를 고를 수
있으므로, 공개 command 경로는 공통 admission에서 canonical hash·replay·CAS·lease를 먼저 확정한 뒤
admission-bound `AgentRequest`를 Supervisor와 선택된 단일 `AgentPort`에 전달한다. 선택된 port는 같은
admission receipt를 검증해 재사용하며 lease를 중복 획득하지 않는다. replay는 Supervisor나 외부 Agent를
다시 호출하지 않고 저장된 terminal Turn을 기존 공개 응답 계약으로 수화한다. route 결정이나 dispatch가
port 실행 전에 실패해도 RUNNING command와 lease를 terminal failure로 닫는다. 현재 production resolver는
즉시 끝나는 명시/default resolver뿐이다. routing 구간도 command lease heartbeat를 소유하고 resolver는
최대 15초 안에 끝나야 한다. timeout이나 route 중 lease 소유권 상실은 AgentPort 실행 전에 terminal
failure로 닫힌다. resolver는 자신이 생성할 decision source 집합을 immutable하게 선언하고 registry가
호출 전에 승인 source와 대조한다. 현재 registry는 `EXPLICIT_COMMAND`과 `GOVERNED_DEFAULT`만 허용하므로
`CAPABILITY_EVIDENCE` resolver는 probe를 호출하기도 전에 차단된다. 교체 RAG·ML의 probe·port·receipt가
검증된 뒤에만 코드 수준의 `capability_routing_enabled` gate를 명시적으로 열 수 있다.
현재 RAG 후보는 2026-08-30 로컬 Docker 검색→근거 답변과 HMAC 보안 경로를 통과해
`TECHNICALLY_VALIDATED`/`LOCAL_DOCKER_VALIDATED`로 기록한다. 그러나 제품 feature flag와 App Tool
Registry는 기본 비활성이고 업무 Gold·제품 release 승인이 없으므로 `rag.answer`와 자동 route는
계속 비활성이다. 검색 probe 구현 완료는 곧 자동 route 승인이라는 뜻이 아니다.
FastAPI router는 구체 port나 Supervisor를 직접 생성하지 않고 admission-first orchestrator dispatch를
호출한다. dispatch 내부의 `build_conversation_agent_supervisor`가 현재 완성된 분석·내부지침 port만
조립한다. ML은 별도 UI/API에서만 실행하며 Conversation 결과 계약과 자동 선택 승인이
완성되기 전까지 이 registry에 추가하지 않는다. Report Assistant도 별도 상태 머신으로 유지한다.

## 4. 의미 체계 권한 모델

DataHub만으로 row-level 계산과 권한 실행까지 하는 것은 아니다. authoring authority와 App
execution responsibility를 다음처럼 분리한다.

| 계약 | 권위/책임 | 필수 연결 |
|---|---|---|
| 이름·별칭·정의·단위·Domain·Owner·승인 | DataHub Glossary | stable Term URN + DataHub release/read-back checksum |
| Dataset·Column·lineage·Context Documents·Structured Properties | DataHub | stable Asset/Document URN + aspect checksum |
| Metric·AI Context·SemanticModel 등 native semantic | pinned v1.7 capability Gate를 통과한 대상만 DataHub | stable entity identity + exact aspect read-back + retirement |
| entitlement·release activation·permission snapshot | App | subject + policy version + product receipt |
| 실행 계산·filter·join·time·identity 계약 | DataHub authoring에서 compile한 immutable RuntimeCatalogProjection | source URN/aspect + projection checksum |
| 실제 물리 존재·type·schema | Trino fingerprint와 DataHub read-back의 교차 검증 | observed version/time |
| Conversation·SQL/ML 실행·APP-Gates·Artifact | App | product receipt + permission snapshot + query/run lineage |
| local JSON | bootstrap·test·versioned schema·검증된 cache만 | source environment/version/checksum/expiry |

질문 runtime은 다음과 같다.

```text
사용자 질문
  → bounded DataHub lexical Search (최대 K, URN/type만)
  → App entitlement + active release membership filter
  → 최소 RuntimeCatalogProjection
  → Node1InterpretationContext → Node 1 candidate
  → server-side exact reference rebind
  → RuntimeContextPackage → APP-G1 → Node 2
```

release compiler는 별도 경로다.

```text
scrollAcrossEntities full membership
  → GraphQL entity + Rest.li/OpenAPI aspect exact read-back
  → Trino schema fingerprint
  → immutable RuntimeCatalogProjection + checksum
  → equality/canary/rollback Gate
  → product receipt activation
```

DataHub 장애에서 cache가 사용되려면 기대 environment·version·checksum이 같고 만료 전이어야 한다. 조건을 만족하지 못하면 `METADATA_UNAVAILABLE`이며 로컬 JSON 독립 판단으로 성공하지 않는다.

DataHub aspect publish는 원자적이지 않으므로 candidate는 staging 또는 stable identity를 가진
shadow 영역에 out-of-place publish한다. release compiler가 전체 entity/aspect와 Trino schema를
다시 읽어 RuntimeCatalogProjection checksum을 만들기 전에는 runtime에 노출하지 않는다.
candidate canary는 전역 pointer를 바꾸지 않고 명시적 `product_release_id`로 조회한다.
activation은 pre-cutover Gate 뒤 DataHub release, projection, code/image/model/policy 기본값을 같은
product receipt로 전환하는 별도 단계다. 사용자별 entitlement는 각 Run의 permission snapshot이다.

기존 Rule/Semantic Registry는 migration/equality 기간의 입력으로만 허용한다. 새 authoring을
양쪽에 병행하지 않으며 projection equality와 rollback이 확인되면 독립 SoT 책임을 퇴역한다.
`semantic.resolve`라는 의미 해석 동작이 필요해도 Context Gateway 내부 operation으로 수행한다.

### 조건부 Neo4j 의미 Graph

Neo4j는 기본 단계에 포함하지 않는다. DataHub Search/lineage와 RuntimeCatalogProjection만으로
복잡한 관계 질문의 held-out recall·회복률·p95가 사전 기준을 반복해서 못 넘고, 별도 read model이
더 단순한 대안보다 정량 개선함을 입증할 때만 ADR과 `graph.resolve`를 연다. Phase 10의 source,
Backend/Frontend image, model, DataHub, Trino, App DB, Browser, host validation과 모든 P0
Requirement·Release Gate가 하나의 product release에서 `VERIFIED`되기 전에는 이 평가를 시작하지
않는다. 채택하더라도 방향은
`DataHub/RuntimeCatalogProjection → read-only graph projection → 후보 → APP-G1 재검증` 한쪽이다.

Raw 예약·매출·고객 row, PII 원문, 사용자별 Effective Policy, 검증되지 않은 LLM 관계는 넣지
않으며 Neo4j에서 DataHub로 역동기화하지 않는다. projection을 채택하면 ontology/release/source
checksum, deterministic invariant, candidate exact read-back, activation·rollback을 같은 receipt에
결속한다. 내부 resolver는 allowlist된 parameterized query template과 hop·후보·결과·timeout
budget만 허용하고 raw Cypher surface를 제공하지 않는다.

Graph 결과는 실행 후보일 뿐이며 Backend가 권한·release·관계·cardinality·grain·unit·time을
APP-G1에서 다시 검증한다. 단순 분석에는 Graph 호출을 추가하지 않는다. Graph 장애는 기본
DataHub-first 경로를 바꾸지 않고 보강만 생략하며, Graph가 필수인 요청은 typed failure로 끝낸다.
`ACCESS_DENIED`, PII·쓰기·미승인 JOIN·데이터 범위 실패를 stale graph·local scan·LLM 추측으로
fallback하지 않는다. 구현 기술과 edition은 gap과 운영 budget이 증명된 뒤 ADR에서 결정하며 특정
graph validator 라이브러리를 사전에 의무화하지 않는다.

이 조건부 경계는 Phase 0~10 검토에서 채택한 안전 계약을 제품 문서에 반영한 결과다. 별도
회고 archive는 현재 작업 트리에서 유지하지 않는다.

## 5. 승인 데이터 단계적 전환 순서

제공된 새 SQL로 전환하는 결정은 끝났지만 즉시 기본 경로로 바꾸는 것은 아니다. 논리 아키텍처에서는 특정 버전명을 쓰지 않고 다음 Gate만 고정한다. 정확한 namespace·view·checksum은 정적 감사와 cutover evidence가 담당한다.

현재 data release 선택은 startup 환경변수로 만든 process-local adapter에 결합돼 있고 host product receipt는 DB 전체 lineage에 전파되지 않았다. P0는 code/image·data·DataHub governed context·RuntimeCatalogProjection·prompt/model/policy·migration·cache namespace를 하나의 `product_release_id`로 고정하고 readiness에서 일치 여부를 검사한다. zero-downtime을 주장하지 않으며 canary/staging에서 process 교체와 rollback을 연습한다. 예상 중단시간·RTO·RPO·측정 시작/종료점·rollback trigger·결정 책임자를 rehearsal 전에 고정한다.

비개발자는 아래 네 묶음으로 읽으면 된다.

| 묶음 | Gate | 답해야 하는 질문 | 실패 시 |
|---|---|---|---|
| 1. 원천 준비 | DATA-G0~G3 | 격리됐고, SQL이 실행되며, 행·키·금액이 계약과 맞는가? | 후보 중단, 현재 승인 데이터 유지 |
| 2. 현실성·재현성 | DATA-G4~G5 | 분포를 사람이 승인했고 같은 seed를 깨끗하게 재생할 수 있는가? | 새 checksum의 후보로 다시 시작 |
| 3. 통합·보안 | DATA-G6~G7 | Serving 값·grain·fan-out이 맞고 인증된 read-only 경계인가? | App 연결·canary 금지 |
| 4. 제품 전환 | DataHub full read-back·projection equality → Gold 봉인 → canary → rollback rehearsal → cutover | 같은 제품 릴리스가 실제 사용자 경로와 복구 조건을 통과했는가? | 기본 pointer를 바꾸지 않음 |

1. **SQL 정합성:** 원본 archive는 불변 보존하고, 알려진 연회 status history 결함과 validator 모순을 수정한 derived release checksum을 새로 고정한다.
2. **격리 적재:** 새 release namespace에 5개 DB를 적재하고 DBMS별 validator·row count·constraint를 통과한다. 모든 Source에 release 전용 read-only `SELECT` 권한을 명시하고 Trino·DataHub principal에서 visibility를 검증한다.
3. **재현성:** 깨끗한 volume에서 동일 seed를 재적재해 row/hash와 수행 시간을 비교한다.
4. **Serving·검증용 oracle 초안:** release manifest가 선언한 모든 view를 만들고 제품 Gold와 분리된 `serving reconciliation oracle`로 값·grain·fan-out·중복·null·row/hash를 검증한다. 운영매출 Golden Path는 승인된 통합 mart 한 개를 조회하고 lineage로 다중 source 근거를 제시한다. 동적 multi-asset JOIN은 별도 계약 없이는 주장하지 않는다.
5. **DataHub governed 후보 게시·역검증:** 후보 Dataset·Column, Glossary Term, Domain·Owner·승인·관계와 지원된 native semantic aspect를 stable identity의 versioned/shadow 영역에 게시한다. full Scroll과 entity/aspect exact read-back, Trino fingerprint에서 immutable RuntimeCatalogProjection을 compile하되 전역 active pointer는 바꾸지 않는다.
6. **최종 제품 Gold 봉인·App 연결:** 후보 projection equality가 확정된 뒤 product Gold·tolerance·held-out checksum과 Golden Dialogue를 봉인한다. DataHub release, projection, prompt/model, API fixture, Conversation routing·View compatibility 계약을 같은 후보 `product_release_id`로 연결한다. 전체 asset 수와 요청당 Context 상한은 별도 안전 한도로 유지한다.
7. **Candidate canary:** 현재 승인 경로는 rollback용으로 유지하고 명시적 후보 ID를 실제 E2E·권한·실패·bounded multi-turn·보고서 조합 흐름에서 검증한다. 서로 다른 릴리스의 금액이 같다고 기대하지 않는다.
8. **복구 훈련(rollback rehearsal):** canary/staging의 candidate process를 후보→이전 승인 릴리스→후보 순서로 전환하고, 데이터 손실·cache 오염 없이 복구되는지와 사전 승인한 중단시간·RTO·RPO를 측정한다.
9. **전환 전 승인과 기본값 변경:** 지정 승인자는 candidate DATA-G0~G7, DataHub full read-back·projection equality, `P0-DATAHUB-SEARCH`, `P0-GOLD`, `P0-GOLDEN-DIALOGUE`, `P0-E2E-REAL`, `P0-REPORT-RERUN`, `P0-SECURITY`, `P0-FAILURE`, `P0-QUANT`, rollback rehearsal receipt를 모두 승인한다. 그 뒤에만 data·projection·App process의 기본값을 같은 `product_release_id`로 바꾼다. DATA-006의 activation·readiness·Golden smoke는 전환 후에 닫는다.
10. **전환 후 확인:** 새 process의 readiness·Golden smoke를 확인한다. 실패하면 즉시 연습한 rollback을 실행하며, 성공 receipt까지 있어야 전환 Gate를 `VERIFIED`로 올린다.
11. **구 경로 폐기:** 안정화·관찰 기간과 별도 승인 후 제거한다. 이 작업에서 삭제하지 않는다.

archive 내부 compose는 새 Source SQL을 자동 적재하는 완결된 installer로 간주하지 않는다. 실제 mount·적용 순서와 volume 이름을 cutover runbook에서 명시적으로 검증한다.

## 6. 신뢰·보안 경계

```text
Untrusted: Browser input, raw transcript, model output, claimed Trino username
    ↓ server validation
Trusted by version: session, RBAC policy, DataHub approved term/relation,
                    RuntimeCatalogProjection, APP-G1/G2/G3 decision, product receipt
    ↓ read-only credential
Execution: Trino → Source DB
    ↓ safe projection
Persistence: App DB artifact/audit → Frontend
```

- Frontend와 model output은 항상 untrusted다. 사용자 질문뿐 아니라 Glossary alias·설명, schema 설명, source/result 문자열도 prompt injection 가능한 데이터로 취급한다.
- Source DB credential은 read-only 최소 권한이어야 한다.
- Trino는 개발·운영 모두 HTTPS, password 인증, CA 검증과 service identity를 강제한다. 익명 statement와 임의 `X-Trino-User` 주장은 거부하며 무인증 데모 경로를 제공하지 않는다.
- P0 인수 환경은 App이 주장한 `X-Trino-User` 값만으로 신원을 결정하지 않는다. 전용 query service principal, credential 저장·rotation·폐기 절차, 서버 권한 mapping, 다른 principal 사칭 negative test를 security manifest에 고정한다. 외부 연결 없는 `MockTransport`는 단위 테스트의 명시적 의존성 주입으로만 허용한다.
- 외부 모델에는 승인된 최소 context만 전송하고 raw source row·secret·불필요한 PII를 보내지 않는다.
- 과거 대화 원문을 모델 권한이나 실행 Context로 신뢰하지 않는다. 상속 가능한 typed field는 server-side source Turn과 checksum을 가지며 매 Turn 변경 diff를 남긴다.
- cancel은 Trino query까지, timeout은 의존성까지 전파한다.
- result·trace·log에는 permission snapshot과 version을 남기되 secret·민감 원문을 남기지 않는다.

## 7. 배포와 관측

P0 release unit은 하나의 `product_release_id`가 가리키는 다음 묶음이다.

```text
code commit
+ Docker image digests
+ approved data release/checksums
+ DataHub governed context release
  - Glossary/Dataset/lineage/Document/native aspect checksum
+ immutable RuntimeCatalogProjection checksum
+ cache namespace
+ permission policy/prompt/model versions
+ DB migrations
```

`product_release_id`는 검증 시작 전에 봉인하는 immutable candidate manifest ID다. Golden·security·rollback 결과를 이 ID 계산에 다시 넣지 않는다. 실행 뒤 receipt는 candidate ID를 참조하는 append-only `evidence_bundle_id`로 별도 봉인하고, cutover 승인은 `product_release_id + evidence_bundle_id` 쌍을 기록한다. 실패를 고친 후보는 새 product ID와 새 evidence bundle로 처음부터 검증한다.

필수 식별자는 `conversation_id`, `turn_id`, 선형 부모 `reply_to_turn_id`, ordered `source_turn_ids`(P0 최대 2), 선택적 `clarifies_turn_id`, `request_id`, `analysis_definition_id`, `analysis_run_id`, `artifact_id`, `view_spec_id`, `report_version_id`, `report_run_id`, `query_id`다. 한 대화의 각 Turn에서 routing 결정, 상속·변경 field source, Run 또는 View/Report action과 최종 evidence를 연결할 수 있어야 한다. owner UI 원문은 암호화 message store와 보관·삭제 정책으로 격리하고 redacted utterance만 generic audit·trace에 남긴다.

제품 반복 평가에 필요한 Turn 관측은 Node 1이 실제 발화에서 찾은 bounded `business_terms`와 실행기가 확정한 `query_strategy`, source asset, join ID, time bucket, plan checksum만 `resolved_slots`에 보존한다. SQL·parameter·raw row는 이 관측 계약에 포함하지 않으며 제품 기대값이나 canonical alias를 사후 합성하지 않는다.

관측 항목은 Turn routing 정확도·확인 요청률·잘못된 상속률, PRESENTATION의 불필요한 model/Trino 호출률, stale head·idempotency 충돌, 단계별 latency, model retry, APP-G1/G2/G3 거부 사유, Trino scanned rows/bytes, result rows, cancellation, source/DataHub readiness, Search candidate 수·entitlement 제거율·freshness, projection equality와 out-of-band 변경 탐지, report block 상태다. 임의 수치 목표보다 기준선과 표본 수를 먼저 측정한다.

## 8. DataHub-first 단계와 확장 경계

| 단계 | 산출물/도입 조건 | 실패 시 |
|---|---|---|
| Phase 0B | versioned capability·evidence schema와 배포 provenance | 다음 Phase 중단 |
| Phase 1 | Conversation required idempotency/CAS, transaction, recovery, release lineage | Search 전환 중단 |
| Phase 2 | DataHub lexical shadow와 사전 threshold 비교 후 `PROMOTE`·`HOLD`·`REJECT`; promote면 canary→default→rollback | 기존 `lexical` 유지 |
| Gate S1 (`CONDITIONAL`) | semantic/hybrid가 lexical 대비 품질 개선, index fingerprint·freshness·failure/rollback 증명 | lexical 유지, hybrid 비활성 |
| Phase 3 | native Metric·별도 `aiContext`의 pinned v1.7 capability, stable identity, retirement 결정 | App transition compile 유지 |
| Phase 4 | immutable RuntimeCatalogProjection equality·activation·rollback | full loader 경계 유지, hot path 전환 금지 |
| Phase 5 | bounded Node1InterpretationContext와 server rebind | Node 1 cutover 금지 |
| Phase 6 | same-asset deterministic single-turn | multi-asset 주장 금지 |
| Phase 7 | bounded multi-turn Golden Dialogue | atomic single-turn 유지 |
| Phase 8 | 나머지 native semantic shadow | 검증된 capability만 유지 |
| Phase 9 | 승인 JOIN edge·policy·logical plan·SQLGlot emitter·Trino oracle | same-asset 유지 |
| Phase 10 | P0 same-release evidence 봉인 | Agent Tool 확장 금지 |
| Phase 11~14 | `analysis.run` → `rag.answer` → `ml.predict` → General Orchestrator | 직전 단계 유지 |
| Neo4j/`graph.resolve` (`CONDITIONAL`) | Phase 10 `VERIFIED` 뒤 DataHub graph/search·더 단순한 대안의 정량 gap과 OFF/ON 순이득 | 도입하지 않음 |

예약 worker, IAM/SSO, 다중 인스턴스, microservice, 장기 기억·branch/merge도 실제 동시성·조직·가용성·개인정보 요구가 측정된 뒤에만 연다. P0 modular monolith의 typed Turn, product receipt, APP-Gates를 우회하지 않는다.

## 9. Architecture Decision

| 결정 | 이유 | 재검토 Trigger |
|---|---|---|
| P0 modular monolith 유지 | 현재 병목은 서비스 분해가 아니라 DataHub-first projection·안전성·실제 E2E | 팀 소유권·scale·배포 독립성 실측 |
| DataHub Governed Context Plane을 authoring SoT로 채택 | Glossary뿐 아니라 Dataset/schema·Search·lineage·Documents·지원 native semantic의 변경·승인 단일 원본 필요 | pinned capability 또는 가용성 한계가 정량 측정됨 |
| App Rule/Semantic Registry의 독립 authoring 퇴역 | 장기 dual authority와 drift 방지; App에는 compiled immutable projection만 필요 | Phase 3/4 equality·rollback 실패 시 이행 기간 연장 |
| 질문 Search와 release full read-back 분리 | 질문 latency/최소 공개와 release completeness를 동시에 보장 | 없음 |
| local JSON 제한 | bootstrap/test/cache는 유용하지만 독립 원본은 drift 위험 | 항상 online인 metadata architecture 확정 |
| same-release E2E Gate | screenshot·mock·과거 결과의 거짓 완료 차단 | 없음 |
| 원자적 single-turn Run + bounded multi-turn 조율 | 대화 편의성과 실행 재현성·권한 재검증을 동시에 지키기 위해 | Golden Dialogue 실패율·지연·비용이 수용 불가할 때 범위 축소 |
| 표현 변경은 Artifact 재사용 | 같은 값의 불필요한 query와 거짓 lineage 방지 | 요구 View에 필요한 grain이 없어 새 분석이 반복될 때 승인 query 계약 추가 |
| Neo4j는 조건부 read model | Phase 10 봉인 뒤 DataHub-first 기본 경로와 더 단순한 대안의 gap·운영비가 입증될 때만 관계 탐색 확장 | OFF/ON Gold의 Recall·회복률·지연 순이득이나 운영 budget이 충족되지 않으면 도입하지 않음 |
| `semantic.resolve` 내부화, `rag.answer` 채택 | raw metadata/tool 표면을 줄이고 의미 결속과 citation 답변을 고수준 contract로 제한 | capability schema 평가에서 다른 고수준 경계가 우수할 때 versioned 변경 |
| Report는 Service 유지 | 승인·부분 실패·Artifact lineage는 자율 Agent보다 결정론적 Workflow가 적합 | 자연어 보고서 조율이 반복 병목으로 측정될 때 상위 Route만 확장 |

과거 Walkerhill V4.3 교체 검토 archive는 현재 작업 트리에서 제거됐다. 현재 실행 여부는
release manifest·코드·migration·runtime receipt를 함께 확인해 판정한다.
