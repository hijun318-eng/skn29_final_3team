## 1. 서론

### 1.1 평가 대상

검토한 제안은 DataHub를 단순 데이터 카탈로그가 아니라 지표와 데이터 관계의 권위 있는 저장소로 사용하고, Backend가 사용자 권한에 맞는 최소 관계 그래프만 가져와 안전한 SQL을 만들며, Trino가 실제 데이터 접근 권한을 최종 집행하는 구조다.

```text
DataHub
├─ Dataset / Schema / Domain / Ownership / Glossary
├─ Native Lineage
├─ Metric entities
├─ Semantic Model
│  └─ Dataset relationships
│     ├─ join key
│     ├─ cardinality
│     └─ allowed join path
└─ AnswerService typed policy aspect
   ├─ temporal predicate
   ├─ pre-aggregation requirement
   ├─ metric별 allowed edge
   ├─ edge permission
   └─ release/checksum

Backend
├─ 사용자 권한에 맞는 Metric/Semantic Model 검색
├─ 필요한 관계 subgraph만 조회
├─ typed policy 검증
├─ 결정론적 SQL 생성·AST 검증
└─ Trino 실행

Trino
└─ 실제 데이터 접근 권한 집행
```

### 1.2 한 줄 평가

**목표 아키텍처로는 타당하고 현재 구조보다 책임 구분이 명확하지만, DataHub 1.7의 Beta 기능과 검색 제약, 정책 원본 중복, 공용 Trino 계정 문제를 해결하지 않은 채 그대로 전환하는 것은 권장하지 않는다.**

평가 결과는 다음과 같다.

| 평가 항목 | 판단 | 이유 |
|---|---|---|
| 개념적 타당성 | 높음 | 카탈로그·의미·실행 정책·최종 권한 집행의 책임이 분리됨 |
| 현재 프로젝트 적합성 | 높음, 조건부 | 현재의 Metric Rule·Join Graph·AST 검증 구조와 방향이 유사함 |
| 즉시 구현 가능성 | 보통 이하 | DataHub 1.7 Metric/Semantic Model은 Beta이며 일반 검색과 MCP 검색이 아직 로드맵 단계임 |
| 권한 안전성 | 현재는 부분 충족 | Backend 권한 필터는 있으나 Trino는 공용 runtime principal을 사용함 |
| 운영·업그레이드 난이도 | 중간 이상 | 커스텀 Aspect, 다중 Entity release, checksum과 전환 절차가 추가됨 |

## 2. 본론

### 2.1 현재 프로젝트와 제안 구조 비교

현재 구현은 제안과 완전히 다른 구조가 아니라, 제안 구조의 여러 개념을 **Dataset의 custom properties와 Glossary Term에 자체 계약으로 구현한 상태**에 가깝다.

| 제안 구성 | 현재 프로젝트 구현 | 상태 | 객관적 판단 |
|---|---|---|---|
| Dataset / Schema / Domain / Ownership / Glossary | DataHub 네이티브 Dataset·Schema·Domain·Owner·Glossary를 읽고 release와 대조 | 구현됨 | 유지하는 것이 적절함 |
| Native Lineage | 발행·검증 범위에는 lineage가 있으나 runtime JOIN 허용 판단의 원본은 아님 | 부분 구현 | Lineage는 영향 관계, Semantic Model relationship은 허용 JOIN이라는 구분이 적절함 |
| Metric entity | Glossary Term과 Dataset의 `metric_rules`로 표현 | 미사용 | 네이티브 Metric으로 이전할 가치가 있으나 기능 안정성 검증 필요 |
| Semantic Model | Dataset custom property의 `join_graph`로 표현 | 미사용 | 네이티브 relationship으로 이전하면 가독성과 탐색성이 좋아질 수 있음 |
| join key / cardinality | `join_graph.edges`의 equality condition·cardinality로 관리 | 구현됨 | 현재 계약이 네이티브 기능보다 더 세밀한 부분도 있음 |
| temporal predicate | join edge의 temporal condition과 `time_rules`로 관리 | 구현됨 | 네이티브 relationship만으로 대체 가능한지 확인 필요 |
| pre-aggregation | join edge별 required·grain·keys로 관리 | 구현됨 | fan-out 방지에 중요하므로 반드시 보존해야 함 |
| metric별 allowed edge | Metric Rule의 `allowed_join_ids`로 관리 | 구현됨 | Semantic Model의 전체 허용 관계와 별도의 실행 정책으로 유지하는 편이 맞음 |
| edge permission | Dataset·Metric entitlement와 연결해 Backend에서 검사 | 부분 구현 | 관계 자체의 사용자별 권한 모델을 더 명시적으로 만들 필요가 있음 |
| release/checksum | catalog·manifest·semantic·Trino schema checksum을 검증 | 구현됨 | 다중 네이티브 Entity로 전환해도 유지해야 할 강점 |
| 사용자 권한 기반 검색 | 전체 active Dataset snapshot 후보를 lexical/hybrid로 평가한 뒤 entitlement 필터 | 구현됨 | DataHub 자체 검색 권한 필터로 오해하면 안 됨 |
| 필요한 subgraph 조회 | seed·Metric dependency·최단 JOIN 경로로 확장하고 전체 자산 권한 재검사 | 구현됨 | 제안과 이미 상당히 일치함 |
| 결정론적 SQL·AST 검증 | SQLGlot 기반 Metric·JOIN·시간·허용 자산 검증 | 구현됨 | 그대로 유지해야 함 |
| Trino 최종 권한 집행 | file access control로 공용 `answervice_runtime`의 read-only 접근을 집행 | 부분 구현 | 쓰기 차단은 되지만 앱 사용자별 Role 권한 집행은 아님 |

현재 검색의 구체적인 동작은 다음과 같다.

1. DataHub의 모든 active Dataset과 Glossary Term을 `query_text="*"`로 페이지 조회한다.
2. 질문을 Unicode token으로 나누고 Dataset·컬럼·Glossary의 lexical overlap을 계산한다.
3. hybrid 모드이면 DataHub Dataset semantic search 순위를 함께 반영한다.
4. 후보 순위를 만든 다음 Backend 로그인 사용자의 Role/Domain을 Dataset entitlement와 대조한다.
5. 선택 Dataset에서 Metric dependency와 JOIN 경로로 관계 subgraph를 확장한다.
6. 확장 과정에서 추가된 중간 Dataset까지 모두 다시 권한 검사한다.
7. Metric별 `allowed_roles`, PII, `allowed_join_ids`, query strategy를 적용한다.
8. 최종 Context로 SQL을 만들고 SQLGlot AST 정책 검증 후 Trino에 실행한다.

즉, 현재 구현도 이미 **검색 후보 생성 → 권한 필터 → 필요한 관계 확장 → 확장 자산 전체 재검사** 순서다. 제안의 핵심 변화는 알고리즘 자체보다는 `metric_rules`와 `join_graph`의 권위 원본을 DataHub 네이티브 Metric/Semantic Model로 옮기는 데 있다.

### 2.2 LLM 기반 독립 평가

#### 2.2.1 장점

첫째, 책임 경계가 명확하다. DataHub는 “무엇을 어떤 의미로 사용할 수 있는지”, Backend는 “이번 사용자와 질문에 어떤 Context를 구성할지”, Trino는 “실제 데이터에 접근 가능한지”를 담당한다. 메타데이터 검색 권한과 데이터 실행 권한을 서로 다른 방어선으로 두는 것도 타당하다.

둘째, 필요한 관계 subgraph만 가져오는 방식은 전체 스키마를 LLM에 전달하는 방식보다 효율적이다. Context 크기와 관계 모호성이 줄고, 허용되지 않은 Dataset·JOIN이 모델 입력에 노출되는 범위도 줄어든다.

셋째, Metric별 allowed edge와 pre-aggregation 규칙은 일반적인 “JOIN 키만 등록”한 구조보다 안전하다. 관계가 문법적으로 가능해도 특정 Metric의 grain을 깨뜨리거나 중복 집계를 만드는 JOIN은 별도로 차단할 수 있기 때문이다.

넷째, release/checksum은 여러 메타데이터가 서로 다른 시점의 값으로 섞이는 문제를 줄인다. 현재 프로젝트가 이미 가진 강점이며 네이티브 Entity 도입 이후에도 유지해야 한다.

#### 2.2.2 보완이 필요한 점

**1. Native Lineage와 허용 JOIN을 같은 것으로 취급하면 안 된다.**

Lineage는 데이터가 어디서 왔고 어디로 흘렀는지를 나타낸다. 두 Dataset에 lineage가 있다고 해서 분석 시 직접 JOIN해도 된다는 뜻은 아니다. 허용 JOIN은 Semantic Model relationship에서 관리하고, lineage는 영향 분석과 근거 표시 용도로 사용해야 한다.

**2. cardinality만으로 fan-out을 방지할 수 없다.**

안전한 relationship에는 최소한 다음 정보가 필요하다.

- 양쪽 Dataset과 JOIN 방향
- equality join key와 필요 시 temporal predicate
- one-to-one, many-to-one 등의 cardinality
- 양쪽 grain과 key uniqueness 근거
- 선집계 필요 여부와 선집계 grain
- Metric별 사용할 수 있는 edge 목록
- 사용자 또는 Role별 edge permission

현재 프로젝트의 `join_graph`에는 equality condition, temporal condition, cardinality, preaggregation grain/keys가 이미 있으므로 네이티브 모델로 옮길 때 기능을 축소하면 안 된다.

**3. 의미적으로 허용된 관계와 권한상 허용된 관계를 분리해야 한다.**

Semantic Model의 relationship은 “이 JOIN은 데이터 의미상 유효하다”를 나타낸다. `edge permission`은 “이 사용자 또는 Metric이 이번 요청에서 이 관계를 써도 된다”는 정책이다. 두 값은 같은 필드가 아니며 각각 검증해야 한다.

**4. 네이티브 원본과 기존 custom property를 동시에 수정 가능한 원본으로 두면 안 된다.**

예를 들어 DataHub Semantic Model relationship과 Dataset `join_graph`를 모두 운영자가 수정할 수 있게 두면 어느 쪽이 정답인지 알 수 없다. 전환 중에는 기존 계약을 runtime 원본으로 유지하고 네이티브 Entity를 shadow read한 뒤, 동등성 검증을 통과한 release에서 원본을 한 번만 전환해야 한다.

**5. Metric의 SQL expression을 그대로 실행하면 안 된다.**

DataHub Metric expression도 외부 메타데이터 입력이다. Backend는 expression을 SQLGlot AST로 파싱하고, 승인 column·함수·grain·filter·dialect 계약과 대조한 뒤 자체 AST에 결합해야 한다. 문자열을 그대로 SQL에 삽입하는 방식은 피해야 한다.

**6. 커스텀 typed Aspect는 타당하지만 운영 비용이 있다.**

`AnswerService typed policy aspect`는 큰 JSON 문자열 custom property보다 구조·타입·버전 검증에 유리하다. 다만 DataHub metadata model 등록, SDK/PDL 호환성, API read-back, 업그레이드 호환성까지 관리해야 한다. 단순 release ID·승인 상태·분류처럼 scalar인 값은 Structured Property가 적합하고, temporal predicate·Metric-edge matrix처럼 중첩 구조인 값만 custom Aspect에 두는 편이 낫다.

**7. 여러 Entity의 release를 원자적으로 활성화하는 절차가 필요하다.**

Metric, Semantic Model, Dataset, relationship, custom Aspect는 각각 갱신된다. 한 번에 모두 바뀐다고 가정하면 중간 상태가 노출될 수 있다. 다음과 같은 release manifest가 필요하다.

```text
release_id
├─ Metric URN + aspect version/checksum
├─ Semantic Model URN + aspect version/checksum
├─ Dataset URN + schema checksum
├─ AnswerService policy aspect checksum
└─ Trino schema/access-policy checksum
```

Backend는 전부 exact read-back한 release만 활성화해야 한다.

### 2.3 인터넷 조사 평가

#### 2.3.1 DataHub 공식 기능과의 일치 여부

DataHub 1.7 공식 문서에는 네이티브 `Metric`과 `Semantic Model` Entity가 존재한다. Semantic Model은 Dataset 묶음, 허용 JOIN 패턴, cardinality, dimension과 metric을 표현하고, Metric은 계산 expression과 Semantic Model 연결, 파생 관계, governance 정보를 가진다. 따라서 제안의 기본 방향은 DataHub가 설계한 최신 모델과 일치한다. 또한 Python SDK로 두 Entity를 발행할 수 있다. 다만 이 기능은 **Beta**이고 UI, lineage 시각화, ingestion 범위가 계속 변경 중이다. OSS 1.7에서는 GMS의 `METRICS_ENABLED=true` 설정도 필요하다. [DataHub Metrics & Semantic Models 공식 문서](https://docs.datahub.com/docs/features/feature-guides/metrics-and-semantic-models)

중요한 제약도 있다. 공식 문서는 현재 Metric 탐색이 `/metrics` browse tree 중심이며, Metric/Semantic Model을 universal Search와 Browse의 일급 Entity로 노출하고 MCP로 검색하는 기능은 “near-term roadmap”이라고 명시한다. 따라서 제안의 “사용자 권한에 맞는 Metric/Semantic Model 검색”을 현재 Dataset 검색 API와 같은 방식으로 바로 구현할 수 있다고 가정하면 안 된다. exact DataHub 1.7 배포본에서 GraphQL/SDK 조회, pagination, search index, 권한 적용 범위를 먼저 PoC해야 한다. [같은 공식 문서의 Search 및 What's Coming Next](https://docs.datahub.com/docs/features/feature-guides/metrics-and-semantic-models#search)

또한 DataHub는 Metric 정의를 catalog할 뿐 Metric 값을 계산하지 않는다. 계산과 시각화는 BI 도구 또는 semantic layer에 남는다고 공식 문서가 밝힌다. 따라서 Backend가 안전한 SQL을 구성하고 Trino가 실행하는 제안은 이 책임 경계와 맞는다. [DataHub Metrics FAQ](https://docs.datahub.com/docs/features/feature-guides/metrics-and-semantic-models#faq)

Structured Property는 Entity에 타입이 있는 확장 속성을 붙이고 허용 값과 검색 facet을 제공하는 공식 수단이다. Metric additivity나 승인 상태처럼 단순하고 탐색 가능한 속성에 적합하다. 반면 여러 edge와 predicate가 중첩된 실행 정책은 별도 typed Aspect 또는 외부 versioned policy registry가 더 명확하다. [DataHub Custom Properties 개요](https://docs.datahub.com/docs/features/feature-guides/properties/overview)

DataHub metadata model 자체는 Entity가 여러 Aspect로 구성되는 schema-first 구조이며, Relationship을 graph edge로 표현할 수 있다. 따라서 AnswerService 전용 Aspect를 만드는 것은 기술적으로 자연스러운 확장 방식이지만 stock schema와 별도 수명주기를 관리해야 한다. [DataHub Metadata Model](https://github.com/datahub-project/datahub/blob/master/docs/modeling/metadata-model.md), [DataHub Entity Registry](https://github.com/datahub-project/datahub/blob/master/metadata-models/src/main/resources/entity-registry.yml)

#### 2.3.2 검색 권한에 관한 공식 제약

DataHub 공식 문서에 따르면 query-time Search Access Control은 DataHub Cloud 기능이다. Self-hosted OSS에서 `VIEW_AUTHORIZATION_ENABLED=true`를 사용해도 entity page gating 또는 post-search masking이며 검색 시점의 query filter는 아니다. 현재 프로젝트가 OSS 1.7을 사용하므로 Backend의 exact entitlement 필터를 제거하고 DataHub 검색만 신뢰해서는 안 된다. [DataHub Search Access Controls](https://docs.datahub.com/docs/features/feature-guides/search-access-controls)

따라서 권장 순서는 다음과 같다.

```text
DataHub 또는 별도 index에서 후보 검색
→ Backend가 사용자 entitlement를 exact 검사
→ 허용 후보만 subgraph 확장
→ 확장된 모든 Metric·Dataset·edge를 다시 exact 검사
→ Context 구성
```

#### 2.3.3 Trino 권한 집행과 현재 프로젝트의 차이

Trino 공식 문서는 system access control이 connector 권한보다 앞서 전역 권한을 검사하며, file access control은 user·group·role·catalog·schema·table·column 규칙과 row filter, column mask를 지원한다고 설명한다. OPA나 Ranger를 사용하면 요청 identity에 기반한 세밀한 정책 집행도 가능하다. [Trino System Access Control](https://trino.io/docs/current/security/built-in-system-access-control.html), [Trino File-based Access Control](https://trino.io/docs/current/security/file-system-access-control.html), [Trino Security Overview](https://trino.io/docs/current/security/overview.html)

현재 프로젝트는 file access control을 실제로 활성화했고, `answervice_runtime`에 허용 catalog 전체의 모든 schema/table `SELECT`를 부여한다. Backend도 모든 요청을 환경 변수 `TRINO_RUNTIME_USER`의 동일한 사용자와 `X-Trino-User`로 전송한다.

따라서 현재 Trino가 집행하는 것은 다음과 같다.

- runtime principal은 읽기만 가능하다.
- 허용 catalog 밖에는 접근할 수 없다.
- 등록되지 않은 principal은 최종 deny 규칙으로 거부된다.

그러나 다음은 현재 Trino가 직접 구분하지 않는다.

- 로그인 사용자가 analyst인지 manager인지
- 사용자 Role별 Dataset 접근 차이
- 사용자별 row filter 또는 column mask
- DataHub의 Metric별 `allowed_roles` 또는 edge permission

즉, 현재는 Backend가 사용자별 권한의 유일한 실질 집행자이고 Trino는 공용 서비스 계정의 넓은 read-only 경계만 집행한다. 제안처럼 “Trino가 실제 데이터 접근 권한을 최종 집행”한다고 표현하려면 다음 중 하나가 필요하다.

1. 인증된 최종 사용자 또는 안전하게 매핑된 Trino group/role로 query를 실행한다.
2. OPA/Ranger/custom access control에 서버가 보증한 사용자·Role identity를 전달한다.
3. 사용자별 구분이 불필요하다면 최소한 capability별 별도 service principal과 제한된 view/schema ACL을 사용한다.

Backend의 권한 검증은 사용자 경험과 Context 축소를 위해 계속 필요하고, Trino 권한은 우회·오류에 대비한 최종 방어선이어야 한다.

#### 2.3.4 유사 실사용 사례

Pinterest는 오픈소스 DataHub 기반 내부 카탈로그 PinCat을 metadata의 system of record로 사용하고, 표·컬럼 설명, Glossary, Metric 정의, 신뢰도 등급, freshness, 과거 query의 검증된 JOIN key·filter·aggregation 패턴을 Text-to-SQL Context로 사용한다. 실행 전에는 Presto `EXPLAIN` 검증과 제한된 `LIMIT`도 적용한다. 10만 개가 넘는 분석 테이블 환경에서 단순 키워드 검색보다 의미 검색과 검증된 구조 패턴, governance-aware ranking을 결합했다는 점에서 이 프로젝트와 가장 유사한 공개 사례다. [Pinterest Engineering: Unified Context-Intent Embeddings for Scalable Text-to-SQL](https://medium.com/pinterest-engineering/unified-context-intent-embeddings-for-scalable-text-to-sql-793635e60aac)

Pinterest의 사례는 제안 구조의 다음 부분을 지지한다.

- 카탈로그를 신뢰 가능한 Context 원본으로 사용
- 전체 스키마 대신 관련 table과 관계만 선택
- JOIN key와 filter를 LLM이 추측하지 않게 함
- governance 신호를 검색 순위에 반영
- SQL 실행 전 구조 검증과 제한 적용

다만 Pinterest도 DataHub 하나만으로 모든 검색과 실행 정책을 해결하지 않는다. PinCat, vector/query index, 내부 문서, query history, MCP 도구, Presto 실행 계층을 조합한다. 이는 현재 DataHub 1.7의 검색 기능 제약을 고려할 때, 이 프로젝트도 DataHub를 권위 원본으로 사용하되 요청 시점 검색 index와 실행 정책 검증기를 별도 책임으로 둘 수 있음을 보여준다.

### 2.4 LLM 평가와 인터넷 조사 결과 비교

| 쟁점 | LLM 독립 판단 | 인터넷 조사 결과 | 종합 결론 |
|---|---|---|---|
| Metric/Semantic Model 도입 | custom property보다 명확한 목표 구조 | DataHub 1.7에 네이티브 Entity가 실제 존재하나 Beta | 조건부 도입 타당 |
| 관계 subgraph | Context와 권한 노출 범위를 줄임 | Pinterest도 관련 table·검증된 JOIN 패턴만 검색 | 적극 권장 |
| Native Lineage 사용 | JOIN 허용 그래프와 분리해야 함 | DataHub도 lineage와 Semantic Model relationship을 별도 개념으로 제공 | 분리 유지 |
| Metric별 edge·preaggregation | 정확도와 fan-out 방지에 필요 | DataHub native relationship은 cardinality를 제공하지만 프로젝트 전용 세부 실행 정책 전체를 보장하지 않음 | typed policy로 보존 |
| DataHub 검색만으로 권한 필터 | OSS에서는 위험 | OSS query-time Search Access Control은 제공되지 않음 | Backend exact 필터 필수 |
| Metric/Semantic Model 직접 검색 | API capability PoC 필요 | universal Search/MCP 지원이 로드맵 단계 | 즉시 전환 금지 |
| Trino 최종 권한 | 사용자 identity가 전달되어야 완성 | Trino는 user/group/role 및 row/column 정책을 지원 | 사용자 또는 capability 단위 principal 설계 필요 |
| DataHub 하나로 전체 해결 | 검색·정책·실행을 한 제품에 과도하게 몰면 위험 | Pinterest도 여러 Context/index/execution 계층을 조합 | DataHub는 권위 원본, Backend는 요청 정책 엔진으로 유지 |

### 2.5 권장 보정 구조

제안은 다음과 같이 보정하는 것이 안전하다.

```text
DataHub — 의미와 거버넌스의 권위 원본
├─ Native Dataset / Schema / Domain / Owner / Glossary / Lineage
├─ Native Metric / Semantic Model            # 1.7 capability PoC 통과 후
│  └─ 의미적으로 허용된 relationship
├─ Structured Properties
│  └─ 승인 상태, 분류, release ID 등 단순 typed field
└─ AnswerService Policy Aspect
   └─ temporal, preaggregation, metric-edge, permission 등 중첩 실행 정책

Release Registry — 일관성 경계
└─ 모든 Entity/Aspect/Trino schema checksum과 active release pointer

Backend — 요청 시점 정책 결정
├─ 인증된 사용자 Role/Domain 확인
├─ 후보 Metric/Semantic Model 검색
├─ OSS query-time 권한 exact 필터
├─ 허용 relationship 중 필요한 subgraph만 구성
├─ custom policy와 release/checksum exact 검증
├─ Metric expression을 SQLGlot AST로 재검증
└─ 서버 소유 parameter를 바인딩한 read-only SQL 실행

Trino — 최종 데이터 권한 집행
├─ 사용자/group/role 또는 capability principal 인증
├─ catalog/schema/table/column ACL
├─ 필요 시 row filter / column mask
└─ SELECT-only, query/resource limit
```

핵심 원칙은 다음 세 가지다.

1. **원본은 하나만 둔다.** 전환 후 relationship의 원본은 Semantic Model, 복잡한 실행 제약의 원본은 AnswerService Policy Aspect로 정한다.
2. **검색과 권한을 분리한다.** 검색은 후보를 만들 뿐이고 Backend와 Trino의 권한 검증을 대신하지 않는다.
3. **release를 Entity 하나가 아니라 계약 묶음으로 활성화한다.** 일부 Aspect만 최신인 혼합 상태는 실패로 닫는다.

### 2.6 단계별 도입안

#### 1단계: 기능 검증

- exact DataHub 1.7 배포에서 `METRICS_ENABLED` 활성 여부 확인
- SDK로 테스트 Semantic Model·Metric 발행
- GraphQL/Rest.li의 조회, pagination, 삭제·변경 read-back 확인
- 일반 검색, `/metrics` browse, authorization 적용 범위를 실제 계정으로 검증
- 현재 `join_graph`의 temporal/preaggregation 정보를 손실 없이 표현 가능한지 확인

#### 2단계: shadow 비교

- 현재 `metric_rules`와 `join_graph`를 runtime 원본으로 유지
- 같은 내용을 네이티브 Metric/Semantic Model에 발행
- 요청에는 사용하지 않고 checksum·relationship·Metric expression 동등성만 비교
- 불일치 시 기존 경로로 조용히 성공시키지 말고 migration 검증 실패로 처리

#### 3단계: 읽기 원본 전환

- 네이티브 Metric/Semantic Model을 단일 원본으로 전환
- 기존 custom `metric_rules`/`join_graph`는 삭제하거나 네이티브 원본에서 결정적으로 생성되는 read-only projection으로 변경
- Metric universal search가 불완전하면 direct Entity API 또는 별도 재생성 가능한 index 사용
- 별도 index는 권위 원본이 아니라 DataHub release에서 재생성 가능한 검색 projection으로 제한

#### 4단계: 정책과 최종 권한 강화

- 단순 필드는 Structured Property, 중첩 정책은 versioned custom Aspect로 분리
- Trino에 사용자/group/role 매핑 또는 capability별 최소권한 principal 적용
- 허용·거부 사용자 모두로 table/column/row 접근 통합 테스트
- Backend 정책을 우회한 직접 SQL이 Trino에서 거부되는지 검증

### 2.7 도입 전 반드시 정해야 할 운영 기준

이 문서만으로 production-ready 여부를 확정할 수는 없다. 현재 요청에는 트래픽, 데이터 민감도 등급, 가용성 목표가 없기 때문이다. 도입 전 다음 값은 제품·보안·운영 담당자가 숫자로 정해야 한다.

- 예상 QPS와 동시 분석 수
- 검색 및 Context 구성 p50/p95/p99 latency 목표
- DataHub 장애 시 허용 가능한 동작과 SLO
- release registry와 정책 데이터의 RPO/RTO
- PII별 row filter·column mask 요구 수준
- cache TTL과 release activation 최대 지연
- native Entity 조회 실패율 및 fallback 금지 기준

최소 검증 지표는 검색 top-k recall, 권한 누출 0건, 미승인 JOIN 실행 0건, release 혼합 0건, SQL AST 정책 우회 0건, Trino 직접 접근 우회 0건으로 두어야 한다. 성능 목표는 임의 숫자를 정하기보다 현재 경로의 p50/p95/p99 baseline을 먼저 측정하고 허용 회귀 폭을 승인하는 방식이 객관적이다.

## 3. 결론

### 3.1 LLM 생성 평가 결론

LLM 관점에서 이 제안은 **조건부 채택할 가치가 높은 목표 아키텍처**다. 특히 Native Lineage와 허용 relationship의 분리, Metric별 allowed edge, pre-aggregation, typed policy, 최소 subgraph, SQLGlot AST 검증, Trino 최종 집행의 조합은 일반적인 “카탈로그 검색 후 LLM이 SQL 생성” 구조보다 안전하고 설명 가능하다.

다만 네이티브 Semantic Model만 도입한다고 문제가 자동으로 해결되지는 않는다. 기존 계약과의 이중 원본, Metric SQL expression 신뢰, 다중 Entity release의 비원자성, custom Aspect 업그레이드, 공용 Trino principal을 반드시 함께 해결해야 한다.

### 3.2 인터넷 조사 평가 결론

공식 문서 조사 결과 DataHub 1.7은 제안의 Metric/Semantic Model·relationship·cardinality·governance 방향을 실제 제품 기능으로 지원한다. Pinterest 실사용 사례도 카탈로그의 스키마·Glossary·Metric·검증된 JOIN 패턴을 Context로 사용하고 실행 전에 SQL을 검증하는 접근의 현실성을 뒷받침한다.

반면 공식 문서는 해당 기능이 Beta이며 Metric/Semantic Model의 universal Search와 MCP 검색이 아직 로드맵이라고 밝힌다. OSS의 query-time Search Access Control도 제공되지 않는다. 따라서 인터넷 조사 역시 “즉시 전면 전환”보다 “기능 PoC → shadow 비교 → 단일 원본 전환”을 지지한다.

### 3.3 최종 종합 결론

**제안은 폐기할 구조도, 그대로 즉시 적용할 구조도 아니다. 보정 후 단계적으로 채택하는 것이 가장 객관적인 결론이다.**

현재 프로젝트는 이미 Dataset custom property 기반으로 관계·시간·선집계·Metric별 edge·release/checksum을 세밀하게 검증하고 있다. 그러므로 이번 전환의 목표는 기능을 새로 만드는 것이 아니라 다음과 같이 정리하는 데 두어야 한다.

1. Metric과 의미적 relationship을 DataHub 네이티브 Entity로 승격한다.
2. 프로젝트 전용 실행 정책은 typed Aspect로 분리한다.
3. 기존 custom property와 네이티브 Entity 사이의 이중 원본을 없앤다.
4. OSS 검색 제약 때문에 Backend exact entitlement 필터는 유지한다.
5. Trino 공용 read-only 계정을 사용자/Role 또는 제한된 capability principal 기반 최종 권한 집행으로 강화한다.
6. 모든 Entity·Aspect·Trino 계약을 하나의 release/checksum manifest로 묶는다.

이 조건을 충족하면 제안 구조는 현재보다 DataHub 표준에 가깝고, 운영자가 이해하기 쉬우며, 향후 Metric 탐색과 lineage 확장에도 유리하다. 반대로 Trino 사용자 권한 분리와 단일 권위 원본을 해결하지 않으면 구조도만 좋아지고 실제 보안과 운영 일관성은 개선되지 않는다.
