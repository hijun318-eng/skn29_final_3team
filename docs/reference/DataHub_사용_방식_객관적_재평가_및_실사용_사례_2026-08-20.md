# Answervice DataHub 사용 방식 객관적 재평가 및 실사용 사례 비교

> 조사 기준일: 2026-08-20
> 코드 기준: `dev` `14fab5d`
> 평가 방법: 최신 코드에 대한 LLM 독립 평가와 인터넷 1차 자료 조사를 분리한 뒤 결론을 비교한다.
> 증거 한계: 코드·단위/계약 테스트와 공개 자료를 평가했으며, 운영 DataHub·Trino의 부하 시험이나 동일 릴리스 live E2E를 수행한 결과는 아니다.

# 1. 서론

## 1.1 평가 목적

Answervice는 DataHub를 단순한 카탈로그 화면이 아니라 자연어 분석을 위한 권위 있는 Context 원본으로 사용한다. Backend는 DataHub에서 Dataset, Glossary Term, Owner, Domain, Lifecycle, Metric, Join, Entitlement를 읽고, 승인된 정보만 SQL 생성과 Trino 실행에 전달한다.

이 문서는 다음 질문에 객관적으로 답하는 것을 목적으로 한다.

1. 현재 DataHub 사용 방식이 제품 목적에 적합한가?
2. 검색 정확성·권한·운영 안정성·확장성 측면에서 장단점은 무엇인가?
3. 실제 DataHub 도입 조직은 유사한 문제를 어떻게 해결했는가?
4. LLM의 코드 기반 평가와 인터넷 실사용 사례의 결론은 일치하는가?

## 1.2 객관성 기준

평가는 다음 원칙을 적용했다.

- 장점과 결함을 같은 기준으로 기록한다.
- 코드가 있다는 사실과 운영 검증 완료를 구분한다.
- 벤더 사례의 성과 수치는 방향성 근거로만 사용한다.
- DataHub 공식 기능과 Answervice의 커스텀 계약을 구분한다.
- 추정 성능 수치를 만들지 않고, 측정하지 않은 latency·recall·동시 처리량은 `미측정`으로 표시한다.
- 최신 코드에서 보완된 문제를 과거 상태로 평가하지 않는다.

## 1.3 현재 구조 요약

현재 기본 실행 흐름은 다음과 같다.

```text
인증된 사용자와 RUN_ANALYSIS Capability 확인
→ DataHub Dataset·Glossary 전체 목록 조회
→ 각 Entity 상세 metadata read-back
→ 승인 상태·release·checksum·Owner·Domain·Lifecycle 검증
→ 질문과 전체 승인 Dataset의 lexical/hybrid 관련도 계산
→ Dataset entitlement 적용
→ Metric dependency·Join 경로 확장
→ 확장된 모든 Dataset entitlement 재검사
→ Metric별 Role·PII 정책 적용
→ Trino live schema 검증
→ SQL 생성용 typed Context 구성
```

중요한 특징은 **전체 승인 Dataset을 검색한 뒤 권한을 적용한다**는 것이다. 권한으로 후보를 먼저 줄인 후 검색하는 구조는 아니다.

# 2. 본론

## 2.1 현재 DataHub 사용 방식의 사실 확인

### 2.1.1 카탈로그 수집과 검증

Backend는 DataHub GraphQL `searchAcrossEntities(query="*")`로 Dataset과 Glossary Term URN을 페이지 단위로 수집하고 각 Entity의 상세 metadata를 읽는다. 검증된 snapshot은 기본 86,400초 동안 재사용한다.

검증 범위는 다음과 같다.

- runtime governance가 존재하는 Dataset
- `approval_status == "APPROVED"`
- 단일 active release와 policy
- release manifest membership·count·checksum
- native Owner·Domain·Lifecycle
- Dataset·Trino FQN 일치
- DataHub schema read-back과 typed schema 계약
- Glossary Term과 Metric rule 일치
- Join graph와 Query policy
- Dataset·Metric entitlement

- [`catalog_snapshot.py`](../../app/backend/app/adapters/catalog_snapshot.py)

### 2.1.2 검색 방식

운영 Compose 기본값은 `DATAHUB_SEARCH_MODE=lexical`이다. 검색 대상 문자열은 Dataset 이름·설명·FQN, 컬럼 이름, 연결된 Glossary Term의 label·alias·definition, Dimension alias다.

질문과 Dataset metadata를 NFKC 정규화·casefold·Unicode token화하고, 일부 한국어 조사를 보조 분리한다. 후보 점수는 다음 순서로 정렬된다.

1. DataHub semantic hit 포함 여부
2. 질문과 Dataset token의 교집합 수
3. semantic rank
4. 결정적 FQN 순서

`hybrid` 모드에서는 전체 snapshot과 DataHub semantic search를 병렬 실행한다. Semantic 기능이 실패하면 lexical로 조용히 우회하지 않고 fail-closed한다.

### 2.1.3 권한 관리

권한은 세 층으로 집행된다.

| 계층 | 현재 집행 방식 |
|---|---|
| API 기능 | 인증 Role이 `RUN_ANALYSIS` Capability를 가졌는지 확인 |
| Dataset | DataHub `entitlements.roles/domains`와 요청 Context 대조 |
| Metric | v2 Metric `allowed_roles`, `contains_pii`, visibility 정책 대조 |

현재 canonical Role은 `analyst`, `report_admin`, `data_admin`, `platform_admin`이다. 일반 Role은 자기 자신만 만족하고 `platform_admin`은 모든 Role entitlement를 상속한다. 알 수 없는 Role 문자열은 거부한다.

Dataset 판정은 `Role 일치 OR Domain 일치`다. 그러나 표준 `RequestContext`에는 사용자 Domain 목록이 없으므로 일반 HTTP 분석은 사실상 Role 기반으로 동작한다.

최신 코드에서는 검색 seed뿐 아니라 Metric dependency와 Join 최단 경로로 추가된 모든 Dataset에 `entitled(context)`를 다시 적용한다. 이전에 존재했던 Join 중간 자산 권한 누락은 코드와 회귀 테스트 기준으로 보완됐다.

Metric은 v2 governance이고 Role이 허용되며 `contains_pii == false`일 때만 runtime Context에 들어간다.

## 2.2 LLM 생성 평가

이 절은 외부 사례의 결론을 적용하기 전에 현재 코드의 책임 경계와 알고리즘만으로 평가한 결과다. 점수는 절대 성능 점수가 아니라 동일 가중치의 5점 진단 척도다.

| 평가 항목 | 점수 | 근거 |
|---|---:|---|
| 거버넌스 무결성 | 4.5/5 | 승인·Owner·Domain·Lifecycle·manifest·checksum·schema를 하나의 release로 fail-closed 검증 |
| 권한 완전성 | 4.0/5 | API·Dataset·Join 확장·Metric 권한을 중첩 집행하나 HTTP 사용자 Domain과 세밀한 row/column mask는 없음 |
| 검색 관련성 | 2.5/5 | 결정적 Unicode lexical 검색은 단순하고 재현 가능하지만 exact token overlap 중심이고 기본 hybrid가 아님 |
| 확장성 | 2.5/5 | 하루 snapshot으로 반복 I/O를 줄였지만 갱신은 전체 Entity hydration, warm ranking도 전체 Dataset 순회 |
| 운영 안전성 | 4.0/5 | stale·semantic 장애·schema drift를 성공으로 우회하지 않고 bounded pagination·concurrency 사용 |
| 표준성·상호운용성 | 3.0/5 | DataHub를 Context 원본으로 쓰는 방향은 표준적이나 entitlement·release 계약과 request-time 전체 scan은 프로젝트 특화 |

단순 평균은 3.4/5다. 이는 “우수”나 “미흡”의 단정이 아니라 다음 조건부 판정을 뜻한다.

> 작은 승인 카탈로그에서 안전성과 재현성을 우선할 때는 적합하지만, 카탈로그와 동시 요청이 커질 때도 효율적이라고 입증되지는 않았다.

### 2.2.1 강점

#### DataHub를 LLM의 참고 문서가 아니라 실행 계약으로 사용한다

LLM이 Dataset·Metric·Join·기간·권한을 임의로 결정하지 않는다. DataHub metadata를 typed Context로 변환하고 SQLGlot·Trino 경계까지 연결하는 구조는 환각으로 인한 잘못된 자산 선택을 줄이는 데 유리하다.

#### Release 일관성을 강하게 보장한다

Dataset 하나가 검색됐다는 이유만으로 사용하지 않고 전체 release membership과 checksum을 검증한다. 여러 시점의 schema·metric·policy가 섞이는 문제를 줄인다.

#### 권한 집행이 최신화됐다

Dataset seed뿐 아니라 Join으로 추가된 중간 자산을 재검사하며, Metric별 허용 Role과 PII 여부도 검사한다. 이는 이전 구조보다 명확한 개선이다.

#### 실패를 성공으로 위장하지 않는다

DataHub·semantic capability·manifest·Trino schema가 불완전하면 mock, stale snapshot, 빈 성공값으로 대체하지 않는다. 분석 제품에서 잘못된 숫자를 정상 응답으로 내는 위험을 낮춘다.

### 2.2.2 한계와 위험

#### 검색 전에 권한 scope를 적용하지 않는다

전체 승인 Dataset의 검색 token과 semantic hit를 계산한 뒤 entitlement를 적용한다. 비권한 Dataset이 사용자 응답에는 반환되지 않지만 Backend 검색 계산에는 참여한다. 보안상 직접 노출은 막았으나 최소 처리 원칙과 대규모 효율 측면에서는 최적이 아니다.

#### 전체 catalog read-back과 질문별 검색 목적이 결합돼 있다

Release 완전성 검증은 배포·활성화 시점의 control-plane 책임이고, 질문별 관련 자산 검색은 request-plane 책임이다. 하루 TTL이 비용을 완화하지만 만료·재시작 직후에는 전체 상세 read-back 비용이 발생한다.

#### 기본 lexical relevance가 단순하다

token 교집합 수는 설명 가능하고 결정적이지만 한국어 합성어, 오탈자, 동의어, 문맥이 다른 동일 단어를 충분히 처리하지 못한다. DataHub search의 field boost·usage·freshness·quality·tier 신호를 기본 ranking에 직접 사용하지 않는다.

#### Domain 권한 계약이 실질적으로 연결되지 않았다

Dataset은 `allowed_domains`를 지원하지만 인증된 `RequestContext`가 사용자 Domain 목록을 가지지 않는다. 따라서 문서상 Role 또는 Domain 정책과 실제 HTTP 실행 정책 사이에 간극이 있다.

#### 세밀한 데이터 권한은 별도 과제다

현재 중심은 Dataset·Metric Role과 PII 차단이다. 호텔 단위 row scope, column mask, purpose/time 제한 같은 정책을 DataHub entitlement만으로 완전하게 표현·집행한다고 볼 근거는 없다.

#### 성능과 검색 품질의 운영 증거가 없다

Dataset 수·Glossary 수, cold/warm p50·p95·p99, 검색 Top-K recall, 권한별 zero-result 비율, DataHub 호출 수에 대한 live 측정 자료가 없다. 따라서 “현재 규모에서 충분히 빠르다”는 결론도 아직 검증되지 않았다.

## 2.3 인터넷 조사 평가

### 2.3.1 공식 기능과 권장 검색 패턴

DataHub 공식 Search SDK 문서는 keyword query와 platform·environment·entity type·Domain·custom property filter를 결합해 후보 범위를 좁히는 방식을 대표 패턴으로 제시한다. 이는 질문마다 `query="*"`로 전체 catalog를 읽어 로컬에서 ranking하는 현재 request path와 다르다. [DataHub Search Client SDK](https://docs.datahub.com/docs/api/tutorials/sdk/search_client)

GraphQL Best Practices는 `search*` API를 얕은 pagination에 사용하고, 전체 결과처럼 깊게 순회할 때는 안정적 URN 정렬을 적용한 `scroll*` API를 사용하라고 안내한다. `search*`는 10,000건을 넘어 pagination할 수 없다. [DataHub GraphQL Best Practices](https://docs.datahub.com/docs/api/graphql/graphql-best-practices)

Self-hosted DataHub OSS는 Cloud와 같은 query-time Search Access Control을 제공하지 않는다. `VIEW_AUTHORIZATION_ENABLED=true`는 entity page gating 또는 post-search masking이며 query-time filtering과 같지 않다. 따라서 Answervice가 Backend에서 별도 entitlement를 적용하는 선택은 합리적이다. [DataHub Search Access Controls](https://docs.datahub.com/docs/features/feature-guides/search-access-controls)

### 2.3.2 가장 유사한 실제 사례: Pinterest PinCat·Analytics Agent

Pinterest의 사례가 현재 프로젝트와 가장 가깝다. Pinterest Engineering에 따르면 PinCat은 DataHub OSS 기반 내부 카탈로그이며, 자연어 질문에서 테이블·기존 쿼리·Metric·Join·Filter를 찾고 검증된 SQL을 Presto로 실행하는 Analytics Agent의 Context 원본이다.

Pinterest의 핵심 흐름은 다음과 같다.

```text
DataHub 기반 tier·owner·retention·glossary governance
→ 과거 SQL을 업무 의도로 변환한 embedding index
→ Join·Filter·Aggregation·사용 빈도 구조 신호 추출
→ semantic retrieval + governance-aware ranking
→ schema·Metric·Join context 조합
→ SQL 생성
→ Presto EXPLAIN 검증 후 제한된 실행
→ SQL·사용 Dataset·근거·경고 공개
```

Pinterest는 단순 table description RAG가 아니라 다음을 함께 사용한다.

- DataHub의 table tier, owner, glossary, freshness, documentation
- 실제 분석가가 사용한 query history
- 검증된 Join key와 Filter pattern
- semantic embedding과 구조·통계 ranking
- schema validation과 `EXPLAIN`-before-execute

Pinterest가 공개한 규모는 100,000개 이상의 분석 테이블과 2,500명 이상의 분석 사용자다. 이 규모에서 매 질문 전체 Dataset token scan이 아니라 OpenSearch 기반 vector/hybrid index와 governance-aware ranking을 사용한다. [Pinterest Engineering: Unified Context-Intent Embeddings for Scalable Text-to-SQL](https://medium.com/pinterest-engineering/unified-context-intent-embeddings-for-scalable-text-to-sql-793635e60aac)

DataHub가 작성한 고객 사례는 40만 테이블을 10만 개의 governed asset으로 정리하고, Analytics Agent가 2개월 내 분석가의 40%에 도달했다고 설명한다. 다만 이는 벤더 고객 사례이므로 성과 수치는 독립 검증값이 아니라 고객·벤더 공동 발표로 해석해야 한다. [DataHub Pinterest customer story](https://datahub.com/customer-stories/pinterest/)

#### Answervice와의 비교

| 항목 | Answervice | Pinterest |
|---|---|---|
| 사용자 입력 | 자연어 호텔 분석 질문 | 자연어 분석 질문 |
| Metadata 원본 | DataHub Dataset·Glossary·Metric·Join·권한 | DataHub/PinCat tier·schema·glossary·ownership |
| 검색 | 전체 승인 snapshot의 local lexical, 선택적 semantic | intent embedding + query history + 구조·통계 + governance ranking |
| 실행 엔진 | Trino | Presto |
| Join 근거 | 승인된 Join graph | query history에서 검증된 Join pattern과 schema |
| SQL 안전성 | SQLGlot AST·capability·typed parameter | schema validation·EXPLAIN·bounded LIMIT |
| 권한 | Dataset·Metric custom entitlement | 공개 자료는 governance ranking 중심이며 exact 실행 entitlement 세부는 불명확 |
| 학습 루프 | 승인 release 중심, query history retrieval 미사용 | 새 분석 query가 검색 지식에 누적 |

판정: 제품 방향은 매우 유사하지만 검색 retrieval 성숙도와 운영 규모는 Pinterest가 더 발전돼 있다. 반대로 Answervice는 공개된 Pinterest 설명보다 release checksum과 명시적 Dataset·Metric entitlement를 더 강하게 코드 계약으로 묶는다.

### 2.3.3 직접 비교 가능한 참조 구현: DataHub Analytics Agent

DataHub는 자연어 질문을 SQL과 chart로 바꾸는 오픈소스 Analytics Agent를 참조 구현으로 공개했다. 공식 문서의 우선순위는 다음과 같다.

```text
업무 문서 검색
→ 관련 Dataset 탐색
→ Schema·Owner·Tag·Classification 확인
→ Lineage 확인
→ Query history 확인
→ SQL 생성·실행
```

Answervice와 마찬가지로 DataHub를 Context 원본, Warehouse를 값 실행 원본, LLM을 생성기로 분리한다. 다만 이 프로젝트는 실사용 기업 사례가 아니라 DataHub가 제공하는 reference application이므로 운영 성과 비교에는 사용할 수 없다. [DataHub Analytics Agent 문서](https://docs.datahub.com/docs/features/feature-guides/analytics-agent), [DataHub Analytics Agent 소개](https://datahub.com/blog/datahub-analytics-agent/)

### 2.3.4 유사한 거버넌스·AI 기반 사례: Deutsche Telekom

Deutsche Telekom Digital Labs는 DataHub Core OSS를 중앙 카탈로그로 사용해 Nifi, Athena, Redshift, Tableau, Redash, Kafka, OpenSearch 등 여러 시스템의 metadata를 통합했다. Business Glossary, Domain, end-to-end lineage, PII 식별을 구성하고 DataHub metadata를 GenAI analytics platform의 LLM Context로 사용했다.

자연어 SQL 실행 세부는 공개되지 않았지만 “여러 source의 metadata + Glossary·Domain·Lineage + LLM Context”라는 점에서 Answervice와 유사하다. 사례는 신규 입사자의 onboarding을 주 단위에서 일 단위로 줄이고 incident resolution을 일 단위에서 분 단위로 줄였다고 설명하지만, 이 역시 DataHub 벤더 사이트의 고객 사례다. [Deutsche Telekom customer story](https://datahub.com/customer-stories/deutsche-telekom/)

### 2.3.5 Business Glossary 운영 사례: Trustpilot

Trustpilot은 DataHub Cloud에 AWS·GCP의 50만 개 이상 asset을 cataloging하고 568개 Business Metric·Dimension 정의를 Glossary로 관리한다고 공개했다. Business 사용자가 기술팀에 묻지 않고 Looker에서 trusted dashboard, 정의, owner, PII 정보를 확인하도록 운영한다.

이 사례는 자연어 Text-to-SQL보다는 “Glossary를 업무 의미의 권위 원본으로 만들고 Dataset·Dashboard에 연결한다”는 점에서 Answervice의 Metric governance 방향을 뒷받침한다. 동시에 DataHub 채택 성공이 검색 알고리즘만의 문제가 아니라 ownership·curation·사용자 workflow에 달려 있음을 보여준다. [Trustpilot customer story](https://datahub.com/customer-stories/trustpilot/)

## 2.4 LLM 평가와 인터넷 조사 결과 비교

| 평가 주제 | LLM 코드 기반 평가 | 인터넷·실사용 사례 평가 | 종합 판정 |
|---|---|---|---|
| DataHub의 역할 | 실행 전 권위 Context 원본으로 쓰는 방향이 강점 | Pinterest·Analytics Agent도 DataHub를 agent context layer로 사용 | 방향 일치 |
| Glossary·Metric | 승인 Term을 SQL Context와 연결한 점이 강점 | Pinterest·Trustpilot은 Glossary를 업무 의미의 원본으로 운영 | 방향 일치 |
| 검색 retrieval | 전체 local token scan은 소규모에 적합, 확장성 미검증 | 공식 패턴은 query+filter, Pinterest는 hybrid index와 usage/governance ranking | 개선 필요 |
| 전체 catalog 검증 | release 무결성에는 유용하나 request path와 결합 | 공식 문서는 deep scan에 scroll 사용, 실제 agent는 관련 후보를 검색 | control/request plane 분리 권장 |
| 권한 | Dataset·Join·Metric fail-closed는 강점, Domain Context는 미연결 | OSS는 query-time search ACL이 없어 앱 보완 필요 | Backend entitlement 유지 필요 |
| Join·SQL 안전성 | 승인 graph와 SQLGlot 정책으로 강하게 제한 | Pinterest는 검증된 query pattern·schema·EXPLAIN 사용 | 서로 보완 가능한 방향 |
| 검색 품질 신호 | lexical overlap 중심 | tier·freshness·documentation·usage·query history 활용 | 신호 확장 필요 |
| 운영 채택 | 기술 계약은 강하지만 live 사용성 증거 미확인 | 실제 사례는 ownership·curation·workflow 정착을 핵심 성과로 제시 | UI·운영 프로세스 검증 필요 |

두 평가의 핵심 결론은 일치한다.

> DataHub를 거버넌스와 LLM Context의 권위 원본으로 사용하는 방향은 타당하다. 다만 질문별 검색은 전체 catalog 순회보다 권한·Domain scope, query/filter, semantic·usage·quality 신호를 활용한 bounded retrieval로 발전시키는 것이 일반적이고 확장 가능하다.

## 2.5 객관적 최종 등급

현재 상태는 다음과 같이 분류하는 것이 적절하다.

| 관점 | 판정 | 이유 |
|---|---|---|
| 제품 방향 | 적합 | 실제 유사 사례도 DataHub를 자연어 분석 agent의 Context layer로 사용 |
| 거버넌스 안전성 | 양호 | 승인·release·checksum·schema·entitlement를 fail-closed로 연결 |
| 권한 관리 | 양호하나 불완전 | Join·Metric까지 강화됐지만 Domain·row/column scope가 완결되지 않음 |
| 검색 정확성 | 보통 | 설명 가능한 lexical baseline이나 의미·usage·quality ranking 부족 |
| 검색 확장성 | 미검증/개선 필요 | 하루 cache는 있으나 전체 hydration·전체 local scan 구조 유지 |
| 운영 성숙도 | 검증 필요 | live latency·recall·권한 E2E·사용자 채택 데이터 없음 |

## 2.6 개선 우선순위

### 1순위: 측정 가능한 기준선 확보

구조를 바꾸기 전에 다음을 실제 운영 후보 환경에서 측정해야 한다.

- Dataset·Glossary Term·Owner·Domain 수
- cold/warm DataHub HTTP 호출 수와 p50·p95·p99
- 질문별 검색 후보 수와 Top-K recall
- 한국어 동의어·띄어쓰기·오탈자·모호어 정확도
- Role별 권한 차단·zero-result 비율
- Context 생성 및 전체 분석 p50·p95·p99

### 2순위: control plane과 request plane 분리

```text
Control plane
DataHub 전체 read-back → release 검증 → immutable snapshot/index 활성화

Request plane
인증·권한 scope → bounded retrieval → 후보 상세 검증 → Join 확장 재검증
```

전체 release 검증에는 stable URN sort의 `scrollAcrossEntities` 또는 versioned manifest membership을 사용하고, 질문 경로에서는 이미 검증된 active release만 조회하는 구성이 적절하다.

### 3순위: scope-first 검색

사용자의 canonical Role과 조직 Domain을 서버가 확정해 Request Context에 넣고 다음 필터를 검색 전에 적용한다.

- active release
- Dataset entity type
- production/serving scope
- allowed Domain·Role
- approved lifecycle

Self-hosted OSS에서는 DataHub query-time ACL을 전제로 하지 말고 Backend 또는 검증된 local index에서 동일 정책을 집행해야 한다.

### 4순위: 검색 신호 확장

Pinterest 사례를 그대로 복제할 필요는 없지만 다음 신호를 단계적으로 비교할 가치가 있다.

- 현재 Unicode lexical baseline
- DataHub query/filter Top-K
- semantic embedding
- approved tier·freshness·documentation completeness
- 사용 빈도와 성공한 query history
- 승인된 Join·Filter pattern

새 retrieval은 held-out 질문 세트와 권한 회귀 테스트에서 기존 구조보다 recall·latency가 개선되고 정보 누출이 없을 때만 전환한다.

### 5순위: 권한 모델 완결

- 사용자 Domain을 인증 저장소에서 서버 소유 값으로 제공
- Role/Domain 정책이 OR인지 AND인지 제품 계약으로 확정
- 호텔·법인 단위 row scope와 column masking 필요성 결정
- `entitlement_hash`에 실제 권한 snapshot을 반영
- DataHub 권한 변경 시 하루 cache 무효화 또는 release 전환 절차 명확화

# 3. 결론

## 3.1 LLM 생성 평가 결론

현재 구현은 DataHub를 단순 검색 UI가 아니라 승인된 업무 의미·schema·Join·권한의 실행 계약으로 사용한다. Release checksum, native governance, Join 확장 entitlement, Metric Role·PII 정책, Trino schema를 fail-closed로 묶은 점은 강하다.

반면 검색은 전체 승인 Dataset에 대해 token/semantic 관련도를 계산한 뒤 권한을 적용한다. 하루 snapshot cache로 반복 I/O는 줄었지만 전체 catalog 검증과 질문별 retrieval이 완전히 분리되지 않았고, lexical relevance와 실제 운영 성능은 검증되지 않았다.

따라서 LLM의 독립 평가는 다음과 같다.

> **안전한 소규모 runtime catalog로는 합리적이지만, 검색 품질과 확장성은 아직 운영 증거가 부족한 과도기형 구조다.**

## 3.2 인터넷 조사 평가 결론

실제 사례는 DataHub를 AI 분석의 Context layer로 사용하는 방향을 강하게 지지한다.

- Pinterest는 DataHub OSS를 governance 원본으로 사용하고 자연어 질문을 SQL로 연결한다.
- DataHub Analytics Agent도 업무 문서→Dataset→Schema→Lineage→Query history→SQL 순서를 채택한다.
- Deutsche Telekom은 Glossary·Domain·Lineage·PII metadata를 GenAI analytics Context로 사용한다.
- Trustpilot은 Glossary와 trusted asset 표시를 business self-service의 핵심으로 사용한다.

그러나 확장된 실사용 사례는 전체 catalog의 단순 lexical scan보다 query/filter, semantic index, query history, tier, freshness, usage, documentation quality를 결합한다. 따라서 현재 Answervice의 제품 방향은 유사하지만 retrieval 구현은 더 단순하다.

## 3.3 두 평가를 비교한 최종 결론

LLM 평가와 인터넷 조사 결과는 다음 결론에서 일치한다.

> **Answervice가 DataHub를 승인된 Context와 거버넌스의 원본으로 사용하는 방식은 객관적으로 타당하며 실제 유사 사례와도 일치한다. 다만 매 질문의 검색은 전체 승인 catalog ranking 후 권한 필터 방식이므로, 장기적으로는 release 전체 검증을 control plane으로 분리하고 권한·Domain scope가 적용된 bounded hybrid retrieval로 전환하는 것이 더 일반적이고 확장 가능하다.**

지금 즉시 현재 구조를 폐기할 근거는 없다. 우선 실제 catalog 규모, cold/warm latency, Top-K recall, 권한 회귀를 측정해야 한다. 측정 결과가 기준을 넘을 때 Pinterest와 같은 governance-aware hybrid retrieval을 단계적으로 도입하는 것이 과잉 설계를 피하면서도 실사용 사례의 장점을 반영하는 방법이다.
