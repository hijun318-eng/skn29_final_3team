### 목표

Answervice의 P0를 “화면이 뜨는 데모”가 아니라 **승인된 호텔 운영 데이터를 실제로 조회하고, DataHub 중심 의미 계약과 현재 사용자 권한을 매 분석마다 검증하며, 같은 대화의 제한된 후속 질문·표현 변경·보고서 조합을 재현 가능하게 처리하는 서비스 Vertical Slice**로 완성하라.

완료 상태에서는 다음 두 원칙이 동시에 성립해야 한다.

1. **원자적 single-turn Analysis Run:** Turn-level understanding preflight가 완전한 typed request를 하나로 확정한 `ANALYSIS`만 새 Run을 만들고 immutable 입력·권한·release evidence를 고정한 뒤 현재 권한·DataHub/Rule Context·APP-G1·G2·Trino·G3를 통과한다. terminal Run은 덮어쓰지 않는다. 모호·범위 밖·unsupported Turn은 terminal Turn만 있고 Run·query는 0건이다.
2. **bounded multi-turn Conversation:** 같은 Conversation에서는 서버가 검증한 조건·변경분·상대기간 기준·현재 초점 Artifact/View·Report Draft만 구조적으로 이어간다. raw transcript 전체, 숨은 LLM memory, 과거 permission snapshot·policy filter·SQL을 현재 실행 근거로 사용하지 않는다.

### 현재 기준선

- Frontend→FastAPI→model adapter→DataHub/Trino→App PostgreSQL의 실제 분석 코드 경로는 존재한다.
- 현재 Agent UI와 `/analysis` 계약은 사실상 single-turn이다. DB의 Conversation과 nullable `conversation_id`는 골격이며 runtime Turn 이력·head·소유권에 연결되지 않았다.
- 현재 runtime 기본 경로는 기존 데이터 계약을 사용한다. 후보 SQL 릴리스는 DB runtime `NOT_RUN`, App cutover `NO-GO`다.
- 후보 SQL에는 정적 blocker가 있다. 연회 CANCELLED 이력 생성과 validator 기대가 모순되고 POS·Facility 후보 schema의 Trino/DataHub read-only grant가 빠져 있다.
- 현재 배포 runtime에는 미리 알려진 Metric Term의 exact lookup과 선택된 Asset URN·schema 검증 경로가 있다. working tree에는 `인식 객실 매출` Term의 DataHub `sourceRef`·Glossary version·checksum을 배포 계약의 pin과 비교해 불일치 시 query 전에 fail-closed 하는 Slice가 구현됐고, 단위·통합 test와 로컬 DataHub read-only 호출을 통과했다. 실행 중인 Backend image 재빌드와 제품 E2E는 하지 않았으므로 배포 반영 증거는 아니다. 이 경로도 선택 후 사후 확인이며 DataHub-first Glossary authority 완료 증거가 아니다.
- Metric·Asset 후보 집합·ranking·publish 원본은 로컬 계약·JSON 중심이다. DataHub 승인 Term discovery, Term→Dataset/Column 관계·역조회, Domain·Owner·승인 검증, relation checksum, cache environment·synced_at·expires_at과 통합 release consistency fail-closed는 완료되지 않았다.
- 계산·filter·join·time·identity·permission의 Rule·Binding·policy 계약은 부분 구현 상태다. Term URN·Glossary version과 결합된 immutable `semantic_release_id`의 전체 read-back과 runtime enforcement는 완료되지 않았다.
- 현재 발화 처리는 공백 정리·alias substring 중심이며 v2 prompt/eval은 candidate·NOT_RUN이다. 오탈자·축약·unsupported intent를 안전하게 처리한다고 검증되지 않았다.
- `객실 매출` 모호성은 현재 두 후보명으로 차단되지만 정의·단위·시간 귀속 차이를 구조화해 API/UI에 보여 주는 clarification option은 구현되지 않았다.
- 분석·보고서 인증 Context는 client `X-As-Of`를 더 이상 입력으로 받지 않고 Backend KST 날짜를 사용하며 Frontend 공통 header에서도 제거됐다. 다만 Conversation 생성 시 immutable `wall_clock_anchor` 저장, 상대기간 resolver와 GD-03 no-Run 차단은 구현 전이다.
- Report 엔진은 여러 block과 Artifact 문서를 지원하지만 대화에서 선택한 여러 Artifact/View를 같은 Draft에 누적하는 orchestration이 없다.
- unit·fake-adapter 통합 test, readiness, screenshot, 과거 Artifact는 release E2E 완료 증거가 아니다.

이 기준선은 작업 시작 시 repository·runtime을 다시 읽어 확인하라. 달라진 사실은 근거와 함께 갱신하되, 확인하지 않은 내용을 완료로 올리지 마라.

### 권한과 금지사항

- 원본 SQL ZIP은 불변 보존한다. 목록·텍스트 정적 검토와 checksum 계산은 허용되지만 원본을 덮어쓰지 않는다.
- SQL 수정본 생성, DB 적재·validator 실행, DataHub publish, 외부 모델 유료 호출, 기본 release pointer 변경, cutover, 삭제, commit·push는 각각 사용자의 명시적 권한 범위 안에서만 수행한다.
- 기존 dirty worktree와 사용자 변경을 보존하고 관련 없는 파일을 정리하지 않는다.
- mock, fake adapter, 고정 응답, cached 과거 결과, Frontend 계산으로 실제 서비스 완료를 가장하지 않는다.
- 테스트하지 않은 항목을 `VERIFIED`, `통과`, `완료`로 쓰지 않는다. `NOT_STARTED`, `PARTIAL`, `READY_TO_VERIFY`, `VERIFIED`, `BLOCKED`를 근거와 함께 사용한다.
- 후보 검증이 끝나기 전에는 현재 승인 경로를 기본값으로 유지한다. 서로 다른 data·semantic·policy·prompt/model release를 한 실행에 섞지 않는다.
- 문제를 숨기기 위해 Gate를 완화하거나 fail-open으로 바꾸지 않는다. blocker를 고친 새 후보 checksum으로 처음부터 재검증한다.

### P0 범위

#### 데이터·의미·실행

- 원본 보존, 수정된 derived data release, 격리 적재, DATA-G0~G7, clean replay, Serving reconciliation oracle
- DataHub의 공식 Metric Term·별칭·정의·단위·Domain·Owner·승인·Term→Dataset/Column 관계
- Rule Layer의 계산·filter·join·time·identity·permission 계약과 Term URN/version/checksum 결합
- 검증 전 immutable `product_release_id`가 code/image, data, semantic, rule/binding/policy, cache, prompt/model, migration과 사전 봉인 Gold manifest를 고정
- 검증 뒤 append-only `evidence_bundle_id`가 해당 product ID의 Golden·security·failure·rollback receipt를 참조하며, evidence를 product ID checksum에 되넣지 않음
- 실제 auth browser→HTTP→Backend→DataHub/Trino→App DB Artifact와 query ID가 연결되는 L3/L4 E2E

#### bounded multi-turn

- 기술 로그인 `session`과 분석 `conversation` 분리
- Conversation owner, 선형 head, 고정 `product_release_id`, Backend-owned `wall_clock_anchor`, timezone, 상태·보관. `ARCHIVED`는 read-only이고 P0 unarchive 없음
- 실행 중에는 idempotent command/request, active lease와 resolved `ANALYSIS`의 Run 생성·상태, attempt·heartbeat·외부 query 제출 증거만 상태 전이한다. immutable Turn, head, focus, ViewSpec, Draft block/revision 같은 사용자 가시 domain mutation은 terminal commit 전까지 만들거나 바꾸지 않는다. 완료 시 Run terminal 상태·결과 Artifact 또는 ViewSpec/focus·Draft mutation, command terminal화, immutable terminal Turn, head 전진, lease 해제를 한 App DB transaction으로 한 번만 commit하고 UI는 실행 중 command/request와 선택적 Run에 재연결한다.
- immutable Turn: `turn_id`, `conversation_id`, 선형 부모 `reply_to_turn_id`, ordered `source_turn_ids`(최대 2), 선택적 `clarifies_turn_id`, `turn_kind`, owner UI용 암호화 원문 참조와 audit용 redacted utterance, 완전한 resolved request, inherited/changed field source, 결과 참조, `turn_status/reason`
- Turn type은 `ANALYSIS`, `PRESENTATION`, `REPORT_ACTION`으로 제한하고 명확화는 원 type의 `BLOCKED + NEEDS_CLARIFICATION` 결과로 표현
- 상대기간은 Backend KST clock의 `WALL_CLOCK`(`이번 달/지난·저번 달`)과 `SOURCE_PERIOD`(`그 전 달/다음 달`)를 분리한다. client clock override를 production에서 거부하고 wall clock 변경은 새 Conversation만 허용
- `data_available_from/through` watermark는 wall clock과 별도이며 가용 최신월을 상대기간 기준으로 대신 쓰지 않음
- 명시 참조는 최대 두 과거 Analysis Turn, 임의 branch·merge 없음
- session 인증과 Conversation/object authorization을 먼저 수행한 뒤 idempotency lookup을 expected-head CAS보다 먼저 수행한다. same key/same canonical hash는 head가 전진했어도 현재 권한으로 직렬화한 기존 command/Turn을 반환하고, same key/different hash는 `409 IDEMPOTENCY_CONFLICT`다. 새 key만 head CAS와 active lease를 검사·예약하며 stale head와 busy를 각각 `409 CONVERSATION_CONFLICT`, `409 CONVERSATION_BUSY`로 처리한다.
- user slot patch는 필드별 `INHERIT/SET/REMOVE`와 source Turn provenance를 저장한다. filter 중에는 `USER_REQUESTED_FILTER`만 상속·설정·삭제할 수 있고, `POLICY_REQUIRED_FILTER`와 permission constraint는 상속·삭제하지 않고 매 resolved Analysis Run의 현재 entitlement/Rule에서 재생성한다.
- 같은 owner·Conversation·release의 `SUCCEEDED Analysis + APP-G3 Safe Artifact`만 data focus와 승인 기본 View focus를 갱신한다. 성공 `PRESENTATION`은 data focus를 유지하고 current View와 ordered visible views만 갱신한다. Report Action과 PARTIAL/BLOCKED/FAILED/CANCELLED는 두 focus를 모두 보존한다.

#### 발화 다양성

- “어떻게 말하든”을 무제한 성공으로 주장하지 말고 P0 지원 intent의 paraphrase robustness로 계약화
- 결정론적 normalizer는 Unicode·공백·명확한 날짜 형식·DataHub 승인 exact alias처럼 의미가 보존되는 변환만 수행한다. 자유 문장 이해나 임의 오탈자 교정은 맡기지 않는다.
- GPT/Node 1 candidate parser는 존댓말/반말, 조사·어순·축약, 경미한 한 글자 오탈자, 한국어/영어 혼용, `지난달/전월`과 후속 지시어 변형을 typed candidate로 만들 뿐 공식 Metric·권한·실행을 확정하지 않는다.
- 결정론적 resolver는 metadata visibility가 적용된 DataHub Term·Rule·Conversation slot·source Turn·Artifact schema·권한으로 후보 하나만 확정하고, 유일하지 않으면 실행하지 않고 가장 작은 clarification을 만든다.
- Metric·기간·filter·grain을 바꿀 수 있는 교정 또는 후보가 둘 이상이면 가장 작은 확인 질문; 지원 밖·권한 우회·prompt injection은 자동 보정 금지
- 숫자·날짜·단위·부정·비교 방향·`이상/초과`·호텔/등급·대체/추가 token은 normalization에서 보존하고 바뀌면 contrast 또는 clarification으로 판정
- 매 응답에 이해한 Metric·절대 기간·filter·dimension·grain·동작 chip을 표시하고 수정은 새 immutable Turn으로 처리
- Golden utterance별 equivalence/contrast manifest를 학습·prompt와 격리한다. equivalence는 같은 resolved request hash **또는 같은 expected clarification**으로, contrast는 다른 hash 또는 명확화로 판정한다. calibration 뒤 held-out 공개 전에 표본·metric·threshold·반복 횟수·승인자와 manifest checksum을 봉인하고 routing·clarification·silent wrong-execution을 측정한다.
- CheckList식 `MFT`(명확한 최소 기능), `INV`(같은 의미 변형), `DIR`(critical token에 따른 방향 변화), `NEG`(실행 금지)를 별도 test family로 봉인한다. critical·negative·Golden 집합은 전건 통과하고 `unsafe_silent_execution_rate=0`이어야 한다.
- BFCL에서 가져온 방식대로 매 Turn의 backend state(owner·release·head·focus·resolved slot/provenance·View·Draft revision)와 실행 path(route·reason·source Turn·model/Run/query/View/block 수)를 함께 채점한다. 답변 문장이 맞아 보여도 상태나 경로가 틀리면 실패다.
- KLUE DST에서 가져온 `joint_slot_exact_match`로 Metric·period·dimension·user filter·grain·action 전체 상태를 평가한다. Answervice 실제 사용 분포의 task-specific held-out을 쓰며 공개 benchmark 점수는 P0 Gate가 아니다.
- 공개 leaderboard 점수는 P0 Gate가 아니다.

#### 표현·보고서

- 각 응답은 1~2문장 결론, 핵심 수치 최대 3개, 작은 표/차트 카드, 조건 chip, 상세·근거 펼치기로 구성
- 동일 Artifact에 필요한 grain·column이 있으면 그래프·다른 그래프·표 전환은 새 query 없이 immutable `ViewSpec`만 생성
- 필요한 grain·column이 없으면 값을 임의 생성하지 말고 확인 후 새 `ANALYSIS` Turn으로 전환
- “표로”는 현재 표현 대체, “표로도”는 추가 의도를 구분
- 사용자가 선택한 `artifact_id + view_spec_id + analysis_definition_id`를 보고서 바구니와 Draft block에 누적
- Draft append는 `expected_draft_revision` CAS+idempotency hash로 block·order·revision을 한 transaction으로 commit
- 승인 Version은 stable block ID/order/`is_required`/criticality policy, layout/static text, Definition·parameter schema·period mode·ViewSpec, product/semantic release를 checksum으로 고정한다. 수정·release·criticality 변경은 새 Version과 재승인을 요구한다.
- Report Run의 `actor`는 `report_admin`, 각 block의 `effective_subject`는 Analysis Definition 원 소유자, Trino 접속 `service_identity`는 인증된 App query principal이다. 관리자 권한으로 subject 권한을 확대하지 않고 세 신원과 policy version을 감사한다.
- Report Run은 승인 Version의 고정 product/semantic release만 사용하고 active pointer를 다시 읽지 않는다. 고정 release가 실행 불가하면 Report Run·Turn 생성 전 `409 RESOURCE_CONFLICT`다. 하나의 `report_as_of`를 idempotency hash에 포함하고 subject별 현재 권한을 한 `report_permission_snapshot_id`로 고정해 모든 child Run이 참조한다.
- 각 data block은 새 child Analysis Run·Trino query·`result_artifact_id`를 만들고 APP-G1~G3를 다시 통과한다. 저장 ViewSpec이 새 Artifact와 호환되지 않으면 `VIEW_SCHEMA_INCOMPATIBLE`로 실패하며 source Artifact·screenshot·과거 query로 대체하지 않는다.

#### 실행 단위 현실화

이 목표는 5개 Source DB·data/semantic cutover·대화·보고서·보안·복구를 포함한 **장기 P0 release program**이다. 한 번의 큰 코드 변경이나 한 세션에서 끝내려 하지 않는다. 각 구현 반복은 하나의 requirement/Gate slice만 닫고, 부분 통과를 P0 완료로 표현하지 않는다.

첫 **release candidate 제품 slice**는 다음으로 제한한다. 아래 항목 전체를 한 번의 코드 변경으로 구현하라는 뜻이 아니다.

- P0 후보 Metric `인식 객실 매출`(`recognized_room_revenue`) 하나, 2025년 7·8월, 전체 호텔, 승인 day grain. DataHub Domain·Owner·승인·관계 read-back 전에는 최종 승인 Metric이라고 부르지 않는다.
- GD-01의 절대 월→`그 전 달`→비교와 GD-02의 `line→bar→table→두 Report block`
- `analyst` 분석과 소유 객체, `report_admin` 승인/수동 실행 경계
- GD-03 범위 초과, 모호성, 타 사용자 객체, 권한 회수, stale head/idempotency negative

다른 Metric·질문·표현을 먼저 넓히지 않는다. 다만 이 작은 제품 slice를 이유로 전체 data release 정합성, 최소권한, DataHub authority, rollback·failure Gate를 생략하지 않는다.

개발 착수의 첫 독립 requirement slice인 production 분석 기준일의 서버 소유 경계는 구현됐다. `/analysis`와 같은 인증 Context가 일반 사용자의 `X-As-Of`를 실행 근거로 사용하지 않고 Backend KST 날짜를 사용하며, Frontend 공통 요청도 해당 헤더를 보내지 않는다. server-owned Conversation anchor 저장·상대기간 resolver·GD-03 전체는 후속 slice이므로 `CONV-004`는 `PARTIAL`이고 Golden Dialogue는 미완료다.

Glossary의 첫 독립 Slice는 working tree에 구현됐다. 로컬 release snapshot 자체의 hash를 먼저 검증한 뒤, 배포 계약이 고정한 `sourceRef`·Glossary version·checksum뿐 아니라 DataHub가 반환한 실제 이름·별칭·정의·단위를 snapshot과 비교한다. 불일치 시 model·Trino 호출 전에 `CONTEXT_SOURCE_FAILED`로 닫고 사용한 checksum은 Context package hash에 포함한다. 실행 중인 Backend image와 release E2E에는 아직 반영하지 않았다. 또한 Term discovery, Domain·Owner·승인, Term→Dataset/Column 관계, cache TTL, immutable semantic release 전체와 UI 근거 표시는 구현한 것이 아니므로 `P0-GLOSSARY`와 `GOV-001~009`는 완료가 아니다.

### P0 제외 범위

- Conversation을 넘는 장기 사용자 기억·성향 추론·vector memory
- raw transcript 전체 재주입, 자율 계획, 임의 tool 사용, branch·merge 대화
- 범용 호텔 질문, 승인되지 않은 Metric·join·chart·grain 자동 생성
- 자동 인과 설명과 여러 Artifact를 근거 없이 합친 경영진 서사
- 예약 실행 worker, Microservice 분해, Kubernetes, 신규 queue, 범용 Agent framework
- Waii API·Waii의 별도 Semantic Layer, Ask DataHub Cloud/Plugin, DataHub Analytics Agent를 P0 runtime dependency로 도입하지 않는다. DataHub-first 조회, SQL 후보와 실행 분리, Artifact 기반 표현 재사용 원칙만 기존 모듈에 적용한다.
- 사용자가 선택하지 않은 결과의 자동 보고서 수록

P0 범위를 추가할 때는 무엇을 제거하거나 후순위로 미루는지 먼저 제시하라. bounded multi-turn을 P0에 넣었다는 이유로 보안·data cutover·DataHub authority·실제 E2E Gate를 축소하지 마라.

### 작업 순서

#### 0. 사전 등록과 기준선 고정

1. repository root, branch, commit, dirty worktree, runtime release, DB migration head와 현재 health/readiness를 읽기 전용으로 기록한다. dirty worktree를 포함한 후보를 재현해야 하면 clean commit 또는 immutable source-tree/diff checksum을 별도로 고정한다.
2. 원본 ZIP checksum, 후보 SQL 정적 결함, 현재 로컬 JSON/DataHub 역할, 현재 single-turn 계약을 evidence index에 고정한다.
3. 구현 전에는 Golden Dialogue·negative dialogue의 input, expected Turn routing, slot·기간 의미, Turn/Run/query/Artifact/View/Report block exact count와 실패 동작을 사전 등록한다. Metric Term ID·oracle SQL·Gold 값·수치 허용오차·최종 held-out checksum은 DATA-001~004와 GOV-001~008 candidate readiness 및 read-back 뒤, prompt 조정·canary 전에 봉인한다.
4. 각 case에 `case_id`, `MFT/INV/DIR/NEG`, redacted utterance, prior state, expected route·joint slots·clarification·backend state·Run/query/View/block count를 넣은 task-specific manifest를 봉인한다. 같은 intent 변형과 contrast를 분리하고 silent Metric·기간·filter·grain substitution을 실패로 판정한다.
5. train/prompt-example/calibration/held-out/release split과 checksum을 분리한다. held-out을 prompt 선택에 재사용하지 않고 critical·negative·Golden 전건 통과 및 `unsafe_silent_execution_rate=0`을 release threshold로 고정한다. 공개 leaderboard 점수는 threshold가 아니다.
6. 외부 변경·비용·쓰기 승인을 data, metadata, model, cutover별로 분리한다.

#### 1. 후보 데이터의 실행 가능성 증명

1. 쓰기 전에 DBMS/container image, timezone·collation·SQL mode, disk/memory/time 예산, checkpoint·중간 실패·재시작 정책과 각 Gate의 입력 파일·명령·oracle·violation 판정·non-zero 종료·receipt 경로·reviewer를 release manifest에 고정한다. ZIP에 실행 계약이 없는 DATA-G4 분포 checklist/허용 범위와 DATA-G5 canonical sort/serialization/hash 계약을 먼저 정의한다.
2. 원본은 보존하고 연회 status history·validator 모순, read-only grant와 그 밖의 정적 blocker를 수정한 derived release를 별도 ID/checksum으로 만든다.
3. 새 namespace·깨끗한 volume에서 DBMS별 순서로 적재하고 다음 DATA-G0~G7을 순서대로 통과한다.

| Gate | 필수 판정 |
|---|---|
| `DATA-G0` 사전점검 | 후보 namespace 충돌 0, 다섯 Source와 Trino preflight 경계·provenance·자원 확인 |
| `DATA-G1` DDL 컴파일 | 엔진별 문법 오류 0, data dictionary·constraint/index·Trino schema 계약 성공 |
| `DATA-G2` seed 생성 | table별 계약 row count 일치, runner 실패 시 non-zero 종료 |
| `DATA-G3` 키·금액 무결성 | 모든 validator violation 0, 알려진 Banquet 모순 해소 |
| `DATA-G4` 분포 현실성 | 호텔·월·요일·이벤트 분포를 봉인된 checklist/범위로 지정 reviewer가 승인 |
| `DATA-G5` clean replay | 같은 seed의 row count와 canonical 정렬 hash 일치 |
| `DATA-G6` Trino 통합 | 모든 승인 Serving view의 값·grain·fan-out·중복·null·row/hash가 독립 reconciliation oracle과 일치 |
| `DATA-G7` 보안 | TLS·인증된 service identity·Source read-only 최소권한, setup/admin principal 위장·write 0건 |

4. 동일 seed clean replay의 row/hash와 수행 시간을 비교한다.
5. Trino의 모든 승인 Serving view에 대해 read-only positive/negative 권한을 실제 principal로 증명한다. 제품 Gold와 Serving reconciliation oracle을 섞지 않는다.

#### 2. DataHub 중심 의미 릴리스

1. 공식 Metric Term·별칭·정의·단위·Domain·Owner·승인 상태와 Term→Dataset/Column 관계를 release별 후보 영역에 게시한다.
2. Rule·Binding·policy checksum을 Term URN과 묶는다.
3. publisher가 Term 발견과 Term→Dataset/Column 관계 역조회를 포함한 전체 후보를 API로 read-back하고 expected environment/version/checksum을 확인하기 전에는 runtime에 노출하지 않는다.
4. local JSON은 bootstrap/test 또는 version·checksum·synced_at·expires_at을 가진 검증 cache로만 제한한다. 불일치·만료·관계 단절·schema drift는 `METADATA_UNAVAILABLE`로 차단한다.

#### 3. 하나의 제품 릴리스 연결

1. release registry 전체 asset 수와 요청당 Context asset 상한을 분리한다.
2. candidate data·Serving·DataHub URN·Rule·Binding·prompt/model·API fixture·Gold를 하나의 `product_release_id`로 연결한다.
3. 현재 승인 경로를 기본으로 유지하고 명시적 후보 ID를 쓰는 App canary를 만든다.

#### 4. Conversation·Turn Backend Vertical Slice

1. 기존 Conversation DB 골격을 migration·repository·service·API에 연결한다.
2. session 인증과 Conversation/object authorization 뒤 idempotency lookup을 수행하고, 새 key에만 head CAS와 active lease를 적용하는 command/request를 구현한다. 기존 응답도 현재 권한으로 다시 직렬화한다. 완료 시 ViewSpec/focus 또는 Draft block/revision, command terminal화, terminal Turn, head 전진, lease 해제를 같은 transaction으로 한 번 commit한다. 실행 중 UI는 command에 재연결하고 archived Conversation mutation은 막는다.
3. Turn-level understanding preflight는 Run의 field/row 실행 권한과 분리된 coarse/object/metadata visibility를 candidate 생성 **전에** 적용한다. 이 단계에서는 현재 principal에게 보이는 DataHub 승인 Term·alias와 data watermark만 발견하고, 권한 없는 Term·Asset 이름·정의는 후보·응답·일반 log에 노출하지 않는다. 보이는 표현 candidate와 승인 Term만 unique-resolution하고 모호·범위 밖·unsupported는 Run 없이 terminal Turn으로 끝낸다.
4. resolved `ANALYSIS`만 기존 원자적 pipeline을 새 Run으로 호출하고 이때 현재 entitlement의 별도 field/row execution permission snapshot을 만든다. Run 안에서는 exact Term·Dataset/Column·Rule·schema·삭제 상태·release checksum을 다시 읽어 고정한 뒤 APP-G1을 수행한다. 사용자 slot은 `INHERIT/SET/REMOVE` provenance를 저장하되 `USER_REQUESTED_FILTER`만 상속하고 정책 필터·permission constraint는 현재 Rule/entitlement에서 새로 만든다.
5. `PRESENTATION`은 compatibility validator와 ViewSpec persistence만, `REPORT_ACTION`은 revision CAS를 가진 Draft append만 호출한다. 봉인된 표현 전환은 model·Trino 호출 0건이다.
6. clarification은 문자열 결합이 아니라 `clarifies_turn_id`를 가진 새 Turn이며 차단 Turn을 수정하지 않는다.
7. 성공 Analysis는 data focus와 승인 기본 View focus를 함께 갱신하고, 성공 Presentation은 View focus와 ordered visible views만 갱신한다. Report Action·비성공 Turn은 focus를 보존하며 source Turn의 owner·Conversation·release·선행 `SUCCEEDED Analysis + Safe Artifact` eligibility를 서버가 검사한다.

#### 5. Frontend·보고서 Vertical Slice

1. 단일 `run` 렌더링을 서버 기반 Turn timeline으로 바꾸고 새로고침 복원을 구현한다.
2. 상속·변경 조건, 절대 기간, Turn 상태, 짧은 결론·핵심 수치·View, 상세·근거를 progressive disclosure로 표시한다.
3. 현재 Artifact/View anchor와 차트 compatibility를 서버 응답으로 표시한다.
4. 보고서 바구니를 서버에 저장하고 `expected_draft_revision`+append hash로 여러 Turn의 Artifact/View를 원자 append한다. 승인 Version은 stable block ID/order/`is_required`/criticality policy, layout/static text, ViewSpec, Definition·parameter schema·period mode와 product/semantic release를 봉인한다. 수정은 새 Version·재승인이다.
5. 수동 실행은 `report_admin` actor, Definition 원 소유자 effective subject, 인증된 App query service identity를 분리 감사한다. 승인 Version의 고정 release가 실행 불가하면 Report Run·Turn 생성 전 `409 RESOURCE_CONFLICT`이고 active pointer를 다시 읽지 않는다.
6. `report_as_of`를 idempotency hash에 포함하고 subject별 하나의 현재 `report_permission_snapshot_id`를 모든 child Run이 참조하게 한다. 각 data block은 새 child Analysis Run·query·result Artifact를 생성하며 source/result Artifact와 View compatibility 실패를 구분한다.
7. OpenAPI에서 Frontend 타입을 생성·검증하거나 동등한 schema conformance Gate를 추가하고 기본 script가 모든 Frontend test를 실행하게 한다.

#### 6. 보안·실패·관측

1. 매 Turn conversation/turn/artifact/report object authorization과 field/row 정책을 재검사한다.
2. 인증된 Trino service identity, TLS/transport, credential rotation·폐기, impersonation negative test를 인수 환경에서 증명한다.
3. prompt injection 가능한 질문·Glossary·schema·result 문자열을 비신뢰 데이터로 다룬다.
4. conversation/turn/run/artifact/view/report/query ID와 routing·field source·permission·release checksum을 같은 trace/evidence에 연결한다.
5. Turn routing 오류, 잘못된 상속, clarification, 불필요한 model/Trino 호출, stale head, latency·scan budget을 측정한다.
6. 각 command/Run의 lease·heartbeat·attempt와 외부 query 제출 상태를 먼저 저장하고 Trino client tag에 `request_id/run_id/attempt`를 넣는다. 시작 시와 주기적으로 실행하는 reconciler는 `query_id`가 없어도 service principal query listing+tag로 고아 query를 찾아 server-side timeout 안에 취소한다.
7. 결과 commit이 불명확하면 Run을 `FAILED + ORPHANED_EXECUTION/RESULT_COMMIT_UNKNOWN`으로 닫고 같은 recovery transaction에서 command terminal화·FAILED Turn 1회 commit·head 전진·lease 해제를 멱등 수행한다. 자동 재조회·지난 Artifact 대체를 금지하고 crash fault injection에서 중복 query·고아 query·영구 진행중 Run이 모두 0건임을 증명한다.

#### 7. 검증 lane

1. PR CI: unit/static, 모든 Frontend test, OpenAPI↔Frontend contract, migration, clean-checkout Compose config
2. dependency integration: real App DB·Source DB·Trino·DataHub와 결정론적 model test double. 제품 E2E라고 부르지 않는다.
3. release Golden E2E: 공식 Compose·실제 승인 model·auth·browser·후보 `product_release_id`; fake·mock·cached result 금지
4. GD-01~03과 negative dialogue를 새 conversation에서 반복하고 browser network·Backend trace·App DB·Trino query ID를 receipt로 남긴다.
5. cache를 사용하는 경로는 `cached=false`인 최초 실행 증거를 별도로 확보한다.

#### 8. 복구 훈련과 전환

1. 후보→이전 승인→후보 순서의 rollback rehearsal에서 중단시간·RTO·RPO·cache 오염·상태 손실을 측정한다.
2. DATA-G0~G7, semantic read-back, P0 Gold, Golden Dialogue, 실제 E2E, Report rerun, security, failure, quant, rollback receipt를 지정 승인자가 검토한다.
3. 승인 뒤에만 data·semantic·App 기본값을 같은 `product_release_id`로 바꾼다.
4. 전환 후 readiness·Golden smoke를 실행하고 실패하면 연습한 rollback을 즉시 수행한다.
5. 안정화 관찰과 별도 승인 전에는 이전 승인 경로를 삭제하지 않는다.

### Gate와 완료 정의

다음 Gate와 연결 Requirement가 모두 같은 `product_release_id`의 durable evidence로 `VERIFIED`일 때만 P0 완료다. Gate 표에 없는 P0 Requirement도 waiver로 간주하지 않는다.

| Gate | 반드시 `VERIFIED`여야 하는 Requirement/증거 |
|---|---|
| `P0-DATA-CUTOVER` | `DATA-001~006`, `OPS-003`; `DATA-G0~G7`, semantic candidate round-trip read-back, candidate canary, App DB/source/serving backup·restore와 rollback rehearsal, 지정 승인자의 cutover 승인, 전환 후 readiness·Golden smoke |
| `P0-GLOSSARY` | `GOV-001~009`; out-of-place candidate 전체 read-back과 activation/rollback |
| `P0-GOLD` | `ANL-010`, `QA-004`와 선행 `DATA-001~004`, `GOV-001~008` candidate readiness |
| `P0-E2E-REAL` | `AUTH-001~003`, `ANL-001~009`, `ANL-011`, `QA-003`; mock/cache 없는 `cached=false` L3 |
| `P0-REPORT-RERUN` | `SAVE-001~003`, `RPT-001~005`; block별 실제 새 child Run·query L3 |
| `P0-GOLDEN-DIALOGUE` | `CONV-001~010`, `AUTH-002~003`, `ANL-001~009`, `ANL-011`, `SAVE-003`, `RPT-001~005`, `QA-003`; GD-01~03 exact count와 negative case |
| `P0-SECURITY` | `AUTH-002~004`, `SEC-001~004` |
| `P0-FAILURE` | `FAIL-001~006`, `OPS-001~002`, `OPS-004`, `QA-001` |
| `P0-EVIDENCE` | `QA-003`과 PRD 2절의 릴리스 증거 묶음 전체 |
| `P0-QUANT` | `ANL-011`, `QA-002`, `QA-004`; task-specific held-out의 MFT/INV/DIR/NEG, per-Turn state+path, joint slot 지표와 `unsafe_silent_execution_rate=0` |

추가 완료 조건:

- P0 requirement의 `VERIFIED` 행이 실제 receipt와 1:1로 연결된다.
- GD-01~03의 Turn·Run·query·Artifact·View·Report block 수가 사전 봉인 exact count 표와 일치한다.
- GD-03 범위 밖 첫 Turn은 `analysis_run_id`·query·Artifact가 모두 0이고, client clock spoof로 우회되지 않는다.
- ANL-011 equivalence set은 같은 resolved request hash 또는 같은 expected clarification으로 수렴한다. contrast set은 다른 hash 또는 명확화로 갈리고, contrast·unsupported set의 unsafe silent execution은 0건이다.
- MFT/INV/DIR/NEG와 per-Turn backend state+path, `joint_slot_exact_match`를 같은 sealed manifest에서 재현하며, 공개 leaderboard 점수를 제품 Gate evidence로 사용한 항목은 0개다.
- Report Draft는 `source_artifact_id`·ViewSpec·Definition을, 실행 block은 새 `result_artifact_id`·query를 구분해 보존한다. `ABSOLUTE`/`RELATIVE` 기간과 `report_as_of` 규칙, 새 Artifact와 ViewSpec 불일치의 `VIEW_SCHEMA_INCOMPATIBLE` 실패를 검증한다.
- DataHub 변경·관계 단절·checksum mismatch·cache 만료가 runtime에 반영되거나 fail-closed한다.
- mock·hardcode·fake adapter·screenshot만으로 통과한 Gate가 0개다.
- 현재 승인 경로와 rollback 절차가 검증 전까지 보존된다.

### 매 작업 반복 규칙

각 작업은 다음 순서로 작게 닫아라.

1. 현재 코드·계약·데이터 evidence를 읽고 재현 가능한 실패 또는 명시 gap을 기록한다.
2. 해당 P0 requirement와 Gate, 입력·출력·실패 의미를 먼저 고정한다.
3. 가장 작은 실제 Vertical Slice를 구현한다.
4. unit → integration → 필요 시 browser E2E 순서로 검증한다.
5. request/turn/run/query/artifact/view/report ID와 checksum을 evidence에 남긴다.
6. 문서 status를 evidence 수준만큼만 올린다.
7. 회의적으로 재검토해 mock, stale fixture, cached result, 권한 우회, release 혼합, 잘못된 상속, 불필요 query가 없는지 확인한다.

한 단계가 실패하면 그 단계에 의존하는 후속 검증·전환은 진행하지 않고 현재 승인 경로를 유지한다. release pointer를 바꾸지 않는 독립적 안전·계약 slice는 별도로 진행할 수 있다. 같은 blocker가 반복돼도 Gate를 완화하지 말고 원인·시도·필요 권한을 보고한다.

### 진행 보고 형식

매 checkpoint와 최종 보고는 다음을 분리한다.

1. 확인된 사실
2. 이번에 바꾼 파일·계약
3. 실행한 검증과 실제 결과
4. 실행하지 못한 검증과 이유
5. Requirement·Gate 상태 변화와 evidence 링크
6. 남은 P0 blocker·회귀 위험·rollback 상태
7. 다음으로 닫을 가장 작은 Vertical Slice

최종적으로 “완료”라고 말하기 전에 처음 작업에 참여하지 않은 검토자의 시각으로 전체 문서·코드·runtime·evidence를 다시 감사하라. 낙관적 추정, 발표용 표현, 과거 결과를 모두 제거하고 같은 환경에서 다시 재현되는 사실만 최종 판정에 사용하라.
